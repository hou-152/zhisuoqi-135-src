## context
> 在任何 AI 智能体交互中，你的系统掌握一些调用方智能体不知道的上下文；而调用方智能体也掌握一些你的系统不知道的上下文……承认你的智能体在哪些地方不擅长，是完全可以的——因为你们其实是在服务同一个用户。
## 费曼一下
- 双方 Agent 各有信息盲区。**差的设计把缺口甩给用户**（"自己从 150 个 GL code 里选一个"），**好的设计反向去要对方手里的上下文**（"这是客户餐还是个人？"），自己再补完归类。
- Diego 报销案例的关键反转：费用系统不再问 GL code，而是问"用餐性质"；用户 Agent 从日历或 Slack 里查得到答案，再交给费用系统套科目。Diego 和会计都受益，GL code 谁都不用懂。
- 设计要点：
	- 列出自家 Agent **掌握**的上下文 vs **需要**的上下文。
	- 把"需要但没有"的部分换成"对方 Agent 能轻松提供的字段"。
	- 承认不擅长，比假装全能更有用——因为最终服务的是同一个用户。
## 与本文其他概念的关系
- 是"为 Agent 设计产品"三原则的**事后**环节：事前供规范、事中收反馈、事后协商上下文。
- 是**A2A 交互**最具体的产品动作：A2A 不是"两个 Agent 自动跑通"，而是"两个 Agent 知道彼此该问什么"。
- 与**Rationale 参数**呼应：rationale 暴露了缺口在哪，上下文协议把缺口补上。
