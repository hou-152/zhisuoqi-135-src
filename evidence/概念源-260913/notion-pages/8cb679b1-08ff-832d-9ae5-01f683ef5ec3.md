## context
> I call it **thin harness, fat skills**.
>
> Push intelligence *up* into skills. Push execution *down* into deterministic tooling. Keep the harness *thin*. When you do this, every improvement to the model automatically improves every skill, while the deterministic layer stays perfectly reliable.
三层架构完整表述：
> **Fat skills** sit on top: markdown procedures that encode judgment, process, and domain knowledge. This is where 90% of the value lives.
>
> **A thin CLI harness** sits in the middle: about 200 lines of code. JSON in, text out. Read-only by default.
>
> **Your application** sits on the bottom: QueryDB, ReadDoc, Search, Timeline — the deterministic foundation.
## 费曼一下
Garry Tan 给 AI agent 架构提出的**方向性原则**，一句话写得下：
- 把判断、流程、领域知识尽量堆在 **skills** 这一层（fat）；
- 把跑模型的程序写得尽量薄、尽量通用（thin **harness**）；
- 把确定性的计算、查询、工具调用沉到最底层（deterministic application）。
**三层架构：**
- 顶层 Fat skills：markdown 写的判断、流程、领域知识 —— **90% 的价值在这里**。
- 中层 Thin harness：约 200 行代码，JSON in / text out，默认只读。
- 底层 Application：QueryDB、ReadDoc、Search、Timeline —— 确定性基础设施。
**为什么这个方向重要：复利。**
- 模型升级 → 所有 skill 里的 latent 步骤自动变好；
- 确定性底层 → 永远可靠不变；
- harness 越薄 → 越能让所有 skill 共享同一份基础能力。
**反模式：**fat harness + thin skills —— 40+ tool 定义吃掉一半 context window、god-tools 一次请求 2–5 秒、REST API wrapper 把每个 endpoint 都包成 tool——3x token、3x latency、3x failure rate。
**实践启示：**你要问的不是「这个 tool 该不该在 harness 里」，而是「这个能力能不能写成一个 skill，然后调用 deterministic tooling」。智能往上推，执行往下沉。
