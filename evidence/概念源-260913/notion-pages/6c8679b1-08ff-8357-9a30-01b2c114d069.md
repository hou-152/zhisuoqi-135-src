## 费曼一下
模型外面那层「项目级感知」。让 AI 不是只盯一段代码，而是先理解整个项目的目录、规则、依赖，再做决定。
模型再强，没有 Harness 也只是聪明的对话框；有了 Harness，它才像个能上工的工程师。Claude Code 之所以打开了「非技术人也能上手」的口子，关键不是模型有多强，而是 Harness 把「让模型懂项目」这件事做得足够轻量——一份 [CLAUDE.md](http://CLAUDE.md) 就能起步。

Sam 把 Harness 推到了一个新高度：**他已经不再把 harness 和 model 当作两件事**——一次惊艳的输出，没人说得清是模型聪明还是 harness 聪明。
几个跨这两篇的共同点收敛得很清楚：
- Harness 是模型外面那一圈**让模型真正干活的脚手架**——工具调用、记忆、权限、状态、Eval；
- 模型再强，没有 harness 只是聪明的对话框；harness 撑起的是 **「能上工的工程师 / 虚拟同事」** 这一步质变；
- Harness 的集成发生在 **post-training + system prompt**，不在 pre-training；
- 历史模式：那些一开始以为可分离的东西最终都被 baked in（tool calling 是先例）；
- Sam 的预测：未来 model + harness、pre-training + post-training **都会更加合体**。
Bedrock Managed Agents 的本质，就是**把 AWS 这一层做成「企业级 harness 标准件」**——客户不用再自己粘工具、记忆、权限、状态，开箱就能跑。

## context
> The harness is the program that runs the LLM. It does four things: runs the model in a loop, reads and writes your files, manages context, and enforces safety. That's it. That's the "thin."
>
> The anti-pattern is a fat harness with thin skills. You've seen it: 40+ tool definitions eating half the context window. God-tools with 2-to-5-second MCP round-trips... Three times the tokens, three times the latency, three times the failure rate.
## 费曼一下
Garry Tan 把 harness 的职责**极端压缩**：只做四件事——跑 loop、读写文件、管 context、enforce safety。其他一切都不是 harness 该管的。
这跟上面两篇文章里「项目级感知 / 企业级标准件」的表述不矛盾，但加了一个**方向性原则**：
- 反模式：fat harness + thin skills。4 十 多个 tool 定义、god-tools、REST API wrapper 把每个 endpoint 都包成 tool——3x token、3x latency、3x failure rate。
- 正确模式：thin harness + fat skills。专用、又快又窄的工具（Playwright CLI 100ms vs. Chrome MCP 15s——75x 快）。智能往上推到 skills，执行往下沉到确定性工具，harness 保持薄。
复利：harness 越薄，越能让所有 skill 共享同一份基础能力；模型升级时，所有 skill 自动变好，deterministic 工具那层不动也稳。
