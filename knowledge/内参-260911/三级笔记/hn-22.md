# 为什么 harness 工程这么难

## 一句话主旨
Agent harness 之难源于概率式基底的六个结构性事实，它们无法被工程掉，只能被吸收——而可吸收不掉的难度本身即护城河。

## 作者试图回答的问题
为什么几乎所有「接上 API、写个 prompt、演示惊艳」的项目都会撞上 harness 工程这堵墙？以及：这层痛苦的来源是什么，能否靠工程手段消除？（子问题：在非确定性、静默失败、移动地基的约束下，工程质量策略应如何重建。）

## 三级论证骨架

### 一、起点：破掉「模型即产品」的幻觉
#### 1.1 经验基础与核心命题
- 作者五个月、104 次 commit，反复撞上同一个教训：harness 工程很难。
- 幻觉内容：接上 API、写个 prompt、第一次演示惊艳，于是感觉难的部分已经结束。作者的回答只有三个字：「It is not.」
- 真正难的是把惊艳演示变成**你能依赖的行为**——不同输入下守同一组约束、不漂移、熬过模型更新、显式失败而非静默失败、在输出永不确定的前提下仍可测试。
- 技术定义：harness 是介于概率式模型与产品使用者之间的 prompts、examples、schemas、validators、evals、guardrails。「The model generates the output. The harness is what makes that output usable.」

### 二、六种失效：源于一组「结构性事实」
作者先列出全部痛点（测试失效、失败静默、调试散文、加法陷阱、地基重写、反馈回路慢贵 + 社会性痛点「没人看见」），再逐一拆解。

#### 2.1 你写不出你想写的那个测试
- 测试直觉整体崩塌：整个职业生涯的测试实践都假设确定性——固定输入产出固定输出、断言相等。
- 同一输入喂两次得到两个不同输出，差异可能只是几个词、一个调换顺序的从句、同义换说，但「足以让严格的等值断言变成废纸」。作者称这不是小麻烦，而是「抽掉了整个质量策略的地板」。
- 退路只剩两条，且都更弱：
  - 断言**结构**（能否解析、必填字段在不在、计数对不对）。
  - 断言**不变量**（有没有违反被告知要遵守的规则）。
  - 两者都比工程师习惯的断言弱，都会放真正的意外输出过去。
- 问题形态转变：从「一个输出是否等于一个预期答案」变成「系统在一个输入分布上、在重复运行中是否满足一份 rubric」——更接近 evaluation 而非单元测试，**得到的是置信度，不是正确性的证明**。

#### 2.2 失败是静默的、分级的，不是二元的
- 普通软件失败会自己喊疼：异常、堆栈、非零退出码、红色日志。模型输出不会崩。
- 一个 95% 正确、5% 崩坏的响应**看上去完全没问题**：没有错误符号、没有异常，错的部分用同样的散文、同样的格式、同样的自信，织进对的部分里。
- 模型不知道自己错了；没有一条独立的「我不确定」通道，即使给它一条，使用也不一致。流水线上没有任何东西报警。
- 关键判断：**最危险的输出恰恰是那些差一点就通过的**。粗暴错误好抓（validator 拒、人扫一眼皱眉），微妙错误通过所有浅层检查抵达用户。
- 「微妙地错」至少包括三类：
  - 因后面的指令间接与前面矛盾而偏离某条约束；
  - 在该承认不知道的地方编出一个听起来合理的值；
  - 守住规则的字面、破坏规则的精神。
  - 这三种都不崩溃，都会发布出去。
- 应对：为**没有信号的失败**建防御。抓不到看不见的东西，因此 harness 工程很大一部分是「making the invisible visible」——加能暴露分级漂移的检查、加能标出「结构合规但语义跑偏」的断言、在置信度低的节点加人工介入；而这些各自又都带取舍。

#### 2.3 你在 debug 散文，不是 debug 代码
- 检测到坏输出只解决一半问题：造成失败的「代码」往往是一段英文，唯一的调试器是你的判断力——读上千字，判断是什么给了模型许可去做它刚做的事。
- 残酷之处：**一个词就可能是那个 bug**。作者花几小时把一次回归追踪到 prompt 里的一个形容词——写时人畜无害，模型读成了某种许可。
- 与源码 bug 的对照：一个字符的 bug 是老段子，但它**可被找到**；prompt 里一个词的 bug **不可见**——机械上什么都没破坏，只是把行为推偏几度，而几度足以在任何人察觉前悄悄腐蚀输出。
- 更糟的是：prompt 有确定的顺序，却**不像有显式控制流的程序那样执行**；靠前与靠后的指令以难以隔离的方式互相影响。
- 因此只能像**作家推敲段落**那样推理：凭感觉、读出声、问「这段话到底在叫读者做什么」，再跑一遍、眯眼看输出验证。多数工程师从未被迫发展过这项技能。

#### 2.4 加法本能是陷阱
- 这是 harness 工程里**最可靠的失败模式**，也是作者掉进去最多的一个：一出问题就往 prompt 里加规则——做错了告诉它别这么做，忘了约束再喊一遍，编造了加一行「do not invent」，经典款是全大写「MAKE NO MISTAKES!」。
- 每条添加都显得负责、甚至细致（你在回应一次真实失败），于是 prompt 一直长下去。但**prompt 变长本身是病，不是药**。
- 机制：规则用自然语言写，与模型的交互**无法被完全预测**：
  - 修新失败的规则会与修旧失败的规则互相矛盾；
  - 「be concise」与「include all of these details」打架；
  - 「never do X」让模型开始想 X，X 于是出现在此前从未出现的输出里。
- 结果：不会收到冲突报错，只会得到**被过度约束**的模型——被拉扯到无法同时满足所有方向，于是安静地挑一条违反。用一个可见的 bug 换来一个更隐蔽的 bug。
- 作者亲历：一份 prompt 从二十行长到两百行，每一行都出于善意、都在修真实失败，直到重到几乎再也产不出好东西。
- 唯一解法是减法：删规则、合并重复、删掉暗中互相打架的指令、把约束从散文搬进代码（在代码里它没法被反驳）。**质量的跃升来自删除，而不是添加。**
- 为什么难执行：删除是当下感觉最不对的动作，因为你在「移除一道保险」，而工程训练里没有任何东西奖励你扔掉一条曾修好过 bug 的规则。

#### 2.5 示例比规则更能改变行为（加法陷阱的推论）
- **模型从示例中学到的远比从指令中学到的更有力**。写了「don't do X」却附上一个恰好做了 X 的示例，模型就会做 X——**示例赢**。规则可以大写、重复、恳求，但示例是一次示范，而示范是比禁令更强的信号。
- 更深的教训：prompt 里的一切都是**行为程序**——指令、示例、章节顺序、你选的词、（也许）甚至格式。prompt 里**没有中立的部分**，每个 token 都在把模型推向某处。
- 因此维护一份 prompt 不像维护配置文件，而像维护一个**每一行都可执行、且输出带范围**的程序。

#### 2.6 地基会自己重写
- 普通软件建在**静止地基**上：语言版本偶尔升级，框架一两年一次破坏性变更且附迁移指南与废弃周期，契约在一个 sprint 尺度上基本稳定。
- 模型不是稳定地基。厂商会更新（**有时不打招呼**），更新会改变行为：
  - 上季度干净的输出这季度微妙不同——不是你改了什么，而是**统计表面在你脚下移动了**；
  - 旧模型读作硬约束的一句话，新模型读作建议；
  - 旧模型稳定产出的格式，新模型偶尔缺一块；
  - 你的 harness 是针对旧模型失效模式调优的，新模型有**不同的**失效模式——防御守着已不再发生的问题，新问题无人看守。
- 当下例证：Opus 5 发布后，很多人反映此前可靠的 skills 文件突然不灵了。
- 根本差异：你不是建在一个平台上，而是建在一个**按别人的日程重写自己行为的概率系统**上。每份契约都是与移动靶子签的；**测试可以是绿的，产品却在退化**。
- 没有永久有效的「锁版本」逃生舱：厂商会废弃旧版本、价格会变，最终不管你是否准备好，都会被推到新表面上。
- 实践后果：**harness 永远不会「做完」**，处在对持续移动地基的持续适配中。会花没预算的时间重新调 prompt、为不是你造成的回归发补丁。这不是计划失败，而是基底的结构性事实。
- 诚实的应对只有三条：
  - 尽量**最小化 prompt**，少依赖模型特有的怪癖；
  - 建能**捕捉漂移**的校验；
  - 保持谦逊——预期下一次更新会弄坏某个你此刻还叫不出名字的东西。

#### 2.7 反馈回路又慢又贵
- 正常 edit-compile-test 循环以秒计，**回路的紧凑度**正是工程可以忍受的原因——让你不必把整个系统装在脑子里就能迭代到正确解。
- harness 完全不是这样：一次模型调用要花钱，足以让你没法像跑单元测试那样跑一千次；多次调用的流水线，**一次端到端测试要几分钟到几小时**。
- 后果一：迭代更慢、脑子里装更多状态。不能「一分钟试二十种变体」暴力求解，只能试三种、等、认真读输出、形成假设、再试一种。**解决问题的整个形状变了**。
- 后果二：习惯紧回路的工程师觉得在慢动作里工作，诱惑是改完 prompt 就推、待会儿再看——而这恰恰是回归被引入的方式，因为**你在停止编辑之前就停止了观察**。
- 后果三（更隐蔽）：**成本让你在验证上变懒**。每次检查都昂贵时就开始少检查，说服自己改动小到可以跳过完整运行——而它几乎从来没有那么小。「昂贵的回路训练你欠测试，而对一个概率系统欠测试，就是在发布漂移。」

#### 2.8 没人看得见这份工作（社会性痛点）
- 「Prompt engineering」这个说法让工作听起来微不足道：暗示这活儿就是**写 prompt**，在没做过的人看来难度约等于写封邮件。
- 几个月的收紧、被移除的矛盾、发布前拦下的静默失败全都不可见。**看起来你几乎什么都没做。**
- 没有干净解法。能做的最好的事是**刻意地让不可见变得可见**：记录抓到的失效模式、度量阻止的漂移、写下那些没有发布出去的回归；并接受一部分价值永远不会被周围人读懂。
- 这是这份工作自带的税，值得说出来——以免你内化那条错误信息：以为自己没做什么。

### 三、收束：难度转化为价值
#### 3.1 六个痛点都是结构性地难
- 它们难，不是因为工具不成熟、也不是最佳实践还没摸索出来，而是因为它们来自基底的本性——一个没有堆栈跟踪、没有确定性、没有稳定契约、也不区分「程序」和「它被训练的数据」的概率系统。
- **这些事实无法被工程掉，你只能造一个吸收它们的 harness。**

#### 3.2 难度即护城河
- 如果 harness 工程很容易，模型就是产品，任何有 API key 的人都能和你竞争。
- 一个真实应用之所以难做，与它之所以难被复制，是同一个原因：把概率输出变成可发布、可靠、可测试的东西，这份工作**不可见、痛苦，且无法靠读你的 prompt 转移**。
- 「The pain is the work, and the work is the moat.」

#### 3.3 概念网络（原文关系图的结构，可用于回看全篇）
- 单一源头是**概率式基底**，四个直接后果：非确定性、静默的分级失败、会自己重写的地基、昂贵的反馈回路。四者互不重叠，共同定义 harness 与普通软件工程的边界。
- 每种失效逼出一种应对：非确定性逼死等值断言 → 测试演化为评估、验收语言从「正确性证明」降为「置信度」；静默失败没有信号 → 刻意造信号（让不可见变得可见）；地基漂移让模型特有调优变成负债 → 反过来要求最小化 prompt，与减法主张合流。
- 三组内在张力：**加法本能 vs 减法解法**（工程直觉在这里是反的）；**昂贵回路 vs 评估式验收**（评估要重复运行，成本压力又把你训练成欠测试的人，想做对与做得起互相抵消）；**提示词即行为程序**是底层解释（没有中立 token，示例必然强于禁令，直接放大加法陷阱，也让调试只能靠读散文）。
- 「看不见」出现两次且同构：系统层面（失败没有信号）、社会层面（劳动没有痕迹）；解法也是同一个动作。调试散文格外消耗人，因为同时占据两种不可见——几小时追一个形容词，既没有报错，也没有产出物可展示。

## 作者边界、反例与不确定性
- **明确给出的边界与反例**：结构断言与不变量断言「都比工程师习惯的断言弱，都会放真正的意外输出过去」；评估式验收「得到的是置信度，不是正确性的证明」；「锁版本」不是永久逃生舱——厂商会废弃旧版本、价格会变，最终都会被推到新表面上；上游指令互相矛盾时，模型会「安静地挑一条来违反」。
- **作者保留与不确定处**：「（也许）甚至格式」是作者对格式是否属于行为程序的自我保留；「这是一项与 debug 截然不同的技能，多数工程师从未被迫发展过」是对工程师群体的概括，未给证据。
- **未回答的问题**：如何度量「被阻止的漂移」、如何在成本约束下设计可承担的评估频率，作者只给出方向性应对（最小化 prompt、建漂移校验、保持谦逊），未给出可操作方案。
- 原文没有给出的内容：具体模型的 harness 实现方案、评估框架选型、成本/频率的量化权衡，均不在其列。
