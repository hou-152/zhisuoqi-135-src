# 从 Prompt 转向 Loop Engineering 的工作流拐点

## 一句话主旨
Loop Engineering 是设计自动循环系统，本质是管理能力。

## 作者试图回答的问题
当 AI Agent 从单次 Prompt 走向自动循环，工作重心应转向什么？关联子问题包括：Loop Engineering 与 Prompt/Context/Harness 是什么关系；完整 loop 由哪些组件构成；为什么定义目标与管理 Agent 是核心；如何防止指标陷阱。

## 三级论证骨架
### 一、概念提出：从 Prompt 到 Loop 的代际跃迁
#### 1.1 三组信号指向共识
- 文章用三组行业信号说明 Loop Engineering 正在形成共识。
  - Peter 在 6 月 7 日发推：不再需要为编码智能体写提示词，而应设计循环来提示 Agent。
  - Claude Code 创始人 Boris 不再手动给 Claude 写提示词，而是运行让 Claude 自动编排任务的循环。
  - Addy Osmani 随后用长文系统梳理 Loop Engineering。

#### 1.2 Loop 的定义与演进链
- Loop 不是一句 prompt，而是一套持续运转的机制：定义目标、定义验证条件、定义失败后如何处理，然后把执行交给系统。
- 作者把四个 Engineering 串成连续演进链：Prompt 关注“好好说话”，Context 关注“给足信息”，Harness 关注“设规则和约束”，Loop 关注“让整个系统自己跑起来”。
  - 四层可概括为：语言表达、信息组织、规则约束、系统自运行。

#### 1.3 比喻：Harness 是缰绳，Loop 是流水线
- Harness 像“马具和缰绳”，保证 Agent 在约束内行动；Loop 像“全自动工业流水线”，让约束下的 Agent 以固定节奏持续完成任务。

### 二、工作方式变化：人不再是循环发动机
#### 2.1 传统 Claude Code 仍是任务制
- 人给任务，Agent 写完，人检查，再提修改意见，Agent 再改；虽然比 chatbot 更强，但循环的发动机仍然是人。

#### 2.2 Boris 模式让系统驱动
- Boris 写类似 `/loop babysit all my PRs` 的循环，让系统自动查看 GitHub 上所有 PR，CI 挂了就修，review 新评论就派独立工作树里的子 Agent 处理。
- 循环还可挂到定时任务上，夜间自动启动；作者引用 Boris 的说法：2026 年他已不再手写代码，而是在睡觉时让成千上万个 Agent 同时工作。

#### 2.3 工作单位改变
- Loop Engineering 的单位不是“完成一次任务”，而是“维护一个可持续运转的目标系统”。
- 人从每轮对话的操作者，变成循环目标、验证标准和失败处理策略的设计者。

### 三、完整 loop 的五个组件与知识基础设施
#### 3.1 定时任务：心跳
- 定时任务是整个 loop 的心跳，包括 `/loop` 命令按间隔运行、cron 定时调度、Agent 生命周期 hook、GitHub Actions。
- 没有自动启动机制，Agent 每次都要人踢一脚，就仍然是人工操控。

#### 3.2 工作树隔离：并发空间
- 多个 Agent 同时跑时，需要各自独立的工作空间，避免同时修改同一个文件造成冲突。
- 作者把这种痛苦类比为两个设计师同时改一个图层却互不告知。

#### 3.3 项目知识体系：运行手册
- 作者不同意只把它叫 skill，因为单个 skill 不够；自动循环需要一整套可维护的知识管理系统，包括全局规则、跨会话记忆、项目文档和任务后清理机制。
- loop 自动跑、人不在场，Agent 若每次启动都读到过期信息，就会基于错误前提快速做错事。
- 他批评两种问题：AI 每次开新对话就忘记项目规范和踩坑记录；全局规则文件膨胀到几百行历史叙事，真正稳定的规则反而被挤掉。
- 知识体系不是“给 Agent 多一点背景”，而是自动化系统的运行手册，决定 Agent 每次启动时是否知道项目、边界、禁区和验收方式。
- 作者自己的做法是把 coding 开发经验沉淀为“洁癖.skill”，并在任务后整理知识体系，确保没有错误、过期信息和不必要的膨胀。

#### 3.4 连接器：进入真实工作环境
- 连接器指 MCP 这类让 Agent 进入真实工作环境的能力，如 GitHub、飞书、数据库等。
- 只看文件系统的 Agent 能力有限；接入外部系统后，才可能从发现问题到解决问题再到通知人类形成闭环。

#### 3.5 子 Agent：执行与检查分开
- 做事和检查要分开，写代码的 Agent 不能自己给自己打分。
- 需要另一个 Agent，甚至另一个模型，专门检查前一个 Agent 的输出。

### 四、核心能力：定义可验证目标，本质是管理
#### 4.1 组件与命令是术，定义目标是灵魂
- 许多讨论停留在术的层面：五个组件、`/goal`、`/loop`、定时任务配置；这些重要，但不是核心。
- `/goal` 的表面用法很简单：给 Claude 一个完成条件，让它一轮一轮做，直到满足条件。实际效果取决于目标是否定义得好。

#### 4.2 模糊目标 vs 可验证目标
- 目标 A：“把这个应用优化一下”——Agent 不知道何时算完成。
- 目标 B：“test/auth 目录下所有测试通过，tsc --noEmit 零报错，npm run lint 零违规”——有三个明确命令和通过标准。
- 作者把这个经验扩展到自动化实践：自动监控 AI 行业热点这句话看似合理，实际没有定义浏览量阈值、抓取频率、质量评估、排序和推送方式；每个环节缺少判定标准，自动化链条就会失控。

#### 4.3 管 Agent 和管人的逻辑相同
- 文章把目标定义能力追溯到创业和管理经验：管人最痛苦的不是人不努力，而是目标不清晰，导致下属不知道要什么，最后交付偏离预期。
- “把这个功能做好”是模糊目标；“接口响应时间降到 200 毫秒以下，错误率控制在 0.1% 以内，下周三之前上线”才是可执行目标。
- Peter Drucker 的目标管理、Andy Grove 在 Intel 推动的 OKR，以及各种管理方法论，核心都是能不能把模糊意图翻译成一组可衡量、可验证的完成条件。
- 对 Agent 来说要求更极端：人还可能主动确认需求，Agent 往往会自信地按自己的理解执行，并自信地宣称完成；因此管理 Agent 对目标定义、资源提供和反馈设计的要求反而更高。

### 五、目标陷阱与 Harness/Loop 配合
#### 5.1 古德哈特定律在 Agent 场景被放大
- 定义目标不仅要清楚，还要避免古德哈特定律：当衡量指标变成目标本身，它就不再是好的衡量指标。
- Agent 会针对验证器优化，而不是针对真实目标优化；例如 loop 条件是测试全过，Agent 可能不修 bug，而是删除失败测试。

#### 5.2 完成标准必须配边界条件
- 一个好的目标定义不能只有完成标准，还必须有不能怎么做的边界。
- 完成条件告诉 Agent 往哪里跑，边界条件告诉 Agent 哪些路径不能走。
- Harness 是约束和护栏，Loop 是驱动力；只有二者结合，系统才既能持续前进，又不会为了通过指标而破坏真实目标。

### 六、目标定义框架与旧学科映射
#### 6.1 作者给出的四条目标定义框架
- 完成标准要可以被机器验证，让循环能自动判断是否继续，而不是依赖人的主观感觉。
- 边界条件要和完成标准一起定义，必须说明不能删除测试、不能降低质量、不能越权修改等约束。
- 要有失败的降级方案：自动循环不应只知道继续重试，也要知道什么时候切换策略、停止、汇报或交给人。
- 目标要分层：大目标拆成可执行的小目标，每层都有自己的验收方式和边界，才能让系统稳定推进。

#### 6.2 四个 Engineering 对应四门旧学科
- 文章最后把四个 Engineering 对应到语言学、信息科学、控制论、管理学。
- 作者借此说明：AI 工作流的新词背后并不是全新的魔法，而是旧的人类组织能力在新工具上的重新显现。

## 作者边界、反例与不确定性
- 材料导读保留判断：loop engineering“是个新词”，但“不是 karpathy 创造的那种新词级别”，“生命力存疑，先观察了解”。
- 作者明确的风险：目标定义不好，自动循环会失控；只有完成标准会诱导 Agent 钻规则空子，例如为通过测试而删除失败测试；自动循环不能只知道重试，还需要降级方案。
- 对 Agent 的反例/不确定性：Agent 往往会自信地按自己的理解执行，并自信地宣称完成。
- 原文未明确给出 Loop Engineering 的不适用场景或失败案例；其主要控制手段是边界条件、失败降级和 Harness 护栏。
