# Harness Engineering：AI-First 组织的信任机制重构

## 一句话主旨
AI-First 的核心是重构系统与信任：让 AI 主导执行，人退到架构与审核。

## 作者试图回答的问题
当 AI 从辅助者变为生产力主导者，组织如何重构工程系统、工作流程、角色分工和信任机制？Harness Engineering 在这套重构中扮演什么角色？人的位置又在哪里？

## 三级论证骨架
### 一、Harness Engineering 是大模型工程能力的第三阶段：从静态提示到动态系统
#### 1.1 演进三阶段：Prompt → Context → Harness
- 2023 年是 Prompt Engineering，2024 年是 Context Engineering，2026 年讨论 Harness Engineering。
- Harness 的对象不只是模型本身，而是围绕模型的一套系统：基建、tooling、安全保障、sandbox 与 host service 交互、启动时间、latency、持续 improve。
- Prompt 和 Context 是静态优化：在一次或少数几次交互中表现更好；Harness 是动态系统：让 Agent 在真实世界里长时间工作、使用工具、吸收信号、发现错误并自我修复。
- Harness 的失败通常不是“模型不聪明”，而是系统缺乏护栏、反馈回路、上下文管理和工具边界。
- Clark：“不要只把 AI 当成一个智能，要把它当成一个系统；系统出错时，重点不是纠正某个回答，而是弥补系统漏洞。”

#### 1.2 Harness 是让组织信任 AI 的工程基础
- 组织从信任人转向信任 AI 系统，需要 guardrails、验证机制、反馈链路和共同工作方式。
- 否则任何成员觉得“不如人做”，转型都会被拖慢。

### 二、AI-First 的核心不是叠加工具，而是重构工作方式
#### 2.1 AI 必须成为生产力主导，而非助手
- Creao 对 AI-First 的定义：不是每个人用 AI 写代码、写 PRD、做图，而是围绕 AI 的能力重新设计流程和组织形态。
- Kai：如果想让效率提升 100 倍、1000 倍，AI 就不能只是助手，而要成为生产力的主导。
- 人的角色改写为 review 结果、定义目标、维护系统、判断价值。

#### 2.2 效率跃迁来自开发、测试、部署、Bug 分诊和市场反馈的 Agent 化
- 六周产品周期压缩成一天：传统一个 feature 六周甚至两三个月；Creao 中 AI 辅助 coding 实现只需一两个小时，关键是 planning、design、testing、feedback 都纳入 Harness。
- Peter 案例：25 人公司，99% 代码由 AI 写；早上 10 点写功能，中午 AB test，下午 3 点砍部分功能，5 点重写更好版本。
- 市场团队从“争论要做什么”变成“从产品库里挑选苹果或香蕉”，因为开发速度超过市场消化速度。
- AI 系统根据代码、部署、数据和功能状态向 go-to-market 团队提供可用信号，降低产研对齐成本。

### 三、AI 驱动的 CI/CD 与 Bug 分诊让质量控制并行化，支撑信任
#### 3.1 质量控制从假设无错转向快速发现、分诊、修复
- Peter 承认 AI 写代码会产生 Bug，但 Harness 重点是系统能更快发现、分诊和修复错误。
- Creao 构建 Agent-driven CI/CD 和 Agent-driven bug triage：AI-driven integration test、unit test、Playwright 端到端测试在进入生产前拦截明显错误。
- 上线后系统继续读取 log、error、incident 信号，反馈给 AI 判断代码质量；Bug 出现后不同 Agent 并行识别前端、后端或 Agent 核心系统问题，几分钟内分派任务。

#### 3.2 Autofixing 系统将修复周期从一周缩短到 1-2 小时
- 发现 bug 可能只要 1 到 2 分钟，分配工程师几秒，工程师用 Agent investigate 并提方案，整个 cycle 从过去一周缩短到 1 到 2 小时。
- 50% 以上 issue 通过 autofixing 处理：改动只涉及风险较低目录时，AI 自动提交 PR，人简单 review 即可上线；涉及安全或 Agent behavior 的敏感文件才需要深审。

### 四、架构师成为 AI 系统的关键角色，角色分工发生根本变化
#### 4.1 Architecture / Operator 分工：从写代码转向系统架构
- Peter 将团队角色分为 Architecture 和 Operator：前者决定 Agent 系统结构、sandbox 与 host 交互、安全性和 latency；后者在系统中运行和处理具体任务。
- 传统搭 Agent 系统需 10 到 20 人，AI 工作流下一个 architecture 用一周完成框架；前提是架构师能识别 AI planning 缺陷、challenge 方案、让模型参考开源框架并修订计划。
- Peter 2026 年没写一行代码，主要工作是和 AI 交流、criticize plan、发现 plan 漏洞。
- Skill 化：安全性、sandbox 与 host 交互等原则沉淀为 skill，下次可直接让 AI follow，团队其他工程师也可引用同一套规则挑战 AI 的 plan。

#### 4.2 产品经理不消失但被组织化，产品判断分散到团队
- 传统 PM 承担大量对齐成本；Creao 把 PM 职能拆解到工程团队和工程管理者身上。
- 开发成本降低后，谁能定义需求方向、快速把想法变成产品，谁就承担 PM 一部分职责；产品角色从一个人变成团队共同能力。
- Kai：未来 PM 仍重要，但要么有工程实现能力，要么有架构思维，要么能把市场想法快速落到产品中。
- Peter：工程师、产品经理、设计师都需要 implementation 能力，因为交流成本大于落地成本时，传统交接流程低效。
- 个人英雄主义式 PM 变弱，组织化产品决策机制变强。

#### 4.3 初级工程师与资深工程师面临不同的转型压力
- 初级工程师更适应 AI-First：技术债和思想束缚少，愿意扩展 scope 到产品设计、数据分析和上线后 impact 判断。
- 资深工程师的问题不是能力不足，而是过去积累的 specialty 正在被 AI coding 稀释；若仍只关心代码交付前部分，难适应新闭环。
- 但资深工程师仍不可替代：真正稀缺的是能 embrace AI mindset、拥有架构能力、产品 sense 和 marketing knowledge 的资深工程师；过去需要很多，现在可能只需要一两个。
- “资深悖论”：专业知识仍有价值，但专业身份本身不再足够；必须从写最优代码的人变成能架构 AI 系统、识别计划缺陷、判断商业价值的人。

### 五、Agent 经济将内容消费者从人扩展到 AI，扩大 Harness 适用范围
#### 5.1 未来很多工作结果的消费者可能是 Agent
- Clark：营销素材、网页、任务管理产品甚至 SaaS Dashboard 都可能先被 Agent 阅读、筛选和调用。
- 这改变评价标准：人类审美上不够好的 go-to-market asset，若被 Agent 读取后带来更好数据反馈，可能是更有效资产；问题不再是“人觉得好不好”，而是“真正的消费者是谁，它如何判断价值”。
- Peter 用 Asana、Linear 举例：过去人需要 dashboard 管理任务，现在团队更关心产品有没有更好的 MCP 和 API 让 Agent 能读懂和使用任务。
- Harness 因此是面向消费者、反馈信号和系统边界的设计方式；不同消费者决定系统优化什么。

### 六、人的核心价值收敛到定义需求与审核结果
#### 6.1 执行权交给 AI，价值判断、系统约束和最终审核仍属于人
- Peter：人需要系统架构能力，从 implement feature 转向 architecture and maintain AI system；核心是搭建能自主运行的 Agent 系统。
- Kai：技术发展仍由人的需求和社会需求决定；人负责定义需求方向，并在最终结果上判断是否符合利益、要求和伦理。
- Clark：人未来的价值是判断任何事情是否还有价值；价值定义延伸出需求定义。
- 底层结论：AI-First 并不是把人移出系统，而是把人放到更高层的判断位置。

## 作者边界、反例与不确定性
- 明确边界：AI 写代码会产生 Bug，Harness 不假设系统无错，而是更快发现和修复；Autofixing 仅适用于低风险目录，涉及安全或 Agent behavior 的敏感文件需要更深人工审核；架构师效率成立的前提是能识别 AI planning 缺陷、challenge 方案、让模型参考开源框架并修订计划。
- 原文未讨论该模式的行业普适性、不同规模或行业组织的适用边界，也未提供失败案例或反例；材料基于 Creao 一家公司的实践和嘉宾观点，结论的泛化程度未被作者明确界定。
