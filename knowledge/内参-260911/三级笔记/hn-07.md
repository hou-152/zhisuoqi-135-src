# Cursor：让 coding agent 连续自治运行数周的工程经验

## 一句话主旨
多 agent 自治编码的真正瓶颈是协调架构，角色分离后数百 agent 可协作数周。

## 作者试图回答的问题
能否靠"往问题上堆更多 agent"来扩展自治编码？真正的瓶颈是什么？什么样的协调架构能让多个 agent 在同一代码库上长时程协作？

## 三级论证骨架

### 一、问题起点：单 agent 速度天花板驱动并行化

#### 1.1 单 agent 在复杂项目上太慢
- 今天的 agent 在聚焦任务上表现良好，但面对复杂项目"很慢"（slow for complex projects）。
- Cursor 的目标是把人类团队通常需数月完成的项目推给 agent，测试 agentic coding 的前沿。
- 不是做不对，是做不快——瓶颈在串行速度，所以下一步只能是并行。

#### 1.2 并行是自然下一步，但协调是难点
- 难点不在启动 agent，在"如何协调"（figuring out how to coordinate them is challenging）。
- 最初直觉：提前规划"太僵硬"（planning ahead would be too rigid），因为大项目路径模糊、分工在开初不明显。
- 因此第一版选择动态协调：agent 根据其他 agent 当下在做什么来决定自己做什么。

### 二、扁平自协调的失败：机制与激励双重崩塌

#### 2.1 共享文件加锁：机制不可靠
- 设计：所有 agent 地位平等，通过共享文件查看状态、认领任务、更新状态，用锁防止两个 agent 抢同一任务。
- 三种失败方式：
  - 机制不可靠：agent 长时间持锁，或干脆忘记释放。
  - 吞吐塌陷：即使锁工作正常，它本身也成了瓶颈——20 个 agent 的有效吞吐掉到两三个的水平，大部分时间花在等待。
  - 系统脆弱：agent 在持锁时崩溃、重复获取自己已持有的锁、或根本不获取锁就直接写协调文件。

#### 2.2 乐观并发控制：修好机制但暴露激励问题
- 第二版：agent 自由读状态，但若状态自上次读取后已改变，写入就失败。
- 原文评价为"simpler and more robust"（更简单更健壮），但更深的问题依然存在。
- 更深的问题在激励而非机制：无层级（no hierarchy）导致 agent 风险规避（risk-averse）。
- 表现：避开困难任务、只做小而安全的改动，没有 agent 为难题或端到端实现负责，工作长时间空转（churning）而无进展。

### 三、Planner–Worker 角色分离：架构重构

#### 3.1 用角色流水线取代平等协商
- 放弃"每个 agent 什么都做"，改为职责分明的流水线。
- Planner：持续探索代码库并创建任务；可为特定领域派生 sub-planner，使规划本身并行且递归。
- Worker：领取任务并全神贯注完成；不与其他 worker 协调，不操心大局，只是"死磕"（grind on their assigned task until it's done）直到完成然后 push。
- Judge agent：每个周期末判断是否继续；下一轮迭代从头开始（start fresh）。

#### 3.2 效果：解决大部分协调问题
- 解决了大部分协调问题，系统扩展到非常大的项目，不会有任何单个 agent 陷入隧道视野（tunnel vision）。

### 四、四个真实实验的实证

#### 4.1 从零写 web 浏览器
- 连续运行接近一周，跨 1000 个文件，写出超过 100 万行代码，源码开源（仓库 fastrender）。
- 数百个 worker 并发向同一分支 push，冲突极少（minimal conflicts）。
- 作者强调：截图看起来简单，但从零造一个浏览器极其困难。

#### 4.2 Cursor 自身代码库 Solid→React 迁移
- 跑了三周多，改动量 +266K/-193K。
- 已通过 CI 与早期检查，但仍需仔细 review。

#### 4.3 性能改造
- 长时程 agent 用 Rust 版本把视频渲染做快 25 倍。
- 加上跟随光标的平滑缩放与平移、自然的弹簧过渡和运动模糊。
- 代码已合并，即将进入生产环境。

#### 4.4 Excel
- 12K commits，1.6M 行代码。
- 仍在运行中。

### 五、学到的经验与总体结论

#### 5.1 模型选择与角色适配
- GPT-5.2 系列在持续自治工作上明显更好：遵循指令、保持专注、避免漂移（drift）、把事情实现得精确而完整。
- 不同模型擅长不同角色：Opus 4.5 倾向于更早停手、在方便时走捷径、很快交还控制权；GPT-5.2 是比 GPT-5.1-Codex 更好的 planner，尽管后者专为编码训练。
- 结论：按角色选最合适的模型，而不是用一个通用模型包打天下。

#### 5.2 减法式改进：删掉 integrator 角色
- 最初为质量控制和冲突解决专建 integrator 角色，结果它制造的瓶颈比解决的问题更多。
- worker 本来就有能力自己处理冲突，于是该角色被删除。

#### 5.3 结构的正确剂量在中间
- 结构太少：agent 会冲突、重复劳动、漂移。
- 结构太多：系统会变脆弱（fragility）。
- 直接照搬分布式计算与组织设计的成熟模型并非都适用于 agent。

#### 5.4 Prompt 主导论
- 原文判断："The harness and models matter, but the prompts matter more."（harness 和模型重要，但 prompt 更重要）。
- 系统行为中相当大一部分归结于怎么写 prompt：让 agent 协调良好、避免病态行为、长期保持专注，需要大量实验。

#### 5.5 核心问题的答案比预期乐观
- 数百个 agent 能在一个代码库上协作数周，在有野心的项目上取得真实进展。
- 这里发展出的技术最终会反哺 Cursor 自身的 agent 能力。

## 作者边界、反例与不确定性
- 多 agent 协调仍然是一个难题：现在的系统能用，但远非最优。
- 已知具体缺口：
  - planner 应该在自己派出的任务完成时被唤醒，去规划下一步，目前未做到。
  - agent 偶尔会跑得太久。
  - 仍然需要周期性的 fresh start 来对抗漂移和隧道视野。
- Solid→React 迁移虽通过 CI 与早期检查，作者仍保留"需仔细 review"的审慎判断。
