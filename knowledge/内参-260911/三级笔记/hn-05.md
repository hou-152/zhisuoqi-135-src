# Harness Engineering for Self-Improvement（把 harness 工程接到「递归自我改进」这条老线索上）

## 一句话主旨
现代递归自我改进更可能发生在 harness 层而非权重层，且 harness 代码本身正成为可优化对象。

## 作者试图回答的问题
核心问题：递归自我改进（RSI）在现代 AI 中如何落地？作者回答：现代 RSI 的实现路径从“模型改写自身权重”转向“改进包围模型的 harness 系统”。
关联子问题：harness 是什么、由哪些设计模式构成？它如何从手工设计逐步变成可执行、可搜索、可进化的代码空间？哪些系统（ACE/MCE/Meta-Harness、ADAS/AFlow、STOP/Self-Harness、AlphaEvolve/DGM、SIA）推动了这一转变？这条路线依赖什么、有何边界与瓶颈？

## 三级论证骨架

### 一、递归自我改进的现代重定位：从权重到 harness

#### 1.1 RSI 老线索与实现路径替换
- 现代模型自我改进更可能发生在 harness 层，而不是模型直接改写权重。
  - 起点：I. J. Good（1965）定义「ultraintelligent machine」为能在一切智力活动上超过人类、并设计出更好机器来改进自身的系统。
  - Yudkowsky（2008）把它收窄成具体反馈回路：AI 用当下的智能去改进那套产生它智能的认知机器。
  - 现代广义形态：模型改进**训练流水线**和**部署系统**，让下一代模型在有经济价值的任务上表现更好。
  - 作者点名「部署系统」（deployment system）：介于原始模型与真实世界之间的那一层，重要性看起来不亚于原始智能（即预训练刚结束时的 evals）；Claude Code、Codex 这类 coding agent 产品证明了这一层价值。

#### 1.2 harness 的定义与操作系统类比
- harness 是环绕基础模型的那套系统，编排执行，并决定模型如何思考与规划、如何调用工具与行动、如何感知与管理 context、如何存储 artifacts、如何评估结果。
  - 相比 2023 年旧公式「agent = LLM + memory + tools + planning + action」，harness 工程额外包含 **workflow 设计（如 loop engineering）、评估、权限控制、持久状态管理**。
  - 类比：harness 之于模型，像操作系统——把复杂逻辑封装起来，同时保持接口简单；设计应刻意简单通用以获得泛化能力，尽量参照既有软件工程实践，以吃到预训练知识红利。

### 二、harness 的三个设计模式：把易失过程变成可检查的持久对象

#### 2.1 工作流自动化 / loop engineering
- 定义一个模型可以在其中操作、测试、迭代的工作流，是自动化的关键设计。
  - 常见目标导向循环：plan → execute → observe/test → improve → execute，直到目标达成；过程中可能主动向用户发起澄清请求，确认任务规格或执行偏好。
  - 代表例子：Karpathy 的 autoresearch 仓库。
  - 强调模型分析自己的轨迹和失败案例，通过「agent runtime」而非静态 prompt 模板迭代进展。

#### 2.2 文件系统即持久记忆
- 长时程 agent 系统不该把整条工作流和全部日志都扛在 context 里，而应把耐久状态放进文件。
  - 长时程 rollout 中，实验日志、代码 diff、论文摘要、错误 trace 的长度常常远超模型训练时见过的 context 窗口。
  - 用 bash 之类命令读、写、编辑文件系统是 LLM 的基础技能；把持久记忆管理成「文件」这种朴素形态，天然能吃到核心模型能力提升的红利。

#### 2.3 子 agent 与后台作业：显式且可检查的并行
- harness 可以派生多个 subagent 并行执行、监控后台作业；父 agent 需要一个小型进程管理器：启动作业、检查日志、取消失败运行、把结果合并回主线程。
  - 关键设计选择：**让并行显式且可检查**。若 subagent 输出只活在临时对话 context 里，很快变得过时且不可见；存成文件、日志和状态记录，模型才能中断后恢复，并对自己的执行历史进行推理。

### 三、coding agent 稳定接口：harness 价值的实证

#### 3.1 主流 coding agent 共用同一套稳定循环
- Claude Code、Codex、OpenCode 和 Cursor 式 agent 的核心接口已经趋于稳定，共用同一套循环：观察仓库、计划、搜索/读文件、编辑/写补丁、跑测试、检查错误、再重来。
- 配上一组工具后，coding agent 就能在给定仓库里开发和调试，就像人类开发者配上 IDE。
- 工具分组（作者声明为演示而非穷举）：
  - 文件系统：glob、grep、ls；read、read_many；write、edit、multi_edit、apply_patch
  - Shell 执行：bash、PowerShell
  - IO：lsp，以及 git_status、git_diff、git_commit 等 git 工具
  - 外部 context：MCP 工具、Skills
  - 网页搜索：web_search、web_fetch、浏览器工具
  - Artifacts：读文档与图片，生成 HTML、图片
  - 后台进程：CronCreate、CronDelete、CronList
  - Agent 委派：spawn_agent、resume_agent、wait_agent、list_agents、close_agent、interrupt_agent

### 四、优化对象的阶梯与「代码是通用语言」的转折

#### 4.1 优化对象阶梯
- 全文主轴：instruction prompts → structured context → workflow → harness code → optimizer code。
  - 模型越强，就越能往阶梯上端、更复杂也更通用的目标走。

#### 4.2 代码是通用语言，harness 成为可执行搜索空间
- harness 说到底就是一段程序，规定 prompt、工具调用、子 agent、控制流、记忆和工作流逻辑如何协同。
- 一旦 harness 设计变成可执行的搜索空间，强 coding agent 就能进入人类工程师使用的同一片设计空间，而且它能访问的空间远大于手写 prompt。
  - 关键支撑：Meta-Harness 在 TerminalBench-2 上通过率 37.6%，高于全部人工 harness；ADAS、AFlow 等工作进一步证明。

### 五、context engineering：从 ACE 到 Meta-Harness

#### 5.1 ACE：上下文 playbook 与增量更新
- Agentic Context Engineering（ACE, Zhang et al. 2025）把 context 当作不断演化的 playbook，而非越来越长的 prompt。
  - 三个组件维护一本 bullet 形式的 context playbook，每条带标识符和描述：Generator 参照条目产出任务轨迹；Reflector 从成功与失败轨迹中提炼洞见；Curator 以增量、逐条方式更新结构化 context。
  - 关键设计是防止 **context collapse 与 brevity bias**：curator 不重写整块 prompt，而是输出结构化（标识符，描述）条目，用确定性逻辑合并进结构化 context 日志，并定期精化与去重。

#### 5.2 MCE：机制与内容分离的双层优化
- Meta Context Engineering（MCE, Ye et al. 2026）把**机制**（如何管理 context）与**产物内容**（context 里有什么）分开：元层跑 skill 演化，基层跑 context 优化。
  - 双层优化：内层在训练数据上寻找给定 skill 下的最佳 context；外层寻找在验证集上表现最好的 skill。
  - skill 数据库记录历史 skill、context 函数与评测指标；元层 agent 对既有 skill 做 agentic crossover 生成新 skill。
  - 一个 context 函数实例化为某个专属目录里的一组文件，含静态部分（skill.md）与动态部分（context 与数据 rollout）；内外层优化都在带标准工具集的 agentic coding 环境执行。
  - MCE 不像 ACE 那样强加「context 该怎么组织」的启发式规则，而是用**自由形式的 skill** 存储任务最重要的知识，并让 skill 与 context 一起迭代演化。

#### 5.3 Meta-Harness：优化「决定信息存取」的代码
- Meta-Harness（Lee et al. 2026）再深一层：被优化对象是那段决定并优化「什么信息该被存储、检索、呈现给模型」的代码——名字里的「Meta-」指它是用来优化 harness 的 harness。
  - proposer 本身是一个 coding agent，最终输出位于帕累托前沿的 harness 候选。
  - 整个执行历史通过文件系统可访问，coding agent 用 grep、cat 等命令去读，而不是把一切铲进单个 prompt。
  - 被提出的 harness 是文件系统里的一个字典，包含源码、分数、rollout 轨迹和状态更新；循环迭代地创造新 harness，只保留合格的。
  - 实测：TerminalBench-2 通过率 37.6%，高于所有人工 harness。

### 六、workflow design：手工流水线与自动搜索

#### 6.1 专家手工流水线：AI Scientist、ScientistOne、Autodata
- AI Scientist（Lu et al. 2026）搭起自动研究流水线：提研究想法、写代码、跑实验、分析结果、写稿、做同行评审。
- ScientistOne（Meng et al. 2026）把**可验证性**当作中心设计约束：每一条主张（引用、数值、方法、结论）都必须追溯到证据来源，并由 Chain-of-Evidence 检查审计。
- Autodata（Kulikov et al. 2026）是生成训练与评测数据的数据科学家：主 agent 管理一个 challenger（出题）、一个 weak solver、一个 strong solver 和一个 verifier/judge，目标是合成「难度刚刚好」的数据——强解题者能做对、弱解题者会做错。
  - challenger 的 prompt 会根据 solver 和 verifier 的反馈迭代更新。
  - 作者点出局限：合成任务只用来微调弱 solver 而非强 solver；如果循环无法迭代改进强模型，它更像是在生成的 prompt 分布上做间接蒸馏，RSI 的味道就淡了。

#### 6.2 把工作流设计当作搜索问题：ADAS 与 AFlow
- Automated Design of Agentic Systems（ADAS, Hu et al. 2025）把 agent 设计本身表述成优化问题，即「meta-agent search」：
  - 用 CoT、self-refine 等简单 agent 初始化工作流档案库。
  - 元 agent 参照档案库里的既有方案，全用代码编写新 agent：先生成高层描述，再实现成代码。
  - 草稿程序经元 agent 两轮 self-refine 以检查新颖性。
  - 评测每个新候选，成功的加回档案库，重复直到最大迭代次数。
- AFlow（Zhang et al. 2025）把 agentic 工作流表示成图：节点是调用 LLM 的动作，边用代码实现逻辑；优化依赖 MCTS——用分数与均匀探索的软混合选择节点，让 LLM 基于评测表现产出改造后的工作流并展开、执行、评测。
  - 在 QA、代码和数学任务上，相对人工设计和 ADAS 都有可观改进。

### 七、self-improving harness：STOP 与 Self-Harness

#### 7.1 STOP：改进改进器本身，以及告诫式结果
- Self-Taught Optimizer（STOP, Zelikman et al. 2023）是递归式脚手架改进的早期例子。
  - 种子改进器接收初始解、效用函数和一个黑箱语言模型，返回改进后的解；STOP 的目标不是直接改进解，而是**改进改进器本身**。
  - 改进后的改进器发现了各种策略：遗传算法、分解并改进局部、多臂 prompt 老虎机、模拟退火、变化温度、beam search / tree search。
  - 最值得记住的告诫式结果：在 GPT-4 上让下游平均表现随迭代提升，在 GPT-3.5 和 Mixtral 这类更弱模型上反而退化。递归结构本身不够，基座模型必须足够有能力去改进机制——harness 改进的是部署，智能仍是核心。

#### 7.2 Self-Harness：有界改动与回归闸
- Self-Harness（Zhang et al. 2026）让 LLM agent 通过 propose-evaluate-accept 循环改进自己的 harness，分三阶段：
  - 弱点挖掘：把失败聚类成有 verifier 依据的失败模式。两次运行可能在错误日志表面共享同一 verifier 结果（如超时、缺 artifact），因果机制却完全不同；需要信息丰富的失败记录，含终端 verifier 级原因、相关 agent 行为的因果状态、trace 暴露出的抽象 agent 机制，才能挖出根因。
  - harness 提案：基于失败模式提出**有界**的改动。模型拿到一份有界提案 context：当前 harness 的可编辑面、有 verifier 依据的失败模式、应保留的通过行为记录、以往尝试过的改动摘要。改动应偏好可处理、能用窄改动解决的复现性错误模式，且候选之间要有区分度和多样性。
  - 提案验证：候选改动在 held-in（测试弱点是否解决）与 held-out（检查是否引入新问题）两个划分上跑回归测试，**两边都无退化才被接受**；接受的合并进新 harness，被拒的只记日志、不动现役 harness。
- 在 Terminal-Bench-2 上跑 MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5 时，Self-Harness 学到了针对不同基座模型不同弱点的模型专属 harness 指令，并提升了 held-out 通过率。
- 担忧：如果一个程序被允许编辑操作系统本身，抽象边界就被打破了；可编辑面必须被妥善设计，权限控制与安全层必须活在这个循环之外；奖励攻击的全部挑战依然存在。

### 八、进化式搜索：从 prompt 进化到 harness 仓库进化

#### 8.1 适用条件与先例
- 进化式搜索受自然选择启发：让一群解变异，只保留高「适应度」个体。适合两种情形：搜索空间极大或形状古怪；难以用梯度直接优化但容易评估解。harness 搜索正好合适。
- 先例：Promptbreeder（Fernando et al. 2023）用丰富变异操作优化任务 prompt，变异 prompt 本身也在进化；GEPA（Agrawal et al. 2025）把基于反思的 prompting 与进化搜索结合，用对试错轨迹的自然语言反思来提出 prompt 更新。

#### 8.2 AlphaEvolve 及其消融
- AlphaEvolve（Novikov et al. 2025）是 coding-agent 式进化搜索系统：存一池候选程序，提示冻结的 LLM 生成改进 diff，反复评测并保留成功者。
  - prompt 中包含父程序、结果、指令，有时还有元信息。
  - coding agent 能访问整个仓库，但待改进代码区域用 EVOLVE-BLOCK-START 和 EVOLVE-BLOCK-END 显式标记。
  - 元 prompt 与指令、context 共同进化，方式与进化解程序如出一辙。
  - 消融实验显示进化流程、prompt 中的 context、元 prompt、整文件进化、使用更强 LLM 各自都有价值。
- 后续变体：ThetaEvolve（Wang et al. 2025）把进化搜索与 RL、上下文学习结合；ShinkaEvolve（Lange et al. 2025）引入三个组件提升采样效率——父代采样兼顾表现排名与子代数量以更高效探索；基于 embedding 余弦相似度做代码新颖性拒绝采样，丢掉过于相似的候选；用 meta-scratchpad 记录成功解中的好模式指导未来变异。

#### 8.3 DGM：固定模型下的 harness 仓库进化
- Darwin Gödel Machine（DGM, Zhang et al. 2025）显式瞄准**可编辑 harness 代码仓库的进化**：coding agent 被允许修改自己的 harness。
  - 从池中一个 coding agent 起步；每轮按「与表现成正比、与子代数量成反比」的概率挑父代，改造并分叉出新 agent。
  - 被选中的父 agent 检查自己的基准评测日志，然后对自己的 harness 代码库提出改进；代码编辑只用两个基本工具：bash 与 editor（view/create/edit）。
  - 新 agent 被评测，只有表现足够高的才加回池，重复直到停止条件。
  - 实验：以 Claude 3.5 Sonnet 为基座、初始 harness 配置很简单，DGM 发现的 agent 在 SWE-bench Verified 上从 20% 提到 50%、Polyglot 上从 14.2% 提到 30.7%，与手工设计的 agent 相当或更优。
- 这一族方法在候选解可自动评测、适应度易量化的领域效果好（矩阵乘法、GPU kernel 优化、算法竞赛、数据中心调度）；在评估缓慢、模糊或主要靠启发式的领域则吃力。进化的算力效率与有效性同样是隐忧。

### 九、与模型权重的联合优化：SIA

#### 9.1 SIA 的双杠杆循环与证据局限
- SIA（Hebbar et al. 2026）是把 harness 改进与模型参数更新放进同一优化循环的早期尝试，三个组件：Meta-Agent 提出初始 harness；Task-Specific Agent 执行任务；Feedback-Agent 根据近期轨迹决定这一步更新 harness 还是更新权重。
- 作者对证据本身持保留态度：实验有若干混淆选择，如任务 agent 比 Meta-Agent 和 Feedback-Agent 用的模型弱得多（gpt-oss-120b 对 Claude Sonnet 4.6），基线也太弱、无法与相关方法干净互参。方向有趣，但证据是暂定的；训练稳定性、Goodhart 效应等挑战仍然开放。

### 十、失败模式与迈向完整 RSI 的瓶颈

#### 10.1 研究 agent 的六种失败模式
- AI Scientist 线证明专家设计的 harness 能协调自动研究回路很大一部分，但**论文生产不等于科学发现**：系统可以写出貌似合理的手稿，同时带着捏造引用、实现漂移或弱实验结果。
- Trehan & Chopra（2026）在最小脚手架与基础工具下测试 LLM 从研究想法走到论文：三个领域各 45–50 篇高质量种子文献，人类专家只挑四个想法进入完整流程，**最终只有一个被完整执行成论文**。六种反复出现的失败模式：
  - 偏向训练数据的默认值（旧库、过时命令、标准格式，或基于非实际仓库/数据集的假设）
  - 执行压力下的实现漂移（技术复杂时转向更简单解法，而非所提方法）
  - 记忆与 context 退化（长时程项目丢失关键细节，除非日志被写成持久 artifact）
  - 过度乐观（实验噪声大甚至失败仍宣布成功；与 Bubeck et al. 2025 的「p-hacking and eureka-ing」同类）
  - 领域智能不足（缺少预判实现复杂度、判断实验是否合理、知道哪些基线重要等默会知识）
  - 科学品味薄弱（实验能跑通，却回答不了对的问题）
- 相关基准数字：PaperBench 上最好模型 Claude 3.5 Sonnet 约 21% 不敌 ML 博士生；CORE-Bench 最难任务最好 agent 只有 21% 准确率；RE-Bench 中专家在 82% 的八小时尝试中拿到非零分、24% 达到或超过强参考解，AI agent 在 2 小时预算下得分是人类的 4 倍，但更长预算下人类反超；MLE-bench 最好配置在 16.9% 竞赛中至少达到铜牌。

#### 10.2 迈向完整 RSI 的七个瓶颈
- 1. 弱而模糊的评估器：许多研究主张没有快速精确的 verifier；当前回路在指标可测量、客观时最有效。研究品味、新颖性、长期科学价值难以度量——研究品味混合了问题构造、实验设计，以及「哪些反常结果值得追、哪些失败值得重试」的判断。
- 2. context 与记忆的生命周期：记忆不断增长，需要 harness 管理以弥补长文本局限；作者判断 context engineering 将会也应该成为智能的核心组成部分，而不是停留在软件系统层。
- 3. 负结果：文献偏向成功，在此数据上训练的 LLM 可能不擅长判断何时放弃假设、报告负结果或承认失败；研究型 harness 应让失败尝试易于保存——从失败中学习是收缩任务搜索空间的最佳方式。
- 4. 多样性坍塌：进化与 RL 回路倾向压榨已知高回报模式，需要机制防止种群坍缩成同一个解的变体；对开放式研究尤其关键，最好路径在当前评估器下最初可能显得更差。
- 5. 奖励攻击：自我改进回路优化的是你给的任何信号——来自单元测试就对测试过拟合；来自裁判模型就学会针对该裁判；来自基准分数就利用基准伪影。
- 6. 长期成功：coding agent 提升了软件工程日常生产力，但许多优化目标太短期；常能完成手头任务，却不清楚如何保护由成百上千工程师共同维护的仓库的长期健康。沙箱式 RLVR 很少捕捉可维护性、所有权边界、迁移成本、向后兼容或未来调试负担。
- 7. 人的角色：人应当**在栈上往上移动，而不是被移出回路**——在正确时机、正确抽象层级提供监督，系统设计要考虑何时以及如何设置触点。

#### 10.3 结构性结论
- 评估器与权限控制大概率应当坐在演化 harness 的循环之外，配合 held-out 测试、trace 审计、以及真正重要决策点上的人类评审；监督能被放大和自动化到什么程度，仍是开放研究领域。
- 收尾立场：许多挑战都需要人的反馈与引导——**我们是在为人类更好的未来造这项技术，而不是反过来**。

## 作者边界、反例与不确定性
- **STOP 负面结果**：同一套递归改进在 GPT-4 上提升、在 GPT-3.5 和 Mixtral 上退化，说明递归结构不能替代基座智能；harness 改进的是部署，智能仍是核心。
- **SIA 证据暂定**：实验存在混淆（任务模型弱于元模型、基线弱），无法干净互参；训练稳定性与 Goodhart 效应仍是开放挑战。
- **进化式搜索的适用范围**：在可自动评测、适应度易量化的领域好使；评估缓慢、模糊或靠启发式的领域吃力；算力效率与有效性是隐忧。
- **Autodata 的局限**：合成任务只微调弱 solver，若不能迭代改进强模型，更像间接蒸馏，RSI 味道淡。
- **论文生产不等于科学发现**：研究 agent 有六种反复失败（训练默认值、实现漂移、记忆退化、过度乐观、领域智能不足、品味薄弱）。
- **奖励攻击与多样性坍塌仍无完善解**：作者只提出结构性防御（评估器与权限控制循环外、held-out 测试、trace 审计），未声称已解决。
- **近期路径判断**：作者判断近期不太可能以「模型直接改写权重」开场，但未来 RSI 多大程度依赖 harness 工程难以预测。
- **递归改进的长期治理**：如果程序被允许编辑操作系统本身，抽象边界被打破；可编辑面必须妥善设计，权限控制与安全层必须活在这个循环之外。
- **最终不确定性**：监督能被放大和自动化到什么程度，仍是开放研究领域；许多挑战都需要人的反馈与引导。
