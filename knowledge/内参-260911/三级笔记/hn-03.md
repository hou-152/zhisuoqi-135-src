# 你的 agent 需要的是 harness，不是又一个框架

## 一句话主旨
Agent 运行时缺的是连接、保护、编排部件的执行外壳，而不是又一个替你做决定的框架。

## 作者试图回答的问题
- 核心问题：Agent 运行时真正缺的那一层是什么？为什么是 harness 而不是 framework？
- 关联子问题：持久化、事件驱动的基础设施如何成为 harness 的充分实现？哪些 agent 问题可以靠基础设施解决，哪些仍然悬而未决？

## 三级论证骨架
### 一、harness 的定义与问题陈述
#### 1.1 harness 是什么：一个不做工作的连接层
- harness 在任何工程学科里都是同一件东西：连接、保护、编排各个部件，**而自己不做工作**。
  - 三个例子：线束在引擎与仪表盘间路由信号；测试 harness 提供可重复、可观测的脚手架；安全带在坠落时接住你。
  - 关键边界在最后半句：它自己不做工作。这条边界正是区别于框架的地方。
- 把 agent runtime 部件对号入座：**LLM 是引擎，tools 是外设，memory 是存储**。
  - 摆齐之后暴露的问题全是「之间」的问题——失败恢复、消息冲突、事件路由。

#### 1.2 框架在重造 harness
- 「每个 agent 框架都在从零重造一个 harness」：自己的重试逻辑、自己的状态持久化、自己的任务队列、自己的事件路由。
  - 作者暗示的浪费不是重复造轮子，而是：**这些框架在用应用层代码解决基础设施层问题**。
- 框架与 harness 的分野：框架替你决定 agent 怎么想、怎么行动；harness 只让这些动作可靠地发生。

#### 1.3 价值主张：这是基础设施问题，不是 AI 问题
- 结论句直白：**「All of these problems are infrastructure problems, not AI problems.」**
  - 这是全文价值主张，也是所有技术选择的依据。

### 二、解答：持久化、事件驱动的基础设施本身就是 harness
#### 2.1 持久化执行：每一次调用都是 step
- 每一次 LLM 调用或工具调用都成为一个 step——**一个可独立重试的工作单元**。
  - 进程在第五轮死掉，前四轮的结果已经落盘。
  - 作者点出这不是为 agent 发明的新机制，而是**为结账工作流设计的持久化执行**，原封不动搬到 agent loop 上。
- step 级 trace 提供对 agent loop 每一轮的完整可观测性。

#### 2.2 事件驱动：触发与工作解耦
- 事件在函数之间路由触发，并发控制防止碰撞。
- Utah 的「universally triggered」是实指：Telegram/Slack webhook、cron 定时、子 agent 调用、函数间事件——**agent 不知道也不关心自己是被什么激活的**。
  - 明天加一个 Slack bot，agent loop 一行不改，harness 负责路由。

#### 2.3 本地执行 + 云编排：connect() 与 webhook transform
- 完整链路：Telegram/Slack webhook 打到 Inngest Cloud → webhook transform 将原始 http payload 转成带类型事件 → 本地 worker 接事件运行 agent function → 发出 reply 事件，由独立函数经渠道 API 送回。
- worker 用 Inngest 的 **connect() API**：从本机（或 mac mini、远程服务器）向 Cloud 建立持久 WebSocket 连接，**不需要公网 endpoint**。
  - 这是「本地跑 agent，但享受云编排」的关键一招。
- 图里标出两向收益：左侧「事件触发，agent loop 在本地跑 step」，右侧「step 被检查点，事件被广播」——本地执行与云端状态/trace/事件是同一套机制的两面。

#### 2.4 与 OpenClaw 的分界：外部编排层 vs 进程内事件
- 作者承认 OpenClaw 和 pi 生态是灵感来源，但关键差异在于：**它们内部用的是进程内事件，事件与编排都在内存里处理**。
- 换成外部编排层带来五项能力：
  - 可观测性（trace 与 step 级检视）
  - 内建持久化执行（可靠性与重试）
  - 多人、分布式 agent 编排的基础
  - 事件历史提供审计轨迹
  - 内建调度（cron 或延迟/定时函数）
- 这条分界线画清了「单机 agent」与「具备运维属性的 agent」的区别。

### 三、Utah 的架构验证
#### 3.1 agent loop 就是一串 step
- 核心是 think → act → observe 循环：每轮调 LLM，检查工具调用，执行工具，把结果喂回去。**关键洞见：每一次 LLM 调用和每一次工具执行都是一个 Inngest step。**
- 循环骨架：`step.run` 包住 `callLLM`（think）；有 toolCalls 则逐个 `step.run` 执行工具（act），把结果推回 messages（observe）；**LLM 返回文本且无工具调用，那段文本就是回复，循环结束**——不需要显式 done 信号。
- 三个机制：
  - **step ID 自动索引**：`step.run("think")` 在循环里调十次，Inngest 内部记为 `think:0`、`think:1`……SDK 自动编号，用户不用管理唯一 ID。
  - **每个 step 独立可重试**：第 3 轮 LLM API 返回 500，只重试那一个 step；前两轮结果已持久化，不会重放。
  - **文本响应即完成**。

#### 3.2 工具用现成的库
- Utah 不手搓文件 I/O 和 shell，直接引入 **pi-coding-agent**（OpenClaw/Pi 生态、经过实战检验）：
  - read、write、edit：文件操作，支持图片、二进制检测、智能截断（edit 工具在 context window 上是亮点）。
  - bash：shell 执行，超时和输出截断可配置。
  - grep、find、ls：搜索与导航，尊重 .gitignore。
- Utah 自己只加三个定制工具：remember（笔记持久化进每日日志）、web_fetch、delegate_task。
- 作者的态度：「AI agent 的工具故事和其他任何软件没有区别——**用现成的库，用 Inngest step 包起来，完事**。」

#### 3.3 六个函数，而非一个巨石
- Utah 是六个通过事件通信的函数：
  - **handleMessage**：主 agent 循环；
  - **sendReply**：把响应送回渠道（负责渠道特有格式化与降级，如畸形 HTML 降级纯文本）；
  - **acknowledgeMessage**：打字指示器，消息到达时**立即触发，不必等 agent loop**；
  - **failureHandler**：跨所有函数的全局错误处理，接住未处理错误并通知用户；
  - **heartbeat**：周期性签到（`*/30` cron，用于 memory compaction）；
  - **subAgent**：经 `step.invoke()` 隔离运行的子 agent。
- 每个函数有自己的重试策略、并发控制和触发条件。
- sendReply 的可组合性：**可以从任何地方触发**——子 agent 或 fan-out 工作流想在循环中途发进度回复，只需从新工具里发事件即可。

#### 3.4 子 agent：step.invoke() 就够了
- 触发场景：任务大到撑爆 context window——重构文件、研究主题、写文档；**单线程对话里的通用 agent 跨几天长会话会遇到 context window 问题**。
- 机制：主 agent 调用 `delegate_task` 工具时，用 `step.invoke()` 启动一次**完全独立的 agent function run**；子 agent fork 会话上下文到自己子会话（独立 session key），配聚焦任务；**工具集去掉 `delegate_task`，禁止递归派生**；最后向父级返回摘要。
- 子 agent 拿到自己的重试、step 级可观测性、持久化执行；父 agent 只看到一个工具结果。
- 结论很硬：**「编排已经解决了，不需要 agent-to-agent 协议，只是函数在调用函数。」**

#### 3.5 单例并发：一次只跑一个对话
- 「一个对话」由渠道特定 session key 定义：Telegram 用 chat id；Slack 精确到 channel + thread。
- 问题：一个对话里连发多条消息，你希望 agent **同时拥有两条消息的上下文**，而非第一个 loop 跑完第二个再回应。
- 方案选择 **cancel + restart**，理由：循环带着全部上下文重启是最干净的做法。
- 实现只需一行配置，做了两件事：
  - 以 sessionKey 为键的**单例并发**：每个 chat 同一时刻只有一次 run，没有竞态和交错回复；
  - **新消息即取消**：用户在 agent 处理中发来新消息，当前 run 被取消，新 run 带最新消息启动。
- 对照传统做法：建队列、管理锁、自己处理取消——**在 Inngest 里这是一行配置**。

### 四、真正的难题与边界
#### 4.1 上下文管理才是真正的难题
- 最难的不是调用 LLM，而是**管理进入 LLM 调用的东西**。
  - 症状：工具单次可能返回数千字符，几轮后对话上下文膨胀，模型开始跟丢——作者**亲眼看到 agent loop 无休止地调用工具却始终产不出回复**。
- 解法是**两级上下文剪枝**：
  - `keepLastAssistantTurns: 3`：最近三轮始终保持完整；
  - `softTrim`：旧工具结果超过 `maxChars: 4000` 时保留头 1500 + 尾 1500 字符；
  - `hardClear`：总量超过 50000 时整段清空并留占位符。
- 另有**压缩（compaction）**作用于会话本身：估算 token 超阈值时，先把历史摘要化再喂进下一次运行。
  - 作者的分工判据：**剪枝处理运行内的上下文，压缩处理跨运行的累积**。
- 再加两道保险：
  - **预算警告**：迭代次数快用完时注入系统消息，让 agent 收尾；
  - **溢出恢复**：运行中途 LLM 返回 context-too-large 错误时，强制压缩消息并重试，**不浪费一次迭代**。
- 四者合起来让 agent 保持在轨。
- 多 provider 支持：用 pi-ai 这个 provider 无关的 LLM 抽象，支持 Anthropic、OpenAI、Google，**换 provider 只是改配置**；展望：子 agent 未来可能用不同模型——写代码用 Codex，做研究用 Opus。

#### 4.2 steering 仍是未解问题
- 用户在 agent 运行中途发新消息怎么办？当前用 singleton 取消当前 run 再起新的，能用，但**在途的工作丢失了**；新 run 从持久化的会话状态接上，**并不无缝**。
- 作者明说这是他们正在探索的领域。

#### 4.3 streaming 与循环中途更新是机会点
- 每个 Inngest step 是原子的：运行、产出结果、结果落盘。
- 尚未引入 streaming，也还没用上 Inngest 的 realtime 能力。
- 团队想再叠一个 web app 和一个 TUI，探索如何向支持流式的客户端**可选地推送循环中途的进度更新**。

#### 4.4 下一步与可复用结论
- Utah 目前是跑在自己机器或服务器上的、**单人的个人 harness**；下一步要让 Utah 真正「多人化」。
- 多人化路径：**可替换的 sandbox、外部化的状态与 memory**——这也会让 Utah 能跑在 serverless 上。
- 其他方向：基于 Inngest 的 session 监控；用 `step.waitForEvent()` 做 human-in-the-loop 审批流；**让 Utah 自己写自己**——构建新的 agent 与工作流、创建新的 webhook、通过 API 自我监控。
- 结尾的推广面：**这个 agent loop 模式适用于任何对话式 AI**——Slack bot、Discord bot、客服 agent、编码助手；加一个新渠道无非是一个 webhook transform 加一个回复函数。
- 最后一句落在：「如果你在做 AI agent 并撞上同样的墙——状态管理、重试、并发、可观测性——**你需要的原语可能已经存在了**。」

## 作者边界、反例与不确定性
- **steering 是明确未解问题**：cancel + restart 以丢弃在途工作为代价，作者承认「并不无缝」，并标记为正在探索的领域。
- **持久性自己制造反作用力**：循环越持久、迭代越多，上下文膨胀越严重，直到 agent 无限调用工具却不出回复——持久化执行本身逼出了剪枝/压缩/预算/溢出四层回应。
- **基础设施接不住的部分**：上下文管理和用户中途介入，恰恰是基础设施解决不了、需要另想办法的问题。作者没有声称基础设施能解决一切。
- **Utah 尚未支持 streaming 和实时更新**：step 的原子性目前意味着无法推送循环中途进度，这是一个未实现的能力，而非设计拒绝。
- **当前定位是单人的个人 harness**：多人化、sandbox 可替换、状态外部化都还是「接下来要探索」，不是已完成能力。
