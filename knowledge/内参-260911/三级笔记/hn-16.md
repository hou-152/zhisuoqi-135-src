# Loop Engineer：把 Agent 工作流变成可复用知识模板

## 一句话主旨
把一次性提示升级为可触发、可记账、可复盘的 agent loop 系统。

## 作者试图回答的问题
如何把 agent 工作流变成可复用的知识模板（loop engineering 的真实搭建方式）。关联子问题：agent 的基本形态是什么、为什么需要 harness、多 loop 如何产生复利、落地要哪些组件。

## 三级论证骨架

### 一、重心转移：从 prompt engineering 到 loop engineering
#### 1.1 底层定义与三阶段演进
- agent 的定义被压缩成一句话：llm runs tools in a loop to achieve a goal。
- 2023：多数用法是 task completion，prompt engineering 在单次调用里安排上下文、约束输出。
- 2024 中：context window 从数千 tokens 扩到 128k 再到 1M 级别，模型带 MCP 等工具自决定下一步，把 tool call 与 tool response 放回对话循环。
- 2025 后：转向长任务、跨 session、多 agent 协作；问题从"完成这次任务"变成"整个系统自己决定下一步，并把状态延续到下一轮"。
#### 1.2 上下文越大反而越稀缺
- 即使标称 1M tokens，作者提醒真实有效窗口可能只有 128k 到 200k。
- 应对手段：prompt cache、compaction strategy、skill，避免每次把所有背景塞进上下文。

### 二、agent 的三部件与模型外的 harness
#### 2.1 agent 基本形态
- 三底层部件：programming language agent loop、memory layer、tool access。
- 新变化发生在这三者之外：任务跨 30 分钟、2 小时、多 session、多 agent 时，系统需要 agent harness 处理触发器、共享文件、日志、编排和验证。
#### 2.2 harness 的定义与二分
- LangChain 语境：凡"non-model 的部分"都算 harness——prompt、context management、orchestration、hooks、state、logs、环境工具；作者自己说这定义很宽、容易让人困惑。
- 更有用的二分：第一层优化 agent loop 本身（让单个 Codex、Claude Code 或自建 agent 更好地完成单任务）；第二层优化 agentic system 的外部环境（何时触发、做什么、交给谁、结果如何沉淀）。
- loop engineer 主要处理第二层，人的角色从发 prompt 转向设计触发器、状态模型、共享目录、验证机制和升级路径。

### 三、价值机制：复利与 shared brain
#### 3.1 support loop：最小可行形态
- cron 每 30 分钟唤醒 agent，读近期 support tickets，回复未被自动处理的问题，并记录用户摩擦、产品想法、工程 bug。
- 第一层价值：自动处理重复问题并留下产品改进线索——如多个用户询问 export files，就在 signals 里创建或更新相关条目。
- 第二层价值：闭环——发现明确 bug 或高频摩擦时触发 coding agent 修复，再监控是否仍有相同问题，甚至告知客户已上线。
- 威力不在"每次执行都很聪明"，而在"每次执行都能把结果写到系统里"；没有共享状态，agent 每 30 分钟醒来只是重复巡检。
#### 3.2 多 loop 共享同一套状态
- 公司的 support、SEO、growth、ads loop 各有触发节奏和职责，但读写同一套共享文件系统。
- signals 是最重要的抽象之一：记录 product ideas、frictions、opportunities、conversion gaps、keyword opportunities；一个 signal 持续追加来源、用户案例和时间线，而非每轮重新生成孤立报告。
- 例：SEO loop 每天 9 点拉数据、研究主题、发布页面，发现某路径点击多但转化不足就写入 conversion gap signal；ads loop 发现某 keyword 点击率好但无 organic content，也反馈给 SEO loop。
#### 3.3 复利发生在"互相读写"
- growth loop 不只看自己的 analytics，还读 support、SEO、ads 的 signals，优先修复多次出现的 bug，或抓住营销团队观察到的机会。
- 多个 loop 每小时或每天运行，但共享同一个决策背景，不同 loop 观察到的机会互相喂给对方。

### 四、落地组件
#### 4.1 四个核心组件
- triggers：cron、webhook、incident、另一个 agent、用户事件、业务数据变化；让 agent 在正确时机醒来，而非等人手动发 prompt。
- file structure：作者认为最重要，跨 session、跨 agent 的工作必须依赖稳定、可读、可追加的状态系统，承担 memory、coordination、review、handoff。
- tools and connectors：访问业务系统、日志、数据库、支付、客服、浏览器、仓库、测试工具，否则 loop 只能写总结。
- parallel and autonomous environment：代码库和运行环境允许多 agent 同时工作、互不踩踏，且每个 agent 都能验证自己的改动，否则 loop 一多就互相冲突。
#### 4.2 codebase harness：三性
- legible：agent 能快速判断"该改哪里"。用 OpenAI 的 AGENTS.md 作索引入口指向其他文档，配合 custom lint、programmatic link check 把规则注入工具链，避免误用 legacy folders 或错误 repo。
- executable：低 token、低认知负担启动本地环境。dev.local 脚本一步拉起开发环境；worktree friendly，使 5 个 parallel agents 在不同 worktree 中都能启动和测试。
- verifiable：agent 有工具证明结果。推荐 Playwright CLI（操作浏览器、记录视频、附到 PR）；关键路径需端到端测试，如 upgrade flow、sign up flow、核心创建流程。
- 不要只做 self-verification：在 PR skill 里要求执行 agent spawn 一个 read-only verifier agent 并给它详细规格，执行与验证分离，减少"看起来完成但实际没完成"。
#### 4.3 文件系统三类抽象
- artifacts：每个 agent 工作或发现的输出，即 shared knowledge layer；类型含 docs、signals、tasks、tickets、campaigns，每种应有独立文件夹和 README，写清内容边界、创建流程、schema 和时间线。
- loop contract：每个 loop 自己的 README，说明 goal、workflow、boundaries、backlog、timeline；agent 每次触发前先读 contract。
- global work log：记录跨领域 ad hoc 信息和当天整体工作上下文；理由是人类一天既 review loop 输出，也与 agent 共同做创造性或困难任务，帮助新 session 先读最近 5 到 10 条。
- 三者分工：artifacts 记结构化业务对象，contract 管单个 loop 的职责与状态，global log 串起跨 loop、跨 domain 的临时上下文。

### 五、实施姿势：先校准，再固化
- 不要一开始就自动化。以 support loop 为例：先让 agent 拉取过去一小时的工单，分析问题、草拟回复、保存 ticket artifacts、记录 signals、创建 engineering tasks、写 log。
- test run 的目的是校准 workflow：哪些问题直接回复、哪些需查 Stripe、Supabase、Render logs、哪些只是产品反馈、哪些应触发 engineering task。
- 试跑符合预期后，创建 domain/support/README 作为 contract（写入 goal、workflow、timeline、backlog），再配置每小时触发的 loop。
- 可复用知识模板不是事后文档，而是下一轮 agent 会真实读取和执行的操作系统。

### 六、收束：三层递进的系统观
- 第一层 agent 基本能力：Agent Loop 依赖 memory layer 与 tool access。
- 第二层 harness 与环境：Agent Harness 与 legible / executable / verifiable codebase 共同决定 loop 能否长期稳定运行。
- 第三层跨循环协作：Shared File System、Signals、Loop Contract、Artifact Schema、Global Work Log、Cross-session Work 构成状态系统。
- 递进关系：没有 Agent Loop 就没有自动执行；没有 Harness 与可验证环境，单 loop 只能偶尔完成任务；没有共享文件和 contract，多 loop 各自为政，形不成 compound effect。
- 优化对象差异：prompt engineering 优化一次模型调用，agent harness 优化一次 agent 执行，loop engineering 优化多轮、多 agent、多业务信号之间的复利结构。

## 作者边界、反例与不确定性
- 作者明确建议不要一开始就自动化，需先人工监督跑一轮。
- 有效 context window 可能远小于标称值（标称 1M → 实际约 128k–200k）。
- harness 的宽定义被作者自己承认很宽、容易让人困惑，其边界并无严格界定。
- self-verification 被明确否定，但只读 verifier 本身的可靠性材料未展开。
- 材料未给出明确的失败案例或反例条件。
