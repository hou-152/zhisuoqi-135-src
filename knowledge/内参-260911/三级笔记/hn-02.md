# The Anatomy of an Agent Harness

## 一句话主旨
智能在模型，可用性在 harness；harness engineering 是围绕模型智能做系统工程。

## 作者试图回答的问题
核心问题：一个 agent 系统中，什么属于模型、什么属于 harness？为什么需要 harness、它由哪些组件构成、这些组件如何推导出来并协同工作？模型训练与 harness 设计如何互相塑造，harness engineering 未来会走向何处？

## 三级论证骨架

### 一、用减法定义 harness：Agent = Model + Harness

#### 1.1 harness 的定义与边界
- 核心等式：**Agent = Model + Harness**。模型承载智能，harness 是让智能变得有用的那个系统。
- 减法定义：**If you're not the model, you're the harness.**——凡是不属于模型本身的代码、配置和执行逻辑，都是 harness。
- 关键判断：**a raw model is not an agent**。裸模型只有在 harness 给了它四样东西之后才成为 agent：
  - state（状态）
  - tool execution（工具执行）
  - feedback loops（反馈回路）
  - enforceable constraints（可强制执行的约束）

#### 1.2 harness 的具体清单
- System Prompts（系统提示词）
- Tools、Skills、MCPs 以及它们的描述（descriptions 本身也算 harness）
- Bundled Infrastructure：filesystem、sandbox、browser
- Orchestration Logic：subagent spawning、handoffs、model routing
- Hooks / Middleware，用于确定性执行：compaction、continuation、lint checks

#### 1.3 为什么坚持这条界线
- 作者明确说不是因为它最准确，而是因为它逼人做一件事——**designing systems around model intelligence**（围绕模型智能来设计系统），而不是围着模型的缺陷打转。
- 切分 agent 系统的方式有很多，很多都很乱（messy），这条界线最干净。

### 二、为什么需要 harness：从模型能力缺口反推

#### 2.1 模型能力的克制素描
- 模型 mostly 吃进 text、images、audio、video，吐出 text，**That's it.**
- 开箱即用做不到的四件事，全部是 harness level features：
  - 跨交互维持 durable state（持久状态）
  - 执行代码
  - 获取 realtime knowledge（实时知识）
  - 搭建环境、安装依赖包以完成工作
- 结构性结论：**LLM 的结构要求某种把它包起来的机器**（machinery that wraps them to do useful work）。

#### 2.2 harness engineering 的推导方法
- 全文方法论是**反向推导**：不列功能清单，而是从「模型这一原语」出发，按 **Behavior we want (or want to fix) → Harness Design to help the model achieve this** 的模式逐项推导。
- 主线心法：**把想要的 agent 行为，转换成 harness 里的一个实际功能**。
- harness engineering 的双重作用：
  - 帮人类注入有用的先验（inject useful priors）来引导 agent 行为
  - 在模型变强之后，用来「surgically extend and correct」模型——外科手术式地扩展与纠正
- 一个日常例子：为了得到 chatting 这种产品 UX，把模型包进一个 while loop、追踪历史消息并 append 新消息——这已经是一副 harness 了。

### 三、从基础到高级的组件推导

#### 3.1 文件系统：最基础的 harness 原语
- 作者定位：文件系统 **arguably the most foundational harness primitive**。
- 想要的行为：持久存储、与真实数据打交道、把塞不进 context 的信息卸载出去、让工作跨 session 存活。
- 为什么是文件系统：**世界本来就在用文件系统干活**，模型天然在数十亿 token 的「如何使用文件系统」上训练过。
- 解锁三件事：
  - agent 拿到 workspace，可读数据、代码和文档
  - 工作可增量累加和卸载，不必把一切攥在 context 里
  - 文件系统是天然协作面：多 agent 与人类通过共享文件协调（Agent Teams 架构依赖它）
- Git 在文件系统之上加版本能力：追踪工作、回滚错误、开分支做实验。

#### 3.2 bash 与代码执行：一个通用工具
- 想要的行为：agent 自主解决问题，人类不必预先设计好每一个工具。
- 今天主流的执行模式是 **ReAct loop**：模型推理 → tool call 采取行动 → 观察结果 → 在 while loop 重复。
- 结构性瓶颈：**harness 只能执行它有逻辑的工具**。如果每个动作都要人先造工具，agent 的能力上限就是工具表的长度。
- 解法：给 agent 一个通用工具——bash。模型靠写代码并执行来自主解决问题。
- 更本质的说法：bash + code exec 是朝 **giving models a computer**（给模型一台计算机）迈出的一大步。模型可以用代码即时设计自己的工具，而不被固定工具集束缚。
- 边界澄清：harness 仍然会带其他工具，但代码执行已成为自主解题的**默认通用策略**。

#### 3.3 沙箱与默认工具链：安全执行并验证
- 想要的行为：给 agent 一个默认配置正确的环境，安全行动、观察结果、持续推进。
- 为什么不能就地跑：本地执行 agent 生成的代码有风险，单个本地环境无法扩展到大规模 agent 负载。
- 沙箱作用：安全隔离执行；可叠加命令 allow-list 和网络隔离；环境可**按需创建、扇出（fanned out）、干完就销毁**。
- 好环境自带好的默认工具：预装语言运行时和包、git 与测试 CLI、用于网页交互与验证的 browser。
- browser、logs、screenshots、test runners 支撑 **self-verification loop**：写应用代码 → 跑测试 → 查日志 → 修错误。
- 归属判定：模型不会自己配执行环境。**agent 在哪运行、有哪些工具可用、能访问什么、如何验证自己的工作，全部是 harness 级设计决策。**

#### 3.4 记忆与搜索：持续学习与对抗上下文腐坏
##### 3.4.1 知识注入的唯一通道
- 硬约束：模型除权重和当前 context 外没有额外知识。既然无法编辑权重，**唯一「加知识」的途径就是 context injection**（上下文注入）。
- 记忆落点仍是文件系统：harness 支持 AGENTS.md 这类 memory file 标准，启动时注入 context；agent 编辑后 harness 再载入更新版。这构成 **continual learning**。
- 知识截止的补法：Web Search 与 Context7 这类 MCP 工具。作者的结论：Web Search 和查询最新上下文的工具值得**直接烤进 harness**。

##### 3.4.2 Context Rot 与管理三件套
- 另一条想要的行为：**agent 的表现不应该随着工作推进而衰减。**
- **Context Rot**：模型在 context window 被填满的过程中，推理与完成任务能力都会变差。context 是宝贵且稀缺的资源。
- 全文最锋利的一句：**Harnesses today are largely delivery mechanisms for good context engineering.**
- 三件武器：
  - **Compaction（压缩）**：处理窗口快满的情况；智能卸载并总结已有上下文，让 agent 继续工作。没有压缩时对话超窗只能让 API 报错。
  - **Tool call offloading（工具输出卸载）**：大段工具输出会污染上下文；超过阈值 token 数时只保留头尾 token，完整输出卸载到文件系统，需要时再去取。
  - **Skills 与 progressive disclosure（渐进式披露）**：解决启动时载入过多工具或 MCP server、未干活先拖垮性能的问题。作者特别点出归属——**模型并没有选择让 Skill front-matter 在启动时进入 context，但 harness 可以支持这件事，替模型挡住 context rot。**

#### 3.5 长时程自主执行：原语开始复利
- 想要的行为：autonomous software creation 是 coding agent 的圣杯（holy grail）。
- 今天模型的三个毛病：early stopping（过早停止）、难以分解复杂问题、跨多个 context window 后失去连贯性（incoherence）。
- 结构性观察：到这一步，**前面的 harness 原语开始复合叠加**（start to compound）。
- 三个组件：
  - **文件系统与 git 用于跨 session 追踪**：agent 长任务中产出数百万 token，文件系统持久捕获；git 让新 agent 能迅速摸清项目状态和历史；多 agent 协作时文件系统是共享的**工作账本**（shared ledger of work）。
  - **Ralph Loop 用于让工作继续**：hook 拦截模型退出企图，在干净 context window 重新注入原始 prompt，逼 agent 继续。可行性来自文件系统：每轮从全新上下文开始，但能读到上一轮留下的状态。
  - **规划与自验证用于不跑偏**：planning 是模型把目标分解成步骤，harness 通过提示词和「如何使用 plan 文件」的提醒支持；self-verification 有两条路径——harness hooks 跑预定义测试、失败回灌错误信息，或提示模型独立自评代码。验证的价值：把解法锚定在测试上（grounds solution in tests），并为自我改进制造反馈信号。

### 四、模型训练与 harness 设计的耦合

#### 4.1 反馈回路
- Claude Code、Codex 这类产品是**模型与 harness 同时在 loop 里**做的 post-training，让模型在 harness 设计者认为它「应该天生擅长」的动作上变强（文件系统操作、bash 执行、planning、subagent 并行）。
- 回路：发现有用原语 → 加进 harness → 用它训练下一代模型 → 模型在自己被训练的那副 harness 里越来越强。

#### 4.2 过拟合与反转
- 副作用：**改动工具逻辑会导致模型表现变差**。例子：Codex-5.3 prompting guide 里的 apply_patch 文件编辑工具逻辑——真正智能的模型在不同 patch 方法间切换本该毫无压力，但「harness 在 loop 里」的训练方式造成了这种 overfitting。
- 关键反转：**模型被 post-train 时用的那副 harness，不一定是你这项任务的最佳 harness。**
  - 证据一：Terminal Bench 2.0 榜单上，Opus 4.6 在 Claude Code 里的得分远低于它在其他 harness 里的得分。
  - 证据二：LangChain 自己**只改 harness**，把 coding agent 在 Terminal Bench 2.0 上从 Top 30 提到 Top 5。
- 结论：为你的任务优化 harness 还有大量汁水可榨（a lot of juice to be squeezed out）。

### 五、harness engineering 的未来

#### 5.1 必然趋势与作者的保留判断
- 趋势：模型变强后，今天住在 harness 里的部分东西会被**吸收进模型**——planning、self-verification、长时程连贯性会变得原生，需要更少 context injection。
- 表面推论是 harness 越来越不重要。作者反驳类比：**正如 prompt engineering 今天仍然有价值，harness engineering 很可能会继续对构建好 agent 有用。**
- 支撑区分：harness 今天确实在**给模型缺陷打补丁**，但它同时也在**围绕模型智能做系统工程**。一个配置良好的环境、正确的工具、持久的状态、验证的回路，会让任何模型都更高效，**与它的基座智能无关**。

#### 5.2 开放问题
- 编排数百个 agent 在同一个共享 codebase 上并行工作
- 让 agent 分析自己的 trace，识别并修复 harness 级的失败模式
- harness 不再预配置，而是为给定任务**即时动态组装**（just-in-time）合适的工具与上下文
- 收束句：**The model contains the intelligence and the harness is the system that makes that intelligence useful.**

## 作者边界、反例与不确定性
- harness 的减法定义「不是因为它最准确，而是因为它把注意力从『模型还差什么』转向『该在模型周围造什么系统』」——作者承认这条界线是选择而非唯一真理。
- 模型与 harness 协同演化的过拟合是真实副作用，但作者反转指出原厂 harness 不等于最优 harness，二者张力未调和。
- harness 未来不会消失的判断，建立在「补缺陷」与「围绕智能做系统工程」的职能区分上；前者会被模型吸收，后者与基座智能无关。原文没有给出这条区分在极端强模型下是否仍成立的论证。
