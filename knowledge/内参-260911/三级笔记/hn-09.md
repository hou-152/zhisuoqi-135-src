# Anthropic 工程实践：如何为长时间运行的 Agent 应用设计 Harness

## 一句话主旨
分离生成与评估的多 agent harness 设计，可突破长时运行 Agent 应用的性能天花板。

## 作者试图回答的问题
如何通过 harness 设计（围绕模型的编排脚手架）突破长时间运行 Agent 应用的质量瓶颈？具体子问题：长时运行 Agent 有哪些系统性失败模式？针对这些失败模式，什么样的架构能显著提升主观与客观任务的输出质量？harness 如何随模型能力进化而调整？

## 三级论证骨架

### 一、起点：两个交织的问题与两大失败模式

#### 1.1 问题定义
- 作者试图同时解决：让 Claude 产出高质量前端设计（主观审美任务）＋ 让 Claude 无需人工干预构建完整应用（可验证正确性任务）。
- 早期通过 prompt engineering 和 harness 设计取得进展，但都撞上天花板。
- 为突破瓶颈，在两个截然不同的领域寻找通用的 AI 工程方法。

#### 1.2 失败模式 1：上下文窗口填满后失去连贯性
- 随 context window 填满，模型倾向失去连贯性；部分模型出现 "context anxiety"——在接近其自认为的上下文极限时提前收尾。
  - Sonnet 4.5 的 context anxiety 严重到 compaction 不够用。
- 解法：context resets——彻底清空上下文、启动全新 agent，配合结构化 handoff 传递状态与下一步计划。
- Context reset 与 compaction 的区别：
  - Compaction：原地总结早期对话，同一 agent 继续在缩短的历史上工作。保持了连续性，但没有 clean slate，context anxiety 仍可能持续。
  - Reset：提供全新起点，代价是 handoff artifact 必须包含足够状态信息让下一个 agent 干净接手。

#### 1.3 失败模式 2：自我评估失败
- Agent 评估自己产出时倾向自信地赞美——即使质量明显平庸。
  - 主观任务（设计）上尤重，因为没有二元化验证手段；有可验证结果的任务上 agent 同样展现糟糕判断力。
- 关键杠杆：将做事的 agent 与评判的 agent 分离。
- 边界：分离本身不能消除宽容倾向，但调教独立 evaluator 变得严格远比让 generator 自我批评更可行。一旦外部反馈存在，generator 就有了具体迭代目标。

### 二、前端设计实验：GAN 启发的 Generator-Evaluator 循环

#### 2.1 两个关键洞察
- 审美无法完全量化为分数，但可用编码了设计原则与偏好的评分标准来改进："Is this design beautiful?" 难以一致回答，但 "does this follow our principles for good design?" 给了 Claude 具体评判依据。
- 将前端生成与前端评分分离，创造出驱动 generator 产出更强输出的反馈循环。

#### 2.2 四项评分标准（同时给到 generator 和 evaluator）
- Design quality：设计是否像连贯整体而非零件拼凑；颜色、字体、布局、图像是否融合为独特氛围与身份。
- Originality：是否有定制化决策痕迹，还是模板布局、库默认值和 AI 套路；明确惩罚 "AI slop" 模式（紫色渐变覆盖白色卡片等）。
- Craft：技术执行——字体层级、间距一致性、配色和谐、对比度；能力检查而非创意检查。
- Functionality：独立于审美的可用性。
- 加权策略：着重加权 design quality 和 originality（Claude 默认已擅长 craft 和 functionality）；用 few-shot 示例＋详细评分分解校准 evaluator 对齐作者偏好。

#### 2.3 实验循环
- 基于 Claude Agent SDK 构建：Generator 生成 → Evaluator 用 Playwright MCP 实际浏览页面、截图、评分＋写详细批评 → 反馈回 Generator 迭代。
- 每次生成 5–15 次迭代，完整运行可达 4 小时。
- Generator 每轮评估后做战略决策：分数趋势好则精炼当前方向，否则彻底转向新的美学方向。

#### 2.4 关键发现
- 评分标准的措辞会以意想不到的方式引导 generator——如 "museum quality" 推动设计向特定视觉方向收敛。
- 分数提升模式并非总是线性——作者经常更偏好中间迭代而非最终版本。
- 即使第一次迭代，输出也已显著优于无任何 prompting 的基线，说明标准本身就能引导模型远离泛化默认。
- 荷兰艺术博物馆案例：第 9 次迭代是符合预期的暗色主题着陆页，第 10 次迭代突然推翻整个方案，重新想象为 3D 空间体验——CSS 透视渲染的棋盘格地板、自由悬挂的画作、门廊式导航。这种创造性飞跃在单次生成中从未见过。

### 三、全栈开发：Planner-Generator-Evaluator 三 Agent 架构

#### 3.1 架构组成
- Planner：接收 1–4 句话简单 prompt，扩展为完整产品规格；被提示在范围上保持雄心，聚焦产品上下文和高层技术设计而非详细实现（避免上游错误级联）；被要求在规格中编织 AI 功能。
- Generator：按 sprint 工作，每次从规格中选取一个功能实现；技术栈 React + Vite + FastAPI + SQLite；每个 sprint 结束后自我评估再交给 QA。
- Evaluator / QA：用 Playwright MCP 像用户一样点击运行中的应用，测试 UI 功能、API 端点和数据库状态；对每个 sprint 按标准打分，低于阈值则退回并给出详细反馈。

#### 3.2 Sprint Contract 机制
- 每个 sprint 开始前，generator 和 evaluator 协商 "sprint contract"——写任何代码前先就 "done" 的定义达成共识。
- Generator 提出要构建什么＋如何验证成功，evaluator 审核确保方向正确；双方迭代直到共识。
- 通信通过文件进行：一个 agent 写文件，另一个读取并回应。

#### 3.3 复古游戏制作器对比实验（Opus 4.5）
- Solo agent：20 分钟，$9 → 表面看起来可以但核心功能（游戏可玩性）完全损坏。
- Full harness：6 小时，$200 → 功能丰富、视觉一致、核心功能可用（虽有物理引擎粗糙边缘）。
- Evaluator 在每个 sprint 逐条验证 contract 标准——Sprint 3 单独就有 27 项标准，发现的问题具体到可直接修复。

#### 3.4 调教 Evaluator 的挑战
- 开箱即用的 Claude 是糟糕的 QA agent——会发现问题然后说服自己 "不是大问题" 并通过。
- 测试倾向浅层，深层 bug 容易溜掉。
- 调教循环：阅读 evaluator 日志 → 找到其判断偏离作者判断的例子 → 更新 QA prompt。
- 经过多轮才达到合理水平，但仍有验证空间可以通过进一步调教捕获。

### 四、简化 Harness：与模型能力共同演进

#### 4.1 核心原则
- Harness 中每个组件都编码了一个关于「模型自身做不到什么」的假设；这些假设值得不断压力测试——因为它们可能是错的，也可能随模型进步而迅速过时。
- 引用 Building Effective Agents："find the simplest solution possible, and only increase complexity when needed"。

#### 4.2 Opus 4.6 带来的简化空间
- 移除 sprint 结构：Opus 4.6 能原生处理长任务的分解。
- Evaluator 从逐 sprint 评审改为构建结束后的单次评审。
- 保留 planner（无 planner 时 generator 会 under-scope）和 evaluator。

#### 4.3 Evaluator 的动态价值
- Evaluator 不是固定的 yes-or-no 决定。
- 当任务处于模型可靠独立完成的边界之内时，evaluator 是不必要的开销；超出该边界时提供真实提升。
- 随着模型能力提升，边界外移，但 evaluator 对边界外任务始终有价值。

#### 4.4 DAW（数字音频工作站）实验（Opus 4.6 + 简化 harness）
- 一句话 prompt → 约 4 小时，$124.70。
- Generator 连续运行 2 小时以上无需 sprint 分解。
- QA 仍捕获真实缺陷：功能只有展示没有交互深度、音频录制是 stub 等。
- 最终产出：浏览器中的功能性音乐制作程序，集成 AI agent 可通过 prompt 驱动创作。

### 五、通用教训
1. **始终实验**：对真实问题上的 traces 进行实验、阅读、调优。
2. **分解与专化**：复杂任务分解并对每个方面应用专门 agent，有时带来额外空间。
3. **随模型迭代 harness**：新模型发布时重新审视——剥离不再承重的部分，增加新能力。
4. **Harness 的组合空间会移动而非缩小**：AI 工程师的有趣工作是持续找到下一个新组合。

## 作者边界、反例与不确定性
- 分离生成与评估本身不能消除宽容倾向——只是让调教严格 evaluator 变得比让 generator 自我批评更可行。
- 前端实验中分数提升非线性，作者常偏好中间迭代而非最终版本——评分标准不能完全代理作者的审美判断。
- 开箱即用的 Claude 是糟糕的 QA agent，调教多轮才达到合理水平，且作者明确承认"仍有验证空间可以通过进一步调教捕获"——evaluator 的可靠性有上限。
- Harness 组件编码的「模型做不到什么」假设可能是错的，也可能随模型进步过时；作者未给出判断组件是否仍承重的系统方法，仅提出逐一压力测试的方向。
- Evaluator 的价值有边界条件：任务在模型可靠独立完成的边界内时不必要，超出边界才提供真实提升；该边界的具体位置随模型能力外移，作者未给出划定方法。
