# Anthropic 干脆把 harness 托管了：Claude Managed Agents 的设计取舍

## 一句话主旨
托管 harness 不是设计更好的 harness，而是把脑/手/会话解耦，让 agent 随模型能力扩展。

## 作者试图回答的问题
为什么此刻需要把 agent harness 托管起来？核心子问题：harness 为何跟不上 Claude 的能力增长速度，以及如何设计一套不随模型进化而过时的架构。

## 三级论证骨架

### 一、问题诊断：messages API 之上有两个结构性压力

#### 1.1 harness 编码的是"Claude 做不到什么"的假设，必然过时
- harness 是构建在 messages API 之上的一层：把 tool call 路由到 handler，并管理 context。
- messages API 只是"通往模型的直连网关"（接收 messages，返回 content blocks），任何 agent 都必须自建 harness。
- 关键判断：agent harness 编码的是"关于 Claude 做不到什么"的假设。模型变强，这些假设就变陈旧（grow stale），反过来成为 Claude 表现的瓶颈（bottleneck）。
  - 因此 harness 必须被持续更新才能跟上模型，否则本身就成了绊脚石。

#### 1.2 任务时域指数增长，压力转向基础设施
- 任务时域（task horizon）正在指数级增长，在 METR benchmark 上已超过 10 个人类小时。
- 作者预期未来的 Claude 会在人类最重大的挑战上连续运行数天、数周乃至数月。
- 时域一长，压力从模型转移到 agent 周围的基础设施：安全、扛住长任务期间必然发生的基础设施故障、可扩展（例如支撑多个 agent 团队）。
- 演进路径：Claude Agent SDK 是第一步（通用 agent harness）；Claude Managed Agents 是下一步——harness 加上托管基础设施，支撑"我们预期 Claude 将要工作的那个时间尺度"上的安全、可靠执行。

#### 1.3 合流判断：这是基础设施挑战，不是 harness 设计问题
- 核心归类的判断：让 agent 随 Claude 的智能一起扩展，是一个基础设施挑战（infrastructure challenge），而不严格是 harness 设计问题。
- 这个归类的分量在于逻辑推论：如果问题只是 harness 写得不好，正确回应是开源一个更好的 harness；既是基础设施问题，回应就是托管一整套 infra。

### 二、产品结构：三个中心概念

#### 2.1 Agent：版本化配置，不是正在干活的人
- 一份版本化的配置（a versioned config），承载 agent 身份：模型、system prompt、工具、skills、MCP servers 等。
- 创建一次，之后按 ID 引用。

#### 2.2 Environment：沙箱模板，不是沙箱本身
- 描述如何 provision agent 工具所运行的沙箱：runtime 类型、网络策略、包配置。
- 心智模型：每次开工都按这份模板现搭一个新沙箱。

#### 2.3 Session：有状态的单次运行
- 使用已创建的 agent 配置与 environment，从模板拉起全新沙箱。
- 挂载单次运行所需的资源（文件、GitHub 仓库），把认证信息存进安全 vault（例如 MCP 凭证）。
- 一个 agent 可以有很多 session——可复用的部分被前置固化，一次性的部分留在运行时。

### 三、核心设计取舍：不押注某一种 harness，而是解耦为可替换接口

#### 3.1 一个刻意的拒绝：不设计"正确的"harness
- 作者与 @mc_anthropic、@gcemaj、@jkeatn 合写的工程博客给出的核心教训是：让 agent 随 Claude 智能扩展是基础设施挑战，而非 harness 设计问题。
- 基于此判断，刻意没有设计某一种特定的 agent harness——因为预期 harness 会不断演化，押注任何一版都会过时。

#### 3.2 brain / hands / session 三层解耦
- 三大接口：brain（Claude 及其 harness）、hands（执行动作的沙箱与工具）、session（会话事件的日志）。
- 每一部分都是一个"对其余部分假设极少"的接口，各自可以独立失败、独立被替换。
- 文中把这一点解释为系统可靠性、安全性与灵活性的来源：未来接入新的 harness、新的沙箱、新的 session 存储都不必重做。
- 原文配图显示 harness 居中，工具、沙箱、会话、编排各成独立接口。

### 四、使用模式：四种已跑出来的触发方式

#### 4.1 事件触发（Event-triggered）
- 由某个服务触发：系统标记出一个 bug，managed agent 写好补丁并开 PR——从"标记"到"动作"之间没有人类在环。

#### 4.2 定时（Scheduled）
- 把 Managed Agent 排进日程。作者和很多人用这个模式做每日简报——X 或 GitHub 动态、agent 团队正在做什么；他本人就在用 X 活动的每日简报。

#### 4.3 触发即走（Fire-and-forget）
- 由人触发：通过 Slack 或 Teams 派任务，拿回交付物——表格、幻灯片、应用。

#### 4.4 长周期任务（Long-horizon）
- 作者认为这是 Managed Agents 特别有用的领域。
  - fork 了 @karpathy 的 auto-research 仓库做探索。
  - 让一个 Managed Agent 把 @_chenglou 的 pretext 库尝试应用到 Anthropic 的工程博客内容上。

### 五、接入路径：skill 做 onboarding，CLI 做 setup，SDK 做 runtime

#### 5.1 skill 作为 onboarding 载体
- 最省事的入门路径是开源的 claude-api skill，在 Claude Code 里开箱即用：升级到最新版 Claude Code，跑对应子命令即可完成 onboarding。
- 作者明确表示很看好把 skill 当作新功能的 onboarding 方式，自己也大量使用——新功能的说明书不再是给人读的文档，而是给 agent 读的技能包。

#### 5.2 SDK 面向代码，六种语言支持
- 在应用里 import，运行时驱动 session。
- 支持 Python、TypeScript、Java、Go、Ruby、PHP。

#### 5.3 CLI 面向终端，每种资源一个子命令
- agents、environments、sessions、vaults、skills、files 均暴露为子命令。

#### 5.4 agent 模板声明式持久化，进 git
- 常见组合：CLI 做 setup，SDK 做 runtime。
- agent 模板是持久的：可存成一份 YAML（模型、system prompt、工具、MCP servers、skills）放进 git，由 CLI 在部署流水线里 apply。
- 把 agent 当基础设施代码来管——改动进版本库、走评审、随部署上线。

### 六、结论：agent 成为 Claude API 的新核心原语

- 作者长期的一个 frustration 就是 agent harness 跟不上模型能力，此前专门写过文章讨论。
- Claude Managed Agents 把 harness 和基础设施一起接管，让人可以在"agent 作为 Claude API 的一个新核心原语"之上做探索。
- 明确看好的方向：多 agent 编排的各种模式，以及长时间运行的任务。
- 根本张力：harness 曾是开发者的主战场，现在被抬进平台内部；开发者的注意力被推向更上层的问题——编排多 agent，以及决定把什么交给 agent 做。

## 作者边界、反例与不确定性
- METR benchmark 的"超过 10 个人类小时"是单一 benchmark 数据，作者以此支撑任务时域指数增长的判断；"连续运行数天、数周乃至数月"明确是预期而非当前能力。
- 四种使用模式是"已经跑出来的"，不是穷举；作者对长周期任务领域的看好是明确个人判断（"特别有用的领域"）。
- 设计取舍的前提是一个预期——"agent harness 会不断演化"——如果这个预期不成立，刻意不设计特定 harness 的理由就被削弱。材料中未讨论该前提不成立的情形。
- 材料承认演进路径不是终点：Claude Agent SDK 是第一步，Managed Agents 是下一步，未来仍需继续替换或接入新的 harness、沙箱、session 存储。
