# Thin Harness, Fat Skills：harness 才是真正的产品

## 一句话主旨
秘密不在模型，而在薄 harness 与厚 skills 的架构。

## 作者试图回答的问题
AI 生产力的 10x-100x 差距从何而来？如何设计 agent harness，使模型能力被正确上下文、可复用 skills 和确定性工具放大，并持续复利？
关联子问题：什么放进 harness，什么留在外面？判断力与确定性计算如何分层？

## 三级论证骨架

### 一、总判断：harness 才是产品，模型不是差距来源
#### 1.1 秘密在包裹模型的那层东西
- 2026 年 3 月 Anthropic 意外泄露 Claude Code 全部 512,000 行源码，Garry Tan 读完后确认：秘密不在模型，在包裹模型的那层东西。
  - 实时 repo 上下文、prompt 缓存、专用工具、context bloat 最小化、结构化 session 记忆、并行 sub-agent。
  - 这些不让模型更聪明，而是在正确时间给正确上下文，不淹没在噪音里。
  - 核心问题：什么放进 harness，什么留在外面？

#### 1.2 架构原则 Thin Harness, Fat Skills
- Harness 只做四件事：循环运行模型、读写文件、管理上下文、执行安全；其余保持薄。
- Skills 做厚：把判断力、流程、领域知识编码进可复用 markdown skill 文件。
- 反模式 Fat harness + thin skills：
  - 40+ tool definitions 吃掉一半上下文窗口；God-tools 的 MCP round-trip 需 2-5 秒；REST API wrapper 把每个 endpoint 变成独立 tool → 3 倍 token、3 倍延迟、3 倍失败率。
  - 正确做法是 purpose-built tooling，fast and narrow；Playwright CLI 每个浏览器操作 100ms vs Chrome MCP 15 秒，快 75 倍。

### 二、关键构件：skills、resolvers、latent/deterministic、diarization
#### 2.1 Skill Files 像方法调用
- Skill file = 可复用 markdown 文档，教模型 how；用户提供 what。
- 关键洞察：skill file 像一个方法调用，接受参数；同一流程用不同参数产生截然不同的能力。
  - /investigate skill：7 个步骤（scope dataset → build timeline → diarize → synthesize → argue both sides → cite sources），接受 TARGET, QUESTION, DATASET 三个参数。
  - 指向安全科学家 + 210 万封发现邮件 → 医学研究分析师；指向空壳公司 + FEC 备案文件 → 法证调查员。
  - 原文："This is not prompt engineering. This is software design, using markdown as the programming language and human judgment as the runtime."

#### 2.2 Resolvers 是上下文路由表
- Resolver = 当任务类型 X 出现时，先加载文档 Y；skills 告诉模型 how，resolvers 告诉模型 what to load and when。
  - 案例：开发者改 prompt → resolver 自动先加载 EVALS.md → 模型知道要跑评测套件。
  - Claude Code 内置 resolver：每个 skill 有 description 字段，模型自动匹配用户意图到 skill 描述。
  - 教训：CLAUDE.md 曾膨胀到 20,000 行 → 模型注意力退化 → 砍到 200 行指针文档，resolver 按需加载。

#### 2.3 Latent vs. Deterministic 是分层判断标准
- 系统中每一步非此即彼；混淆两者是 agent 设计最常见的错误。
  - Latent space：模型阅读、解释、判断；判断力、综合分析、模式识别。
  - Deterministic：相同输入 → 相同输出；SQL 查询、编译代码、算术。
  - 案例：LLM 能安排 8 人晚宴座位（考虑性格和社交动态），但安排 800 人就会幻觉出看似合理但完全错误的座位表——组合优化问题被错误地塞进 latent space。

#### 2.4 Diarization 是核心 latent 能力
- Diarization = 模型阅读关于某个主题的一切，写出一份结构化 profile；从数十/数百份文档中提炼出一页判断。
  - 没有 SQL 查询能做到，没有 RAG 管道能做到；模型必须真正阅读、持有矛盾、注意变化、综合出结构化情报。
  - 本质区别：database lookup vs. analyst's brief。

### 三、架构落地：三层分工与方向性
#### 3.1 三层架构
- 顶层 Fat Skills：编码判断力、流程和领域知识的 markdown 程序，90% 的价值在这里。
- 中层 Thin CLI Harness：约 200 行代码，JSON in / text out，默认只读。
- 底层 Your Application：QueryDB、ReadDoc、Search、Timeline——确定性基础设施。

#### 3.2 方向性原则与收益
- 智能向上推进 skills，执行向下推进确定性工具，harness 保持薄。
- 好处：模型每次升级，自动改善所有 skill；确定性层保持完全可靠。

### 四、实战验证：Startup School 6000 人系统
#### 4.1 背景与传统方法崩溃
- Chase Center，2026 年 7 月，6000 名创始人的 Startup School。
- 传统方法：15 人项目团队读申请、拍脑袋、更新表格——200 人时可行，6000 人时崩溃。

#### 4.2 Enrichment：看出“说的”和“实际在做的”差距
- /enrich-founder skill：拉取所有来源 → enrichment → diarize → 高亮创始人说的和实际在做的之间的差距。
- 确定性层：SQL 查询、GitHub 统计、浏览器测试 demo URL、社交信号、CrustData 查询；cron 每晚运行。
  - 案例：Maria Santos 说 "Datadog for AI agents"，但 80% 的 commit 在 billing 模块 → 实际在做的是伪装成 observability 的 FinOps 工具。
  - 发现这个差距需要同时阅读 GitHub commit 历史 + 申请 + 顾问访谈；没有 embedding 搜索能做到。

#### 4.3 Matching：同一 skill 的三种调用
- /match-breakout：1200 人按行业亲和度聚类，30 人/房间。
- /match-lunch：600 人跨行业偶遇匹配，8 人/桌，不重复。
- /match-live：当前在场者实时 nearest-neighbor，200ms，1:1 配对。
  - 模型做出聚类算法永远做不到的判断：Santos 和 Oram 都是 AI infra，但不是竞争对手——Santos 做 cost attribution，Oram 做 orchestration，可放同一组。

#### 4.4 Learning Loop：skill 自我重写
- /improve skill 读 NPS 调查 → diarize 那些评价为 OK 而非差的反馈 → 提取模式 → 提出新规则 → 写回 skill file。
  - 7 月活动 12% OK → 下次活动 4%。
  - 通用模式：retrieve → read → diarize → count → synthesize；然后 survey → investigate → diarize → rewrite the skill。

### 五、纪律与复利：skills 是永久升级
- 给 OpenClaw 的指令："You are not allowed to do one-off work. If I ask you to do something and it's the kind of thing that will need to happen again, you must: do it manually the first time on 3 to 10 items. Show me the output. If I approve, codify it into a skill file."
- "The test: if I have to ask you for something twice, you failed."
- 每个 skill 是系统的永久升级——不退化、不遗忘、凌晨 3 点自动运行。
- 下一个模型发布时，所有 skill 即刻变强（latent 步骤判断力提升，deterministic 步骤保持可靠）。
- "That's how you get Yegge's 100x. Not a smarter model. Fat skills, thin harness, and the discipline to codify everything."
- "The system compounds. Build it once. It runs forever."

## 作者边界、反例与不确定性
- Harness 必须克制：只做四件事；Fat harness + thin skills 是反模式，40+ tool definitions、God-tools、REST endpoint 包装都会导致 context bloat、延迟、失败率上升。
- 上下文不是越多越好：CLAUDE.md 从 20,000 行砍到 200 行指针文档，说明过量上下文会让模型注意力退化。
- latent/deterministic 不能混：800 人座位表是反例，组合优化应下沉到确定性层。
- Skill 化有条件：先手动做 3 到 10 个样本，经批准后才 codify；重复出现才值得写成 skill。
- 作者未展开的：未给出 harness 四件事之外的具体安全/权限实现，也未系统列出失败案例；边界主要来自实践教训与反模式。
