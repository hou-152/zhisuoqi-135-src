# Harness Engineering

## 一句话主旨
harness 是管住 AI agent 的那套工具与实践，它让AI自治的代价是收窄解空间。

## 作者试图回答的问题
- harness 这个词是否准确？它由什么构成、如何生长？
- 当代码由 AI agent 维护时，什么在守住代码质量底线？
- OpenAI 的"无手打代码"实验说明了什么？有哪些空白与保留？
- 这套实践会如何改变技术栈选择、代码库结构，甚至编程的抽象层？

## 三级论证骨架

### 一、起点：OpenAI 的"无手打代码"实验与 harness 的命名

#### 1.1 实验的关键不是 AI 能力，而是自我设限
- 把"一行代码都不手打"当作 forcing function，逼团队把质量保障能力外化成工具与规则。
  - 五个月做出一个上线产品，代码量超过 100 万行。
  - 前提是"用 AI agent 维护"这套代码库。
- 作者认可 harness 这个词：它准确描述了"把 agent 套住、同时让它使得上劲"的那套工装，即"the tooling and practices we can use to keep AI agents in check"。
  - 但 OpenAI 原文标题挂着 harness，正文只出现一次；作者猜测是事后追加，灵感可能来自 Mitchell Hashimoto 的 "engineer the harness"。

### 二、harness 的构成：确定性与 LLM 混合的三类组件

#### 2.1 上下文工程（context engineering）
- 代码库里持续增强的知识库，加上让 agent 取到动态上下文的通道。
  - 动态上下文包括可观测性数据、浏览器导航。
  - 文末扩展：代码设计本身就是上下文的一大部分，上下文工程不只是策展知识库。

#### 2.2 架构约束（architectural constraints）
- 约束不只由 LLM agent 盯，还由确定性的自定义 linter 和结构性测试强制。
  - 确定性这一层是重点：它不依赖模型当天的状态，规则违反就是违反。
  - 作者自检清单中点名 ArchUnit 这类结构性测试框架。

#### 2.3 「垃圾回收」型 agent（garbage collection）
- 周期性运行的 agent，专门找文档不一致、架构约束违反，对抗熵与腐化（fighting entropy and decay）。
  - 前两类管一次生成的质量，这一类管长期不塌。

#### 2.4 生长机制：卡住即信号（struggle as signal)
- 迭代机制的核心不是组件，而是演化规则：agent 卡住不算失败，算信号。
  - 原话："When the agent struggles, we treat it as a signal: identify what is missing — tools, guardrails, documentation — and feed it back into the repository, always by having Codex itself write the fix."
  - 缺的工具、护栏、文档补回代码库，补丁仍由 Codex 自己写。
  - 这改变了 debug 对象：从"这次的输出"变为"产生输出的环境"。

### 三、作者的两处保留

#### 3.1 功能与行为验证的缺口
- OpenAI 描述的所有手段都指向长期内部质量与可维护性，唯独缺了"verification of functionality and behaviour"。
  - 这是结构性缺口：能保证代码"长得对"的装置，并不自动保证代码"做得对"。

#### 3.2 OpenAI 的既得利益
- 作者明确说：尽管尊重作者与团队，但 OpenAI 对"让我们相信 AI 可维护代码"有既得利益。
  - 她选择先把这份折扣打出来，再谈文章里确实存在的东西。

### 四、从装置到范式：harness 的推演

#### 4.1 harness 会成为新的 service template 吗
- 大多数组织只有两三套主力技术栈，不是每个应用都是 snowflake。
  - 设想：团队从一组现成 harness 里按常见应用拓扑挑一个开工，就像今天用 service template 沿 golden path 实例化新服务。
  - 起点包含：自定义 linter、结构性测试、基础上下文与知识文档、额外上下文提供者。
  - 老问题可能重演：team forking 与同步难题——每个团队改出自己的样子，上游更新难以合并。

#### 4.2 更高的 AI 自治要求收窄解空间
- 早期叙事假设 LLM 带来无限灵活，任何语言、任何模式随便生成。
  - 但要在规模上得到可维护、可信任的 AI 生成代码，"something has to give"。
  - 这套 harness 指向相反方向：具体的架构模式、被强制执行的边界、标准化的结构。
  - 交换关系：放弃一部分"什么都能生成"的自由，换来装满技术细节的 prompt、规则和 harness。这是个价格，不是免费升级。

#### 4.3 收敛：技术栈、代码库拓扑与"新抽象层"之问
- AI 可能把我们推向更少的技术栈。
  - 选型标准变化：优先挑"有好 harness 可用"的栈，把 AI 友好度放进考量。
  - 但反向判断同样成立："what's good for humans is good for AI"——清晰的接口对人好，对模型也好。
  - 开发者在细节层面的口味变得不重要：接口里的小低效、小怪癖不再烦人，因为人不再直接打交道。
- 收敛不止于技术栈，也可能发生在代码库结构与拓扑。
  - 具体抓手：保持数据结构稳定，定义并强制模块边界。
  - 作者承认卡在细节上：OpenAI 说"we require Codex to parse data shapes at the boundary"，没有具体例子，她想象不出长什么样。
- 全文最大一问：代码库拓扑会不会成为新的抽象层，而不是自然语言本身。

### 五、存量代码库与读者的今天

#### 5.1 存量代码库的问题
- 哪些技术能用在既有应用上，哪些只对"一开始就为 harness 而建"的应用成立？
  - 老代码库往往极不标准化、充满熵，改造（retrofitting）可能根本不划算。
  - 类比：像给一个没跑过静态分析的代码库第一次跑分析工具，然后淹没在告警里。

#### 5.2 回到读者自己
- 五个月才做出这套东西，说明不是能跳进去拿快速结果的事。
  - 自检清单：有没有 pre-commit hook，里面装了什么；有没有想做的自定义 linter；想给代码库加哪些架构约束；有没有试过 ArchUnit 这类结构性测试框架。

### 六、结论：rigor 被搬到了别处

#### 6.1 严谨没有消失，它换了位置
- 这套做法听起来远比重得多，但他们为确定性部分建了大量工具。
  - OpenAI 团队自述："Our most difficult challenges now center on designing environments, feedback loops, and control systems."
  - 作者借 Chad Fowler 的 "Relocating Rigor" 收束：听到关于"严谨该往哪儿搬"的具体想法和经验，比一味指望"更好的模型"自动解决可维护性问题更清爽。
- 结尾自嘲：这次她终于喜欢上一个词，但这个词才两周大——大概能屏住呼吸撑到有人把"一句 prompt 的 LLM 代码评审 agent"也叫作 harness 为止。

## 作者边界、反例与不确定性
- 功能与行为验证是整个 harness 覆盖面之外的空地，作者明确指出 OpenAI 写作没有解决，也未给出自己的方案。
- 作者明确标注自己读者立场：OpenAI 的既得利益让她对可信度打折读。
- 对"拓扑作为新抽象层"持开放但不确定的态度：承认看不清 OpenAI 具体实现细节（如 data shape parsing），只抛出问题而非给出答案。
- 存量代码库是否值得补 harness，作者没有给出普适结论，只提供判断框架（熵高低、改造是否划算）。
- 对"更好模型能否自动解决可维护性"持否定倾向，但以借他人概念（relocating rigor）而非直接断言的形式表达。
