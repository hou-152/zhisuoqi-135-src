# 拆开 Claude Code：一个编码 agent 的 harness 内部长什么样

## 一句话主旨
拆开请求 log 可见，Claude Code 的 harness 重心是任务管理，agent 模式未必需要 IDE。

## 作者试图回答的问题
Claude Code 内部究竟怎么工作？作者借"看对话 log"这一方法，读出它的 system prompt、工具清单、大小模型分工，并由此追问：agent 模式下，cursor 相比它多出的东西是否真的强依赖 IDE？

## 三级论证骨架

### 一、方法论起点：看对话 log，而非读宣传
#### 1.1 核心判断
- 想知道 AI app 怎么工作，最可靠不是读宣传，而是看它和模型之间的对话 log。作者用 custom endpoint 截下 Claude Code 请求，直接读到 system prompt、工具清单和小模型调用。
  - 自称"小小升华"：prompt 对话是 LLM 的第一性原理，任何 AI app 归根结底就是和 LLM 对话（工具调用也是对话），把结构化结果抠出来，再用确定性代码缝合。
#### 1.2 窥探 prompt 的三种方法
- 方法 1：openai platform 原生 request log（首次进页面需手动 enable），信息非常详细，能看到 project_layout 等 beta 功能。
  - "tools 是一大关键"：codebase_search 是从索引过的 codebase 做 vector search，edit_file 调用 cursor 训练的 apply change 模型——工具清单本身暴露产品架构。
- 方法 2：Cloudflare AI gateway（免费），在 app 里换 custom endpoint 即生效，针对 openai/anthropic/openrouter 有不同变种。
  - 本质是反向代理，原封不动转发、中间截取做 log 与 metrics；比 openai 多了请求级计费与时长统计、支持非 openai 模型、能看到更完整请求（choices）；缺点是不渲染成对话形式。
- 方法 3：自制 HTTP proxy，几行代码即可；少了 token 统计、计费，但更灵活。

### 二、进入 Claude Code：一大一小两个模型
- 研究动机朴素：看到 twitter 说 claude code 能替代 cursor，"很难不好奇是不是真有这么牛"，问 ChatGPT 没问出来，只能自己上手。
- 要看 prompt 就得用 custom endpoint：ChatGPT 给出 undocumented env var `ANTHROPIC_BASE_URL`；claude SDK 与 openai API 不兼容，无法直接用 openrouter/openai 的 key；搜到 "Run Claude Code on OpenAI models" 的 claude-code-proxy，完美符合。
- 初步观察两条：会使用一大一小两个模型；每次打字都会发请求给小模型。
  - 氛围组请求：小模型被要求生成积极、欢快、带点 whimsy 的动名词给状态提示添彩，明令禁止 Terminating、Killing 这类字眼；作者判断"纯氛围组"，使用中没发现实际作用。
  - new topic 判定：发消息时判断 isNewTopic 并抽一个 2-3 词标题，作者判"感觉是用来管理 context"。

### 三、正式请求：13k 字符 prompt 与任务管理
- prompt 非常长，13k 字符，相比之下 cursor 只有不到 6k；tools 里大多是 Bash、Grep、Edit、WebFetch 标配，但内置了 TodoRead/Write 和 NotebookRead/Write（jupyter）。
- prompt 本身的取舍：
  - 反复要求 concise、direct、to the point，明确 "fewer than 4 lines" 输出上限，禁止 unnecessary preamble or postamble，给出 "2+2 → 4" 极端简洁示例。
  - 也交代 tone、proactiveness、synthetic messages、following conventions（不假设库存在、先看邻近文件和 package.json）、code style（除非被要求不加任何注释）。
- 最大亮点是 task management：
  - 着重强调 TodoWrite/TodoRead 要 VERY frequently 地用，写明 "If you do not use this tool when planning, you may forget to do important tasks — and that is unacceptable"，要求做完一项立刻标记完成、不要攒着一起标。
  - 对比让 plain cursor 有更强 agent 能力的 devin.cursorrules：这是"更进阶版的 scratchpad.md"，主要胜在多个子任务的管理。
- 本地状态层：TODO list 不在项目路径下，藏在 `~/.claude`；todo 是 json，同目录还有 sqlite 数据库 `__store.db`（表含 __drizzle_migrations、assistant_messages、base_messages、conversation_summaries、user_messages），以及 statsig 缓存文件——由此判断"claude 还是很重视做数据实验的"。
- 大胆预测：task management（以及 memory/knowledge management？）必定是未来 agentic coding tool 乃至所有 agentic app 的标配；疑惑 cursor 为何还没推出，"感觉有点落后了"。
  - 随即自我反问：是不是通过 MCP 插一个 todo manager 就够用？并不需要 app 原生工具。外置已有 task master，但作者直觉它"有点不必要地复杂"（弄个很长的 prd 再分解成十几个 subtask）。
  - 这个"原生 vs 外挂"悬念作者没给结论，只留"因为暂时还没有深度在项目中使用，所以这个 todo 的具体效果还有待检验"。

### 四、其他有趣观察：编辑、WebFetch 与神秘的 code context
#### 4.1 apply edit：用 Write 全文覆盖绕过困难
- cursor 自训了一个 LLM 专做 apply edit；作者好奇 claude code 怎么做到，试下来发现 tool call 基本只用 Write 而不用 Edit。
  - 看 Edit 的 tool spec，有 "For larger edits, use the Write tool to overwrite files"，作者"一下子顿悟"：无脑全文覆盖不就绕过了 apply edit 的困难？只要 instruction following 强效果应该不错，"只是费电 token 罢了"；写完后还渲染 diff。
- 代价：作者一度以为看到 (Rest of file unchanged) 的 magic 体验，结果"…………并不是，它是真的把代码删了，把这个注释写进去了"。结论：完全依赖 AI 的 instruction following 还是没那么靠谱（此处用 gpt4.1，默认 claude3.7 或许好一点）。
#### 4.2 WebFetch 两阶段总结
- 参数除 URL 外还有一个 prompt：大号模型生成 tool call 与 prompt，系统把网页与 prompt 组合交给小模型总结，最后只把一小段文字传回大号模型作 context。
- 评价这个两阶段过程"还是挺细腻的"，应比把高噪音 html 直接给模型效果好。
#### 4.3 隐式 code context
- 发出指令后，claude code 自己挑选一些文件加入 context，"并没有 tool use，也没有额外的模型总结"，`~/.claude` 下也没发现类似代码索引的东西。
- "感觉有点神秘。感觉 claude code 还是藏了点东西的。"

### 五、结论：terminal 形态与 IDE 护城河
- 整体印象：细节打磨不错，terminal UX 好，prompt 和 task management 用心；但效果还没经过大规模实战检验。
- 作者在想：AI coding 好像确实没那么需要一个 IDE，terminal 这个形态很合理——让 agent 在 terminal 写，人用寻常 IDE（如原生 VS Code）review、进一步编辑，不比在 IDE 里 chat 慢或差。
- 对 cursor 相比 claude code 多出的三样逐一祛魅：
  - apply 模型：或许准确率和性能更高？但有点存疑，"因为最近一段时间感觉失败率甚至有点高"。
  - 原生 fix lint：或许依赖 IDE/LSP 静态分析，但从命令行跑 lint 也完全能达到效果。
  - codebase index & vector search：同理，并不强依赖 IDE，原则上做进命令行也没什么不可。
- 结论指向不乐观判断：agentic coding tool（startup）未来越发不明朗，特别是 cursor 这种 fork 的 IDE；或许像 Augment Code 这样的纯插件方案更有前途——连当初最吸引作者的 cursor tab，都已以纯插件方式做到。
- 后记：openai codex 是纯开源的，prompt 和 tool 直接看得一清二楚，不用特意扒；但发现 codex 的 issue 里没人提 task management，作者自己提了一个。

## 作者边界、反例与不确定性
- todo 效果"还有待检验"，因尚未深度在项目中使用；"原生 vs MCP 外挂"悬念作者明确没给结论。
- 隐式 code context 无法解释，作者自称"感觉 claude code 还是藏了点东西的"，是未解之谜。
- 反例：(Rest of file unchanged) 实为模型真删代码写注释，说明完全依赖 instruction following 不靠谱。
- 限定条件：该翻车案例用的是 gpt4.1，默认的 claude3.7"或许会好一点"；Claude Code 的整体效果"还没经过大规模实战检验"。
