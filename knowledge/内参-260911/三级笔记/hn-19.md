# Harness engineering：把 agent 能力落到工具、约束和循环里

## 一句话主旨
把 agent 可靠性从模型能力问题转为环境工程问题。

## 作者试图回答的问题
如何把 AI agent 从模型能力问题转成系统工程问题，让它在真实工作流里可靠运行？关联子问题：harness engineering 覆盖哪些工程原语？清单按什么标准筛选资源、又如何组织成从 foundations 到 runtimes 的路线图？

## 三级论证骨架
### 一、定义转向：从模型能力到环境工程
#### 1.1 harness engineering 的交叉位置与排除法
- 定义：让 AI agent 在真实工作流里可靠运行的环境工程，系统性处理 context、memory、working state、constraints、guardrails、evals、observability、runtime 和 workflow design。
  - 交叉点：context engineering、evaluation、observability、orchestration、safe autonomy 和 software architecture。
  - 排除泛泛 agent tooling，只纳入直接覆盖 harness design、context management、evaluation、runtime control 或 reliability-critical primitives 的资源；区分“工具很多”与“工具能形成可靠闭环”。
#### 1.2 多来源共同判断：agent 是被环境塑形的执行系统
- 清单同时收录 OpenAI、Anthropic、LangChain、Thoughtworks、HumanLayer 和 Inngest 的文章，共同判断 agent 成败取决于 prompts、tools、middleware、orchestration、runtime infrastructure 和 repo-local instructions 的组合。
  - OpenAI field report：architectural constraints、repo-local instructions、browser validation 和 telemetry。
  - Anthropic long-running agents：initializer agents、feature lists、init.sh、self-verification 和 handoff artifacts。
  - LangChain：agent = model plus harness。
- 对实际团队的启发：agent-first development 不能只靠提示词热情；可复用能力来自约束、状态、验证、反馈、交接和可观测性等外部结构。

### 二、context、memory 和 working state：长任务 agent 的第一层基础设施
#### 2.1 context 是 working memory budget，不是资料倾倒场
- Anthropic 的 context engineering、Manus 的 KV-cache locality、filesystem memory 和失败保留策略，都在回答同一问题：怎样让 agent 在长任务里不漂移。
- Thoughtworks、HumanLayer 和 OpenHands 补充 coding agents 场景：任务跨文件、跨测试、跨上下文窗口推进，agent 必须知道目标、当前状态、关键文件、失败测试和已经尝试过的路径。
- CLAUDE.md / AGENTS.md / agent.md 被放在 context、memory、specs 和 workflow 附近，意味着“记忆”不只是模型上下文，也包括项目内可重复读取的规则、任务约束和本地约定；这类文件是 harness 的持久化接口。
#### 2.2 上下文管理同时包含“放进来”和“挡出去”
- Context-efficient backpressure：好 harness 不只是给更多信息，也要防止 agent 被低价值日志、噪声输出和无关探索消耗上下文。
- OpenHands 的 context condensation：长任务需要压缩会话历史，同时保留 goals、progress、critical files 和 failing tests；这是有结构的状态转移，而不是简单摘要。

### 三、constraints 和 guardrails：让 autonomy 可用，而不是卡在审批循环里
#### 3.1 核心矛盾：更自主，但不能失控
- Anthropic 关于 sandboxing、MCP code execution 和 writing tools for agents 的文章，都在降低 approval friction，同时保持明确边界。
  - Claude Code sandboxing：不是让 agent“随便做”，而是通过安全策略、隔离环境和权限模型，让更多动作在可接受风险内自动执行；自主性来自可验证边界。
  - MCP code execution：把工具执行变成可检查、可组合的协议边界；工具是明确输入、输出、权限和失败模式的接口。
#### 3.2 guardrails 不只面向安全，也面向质量一致性
- OpenHands 的 prompt injection 防护、Thoughtworks 的 internal quality 和 anchoring to reference，说明确认模式、静态分析、沙箱、参考应用和质量检查都可以成为循环中的约束。
- Humans and Agents in Software Engineering Loops 提供角色分工：人不应该微管理每个 token，而应该强化 harness；人类杠杆点是改善约束、样例、验证和任务边界。

### 四、specs、agent files 和 workflow design：把任务意图变成可执行协议
#### 4.1 两类问题：agent 怎么工作、agent 执行什么
- AGENTS.md 和 agent.md 解决“agent 进入一个 repo 后怎么工作”：命令、测试、目录边界、提交规则、权限约定、语言偏好和项目禁区，都应该被显式写下来。
- Spec Kit 和 spec-driven development 解决“agent 执行什么”：越复杂的任务越不能只靠一句自然语言目标，必须把产品意图、验收标准、阶段边界和工程约束拆成可检查的规格。
#### 4.2 生产 agent 的原则与前后呼应
- 12 Factor Agents 把生产 agent 的 prompt、state ownership、pause-resume、tool boundaries 等原则工程化；可靠性不是聊天体验，而是可暂停、可恢复、可审计的工作流系统。
- 12-Factor AgentOps 与上述资源一起，说明 harness engineering 需要机器可读或至少 agent 可读的工作协议。
- 与 context/memory 呼应：context 告诉 agent 当前在哪里，specs 告诉 agent 要去哪里，workflow design 告诉 agent 每一步如何推进和何时停下。

### 五、evals 和 observability：harness 改进的反馈回路
#### 5.1 可测量、可复现、可回放
- OpenAI 的 skill evals、agent evals、evaluation best practices 和 trace grading 指向同一实践：把 agent traces 转成 JSONL、确定性检查和任务级指标，才能判断某个 skill 或 harness 改动是否真的提升。
- OpenHands 的 evaluate agent skills 强调 bounded tasks、deterministic verifiers、no-skill baselines 和 trace review；把“这个 skill 有没有用”变成可比较实验，而不是凭单次成功判断。
#### 5.2 关注过程质量、环境噪声与回路设计
- Anthropic 的 evals for agents 和 infrastructure noise 提醒：agent 轨迹可能有很多成功路径，运行时配置也能显著影响 benchmark 分数；评测要关注过程质量、环境噪声和稳定性，而不只是最终答案。
- LangChain 的 deep agents eval 和 harness engineering 文章指出：harness changes alone 可以显著改善 benchmark performance；模型不变时，状态、工具、规划和回路设计仍可能带来实质提升。

### 六、benchmarks：把 harness 质量放进不同任务环境里测试
#### 6.1 选择标准与覆盖范围
- Benchmarks 部分很长，覆盖 Agent Arena、AgentBench、AgentBoard、AppWorld、AssistantBench、BrowseComp、BrowserGym、GAIA、OSWorld、SWE-bench Verified、Terminal-Bench、WebArena 等。
  - 选择标准：测试 context handling、tool calling、environment control、verification logic 和 runtime scaffolding。
  - 共同点：不只考模型知识，还考 agent 在环境中行动的能力。
#### 6.2 代表性环境与团队意义
- AppWorld 看 app state 和 execution-based tests；OSWorld 看真实桌面任务；SWE-bench Verified 看真实 GitHub issue 和测试；Terminal-Bench 看 shell、filesystem 和验证重任务。
- WebArena、VisualWebArena、BrowserGym 和 WorkArena 把 web navigation 放进更真实的 UI 环境，让 harness 必须处理视觉上下文、页面状态、登录态、网络变化和多步任务。
- MCPBench、MCP Universe 和 MCPMark 直接把 MCP 工具交互作为评测对象；工具调用的准确性、延迟、状态处理和错误恢复都可以被测量。
- 对团队的意义不是“追榜”，而是选择与自己任务形态接近的压力测试；研究型、编码型、浏览器型、桌面型、多 agent 型和安全型 harness，都需要不同的验证环境。

### 七、runtimes、harnesses 和 reference implementations：把理念落到可运行系统
#### 7.1 framework、runtime、harness 的分解
- LangChain 的分解很重要：framework 提供抽象，runtime 负责执行环境，harness 把模型、工具、状态、评测和任务循环组装成可靠系统；混淆三者会让团队以为装了框架就拥有了 harness。
- Claude Agent SDK、deepagents 和 AgentKit 代表生产化 agent runtime 的方向：sessions、tools、orchestration、event-driven infrastructure、durable workflows 和 long-running agents 都成为一等能力。
#### 7.2 参考实现与 harness 自身演化
- SWE-agent 和 SWE-ReX 是 coding agent 的参考实现：SWE-agent 让 prompt、tools 和 environment design 可检查，SWE-ReX 提供 sandboxed code execution infrastructure；好 harness 要能被阅读、复现和修改。
- Harbor 和 Harness Evolver 展示更进一步的方向：harness 本身也可以被评估、改进，甚至由多 agent 系统在隔离 worktree 和 eval 反馈下演化；harness engineering 未来可能变成一套持续优化的工程流程。

### 八、清单自身与概念网络：筛选原则和路线图
#### 8.1 Contributing 标准就是 harness 设计原则样本
- 资源必须 specific about how agents are constrained, evaluated, resumed, observed, or orchestrated，并优先 original implementations、primary-source articles 和 high-signal technical write-ups。
- 相似链接中，选更 primary、practical、implementation-oriented 的一个；精神是不堆概念，寻找能改变实际循环的资料。
- 虽是 awesome list，实际组织出一张路线图：先 foundations，再 context 和 constraints，再 specs 和 workflow，再用 evals/observability 反馈，最后用 benchmarks 和 runtimes 落地。
#### 8.2 概念网络主线与费曼比喻
- 起点是“模型能力外部化”：把 agent 可靠性从模型内部能力，外移到可设计、可观察、可评测的工程系统。
- 第一层是 context as working memory budget 和 repo-local instructions：前者管理短期工作记忆，后者提供长期项目规则，共同解决遗忘、漂移和误操作。
- 执行边界由 safe autonomy 和 spec-driven agent workflow 构成：回答“agent 能不能放手做事”——可以，但必须在明确边界和可检查协议内。
- 反馈回路由 trace-based evals、infrastructure noise 和 harness-level benchmarks 构成：看见过程错误、控制运行环境，并把 agent 放进真实工具、浏览器、终端、桌面和 MCP 环境里测试。
- 生产化由 runtime-harness separation、long-running agent handoff 和 harness evolution 推向落地：context/instructions 让 agent 站稳，constraints/specs 让 agent 可控，evals/benchmarks 让 agent 可测，runtime/handoff 让 agent 可持续运行，最终形成可迭代的 agent 工程系统。
- 原文费曼比喻：模型像发动机，harness 是让发动机能在真实道路上稳定行驶的车身、仪表盘、刹车、导航和维修流程；上下文像一张工作台；长任务里的 agent 像接力队。

## 作者边界、反例与不确定性
- 这份清单是 git repo / awesome list，定位为资源索引和路线图，不提供单一结论；其价值被作者放在把 agent 可靠性拆成可建设原语，而非单个链接。
- 清单明确排除泛泛 agent tooling，只收录直接覆盖 harness design、context management、evaluation、runtime control 或 reliability-critical primitives 的资源。
- benchmark 对团队的意义不是“追榜”，而是选择与任务形态接近的压力测试；研究型、编码型、浏览器型、桌面型、多 agent 型和安全型 harness 需要不同验证环境。
- infrastructure noise 提醒运行时配置、环境差异和基础设施噪声可能显著影响 coding benchmark 分数，harness 评测要控制环境。
- LangChain 文章称 harness changes alone 可以显著改善 benchmark performance；材料只转述这一判断，未给出统一实验细节或效应量。
- Harbor 和 Harness Evolver 被作者用作“更进一步的方向”，即 harness 本身可被评估、改进甚至演化；材料未说明其成熟度或反例。
- 材料没有给出反面案例或对单个资源的失败复盘；概念网络图由 Codex 据原文概念网络文字整理，非原文配图。
