# OpenAI Agents SDK 官方文档：抽象极少的轻量 agent 框架

## 一句话主旨
三个原语加 Python 本身，即可构建生产级 agent 应用，无需多学抽象。

## 作者试图回答的问题
一个 agent 框架最少需要多少抽象，才能构建生产级应用？

关联子问题：
- 少抽象会不会牺牲表达力？（由 Python 接管编排来化解）
- 框架的运行时需要提供哪些能力？（Agent loop 及其周边）
- SDK 与底层 Responses API 如何分工？（按路径选择，不必全局二选一）
- 少抽象凭什么算 production-ready？（Tracing 闭环：调试 → 评估 → 微调）

## 三级论证骨架

### 一、定位：抽象极少是竞争力，地基是三个原语 + Python

#### 1.1 全文第一句把「抽象极少」当产品承诺
- OpenAI Agents SDK 自我定位只有一句话：在一个 lightweight、easy-to-use 包里构建 agentic AI 应用，且 with very few abstractions。
  - 由两处表述反复印证："a very small set of primitives"、"without a steep learning curve"。
- 它是此前实验项目 Swarm 的 production-ready upgrade——同一条设计思路从实验转正。

#### 1.2 全部地基只有三个原语
- **Agents**：LLMs equipped with instructions and tools，即「模型 + 指令 + 工具」三件套，没有更多。
- **Agents as tools / Handoffs**：同一机制两种用法——把子 agent 当工具调用，或把控制权整体交接出去。
- **Guardrails**：对 agent 的 inputs and outputs 做 validation，是横切输入输出两端的校验层。
- 关键判断：In combination with Python，这三个原语足以表达 tools 与 agents 之间的复杂关系。
  - 框架负责给出原语，表达能力交还给宿主语言。

#### 1.3 两条设计原则同时约束特征数量与定制能力
- 原则一：Enough features to be worth using, but few enough primitives to make it quick to learn.
  - 「值得用」和「学得快」是一对同时满足的约束，不是先做大再减法。
- 原则二：Works great out of the box, but you can customize exactly what happens.
  - 默认开箱可用，定制路径能精确到「究竟发生了什么」，不留黑箱。

#### 1.4 Python-first：少抽象与强表达力的张力在此化解
- 用 built-in language features 编排和串联 agent，rather than needing to learn new abstractions。
  - 编排逻辑写在普通 if、for、函数调用里，而非框架自造的 DSL。
  - 直接收益：原有调试器、类型检查、测试工具依然可用。
- 这是全文最重要的一条因果链：既然只留三个原语，表达复杂关系的重担必须转移，Python 承担了这份职责。

### 二、运行时展开：Agent loop 是枢纽

#### 2.1 内置 Agent loop 是「不用自己写 while 循环」的那一层
- 内置循环负责 handles tool invocation、sends results back to the LLM、continues until the task is complete。
- SDK 的实质是 adds a higher-level runtime around model calls——不是替代模型 API，是套在模型调用外面的一层运行时。

#### 2.2 两个工具来源在调用面上同构
- Function tools：任意 Python 函数变工具，schema 自动生成，Pydantic 做参数校验。
- MCP server tool calling：与 function tools works the same way。
  - 关键判断：外部 MCP 能力与本地 Python 函数在调用面上拉平，是「同构而非新增一层」。

#### 2.3 挂在 Agent loop 周边的其余运行时能力
- Sessions：a persistent memory layer，在 agent loop 内维持跨轮 working context。
- Sandbox agents：specialist agent 跑在 real isolated workspaces，支持 manifest-defined files、sandbox client 选择、resumable sandbox sessions。
- Human in the loop：跨 agent 运行过程中引入人的内置机制。
- Realtime Agents：基于 gpt-realtime-2.1 构建语音 agent，带 automatic interruption detection、context management 与 guardrails。

### 三、Guardrails：与主流程并行的横切护栏

- Guardrails 不是 Agent loop 的上游或下游，而是与之 **in parallel with agent execution** 运行。
  - 检查不通过就 fail fast，不让错误输入白白消耗一整轮推理。
- 设计含义：护栏不参与主流程，却随时能叫停主流程；是横切关系而非串行关卡。

### 四、分层边界：SDK 与 Responses API 按路径选择

#### 4.1 文档先画边界，而不是宣称自己更好
- SDK 默认对 OpenAI 模型走 Responses API，本身只 adds a higher-level runtime around model calls。
- 直接使用 Responses API 的场景：
  - 想自己 own the loop, tool dispatch, and state handling。
  - workflow 是 short-lived 的，主要目的就是拿到模型的一次响应。
- 使用 SDK 的场景：
  - 希望 runtime 管理 turns、tool execution、guardrails、handoffs、sessions。
  - agent 需要 produce artifacts，或跨多个协调步骤运行。
  - 需要 real workspace 或 resumable execution，即 Sandbox agents。

#### 4.2 关键判断：选择粒度是路径而不是项目
- **You do not need to choose one globally.**
  - 同一应用中，托管工作流走 SDK，低层路径直连 Responses API，二者共存。

### 五、Tracing 闭环：从「跑一次的工具」到「越跑越好」

- built-in tracing 让用户可视化、调试、监控 agentic flows，并进一步接入 evaluate 与 fine-tune 链路。
  - 同一份运行轨迹在三个环节复用：先排错，再评估，最后成为微调模型的训练材料。
- 这条回路是 SDK 敢于宣称 production-ready 而非 experimentation 的底气。

### 六、最小示例与上手路径

- Hello world 只需三步：导入 Agent 与 Runner → 构造带 name 与 instructions 的 Agent → Runner.run_sync 跑一次并打印 result.final_output。
  - 示例任务是「写一首关于递归的俳句」，运行前提只有一条：设置 OPENAI_API_KEY 环境变量。
- Start here 按依赖顺序组织：Quickstart 建 text-based agent → Running agents 决定 carry state across turns → 依赖真实文件/仓库/隔离状态时读 Sandbox agents quickstart → 在 handoffs 与 manager-style orchestration 间摇摆时读 Agent orchestration。
  - 配套「Choose your path」表，以任务而非模块组织文档索引。

## 作者边界、反例与不确定性

- 明确给出的边界：SDK 不是所有场景的默认选择——想要自己掌控 loop、tool dispatch、state handling，或 workflow 是 short-lived 时，文档明确建议直接用 Responses API。
- 明确拒绝全局二选一：You do not need to choose one globally，选择粒度是「路径」而非「项目」；混合使用是预期状态而非过渡状态。
- 少抽象被当作产品指标来管理，但文档未给出三个原语在极端复杂场景下的表达上限，也未讨论 Guardrails 并行执行时的资源开销，以及 Python-first 在非 Python 语言环境中的适用性。
