# 一个被 harness 套住的 LLM agent：这个词到底指什么

## 一句话主旨
harness 是包裹 LLM 的非模型基础设施，agent 只是它产生的涌现行为。

## 作者试图回答的问题
agent harness 到底指什么，和 agent、模型如何分工？主流 SDK 如何实现同一模式，设计 harness 有哪些关键决策与取舍？模型变强后 harness 会消失吗，为什么说 harness 就是产品？

## 三级论证骨架

### 一、定名：harness 是包裹 LLM 的非模型基础设施，agent 是被它产生的行为
#### 1.1 反直觉架构：模型被做薄，智能外置
- 多数人把 agent 想成「一个模型外面栓了几把工具」；作者说真实架构倒过来：模型刻意做薄（deliberately thin），智能被推到外面（pushed outward），由 harness 在运行时组装。
  - 这是全文第一句反直觉判断，也是后续所有结论的地基。
#### 1.2 划界公式与 agent/harness 分工
- LangChain 的 Vivek Trivedy 给出划界公式："If you're not the model, you're the harness." 取消中间地带。
- agent 是目标导向、会用工具、能自我纠错的涌现行为，是用户打交道的东西；harness 是产生这种行为的机器。
  - 说「我造了个 agent」，真实含义是「我造了个 harness，然后把它指向一个模型」。
- Anthropic Claude Code 文档称 SDK 就是 "the agent harness that powers Claude Code"；OpenAI Codex 团队把 agent 与 harness 等同，指让 LLM 有用的 "non-model infrastructure"。
#### 1.3 操作系统类比与三层工程
- Beren Millidge 2023《Scaffolded LLMs as Natural Language Computers》：裸 LLM = 无内存、硬盘、I/O 的 CPU；上下文窗口=RAM；外部数据库=磁盘；工具集成=设备驱动；harness=操作系统。结论："We have reinvented the Von Neumann architecture"。
- 三层同心工程：prompt engineering 打磨模型收到的指令；context engineering 管理模型看到什么、何时看到；harness engineering 包住前两者，再加工具编排、状态持久化、错误恢复、验证循环、安全执行、生命周期管理。
  - harness 不是包着 prompt 的一层壳（"not a wrapper around a prompt"），而是让自主 agent 行为成为可能的完整系统。
#### 1.4 推文原始框架：薄模型、三维度、中介层
- 三个维度绕 harness 内核：Memory 装模型不该扛在权重或上下文里的状态（working context、semantic knowledge、episodic experience、personalized memory）；Skills 装程序性知识（操作规程、决策启发式、规范性约束）；Protocols 装交互契约（agent 对用户、对 agent、对工具）。
- 内核与模块之间坐 mediators：sandboxing、observability、compression、evaluation、approval loops、sub-agent orchestration。
  - 由此问题变成 "for any new capability, where should it live?" 稳定知识去记忆，学到的打法去 skills，通信契约去 protocols，循环治理交给中介层。
- 作者预告正从零写一个极简 agent harness，didactic、易读、no magic，即将开源。

### 二、运行时机制：编排循环是心跳，其余组件处理每一拍
#### 2.1 编排循环：TAO/ReAct 与 dumb loop
- harness 的心跳，实现 Thought-Action-Observation（TAO）/ReAct 循环：组装提示、调用 LLM、解析输出、执行工具调用、结果回喂、重复直到完成。
  - 机制上常常就是一个 while 循环；"the complexity lives in everything the loop manages"，复杂性住在循环管理的一切里，不在循环本身。
  - Anthropic 把自家 runtime 描述为 "dumb loop"，智能全在模型，harness 只管回合。
#### 2.2 七步走查与终止条件
- 第一步提示组装：系统提示+工具 schema+记忆文件+对话历史+当前用户消息；重要上下文放开头和结尾，直接应用 Lost in the Middle。
- 第二步 LLM 推理；第三步输出分类：只有文本无工具调用则结束，有工具调用则执行，请求 handoff 则更新当前 agent 并重启。
- 第四步工具执行：逐个校验参数、检查权限、沙箱内执行、捕获结果；只读操作可并发，改写操作串行。
- 第五步结果封装：工具结果格式化成模型可读消息；错误也捕获并作为 error result 返回，让模型自我纠正。
- 第六步上下文更新：结果追加进对话历史；接近上下文窗口上限则触发 compaction。
- 第七步循环：回到第一步，重复直到终止。
- 终止条件分层：模型给出不含工具调用的回复、超过最大回合数、token 预算耗尽、护栏 tripwire 触发、用户中断、返回安全拒答。简单问题 1-2 回合，复杂重构可能串起几十次工具调用、跨许多回合。
- 长任务跨上下文：Anthropic 提出两阶段 "Ralph Loop"——Initializer Agent 先搭环境（init 脚本、进度文件、特性清单、首次 git commit）；此后每个会话里的 Coding Agent 读 git log 与进度文件定位，挑优先级最高的未完成特性去做，提交并写摘要。文件系统提供跨上下文窗口的连续性。
#### 2.3 生产 harness 的关键组件与证据
- 工具：agent 的手。以 schema（名称、描述、参数类型）注入模型上下文；工具层负责注册、schema 校验、参数抽取、沙箱执行、结果捕获、格式化为 observation。Claude Code 六类工具：文件操作、搜索、执行、网络访问、代码智能、子 agent 派生。OpenAI Agents SDK 支持 function tools（@function_tool）、hosted tools（WebSearch、CodeInterpreter、FileSearch）、MCP server tools。
- 记忆：多时间尺度。短期记忆=单次会话内对话历史；长期记忆跨会话持久化——CLAUDE.md、自动生成的 MEMORY.md、LangGraph 命名空间 JSON Store、OpenAI SQLite/Redis Sessions。Claude Code 三层：常驻轻量索引（约 150 字符一条）、按需拉入的主题文件、只能搜索访问的原始 transcript。关键原则：agent 把自己的记忆当作 "hint"，行动前先校验真实状态。
- 上下文管理：很多 agent 在此静默失败。核心是 context rot——关键内容落在窗口中部时模型表现下降 30%+（Chroma 研究，与 Stanford "Lost in the Middle" 互证）；百万 token 窗口也会随上下文变长出现指令遵循退化。生产策略：compaction（保留架构决策与未解决 bug，丢弃冗余工具输出）、observation masking（JetBrains Junie 隐藏旧工具输出但保留工具调用可见）、just-in-time retrieval（用 grep、glob、head、tail 而非整文件加载）、子 agent 委派（只回传 1000-2000 token 浓缩摘要）。目标 "smallest possible set of high-signal tokens"。
- 提示组装：拼出模型每一步真正看到的东西，分层——系统提示、工具定义、记忆文件、对话历史、当前用户消息。OpenAI Codex 用严格优先级栈：服务端控制的系统消息（最高）、工具定义、开发者指令、用户指令（级联 AGENTS.md，32 KiB 上限）、对话历史。
- 输出解析：现代 harness 依赖原生 tool calling，模型返回结构化 tool_calls 对象；harness 只判断：有工具调用就执行并继续循环，没有就是最终答案。结构化输出可由 Pydantic 模型约束；RetryWithErrorOutputParser 这类老办法留给边缘情况。
- 状态管理：LangGraph 把状态建模成流经图节点的 typed dict，用 reducer 合并更新，在 super-step 边界 checkpoint，支持中断恢复与时间旅行调试。OpenAI 四种互斥策略：应用自管记忆、SDK sessions、服务端 Conversations API、轻量 previous_response_id 串接。Claude Code 用 git commit 当 checkpoint、进度文件当结构化 scratchpad。
- 错误处理：硬数字——10 步流程每步 99% 成功率，端到端只剩约 90.4%，错误复利快。LangGraph 分四类：瞬时错误（退避重试）、LLM 可恢复错误（作为 ToolMessage 回给模型自行调整）、用户可修错误（中断请求人工输入）、意外错误（冒泡调试）。Anthropic 在工具处理器内部捕获失败并作为 error result 返回。Stripe 生产 harness 把重试上限压在两次。
- 护栏与安全：OpenAI SDK 三级——输入护栏（在首个 agent 上运行）、输出护栏（在最终输出上运行）、工具护栏（每次工具调用都跑）；tripwire 一触发立即停机。Anthropic 架构上把权限执行与模型推理分开：模型决定尝试什么，工具系统决定允许什么。Claude Code 独立管控约 40 项离散工具能力，三阶段：项目加载时建立信任、每次工具调用前权限检查、高风险操作用户显式确认。
- 验证循环：玩具 demo 与生产 agent 的分水岭。Anthropic 三种：规则式反馈（测试、linter、类型检查）、视觉反馈（Playwright 截图做 UI）、LLM-as-judge（另一个子 agent 评判输出）。Claude Code 作者 Boris Cherny：给模型一条能验证自己工作的通路，质量提升 2-3 倍。
- 子 agent 编排：Claude Code 三种执行模型——Fork（父上下文逐字节副本）、Teammate（独立终端窗格，基于文件信箱通信）、Worktree（自己的 git worktree，一 agent 一分支）。OpenAI SDK：agents-as-tools（专家处理有界子任务）与 handoffs（专家接管全部控制）。LangGraph：嵌套状态图。

### 三、真实框架：同一模式的不同实现
- Anthropic Claude Agent SDK：单个 query() 函数暴露 harness，创建 agentic loop 并返回流式消息的异步迭代器；runtime 是 "dumb loop"，所有智能住在模型里。Claude Code 走 Gather-Act-Verify：收集上下文、采取行动、验证结果、重复。
- OpenAI Agents SDK：Runner 类实现 harness，三种模式 async、sync、streamed；SDK 是 code-first 的，工作流逻辑用原生 Python 而非图 DSL。Codex harness 扩出三层——Codex Core（agent 代码+runtime）、App Server（双向 JSON-RPC API）、客户端界面（CLI、VS Code、Web app）；所有界面共用同一 harness，解释 Codex 模型在 Codex 界面上比在通用聊天窗口手感更好。
- LangGraph：把 harness 建模成显式状态图。两个节点 llm_call 与 tool_node 由条件边连接：有工具调用路由到 tool_node，没有路由到 END。从 LangChain 的 AgentExecutor 演化而来，后者因难扩展、缺多 agent 支持在 v0.2 弃用。Deep Agents 明确使用 "agent harness"：内建工具、规划（write_todos）、用于上下文管理的文件系统、子 agent 派生、持久记忆。
- CrewAI：角色制多 agent 架构——Agent（围绕 LLM 的 harness，由 role、goal、backstory、tools 定义）、Task、Crew。Flows 层加一根确定性主干，智能只放在真正需要的地方，负责路由与校验，Crew 负责自主协作。
- AutoGen（正演化为 Microsoft Agent Framework）：开创对话驱动编排。三层 Core、AgentChat、Extensions；五种编排模式：顺序、并发（fan-out/fan-in）、群聊、handoff、magentic（一个管理者 agent 维护动态任务账本来协调专家）。

### 四、设计空间：七个决策与 harness 厚薄
- 单 agent vs 多 agent：Anthropic 与 OpenAI 口径一致——先把单 agent 榨到极致。多 agent 有额外开销（路由多花 LLM 调用、handoff 丢上下文）。只有重叠工具超过约 10 个、或存在明显分离的任务域时才拆。
- ReAct vs plan-and-execute：ReAct 每步交错推理与行动，灵活但每步成本更高；plan-and-execute 分开规划与执行，LLMCompiler 报告相对顺序式 ReAct 有 3.6 倍加速。
- 上下文窗口管理策略：五种生产做法——按时间清理、对话摘要、observation masking、结构化记笔记、子 agent 委派。ACON 研究显示，优先保留推理轨迹而非原始工具输出，可在保持 95%+ 准确率的同时减少 26%-54% 的 token。
- 验证循环设计：计算式验证（测试、linter）提供确定性的 ground truth；推断式验证（LLM-as-judge）能抓语义问题但增加延迟。Martin Fowler 的 Thoughtworks 团队把这组对立表述为 guides（前馈，行动前引导）与 sensors（反馈，行动后观察）。
- 权限与安全架构：宽松（快但有风险，多数动作自动放行）对严格（安全但慢，每个动作都要审批），选择取决于部署场景。
- 工具收窄策略：工具越多往往表现越差。Vercel 从 v0 里删掉 80% 的工具，结果反而更好；Claude Code 靠懒加载做到 95% 的上下文缩减。原则：只暴露当前这一步所需的最小工具集。
- harness 厚薄：多少逻辑住在 harness 里、多少留给模型。Anthropic 押注薄 harness 加模型进步，图式框架押注显式控制；Anthropic 会随新模型内化规划能力，定期从 Claude Code 的 harness 里删掉规划步骤。
  - 厚薄光谱：薄端由模型决定所有决策（Claude Agent SDK、OpenAI Agents SDK），厚端用显式路由与规划步骤（CrewAI Flows、LangGraph）。
  - 与工具收窄、协同进化存在张力：安全要求收窄暴露面，能力要求扩大暴露面；经验数据常偏向收窄。

### 五、趋势与结论：脚手架、协同进化、harness 就是产品
- 脚手架隐喻：施工脚手架是临时基础设施，让工人够到本来够不到的结构；它本身不盖楼，但没有它工人上不了高层。楼盖完，脚手架拆掉——模型变强，harness 复杂度应下降。
  - Manus 在六个月里重写五次，每次重写都在删复杂度：复杂工具定义退化成通用 shell 执行，「管理 agent」退化成简单的结构化 handoff。
- 协同进化原理（co-evolution principle）：模型现在带着特定 harness 一起做后训练；Claude Code 的模型学会的是它训练时那一套 harness；换掉工具实现反而可能让性能下降，因为耦合非常紧。
- 未来防腐测试（future-proofing test）：换上更强模型、不增加任何 harness 复杂度、性能就能跟着涨，这个设计就是稳的。
- harness 就是产品：用同样模型的两个产品，性能可以天差地别，差别只在 harness 设计。TerminalBench 证据——只改 harness，agent 排名移动 20 位以上。
  - LangChain 只换包在 LLM 外面的基础设施（同一模型、同一份权重），在 TerminalBench 2.0 上从 30 名开外冲到第 5；另一个研究项目让 LLM 自己优化基础设施，pass rate 达到 76.4%，超过手工设计的系统。
- harness 不是已经解决的问题，也不是一层商品化的中间件。难工程都在这里：把上下文当稀缺资源管理、设计能在错误复利之前抓住失败的验证循环、构建有连续性又不产生幻觉的记忆系统、对「造多少脚手架、留多少给模型」下架构赌注。
- 大势：模型越强，harness 越薄，但 harness 不会消失。即使最强模型，也需要有东西替它管上下文窗口、执行工具调用、持久化状态、验证工作。
- 收束："下次你的 agent 失败，别怪模型，去看 harness。"

## 作者边界、反例与不确定性
- 多 agent 不是默认答案：作者引 Anthropic 与 OpenAI 口径，先单 agent 榨到极致；只有重叠工具超过约 10 个或任务域明显分离时才拆。
- 工具收窄与能力需求有真实张力：安全要求收窄暴露面，能力要求扩大暴露面；经验数据（Vercel 删掉 80% 工具反而更好）说明最优解常偏向收窄，但材料未给出普适阈值。
- harness 厚薄是架构赌注，没有普适答案：押模型进步可能遇到模型未内化某些能力；押显式控制可能臃肿。押错要么脆弱，要么臃肿。
- 协同进化限定改造成本：模型与 harness 紧耦合，换掉工具实现可能反降性能，不能随意增删 harness。
