# 为什么「软件工厂」会失败：光有 harness 工程还不够

## 一句话主旨
软件工厂失败根因在模型训练，不在 harness；人须回到循环。

## 作者试图回答的问题
- 为什么光有 harness 工程撑不起可靠的“软件工厂”？
- 编码 agent 为什么能通过测试，却持续侵蚀代码库的可维护性？
- 在模型能力约束下，怎样用 agent 跑得可持续地快，而不烧毁代码库？

## 三级论证骨架

### 一、从软件工厂承诺到现实警报：自动化循环不断吃掉“人做的事”
#### 1.1 三种形态递进
- 2022 基线（AI 之前）：人决定做什么→进 tracker（Linear/Jira）→有人认领实现并做测试→PR（自动检查+人工评审）→有问题打回→上线→监控→用户反馈回 tracker。
  - 循环已经一堆；团队早就知道 build 和 review 要花几小时到几天，所以要把工作前置，即 front-loading alignment。
- agentic 软件工厂：把“有人建造”换成 agent 建造，配编排、harness、沙盒、模型、computer use。
  - Ramp、Stripe、WorkOS、Brex 等今年对外讲述能产出约 75% 代码的 agent 工厂。
  - 后果：建造时间降到几分钟/几小时，评审仍要几小时到几天，评审变成新瓶颈。
  - 应对：agentic code review、agentic 回归测试、把线上事故和用户反馈路由进工厂；问题简化为队列能塞多少、评审测试跟不跟得上。
- lights-off 软件工厂：Dan Shapiro 命名，StrongDM 用 factory.strongdm.ai 实践，连代码评审也去掉，不再有人读代码。
  - 逻辑：人读每一行改动太烦，把精力投入测试、沙盒、编排、自动化评审、监控、发布、反馈信号。
  - 问题变成：我们想让 agent 建造多少东西？想“烧多大一片海”（boil the ocean）？

#### 1.2 承诺与警报同时存在
- 主流承诺：多写循环、堆 harness 工程——更多 linter、PR 机器人加“adversarial review”——终点是 10-100 倍速度、高质量、再也不用代码评审。
  - 作者点破最刻薄解读：这可能是把更多 VC 的钱泵进“slop 大炮”（slop cannon）的借口。
- 警报：Mario（badlogicgames）在 AI Engineer Europe 恳求慢下来，因为一些不该因编码 agent 出岔子的公司正在宕机（金融时报报道过）。
  - Matt Pocock：代码库正在以前所未有的速度“散架”。
  - Faros AI 报告：自今年 1、2 月普遍用上 AI coding 工具以来，PR 评审质量明显下滑——评论更多更长，大量 PR 未评审就合并，事故数上升，人均 bug 数上升。
  - StrongDM 自家 weather-report 页面在 2 月到 6 月只有寥寥几次更新，作者没挖到灯灭实验结果的确凿数据。

### 二、HumanLayer 亲历：灯灭模式翻车，证明问题不是“用对姿势”
#### 2.1 2025 年 7 月全面转向灯灭
- 只读 spec 和 ticket，中小任务全交给后台 agent。
- 结果：总会撞上至少一个 agent 解决不了的棘手问题，即便用最高级 prompt 和工作流也不行；做带上下文的深度研究、让 agent 用十种方式复现，最后还是得回去啃三个月没读过的代码库。

#### 2.2 代价累积到推倒重写
- 网站宕机、用户不满；作者形容自己读着放任溜进系统的一堆 slop 代码。
- 第一次出事，他咬牙挺过，认为“下行风险配得上速度收益”；11 月前后第三次撞上同类问题时，团队决定推倒重写。
  - 联合创始人花两周，在 VS Code（甚至不是 Cursor）里手工梳理所有模式。

#### 2.3 作者定位模型短板：没有人工引导，模型无法长期维护并提升代码库质量
- 可维护性具体指“改一处却容易牵连别处”变得异常困难，即 Martin Fowler 说的“shotgun surgery”（霰弹式手术）。
  - 指向 Ousterhout《A Philosophy of Software Design》、Robert C. Martin《Clean Code》、Fowler《Refactoring》。
- 模型在单点问题、随手 vibe-code 一个营销站上强很多，但长期维护代码库质量进步不大，至少作者看不出来。
  - 作者和读者都拿不出证据，因为根本没有衡量模型维护代码库质量能力的靠谱基准。
- 可让顶级模型做漂亮重构，但前提是你先告诉它要重构；要能告诉它，你得先懂代码库到知道哪里需要重构——灯灭没人看，就没人知道让模型修哪里。

### 三、根因：RL 训练的打分机制，让模型过测试却侵蚀可维护性
#### 3.1 编码 agent 的 RL 训练循环
- 三步：生成一批编码 agent trace 解决问题→用 verifier 给 trace 打分→更新权重，让好 trace 更可能、坏 trace 更不可能。
  - 循环跑上百万次，持续数周到数月。
  - 问题出在“打分”这一步，经常单薄、单维度。

#### 3.2 SWE-bench 案例：二元打分只看 FAIL_TO_PASS/PASS_TO_PASS
- SWE-bench Multilingual 任务规模不大，平均约 15 分钟工作量，从 Redis、jq、Django 等开源仓库扒出；打分是 0/1 二元。
- 真实案例 fastlane__fastlane-19304（Ruby 项目 fastlane）：zip action 拿到两个可选参数直接调 .empty?，调用方没传 include/exclude 就报 undefined method 'empty?' for nil:NilClass。
  - 人类修复只有两行：把两个参数为 nil 时兜底成空数组。
- 评测流程：模型从“修复落地前一刻”的 base commit 出发，只看 bug 报告，看不到金标准补丁或 test patch；它写的补丁保留，但对测试文件的改动整体丢弃；随后盖上基准自带 test patch，跑全套测试，看是否全过。
- 关键结论：模型是“怎么”得到正确答案完全不重要，测试通过就算赢；但这套打分对“侵蚀代码库可维护性”没有任何惩罚。
  - 这正是满地 try/catch 包裹一切、架空类型系统意义的偷懒类型转换的来源。

#### 3.3 可维护性难验证：时间尺度不匹配，缺一个可靠的“预言机”
- 跑测试几秒就能拿到明确过/不过结果，所以 RL 能在一代模型训练时跑上百万次循环。
- “架构差”的代价以周、月甚至年计量；有人为改一行打开文件才发现根本没法一行改完，同一处改动得在十一个地方各改一遍。
  - “设计差”是今天的基准测不出来的东西。
- 用模型当质量判官有天花板：如果一个模型真能可靠分辨代码好坏，它很可能一开始就直接写出了好版本。
  - RL 需要一个又快又可靠的“预言机”（oracle），可维护性目前没有。
  - 更多评审 agent、更多 token 能抬高地板，抓住明显愚蠢错误；但撑不高天花板，因为天花板取决于 RL 阶段到底教会模型什么，而“好设计”是我们还不知道怎么教的东西。

#### 3.4 平行证据：Claude Code 赢在把 RL 做进 harness 里面
- Claude Code 不到一年内据作者说营收从零冲到约 40 亿美元、现在被形容为逼近 90 亿美元；此前已有 aider、cline、codebuff，工具集和上下文工程不差。
- 作者体验：工具调用时不时失败，盯同一处修改扑腾三次，最后自己打开编辑器。
  - SWE-Agent 2024 论文：工具形态微小变化带来明显差异，比如 ReadFile 结果里加行号，或 Edit 从查找替换换成按行区间编辑。
- 公认解释：Anthropic 把模型训练直接放进 harness 里——第一次有实验室拿即将发布的那套工具去 RL 训练模型，让模型在 agentic 循环里擅长调用这些工具。
  - OpenAI 团队 11 月演讲：如果搭了 harness 却不掌握权重、无法在 harness 内部做 RL，你永远会输给同时拥有两者的团队。
  - 呼应标题：harness 工程本身不是没用，但不掌握权重就做不到位。

### 四、前沿努力与边界：有人认真给可维护性打分，但炒作跑赢工程投入
#### 4.1 三个方向
- SWE-Marathon（Abundant AI）：约 400 小时量级任务，如把整个 Excel 每个功能克隆一遍；用一条复合奖励通道取代单一 pass/fail。
- DeepSWE（Datacurve）：基于现实中从未真正被构建过的开源仓库出大任务，靠构造方式避免训练集污染；但没解决质量问题本身。
- Frontier Code（Cognition）：多 PR 任务；确定性质量评估——如果模型写的测试在打补丁之前的代码上不会失败，就要受罚，即 mutation testing 核心思路；另外跑判官模型检查 diff 是否符合代码质量规则。
  - 作者类比早年在 Sprout Social 时老板的游戏：看你能从 Python 大单体里删掉多少行代码，同时不让成千上万个单元测试挂掉；能删掉一大截还全绿，说明测试套件很多地方形同虚设。

#### 4.2 作者判断
- 不是“做不到”，而是“炒作正在跑赢真正的工程投入”（the hype is outrunning the discipline）。
- 更多评审 agent、更多 token 确实有用，能抬高地板；但天花板取决于 RL 教给模型什么。
- 作者还不敢把代码库押注在这些新基准上，但它们至少是第一批认真尝试给可维护性打分、而不只停在 pass/fail 的评测。

### 五、药方：把代码评审请回来，用四个前置阶段把返工提前
#### 5.1 总原则：front-loading alignment
- 30 分钟的规划，换来几小时评审时间的节省。
- 不是每次都走全套：约 40% 任务直接一次成型或配 1-2 轮轻量反馈；中等任务把产品/系统设计合并成一份文档；大任务才走全部四步；大型重构甚至会跳过产品这一步。
  - 多数情况下一次只放 1-3 个切片出去，边走边评审，比等到 2000+ 行代码后更容易早期重新引导。

#### 5.2 产品评审
- 从一份简短文档开始，钉死“做什么”和“为什么”：先对齐要解决的问题，用用户自己的语言讲清用户痛点；再对齐成功的样子，看上线后什么指标能判断值得做。
  - 理想是“能更快完成 XYZ 工作流”这类用户结果；有时是错误率、延迟；有时就是“关于 X 的支持工单不再出现了”。
  - 刻意把讨论拉回产品层面；技术决策卡住产品决策时，先定已有东西，再进架构阶段或做可行性原型研究。
- 依赖“不描述、而是做出来”：粗糙 HTML mockup 能让三段文字摆不平的争论一眼定。
  - 做法是“作者自选评审人”：自己挑出会评审这个 PR 的人，提前和 ta 过产品/技术 spec，可异步文档评论或用 GitHub/Notion 等工具。
- 不适用：文案微调、一次性脚本、复现路径明确的 bug，直接一步到位丢给 agent；这一阶段为“agent 误解意图代价很高”的改动准备。

#### 5.3 系统架构
- 产品评审后，对齐服务、接口、schema、队列、存储之间怎么互通，但不深入程序设计细节。
- 大量使用可视化提升人和 agent 的沟通带宽：时序图（如 UI → API → ResourceService → Store 的创建流程）、接口/契约形状（如 PUT /api/resources/:slug 的请求响应结构）、数据模型和表结构变化。
  - mermaid 够用，但有时显得多余，甚至会营造“我们已经对齐了”的假象。
  - 架构层面杠杆很高，能提前挡掉不少模型坏习惯；单靠它不足以产出高质量代码。

#### 5.4 程序设计
- 作者认为这是 agentic coding 里“被严重低估”的一步：在写实现前，从架构再往下一层进入“代码的形状”——类型、方法签名、程序布局、调用栈。
- 真正好用形式是伪代码式轻量可视化：
  - 调用栈树：涉及编排或控制流变化时用，变化部分可用 diff 语法标出，如新增 handleCreateResource 调用链、删掉 legacyCreateFlow。
  - 文件树 diff：如新增 resource-client.ts、resource-client.test.ts，修改 resource-route.ts。
  - 关键新函数的类型和方法签名：如 Item、Cursor 两个 interface，加上 resolveTarget(items, cursor) -> ItemId | null 这样的签名。
- Dillon Mulroy 印证：他的“计划”很大程度上就是伪代码式类型/接口定义、它们怎么组合、边界在哪，最近还开始加入调用栈。
  - 这些做不了多久，但每一个都是原本会在代码评审时才隐性做出的决定，而代码评审是改主意成本最高的时间点。

#### 5.5 垂直切片 / tracer bullets
- 模型天生偏爱“横向计划”：按数据库迁移→服务层→API→前端的技术分层顺序推进，做到一半根本没法真正“摸到”东西。
- 作者 AI 之前的习惯是从中间开始、向外扩展：先建 API 契约、喂 mock 数据、用 curl 测；再建前端消费 mock 数据、在浏览器里迭代打磨；再把 API 接到服务层（服务层先继续吐 mock）；再加数据库迁移、把服务层接上数据库；再补业务逻辑；最后补错误处理。
  - 每一步都在测试、迭代、打磨；在意或不太信任模型时，每一步都评审，每次检查 100-200 行，随时重新引导，成本比等到 2000+ 行后再回头低得多。
  - 多数前沿模型没有人工引导不会自己规划切片式路线，且很难按代码库或任务泛化；作者更愿意全程在场。

#### 5.6 PR 与 2026 版“约束理论”
- 不是 PR 太多，是烂 PR 太多；AI 之前大家也一直评审需要返工的 PR。
  - 好 PR 逐文件看下去代码干净，处处遵循团队已讨论、争取来的共识。
  - 一份 PR 哪怕只需 20% 返工（作者认为已乐观，多数 AI 一次成型 PR 更接近 50%），对提交者和评审者都是智力负担和情绪负担。
- 结论：目前为止，还是得读代码。
  - 作者铺陈出来的只是一系列约束：模型在某些事情上很强，某些事情上不然；在这些约束下优化流程。
  - 一边拼命冲 10-100 倍并说服自己代码质量不重要是一种选择；拥抱约束、安全跑出 2-3 倍是另一种选择。
  - 收尾建议：把约束摸熟，在约束划出的场地里优化系统，主动找杠杆，然后“读那该死的代码”（read the dang code）。

## 作者边界、反例与不确定性
- Faros AI 报告更多是相关性信号而非确凿证据；作者说“从我看到的情况说，方向感觉是对的”。
- StrongDM 的 weather-report 在 2 月到 6 月只有寥寥几次更新，作者没挖到灯灭实验结果的确凿数据。
- 模型是否更强：作者承认在某些方面强很多，但在长期维护代码库质量上进步不大；他和读者都拿不出证据，因为根本没有靠谱基准。
- 作者承认 RL 不等于 Benchmark；但认为如果问题在 RL 里被解决，理应开始体现在基准设计方式上；他个人不相信当前基准进步能说明模型不再往代码库倒垃圾。
- 对前沿评测：作者判断不是“做不到”，而是“炒作正在跑赢真正的工程投入”；他还不敢把代码库押注在这些新基准上。
- 四阶段不是每次全套：约 40% 任务直接一次成型或轻量反馈；中等任务合并产品/系统设计；大任务才走四步；大型重构可能跳过产品；多数情况一次只放 1-3 个切片。
- 材料未给出可维护性“预言机”的具体实现路径，只说明它目前不存在，以及模型当判官有天花板。
