# 《Harness 工程学习仓库：从原始文献到能跑的 skill》

## 一句话主旨
让 coding agent 可靠的不是更强的模型，而是围绕它设计的完整工作环境。

## 作者试图回答的问题
能不能在真实仓库里，跨越多次会话、不需要人一直盯着，就可靠地完成真实的工程任务？作者的重定义：「问题不是『模型能不能写代码』。能写。问题是能不能跨会话、无人盯梢、可靠交付。」

## 三级论证骨架

### 一、立论：模型没换，换的是 harness
#### 1.1 分工判据（全文最锋利的一句）
- **模型决定写什么代码。Harness 管控什么时候写、在哪里写、怎么写。**
  - Harness 不会让模型变聪明，它让模型的产出变可靠。
- Harness engineering 定义：围绕模型搭建一整套工作环境，让它产出可靠的结果。
  - 「不只是写更好的提示词，而是设计模型运行所在的系统。」把注意力从换模型、改 prompt 转向设计模型运行所在的系统。

#### 1.2 硬证据：Anthropic 同模型同提示词对照实验
- 同一个 Opus 4.5，同一段提示词（「做一个 2D 复古游戏编辑器」）。
  - 无 harness：20 分钟、9 美元，游戏核心功能跑不起来。
  - 完整 harness（planner + generator + evaluator 三 agent 架构）：6 小时、200 美元，做出来的游戏可以正常游玩。
- 结论一句话：**模型没换，换的是 harness。**
- OpenAI 用 Codex 得出同样结论：harness 搭得好的仓库里，同一个模型从「不可靠」变成「可靠」——作者特意强调「不是『好了一点』，是质变」。

#### 1.3 失败模式的形态
- 起手场景「几乎人人有份」：agent 读文件、写代码、很努力，然后——跳过了一个步骤、搞坏了一个测试、说「完成了」但什么都没跑通。
  - 结果：「你花在收拾烂摊子上的时间比自己做还多」。
- 作者据此判定：这不是模型的问题，是 harness 的问题。

### 二、五个子系统
#### 2.1 指令——渐进式展开
- 告诉 agent 做什么、按什么顺序、开工前先读什么。
  - 关键限定：「不是一个巨大的文件，而是渐进式展开的结构，agent 按需导航」。载体是 AGENTS.md、CLAUDE.md、feature_list、docs/。
- L04 的概括：**给地图，不给百科全书。**

#### 2.2 状态——进度持久化到磁盘
- 跟踪做了什么、正在做什么、下一步是什么，**持久化到磁盘**，下次会话从上次停下的地方继续。
  - 载体是 progress.md、feature_list、git log、会话交接笔记。

#### 2.3 验证——只有可运行的证据才算数
- **agent 不能没有可运行的证据就说「做完了」。**
  - 载体是 tests + lint、type-check、smoke runs、e2e pipeline。

#### 2.4 范围——一次只做一个功能
- 「不多做，不少做，**不偷偷改功能清单掩盖未完成的工作**。」配套是显式的完成定义。

#### 2.5 会话生命周期——开工初始化、收尾清理
- 开始时跑 init.sh，结束时跑清理检查清单，给下次会话留交接笔记与一条干净的重启路径；**只在可以安全恢复时才 commit**。

### 三、问题重定义：跨会话的可靠交付
#### 3.1 无 harness 的两次会话
- 会话 1：写代码 → 搞坏测试 → 说「做完了」→ 你手动修复。
- 会话 2：从头开始、没有上次记忆、重做一遍或做了完全不同的东西 → 你再修一次。
  - 结果：你花的时间比自己做还多。

#### 3.2 有 harness 的两次会话
- 会话 1：读指令 → 跑 init.sh → 一次只做一个功能 → 验证后才说完成 → 更新进度日志 → 干净地 commit。
- 会话 2：读进度日志 → 从上次停下的地方继续 → 继续未完成的功能。
  - 结果：agent 干活，你验证结果；**你是审查，不是救火。**

#### 3.3 课程真正关心的四个问题（研究提纲）
- 哪些 harness 设计会提升任务完成率？
- 哪些设计会减少返工和错误完成？
- 哪些机制能让长时任务更稳定地持续推进？
- 哪些结构能让系统在多轮 agent 运行后仍然可维护？

### 四、落地路径：12 讲义 + 6 项目
#### 4.1 12 个讲义——把失败模式逐个命名
- L01 能力鸿沟：基准测试与真实工程之间存在落差，模型能力强 ≠ 执行可靠。
- L02 Harness 到底是什么：五个子系统。
- L03 仓库即唯一事实来源：**agent 看不到的东西，对它来说就不存在。**
- L04 巨型指令文件为何失败：渐进式展开。
- L05 长时任务为何丢上下文：进度持久化到磁盘。
- L06 初始化为何单独成阶段：开工前先验证环境是否健康。
- L07 agent 为何多做或少做：一次一个功能，显式完成定义。
- L08 功能清单为何是 harness 原语：**机器可读的范围边界，agent 无法忽略。**
- L09 agent 为何提前宣告完成：验证缺口，**自信 ≠ 正确。**
- L10 端到端测试为何改变结果：只有跑通完整流程才算真正验证。
- L11 可观测性为何属于 harness：**看不到 agent 做了什么，就修不了它搞坏的东西。**
- L12 为何每次会话都要留干净状态：下次会话的成功取决于这次会话的清理。

#### 4.2 6 个项目——同一 Electron 应用上层层加码
- 共享基础是 Electron + TypeScript + React；每个项目的 solution 成为下一个项目的 starter，应用跟着你的 harness 技能一起进化。
- P01 跑两次同样任务：只写提示词 vs 定好规则——最小 harness（AGENTS.md + init.sh + feature_list.json）。「你看到问题」。
- P02 重组项目结构让 agent 读懂——可读工作空间 + 持久化状态文件。「你重组仓库」。
- P03 关掉再打开还能接着干——进度日志 + 会话交接 + 多会话连续性。「你连接会话」。
- P04 防止多做或少做——运行反馈 + 范围控制 + 增量索引。「你加上反馈循环」。
- P05 让 agent 自己验证——自验证 + 带引用的问答 + 基于证据的完成判定。「你让 agent 检查自己」。
- P06 从零搭建完整 harness（综合项目）——全部机制 + 可观测性 + **消融实验**。「你搭建完整系统」。

#### 4.3 验收口径是工程化的
- 每个项目都要求 agent 真正干活，都要做弱 harness / 强 harness 对照。
  - 评价立场：「我们关心的是效果变化，而不是『写了多少说明文档』。」

### 五、会话生命周期：一台 16 步的状态机
#### 5.1 核心理念
- **agent 的会话应该遵循结构化的生命周期，而不是自由发挥。**

#### 5.2 四段式
- 开工（1–5）：读 AGENTS.md / CLAUDE.md → 跑 init.sh（安装、验证、健康检查）→ 读 claude-progress.md（上次做了什么）→ 读 feature_list.json（做完哪些、接下来做哪个）→ 检查 git log。
- 选择（6–7）：选定且只选一个未完成的功能；只做这一个功能。
- 执行（8–11）：实现功能 → 运行验证（测试、lint、类型检查）→ 失败则修复后重跑 → 通过则**记录证据**。
- 收尾（12–16）：更新 claude-progress.md → 更新 feature_list.json → 记录还没做完和还没验证的东西 → commit（只在可以安全恢复时）→ 给下次会话留干净的重启路径。

#### 5.3 第 9 步的分水岭
- 无 harness 时，第 9 步变成「agent 说看起来没问题」；有 harness 时，第 9 步是「测试通过、lint 干净、类型检查通过」。
  - Harness 管控生命周期里的每一次状态转换，模型只决定每一步写什么代码。

### 六、概念网络中的关键关系（作者自述的组织逻辑）
- 因果链起点：**能力鸿沟**逼出 **harness engineering**——跑分与真实工程有落差，且落差不会随模型变强自动消失。
  - 弱强 harness 对照与消融实验是这条链上沉淀下来的固定方法：每个项目跑两遍，关心效果变化而非文档篇幅。
- 跨层约束性前提有两个：**仓库即唯一事实来源**（同时支撑指令与状态，载体必须是仓库文件），**渐进式展开**（约束指令形态，防止退化成没人读的巨型文件）。
- **功能清单**是身份最特殊的节点：既是范围边界的机器可读载体，也被状态子系统复用为进度记录——「一个对象在多个子系统里同时承担职责，才算得上原语」。
- 收益兑现路径：状态支撑会话生命周期 → 与验证共同演化出**从救火到审查**的角色转移；成立需要两个条件——跨会话连续性让 agent 不必重来，可运行的证据让你不必逐行复核。

## 作者边界、反例与不确定性
- **适合谁**：已在用 coding agent、希望提升稳定性与质量的工程师；想系统理解 harness 设计的研究者或构建者；需理解「环境设计如何影响 agent 表现」的技术负责人。
- **不适合谁**：只想要零代码 AI 入门的人；只关心 prompt、不打算做真实实现的人；不准备让 agent 在真实仓库里工作的学习者。
- **环境要求**：真正需要动手跑 coding agent，至少要有 Claude Code、Codex 或其他支持文件编辑、命令执行、多步任务的 IDE / CLI coding agent，且允许 agent 编辑文件、运行命令、检查输出并重复执行任务。
- **先修要求**：熟悉终端、git 和本地开发环境；至少会读写一种常见应用栈的代码；有基本调试经验。用过 Electron、有测试与架构经验则加分。
- **不要读完 12 讲义再动手**：「思路很简单：不是光写提示词，而是在仓库里放一组结构化的文件……这些文件就放在项目里，**每次会话都从同一个状态开始**。」
- **仓库形态**：文档站用 VitePress；npm run pdf:build 生成中英双语 PDF 到 artifacts/pdfs/，GitHub Actions release-course-pdfs.yml 自动构建并上传 Release。目录分 docs/（中英双语讲义、项目、资源）、projects/（shared 基础 + 每项目 starter/solution）、skills/harness-creator/（几分钟内为自项目搭出生产级 harness）。
- **参考谱系**：主参考为 OpenAI Codex harness 文章与 Anthropic 两篇长时 agent harness 文章；辅助参考包括 LangChain 的 The Anatomy of an Agent Harness、Thoughtworks 的 Harness Engineering、HumanLayer 的 Skill Issue；灵感致谢 learn-claude-code。
