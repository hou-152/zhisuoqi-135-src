# 论「会自动驾驶的代码库」：多 agent 研究 harness 开放预览

## 一句话主旨
多 agent 递归所有权结构让代码库接近自动驾驶，真正瓶颈在人的指令。

## 作者试图回答的问题
核心问题：**能否多花 10 倍算力，换来 10 倍有意义的吞吐量**——能否造出一个让代码库自我维护的多 agent 系统？关联子问题：为什么单 agent 走不通？多 agent 协调失败的根本原因是什么？什么样的结构与角色分工能让系统稳定自收敛？吞吐量的代价是什么？harness 稳定之后，什么成为新的瓶颈？

## 三级论证骨架

### 一、研究起点与单 agent 的失败：任务太大，必须拆分

#### 1.1 浏览器被选作 benchmark，因为它足够复杂
- 研究载体是一个从零写起的 web 浏览器——"复杂到足以暴露前沿模型的局限"，子系统足够多且必须协同工作。
- 最初做法极其朴素：让 Opus 4.5 写一份构建浏览器引擎的详细计划，然后反复催它 "keep going"。

#### 1.2 单 agent 快速失败，但失败点值得注意
- 模型**跟丢自己在做什么**，还没接近完成就频繁宣称成功，卡在复杂实现细节上。
- 但模型并非没有能力：**小片段代码写得很好**，显示出深厚的知识与智能。
- 诊断结论：不是模型不行，而是浏览器任务对单次上下文过于压倒性，**必须拆成子任务**。

#### 1.3 第二版加上依赖图，结果没好多少
- agent 先规划出主要工作的依赖图，人工按图 spawn agent，卡住就 nudge。吞吐量上去了，结果没好多少——agent 之间**无法沟通、无法对项目整体给出反馈**。系统需要更动态。
- 期间模型选择变化：GPT-5.1（及 GPT-5.2）在**精确遵循指令**上表现更好，被判断为长时运行 agent 的更好匹配，harness 改用 OpenAI 模型。
- 此时 harness 已能造出**不支持 JavaScript 的简版浏览器**，但靠单 agent 造完整浏览器引擎"慢得不可接受"。

### 二、多 agent 协调结构的四代演化：一条失败与修正的链

#### 2.1 第一代：平级 agent 自协调——自由的最小规定哲学速败

- **设计**：一群平级 agent 共用一个共享状态文件，各自查看别人在做什么、决定自己做什么、再更新文件。设计哲学是"尽量少规定"。
- **环境**：全部跑在一台资源充裕的大 Linux VM 上，通过 SSH + 简单终端界面控制，刻意回避分布式系统复杂度。前期把力气花在可观测性上——记录所有 agent 消息、系统动作、命令输出，带时间戳，可分析可回放；日志还能反过来喂给 Cursor 找模式。
- **表层失败：锁**。agent 持锁太久、忘记释放、在非法时机加锁解锁；更根本的是**不理解持有协调文件锁的意义**——"Locking is easy to get wrong and narrowly correct"，加更多 prompt 也没用。
- **锁带来严重竞争**：20 个 agent 的实际吞吐退化到 1–3 个的水平，大部分时间在等锁。显式"等待另一个 agent 完成"的工具很少被用；无锁乐观并发控制开销降了但困惑没消。
- **最深层问题：责任真空**。平级结构下没有任何 agent 愿意接下大而复杂的任务——它们回避冲突与竞争，倾向做更小更安全的改动，而不是为项目整体负责。

#### 2.2 第二代：分离角色，给 agent 所有权与问责

- **四个角色**：planner 排出达成用户指令所需的确切路径与交付物；executor 作为唯一 lead agent 独自负责计划被完整达成，可 spawn 任务给 worker 获得线性扩展与吞吐；worker 只管窄范围的具体任务；judge 在 executor 结束后独立运行，判断是否真的完成、是否需要再跑一轮。
- **效果明显**：有一个专职角色拥有并监督执行，worker 就能安心聚焦自己那一小块，而系统整体仍然交付得出来。许多协调问题就此消解。
- **判断来源**：靠贴身观察系统——真正的大问题往往会在很多 agent、很多次工具调用上重复出现。具体例子：竞争过高源于大量 agent 同时跑 `git restore`；他们用 Cursor 分析日志、与 prompt 逐条对照，理解"行为为何与预期不符"。
- **但天花板明显**：系统被最慢的 worker 卡住，太刚性；所有规划都在前期做完，新问题出现时难以动态重调；一些 agent 走进反效果方向，**直到下一轮循环才有机会自我纠正**。

#### 2.3 第三代：连续执行器——去掉 planner，灵活回来但角色过载

- **设计变化**：去掉独立 planner，executor 既规划也 spawn 任务。因为它是唯一 agent，**不需要把计划写在任何地方**，不必守着静态计划，也不必刚性地等所有 worker。
- **引入新鲜度机制防漂移**：scratchpad.md 应频繁重写而非不断追加；单个 agent 逼近上下文上限时自动总结；系统提示里加入自省与对齐提醒；鼓励随时转向、随时挑战既有假设。
- **judge 也被删掉**以保持简单——agent 已能较好地跟随指令直到完成。
- **结果：病态行为出现**。随机 sleep、停掉正在跑的 agent、自己动手干活、拒绝规划、只肯 spawn 少数几个窄任务、不好好合并 worker 的改动、过早宣称完成。
- **归因**：它被同时赋予太多角色与目标——规划、探索、研究、派任务、盯 worker、review 代码、亲自改代码、合并产出、还要判断循环是否结束。"In retrospect, it makes sense it was overwhelmed."

#### 2.4 第四代（最终设计）：递归 planner + 隔离 worker + 单向 handoff

- **三类角色**：
  - **root planner** 拥有用户指令的全部范围，负责理解当前状态、给出具体而针对性的任务。它**自己完全不写代码**，也**不知道任务被谁接走、有没有被接走**。
  - 当 planner 觉得自己的范围可以再切分时，spawn **subplanner**，后者以同样方式完全拥有被委派的那一窄片。这过程是**递归的**。
  - **worker** 领取任务并独自负责推到完成，对更大的系统一无所知，不与任何其他 planner 或 worker 通信，在**自己的仓库副本**上工作，完成后写一份**单一 handoff**，由系统提交给下达任务的那个 planner。
- **subplanner 的价值**：既能快速扇出 worker 提升吞吐，又能保证整个系统**始终被某个 agent 完全拥有和负责**；同时避免单一 planner 在大项目上被压垮、陷入隧道视野。
- **handoff 的内容**：不只写"做了什么"，还包含重要笔记、顾虑、偏离、发现、想法与反馈。planner 以 follow-up 消息的形式收到。
- **handoff 的系统性后果**：即使一个 planner"已完成"，它仍会持续收到更新、拉取最新仓库、继续规划与决策。信息沿链条向上传递给视野越来越全局的所有者，**却不需要全局同步或交叉通信的开销**——系统因此保持极度动态且自收敛。
- **删除 integrator**：原本加了一个 integrator 做全局质量控制，并缓解大量 worker 同时 push、rebase、解冲突、merge 的竞争。但它很快成为瓶颈——几百个 worker，一道所有工作都必须通过的闸门，作者直接称之为 "red tape"。改 prompt 无果后判定它并非必需，直接删掉以简化系统。
- **作者评价**："Interestingly, this does represent how some software teams operate today."

### 三、吞吐量与错误：两个刻意的取舍

#### 3.1 成绩单与取舍的代价
- 系统峰值约 **1,000 commits/hour**，一周内累计 **10M 次工具调用**，启动后无需任何人工干预。
- 这个吞吐量是**用刻意的取舍换来的**，主要有两处。

#### 3.2 取舍一：不追求每次 commit 都 100% 正确
- 强制"每次 commit 前必须 100% 正确"会造成严重串行化，有效吞吐大幅下降。
- 哪怕一个小错误——一次 API 变更或一个 typo——都会让整个系统停摆：worker 会越出自己的范围去修不相干的东西，大量 agent 一拥而上、互相踩踏地修同一个问题。
- 允许一些"松弛"（slack）后，agent 可以信任别的 agent 很快会修掉其他问题；因为系统对整个代码库有有效的所有权与委派，这个信任是成立的。
- 关键判断：**错误率保持小而恒定**——也许很少完全干净，但稳定可控，不会爆炸也不会恶化。
- 推论出的设计原则：理想的高效系统接受一定错误率，但需要一条最终的 "green" 分支，由一个 agent 定期打快照、在发布前做一次快速修复 pass。

#### 3.3 取舍二：容忍同步开销与局部湍流
- 多个 agent 有时会碰同一个文件、重构同一段代码。他们**不去彻底消灭这种情况，也不过度工程化**，而是接受短暂的"湍流"，让系统在一小段时间内自然收敛、自行安定。
- 代价是多花一些 token、制造局部竞争；收益是系统整体更简单：更容易对齐模型、不压垮模型、更容易管理和观测、摩擦更少、全局生产力更高。

### 四、基础设施的教训：单用户假设在几百个 agent 面前失效

#### 4.1 环境选择与热点转移
- 每次多 agent 运行都独占一台资源充裕的大机器，**刻意避免过早引入分布式系统的复杂度**。多数运行峰值在几百个 agent，正好把机器吃满而不超配；这个架构也让观测系统指标、共享和复制状态更容易。
- 限制 agent 的 RAM 用量之后，**磁盘成为新热点**。尤其在 monolith 项目上，几百个 agent 同时编译会产生每秒数 GB 的构建产物读写，显著拖累整个 harness 的吞吐。

#### 4.2 一个可迁移的教训
- **项目结构、架构决策和开发者体验会直接影响 token 与 commit 吞吐**——因为"与代码库打交道"（比如编译）主导了时间，而不是理想中的思考与写代码。
- 那些在单用户工作区里合理、不起眼的约束和低效，**在一台机器上几百个 agent 同时做同样的事时会格外扎眼**。
- 一个平凡解法是给每个 agent 一台机器；但作者认为**重新思考和重新设计这些原语与工具，存在唾手可得的巨大效率空间**：
  - git、Cargo 这类工具广泛使用共享锁，只是作为一种简单的并发控制机制——能不能把数据库等并发系统里成熟的机制搬过来？
  - 所有 agent 各持一份仓库副本，但大多数文件与构建产物是相同的——给这种典型"单用户"系统加上简单的写时复制（copy-on-write）与去重，能否像成熟的生产级存储系统那样，不必另建基础设施就拿到同等收益？

### 五、harness 稳定之后：指令成为瓶颈

#### 5.1 指令的重要性是被放大出来的
- 起初他们并没把指令当作首要目标，而是先追求一个稳定有效的 harness。但指令的重要性很快浮现。
- 本质上，他们面对的仍是一个典型的编码 agent，只是**多了数量级的时间与算力**——而这会放大一切，包括次优的、含糊的指令。
- 一句冷峻的判断：**"Ultimately, agents are still agents: trained to follow your instructions strictly, go down those paths, not change or override them, even if they're bad."**
- 项目推进中不断修改初始指令，因为看见"糟糕或欠规约的 spec"直接反映在产出质量上——**这不是 harness 的问题，harness 只是在精确地执行他们的指令**。

#### 5.2 浏览器项目的三个具体例子
- 最初的指令聚焦"实现规范、消灭 bug"，但 "spec implementation" 太含糊，agent 会一头扎进冷僻罕用的特性，而不是智能地排优先级。
- 他们**隐含地假设**性能会落在可接受范围内，实际上需要**显式指令和强制超时**才能逼 agent 在性能与其他目标之间做平衡。
- 在系统复杂部分，agent 写的代码可能有内存泄漏或死锁——人类会察觉，agent 未必；必须提供**显式的、基于进程的资源管理工具**，让系统能优雅恢复、更具防御性。

#### 5.3 两次更大的失败与修正
- 第一版不带 JavaScript 的简版浏览器**收敛到了一个无法演进为完整浏览器的架构**——这是初始规约的失败。
- 尽管被告知"从零造浏览器"，agent 仍拉进了一些本可自己实现的依赖，或把依赖当临时脚手架用；后来的一次运行**显式写清依赖哲学、列明哪些库不得使用**，问题被纠正。
- 那次运行同时做了一项**大重构：从 monolith 拆成许多自包含的 crate**。过程中仓库一度严重损坏，多 agent 系统却在几天内收敛回可用状态——说明系统能在完全破碎的状态下协作并保持智能，不会进一步退化或卡死。这次运行等待编译的时间也大幅减少，吞吐量数倍于之前。

#### 5.4 总结与方向
- **架构与指令都重要**。agent 有极强的工程能力，但会把指令执行到底，不论好坏。
- 难点在于拿捏"过窄的指标"与"无结构的自由"之间的平衡，以及判断什么是不言自明的、什么必须明说。
- 由此指向两个研究方向：**可引导性（steerability）与可观测性（observability）**。

### 六、prompt 优化的四条经验

#### 6.1 只教模型不知道的事
- 不要指导模型本来就会做的事，只指导它不会的（例如多 agent 协作）或与你的领域强相关的（例如怎么跑测试、你的部署流水线）。
- 类比：**把模型当作一个懂工程但不懂你的代码库与流程的、才华横溢的新员工**。

#### 6.2 约束比指令更有效
- "No TODOs, no partial implementations" 比 "remember to finish implementations" 管用。
- 模型默认就倾向做对的事，**约束是在为它划定边界**。

#### 6.3 避免打勾式（checkbox）心态
- 对更高层、更深入的任务，要给出关于你意图的详细说明。
- 但要记住：给出具体的待办清单会让模型专注于完成这些条目，而不是更广的范围，**也隐含地把没列出的东西降级了**。通常更好的做法是让模型自己判断、自己发挥能动性。

#### 6.4 谈"量"时给具体数字与范围
- "generate many tasks" 反而产出很少——保守的默认值、求稳、技术上又确实遵循了指令。
- =="Generate 20-100 tasks" 传达出"范围要大、要有野心"的意图==，他们观察到系统行为随之显著变化。

### 七、系统设计原则与更大的判断

#### 7.1 三条从研究中确立的原则
- **系统应当反脆弱（anti-fragile）**：同时运行的 agent 越多，出故障的概率越高；系统必须能承受个体 agent 失败，让其他 agent 恢复或尝试替代路径。
- **经验优先于假设**：用数据和观察来做调整，而不是带着"人类组织应该怎样"或"既有系统设计应该怎样"的先验进场。
- **显式地为吞吐量设计**：这意味着要在编码的其他方面做取舍——接受一个小而稳定、需要最终对账 pass 的错误率，而不是追求 100% 完全正确却让系统大幅变慢。

#### 7.2 关于"简单"的一个重要限定
- 这类系统做对了往往优雅而简单，**但在探索过多种方案之前，你并不知道是哪一种简单方案会奏效**。
- 当前设计以极小的开销运行，提供可用的线性 token 吞吐扩展，harness 本身已无需重大迭代。

#### 7.3 人机分工与两个更大的判断
- **品味、判断与方向来自人类，AI 是快速迭代和探索这项研究的强力放大器（force-multiplier）**。
- 这与所谓"良性 AI 循环"有相似之处——**用 AI 开发 AI**，模型、agent 与 harness 一起变好，自我馈入、越来越快。作者引用了那句 **"We shape the tools which shape us."**
- 这套架构与今天某些软件团队的运作方式有"诗意的相似"。而这些模型**并没有被显式地这样训练过**，这意味着它是**涌现行为**，也可能说明这本来就是组织软件项目的正确方式。
- Cursor 将继续研究极长时运行的 agent，研究发现会反哺产品；本次研究的一部分已向部分用户开放试用。

## 作者边界、反例与不确定性
- **关于"简单"的不确定性**：当前设计看似优雅而简单，但作者明确说，在探索过多种方案之前，**你并不知道是哪一种简单方案会奏效**——即简单是演化结果，不是预判起点。
- **错误率取舍得有限定条件**：容忍错误率的前提是错误率**小而恒定**（stable and constant），"稳定"是刚性的——不爆炸、不恶化；且必须有最终的 green 分支做修复 pass 作为补偿，否则就是单纯的质量滑坡。
- **涌现行为的判断留有余地**：架构与人类团队运作方式的相似性，作者用的是"诗意的相似"（poetic similarity），并说"这也可能说明"（it may also suggest）这本来就是正确方式——投成定论，而是勾画方向。
- **未解决的开放问题**：作者明确指出 steerability 与 observability 是下一步要研究的方向——即"如何把意图说清楚、如何看得见 agent 在做什么"仍未解决。工程结构确定了，但人与系统的接口仍是前沿。
- **基础设施改造只是提议**：对 git、Cargo 做写时复制与去重、借鉴数据库并发机制，是作者提出的"唾手可得的巨大效率空间"（low-hanging opportunities），但文章并未给出实现或验证，属于判断性方向而非已验证的结论。
