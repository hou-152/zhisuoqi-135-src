# Skill Issue: Harness Engineering for Coding Agents

## 一句话主旨
Coding agent 的失败多是配置问题，应从 harness 各配置点系统性榨取模型能力。

## 作者试图回答的问题
核心问题：不从「等更强模型」出发，如何从今天的模型身上榨出最多的东西？关联子问题：harness 是什么、它包含哪些配置点、每个配置点怎么用、为什么「把上下文窗口做大」不是解法。

## 三级论证骨架
### 一、立论：失败根因是配置，不是模型
#### 1.1 作者反复观察到同一结论
- 在几十个项目、几百次 agent session 之后，反复得到的结论是：这不是模型问题，这是配置问题。
  - 失败形态包括：无视指令、未经允许执行危险命令、在最简单任务上原地打转、团队交付垃圾代码（作者承认自己也交付过一点）。
  - 每次本能反应都一样：等 GPT-6、等指令遵循变强、等小众库进入训练数据。
#### 1.2 模型变强不会消除失败
- 模型更聪明后，我们会把更大更难的问题交给它，它继续以出乎意料的方式失败。
  - 对非确定性系统而言，意料之外的失败模式是根本性问题。
#### 1.3 harness 是 agent 的配置面与运行时
- skills、MCP servers、sub-agents、memory、agentfile 等技术上分立的概念，同属 coding agent 的配置面，称为 harness。
  - 理解方式：agent 的运行时，或者说 agent 的外设——模型靠什么与环境交互。
- harness engineering 定义（Viv 提出）：利用这些配置点定制和改进 coding agent 输出质量与可靠性。
  - Mitchell Hashimoto 的定义：每当你发现 agent 犯了一个错，就花时间工程化出一个解法，让 agent 再也不会犯这个错。
  - 这句话把 agent 可靠性从「祈祷模型升级」变成可积累、可迭代、可交付的工程活：失败不是等待的理由，是配置的输入。

### 二、定位：harness 工程是上下文工程的子集
#### 2.1 与上下文工程的关系
- harness 工程明确定位为 context engineering（由 Dex 在 12-factor agents 中提出）的子集。
  - 更精确表述：是上下文工程中主要通过 harness 配置点精细管理 coding agent 上下文窗口的那一部分。
- 它回答的一串问题：怎么给 agent 新增能力、怎么教它训练数据里没有的代码库知识、怎么在系统消息里写 CRITICAL 之外获得确定性、怎么适配特定代码库、怎么在魔法提示词之外提高成功率、怎么防止上下文窗口膨胀或被坏上下文污染。
  - skills、MCP servers、sub-agents、hooks、back-pressure 机制都是战术解法。

### 三、张力边：模型可能对 harness 过拟合
#### 3.1 常见反驳：「官方 harness 最好」
- 前沿编程模型在自家 harness 上做后训练（Claude 在 Claude Code、GPT-5 Codex 在 Codex），所以最好别改配置。
  - 佐证：Codex 模型与 Codex harness 的 apply_patch 工具耦合极深，开源替代品 OpenCode 不得不专门为 GPT/Codex 模型加一个 apply_patch 工具模仿 Codex harness；Claude 等模型在 OpenCode 里照旧用 edit 和 write。
#### 3.2 但这是双刃剑
- 模型也可能对自己的 harness 过拟合。
  - Viv 引用 Terminal Bench 2.0 数据：Opus 4.6 在 Claude Code 里排第 33，换到后训练时没见过的 harness 里升到第 5（上下浮动约 4 位）。
- 作者的判断：「用官方 harness 最好」是经验判断而非定律；harness 是变量，不是常量。

### 四、agentfile：先调确定性注入
#### 4.1 优先定制仓库顶层 agentfile
- 这些 markdown 文件会被 harness 确定性地注入 agent 的系统提示。
  - 优先度：在碰任何其他 harness 配置点之前，通常值得先调这个。
#### 4.2 ETH Zurich 研究的误读与正读
- 研究在多个仓库测试了 138 个 agentfile，结论是大多数无益甚至有害；很多人据此说「这东西没用」。
  - 研究具体发现：LLM 自动生成的 agentfile 损害性能，且多花 20% 以上成本；人工撰写的只带来约 4% 提升；agent 处理上下文文件指令多花 14–22% 推理 token，步数更多、工具调用更多，解决率没提高；代码库总览和目录清单完全无用——agent 自己能摸清仓库结构。
- 作者的读法：该研究恰恰验证了他们的主张。
  - 对应原则：避免自动生成（要精心撰写）；指令越少越好（不该省的不省，但能少写就少写）；用渐进披露，不塞无关上下文；内容要简洁且普遍适用。
  - 自家 agentfile 不到 60 行。

### 五、MCP server：接工具，但要防指令预算烧光
#### 5.1 基本用途与风险
- 主要用途是把工具插进 coding agent，让能力超出文件读写和 bash。
  - MCP 规范里的 resources、prompts、elicitations 等特性在各家客户端和 harness 里普遍支持得不好。
- 关键机制：接入后，可用工具列表、描述和调用参数被注入系统提示，因此 server 可以通过工具描述影响 agent 行为。
  - 安全警告：工具描述进了系统提示，绝不要连接你不信任的 MCP server（提示注入入口）；用 npx 或 uvx 本地运行的 STDIO server，即使没有提示注入也能在主机上执行代码。
#### 5.2 工具过多进入笨蛋区
- 插入的 MCP 工具一多，上下文窗口被工具描述填满，更快推进「笨蛋区」。
  - 指令预算同样重要：每一条无关工具描述都是 agent 必须处理却毫无收益的指令。
  - Anthropic 发布实验性 MCP tool search 在工具过多时向 Claude 渐进披露工具。
  - 结论：不在主动使用、又提供大量工具的 server，关掉。
#### 5.3 有成熟 CLI 时优先用 CLI
- 如果某个 MCP server 复制的功能已有训练数据充分覆盖的 CLI，直接提示 agent 用 CLI 效果更好。
  - GitHub、Docker、大多数数据库属于此类：模型本来就会用，还能与 grep、jq 组合提高上下文效率。
- HumanLayer 实操：用 Linear MCP server 只用一小部分工具，改为写一个包装 Linear API 的小 CLI，返回极度精简响应，并在 agentfile 里给 6 条示例用法（取 issue、列 issue、加评论、加链接、改状态、取分支名、取工单图片）。
  - 收益：省下系统提示里成千上万个 MCP 工具定义 token，以及更多冗长 MCP 响应 token。

### 六、skills：装可复用知识与工具，核心是渐进披露
#### 6.1 定义与安全
- skills 最初由 Anthropic 为 Claude Code 引入，后成为开放标准，Codex、OpenCode 等已支持。
  - 作者关心的是它为什么有用，不是怎么组织。
- 安全警告：技能注册表已抓到分发过数百个恶意 skill；要像对待 npm install random-package 一样读清楚你装了什么。
  - ClawHub、skills.sh 等注册表能在你机器上执行任意代码。
#### 6.2 渐进披露是核心价值
- 把每条指令、每个工具都塞进系统提示，agent 越用越糟——还没开工，指令预算就烧光了。
  - skills 的解法：只有当 agent 判断（或你替它判断）需要时，才拿到那部分指令、知识或工具。
- 激活机制：skill 目录下 SKILL.md 作为一条 user message 载入上下文，agent 同时被告知文件所在目录，SKILL.md 可进一步说明目录里捆绑了什么（模板文件、若干 CLI 等）。
  - 可玩得更深：一个 skill 里放多个 markdown 文件，各承载不同功能，主 SKILL.md 告诉 agent 其他文件是什么、什么时候读。
#### 6.3 现实限制
- 没法把 MCP server 或自定义 agent 工具直接打包进 skill；要写成可执行文件、CLI、NPM 包等随 skill 分发，或指示 agent 去安装。
  - 例：与其配 Playwright MCP server，不如给 agent 一个用 BrowserBase 或 Vercel 浏览器 CLI 的 skill。

### 七、sub-agents：上下文控制与隔离
#### 7.1 真正用途是上下文控制
- 流行的「前端工程师 / 后端工程师 / 数据分析师子 agent」那套不管用；真正管用的是把 sub-agents 用于上下文控制。
  - 机制：sub-agent 把一整个 session 的工作封装起来，派发方只看到自己写的提示和最终结果；中间工具调用、返回、其他消息一概不进入父 agent 上下文窗口。
#### 7.2 上下文防火墙与多 session 连贯性
- 复杂、棕地、企业级代码库上，一个问题需要非常多个上下文窗口才能解决时，sub-agents 是跨多个 session 维持连贯性的关键。
  - 它们扮演上下文防火墙：离散任务在隔离窗口里跑，中间噪音不累积到父线程。
  - 把工作拆成离散任务派给 sub-agents，是让主线程留在聪明区的办法；研究、实现等吃上下文的日常工作都这么干。
#### 7.3 反驳「把上下文窗口做大就行」
- Chroma 的 context rot 研究：在 18 个模型上大海捞针任务，结论是上下文越长性能越差，简单任务也不例外。
  - 当问题与上下文中相关信息的语义相似度低时衰减更陡；每次无关工具调用、grep 结果、文件读取都是潜在干扰项，干扰效应在长上下文里会叠加。
- 扩展上下文版本通常不是指令预算更大的更大模型，而是同一个模型加聪明数学（例如 YaRN）延长可注意序列长度。
  - 更大窗口不会让模型更擅长找针，只是把草堆堆得更大；对使用者而言，只是能塞进更多指令，把自己推得离笨蛋区更深。
- 结论：如果你觉得自己需要更长的上下文，可能真正需要的是更好的上下文窗口隔离。
  - sub-agents 结构上解决：每个拿到全新、小、高相关的上下文窗口和全新指令预算，只有浓缩结果回流父 agent——可以把很多个上下文窗口缝起来解同一个问题。
#### 7.4 适合的任务与返回格式
- 适合任务：定位代码库中的定义或实现；分析代码库找某类工作模式；追踪信息流向（如跨服务边界追请求）；其他代码、文档、网页研究类任务。
  - 特点：问题直白、答案简单，但需要大量不想留在父 session 的中间工具调用。
- 返回要遵循渐进披露：给答案同时以 filepath:line 或 URL 附出处，父 agent 不必接触所有原始材料，需要确认时又有线索。
- Claude Code 等内置任务专用 sub-agent：用于代码库探索的 Explore、执行冗长 bash 并提炼信息回父 agent 的 Bash；另一些需用户手工配置。
#### 7.5 成本控制与不支持时的变通
- sub-agents 可省钱：父 session 用昂贵模型（Opus）做规划编排，每个 sub-agent 用更便宜更快的 Sonnet 或 Haiku——任务更小更离散，够用即可，没必要为一次 grep 烧 Opus token。
- 有些 harness 不支持 sub-agents（Codex 直到最近才有，仍实验性）。
  - 变通：自己写 MCP server，提供「用父 agent 给的提示启动新 agent session、并返回最终回复」的工具。
  - 作者警告：在本身支持 sub-agent 的 coding agent 上再走 MCP 派发，原生 sub-agent 也能再派发 sub-agent，会变成不可预测的传话游戏。
- 写 sub-agent 系统提示必须把角色范围界定清楚：该做什么、不该做什么；返回什么信息、以什么形式返回；给它哪些工具。
  - 很多 harness 有 MCP 工具调用超时，用此模式可能需调大超时。

### 八、hooks：确定性控制流
#### 8.1 概念与能力
- Claude Code 有 hooks：在特定事件发生、agent 生命周期各节点自动执行的用户自定义命令或脚本。
  - OpenCode 的 plugins 是同类概念；Codex 没有对应物。
- 类似 git hooks，但灵活得多：可加新功能、集成外部服务、自动化例行动作、修改权限、配置默认行为。
- 一个 hook 一般能做到：事件发生时静默自动执行；在工具被调用时运行并向 agent 返回额外上下文；在 agent 收尾前把构建或类型错误抛给它，逼它继续干活直到解决。
#### 8.2 常见用例
- 通知：agent 完成或需要人介入（如审批挂太久）时播放提示音。
- 审批：基于输入值和比默认权限模型更有表达力的规则自动批准或拒绝工具调用，如自动拒绝任何试图跑数据库迁移的 Bash，要求 agent 让用户自己跑。
- 集成：完成后发 Slack、创建 GitHub PR、拉起预览环境。
- 验证：框架和仓库能在几秒内跑完类型检查或构建，就在每次停下时跑一遍，把错误暴露给它。
#### 8.3 示例与核心原则
- 示例 hook：Claude 停止时运行 biome 格式化和 TypeScript 类型检查，有错误抛给 Claude，无则静默退出。
  - 细节：biome 改写文件后即使全部修好也以退出码 1 结束，所以跑两遍，第二遍无事可做时才返回 0。
- 精髓是成功彻底静默：成功时什么都不进上下文；失败只暴露错误，并用退出码 2 告诉 harness 重新唤起 agent，先修好再收工。

### 九、back-pressure：提高成功概率的自我验证
#### 9.1 核心命题与关键限定
- 用 coding agent 成功解决问题的概率，与 agent 验证自己工作的能力强相关。
  - 在仓库里花大量时间建设测试和 back-pressure 机制，仍是投入产出比最高的事情之一。
- 关键限定词是「上下文高效」。
  - 早期教训：让 agent 每次改动后跑完整测试套件，4000 行通过的测试输出把上下文窗口冲垮，agent 跟丢真正任务，开始对刚读过的测试文件产生幻觉。
#### 9.2 现在的做法
- 吞掉输出、只暴露错误；构建同理——成功静默，只有失败才产生冗长输出。
  - 使用机制的说明写在 agentfile 里，写得简洁；一部分打包进 skill，走渐进披露。

### 十、收尾：什么没用，什么有用
#### 10.1 偏向交付，不预先优化
- 诚实警告：你完全可能把时间花在优化配置上，比真正用它交付代码还多——作者说他们就经历过。
  - 取向：只在 harness 配置确实能更快交付更高质量代码时才投入；agent 失败时就工程化一个解法让它不再那样失败，但不预先找问题解决。
#### 10.2 没用的做法
- 在真正遇到失败之前就试图设计出理想的 harness 配置。
- 「以防万一」装几十个 skill 和 MCP server。
- 每次 session 结束都跑完整测试套件（5 分钟以上）——应该跑子集。
- 微调哪个 sub-agent 能访问哪些工具：带来大量工具抖动，结果更差；多数 coding agent 也没有健全的相应配置面。
#### 10.3 有用的做法
- 从简单开始，只有当 agent 真的失败时才加配置。
- 设计、测试、迭代，并扔掉没用的东西（作者扔掉的 hooks 比今天在用的多得多）。
- 通过仓库级配置把久经考验的配置分发给整个团队。
- 优化迭代速度，而不是「第一次就一把过」的概率。
- 先给 agent 一整套能力（如 Linear），等摸清真正需要什么之后再仔细裁剪暴露给模型的部分。
- 全文收束：下次 coding agent 表现不如预期，在怪模型之前先查 harness；agentfile、MCP server、skills、sub-agents、hooks、back-pressure——杠杆大多藏在这里；模型大概率没问题，这只是个 skill issue。

## 作者边界、反例与不确定性
- 作者明确承认自己交付过垃圾代码，并承认团队经历过「花在调配置上的时间比交付代码还多」，因此给出偏向交付的原则：只在配置确实加速交付时才投入，不预先找问题解决。
- 「用官方 harness 最好」被否认为定律，但作者未彻底否定官方 harness 的优势：Codex 与 apply_patch 的深度耦合说明原生配置确有作用，Terminal Bench 2.0 的排名变化又说明过拟合可能是路径依赖——两者构成张力，不给出单边结论。
- MCP 规范中 resources、prompts、elicitations 等特性被认定支持得不好，是作者的经验判断，未展开各家客户端的具体支持现状。
- Eth Zurich 研究中「人工撰写的 agentfile 只带来约 4% 提升」是原文引用的研究结果，作者将其解读为对自己原则的验证，但研究本身对 agentfile 总体评价偏负面；这一张力原文未再调和。
- sub-agent 的变通实现（通过 MCP server 派发）被作者标记为非常粗糙，并警告会产出不可预测的传话游戏；这是作者自己给出的边界和反例。
- 作者提到微调 sub-agent 工具访问权限的配置面大多不健全，但未深入说明是哪些 harness、缺什么能力。
- 对 skills 的安全警告（恶意 skill 分发、任意代码执行）属于风险提示，作者未提供缓解方案之外的补救路径（仅「读清楚你装了什么」，在实践中如何审计未展开）。
- 文章中引用的 Terminal Bench 2.0 排名有明确浮动范围（约 4 位），作者保留了这一不确定性；Chroma 的 context rot 研究本身被作者承认与 agentic coding 差别不小，但结论与体感一致。
