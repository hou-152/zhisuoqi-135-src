# The Anatomy of an Agent Harness

## 一句话主旨
决定生产级 agent 表现的不是模型，而是包裹模型的 harness。

## 作者试图回答的问题
为什么同一模型在不同 agent 产品中表现差异巨大？生产级 agent 由哪些非模型基础设施构成，架构师如何在单/多 agent、上下文、验证、权限、工具范围、harness 厚度之间取舍？模型变强后，harness 会消失吗？

## 三级论证骨架

### 一、总论点：harness 才是硬工程，模型不是唯一变量
#### 1.1 TerminalBench 证据
- 仅更换 harness，就能让同一个 LLM 在榜单上移动 20+ 位，从榜外跃升到 rank 5。
  - 结论：harness 而非模型，才是硬工程真正所在。
  - 结语式判断：agent 失败时，先看 harness，不要只怪模型。
#### 1.2 agent 与 harness 的区分
- agent 是用户看到的涌现行为：目标导向、会用工具、能自我纠错。
- harness 是产生这个行为的机器。
  - Vivek Trivedy 的公式："If you're not the model, you're the harness."
  - 说搭了个 agent，本质是搭了个 harness 并对准一个模型。

### 二、harness 的定位：LLM 的操作系统与三层工程
#### 2.1 定义
- harness 指包裹 LLM 的全部软件基础设施：orchestration loop、tools、memory、context management、state persistence、error handling、guardrails。
- 术语在 2026 年初正式化，但概念早已存在。
  - Anthropic：Claude Agent SDK 是 "the agent harness that powers Claude Code"。
  - OpenAI Codex 团队把 agent 等同于 harness，指让 LLM 好用的非模型基础设施。
#### 2.2 冯·诺依曼式 OS 类比
- 原始 LLM 是没有 RAM、磁盘、I/O 的 CPU。
- context window = RAM；外部数据库 = 磁盘；工具集成 = 设备驱动；harness = 操作系统。
  - "We have reinvented the Von Neumann architecture"。
#### 2.3 三层工程
- Prompt engineering：打磨给模型的指令。
- Context engineering：管理模型看到什么、何时看到。
- Harness engineering：囊括以上两者，加上整个应用基础设施——tool orchestration、state persistence、error recovery、verification loops、safety enforcement、lifecycle management。
  - harness 不是 prompt 外壳，而是让自主 agent 行为成为可能的完整系统。

### 三、生产级 harness 的组件与循环
#### 3.1 12 个核心组件（原文列 11 项，第 12 项对应 Lifecycle/整体治理层）
- Orchestration Loop：心跳，实现 TAO 即 ReAct 循环。Anthropic 称 runtime 为 "dumb loop"，智能在模型里，harness 只管轮次。
- Tools：agent 的手，以 schema 注入 LLM context。Claude Code 分六类：文件操作、搜索、执行、网络访问、代码智能、sub-agent spawning。
- Memory：多时间尺度。
  - 短期是单会话对话历史；长期跨会话持久化，如 Anthropic 用 CLAUDE.md + MEMORY.md，LangGraph 用 namespace 化 JSON Stores，OpenAI 用 SQLite/Redis Sessions。
  - Claude Code 三层分级：轻量索引约 150 字符/条常驻 → 按需详细主题文件 → 原始 transcript 仅通过搜索访问。
  - 关键原则：agent 把自己的 memory 当 hint，行动前必须对照实际状态验证。
- Context Management：很多 agent 死在这里。
  - 核心问题是 context rot：关键内容落在窗口中段时，模型性能下降 30%+（Chroma 研究 + Stanford "Lost in the Middle"）。
  - million-token 窗口也会随 context 变长而降低指令跟随能力。
  - 生产策略：compaction、observation masking、just-in-time retrieval、sub-agent delegation；Anthropic 目标："smallest possible set of high-signal tokens"。
- Prompt Construction：分层装配 system prompt + 工具定义 + memory 文件 + 对话历史 + 当前用户消息。
  - OpenAI Codex 严格优先级栈：server system message ＞ 工具定义 ＞ 开发者指令 ＞ 用户指令（级联 AGENTS.md，32 KiB 上限）＞ 对话历史。
- Output Parsing：现代 harness 用 native tool calling 返回结构化 tool_calls，而非解析 free-text。有 tool call 就执行并继续，没有就是最终答案。
- State Management：
  - LangGraph：类型字典在图节点间流转，reducer 合并更新，super-step 边界 checkpoint，支持中断恢复与时间旅行调试。
  - OpenAI 四选一：application memory / SDK sessions / Conversations API / previous_response_id chaining。
  - Claude Code：git commits 作为 checkpoint，progress 文件作为结构化 scratchpad。
- Error Handling：错误会复利式放大——99% 单步成功率 × 10 步 = 90.4% 端到端成功率。
  - LangGraph 区分四类：transient（退避重试）、LLM-recoverable（把 error 作为 ToolMessage 让模型调整）、user-fixable（中断请求人类输入）、unexpected（上抛调试）。
  - Stripe 生产 harness 重试上限 = 2。
- Guardrails and Safety：
  - OpenAI 三级：input guardrails、output guardrails、tool guardrails；tripwire 触发立即停机。
  - Anthropic 把权限执法与模型推理在架构上分开——模型决定尝试什么，工具系统决定允许什么。
  - Claude Code 独立管理约 40 个工具能力：项目加载时建立信任 → 每次工具调用前权限检查 → 高危操作显式用户确认。
- Verification Loops：区分玩具 demo 与生产级 agent 的关键。
  - 三种方式：rules-based（测试/lint/类型检查）、visual（Playwright 截图）、LLM-as-judge。
  - Boris Cherny：给模型一个验证自己工作的方式，质量提升 2-3 倍。
- Subagent Orchestration：
  - Claude Code 三种执行模型：Fork（父 context 字节级副本）、Teammate（独立终端面板 + 文件邮箱）、Worktree（独立 git worktree，按 agent 隔离分支）。
  - OpenAI：agents-as-tools 与 handoffs；LangGraph：子 agent = 嵌套状态图。
- Lifecycle/整体治理层：由上述各部件共同构成，落在文末架构选择中展开。
#### 3.2 7 步循环 walkthrough
- Prompt Assembly：装配完整输入，重要 context 放首尾。
- LLM Inference：调模型 API。
- Output Classification：无 tool call 结束；有 tool call 执行；handoff 切换 agent 重启。
- Tool Execution：校验参数、检查权限、沙盒执行；只读可并发，可变串行。
- Result Packaging：格式化为 LLM 可读消息；错误作为 error result 返回以便自纠。
- Context Update：追加到历史；逼近窗口上限时触发 compaction。
- Loop：回到 Step 1，重复直到终止。
- 终止条件分层：模型无 tool call 的回复 / 超轮次上限 / token 预算耗尽 / guardrail tripwire / 用户中断 / 安全拒答。
#### 3.3 跨 context window 长任务：Ralph Loop
- Initializer Agent：初始化环境（init 脚本、progress 文件、feature 清单、初始 git commit）。
- Coding Agent：后续每个 session 先读 git log 和 progress 文件回忆自己干到哪，选最高优先级未完成 feature，干活 → commit → 写摘要。
- 文件系统提供跨 context window 的连续性。

### 四、主流框架如何落地
#### 4.1 Anthropic
- Claude Agent SDK 用一个 query() 函数暴露全部，返回 async iterator；runtime 是 "dumb loop"。
- Claude Code 用 Gather-Act-Verify 循环：查上下文 → 改文件跑命令 → 跑测试查输出，反复。
#### 4.2 OpenAI
- Agents SDK 的 Runner 类三种模式：async、sync、streamed。
- code-first：workflow 用原生 Python 表达，不是 graph DSL。
- Codex harness 三层架构：Codex Core + App Server + 客户端（CLI/VS Code/web），共享同一 harness；这也解释 Codex 模型在 Codex surfaces 上表现比在通用 chat 里更好。
#### 4.3 LangGraph
- 显式状态图：两节点（llm_call + tool_node）一条条件边。
- 由 LangChain AgentExecutor（v0.2 弃用，因难扩展、缺多 agent 支持）演化而来；Deep Agents 明确使用 "agent harness" 术语。
#### 4.4 CrewAI 与 AutoGen
- CrewAI：基于角色的多 agent 架构——Agent（harness 包裹 LLM，由 role/goal/backstory/tools 定义）+ Task + Crew；Flows 层提供 "deterministic backbone with intelligence where it matters"。
- AutoGen（演化为 Microsoft Agent Framework）：对话驱动编排的开创者；三层架构 Core/AgentChat/Extensions；五种编排模式：sequential、concurrent（fan-out/fan-in）、group chat、handoff、magentic（manager agent 维护动态任务账本协调专家）。

### 五、设计哲学：harness 是临时的，但不会消失
#### 5.1 脚手架隐喻
- 建筑脚手架是临时基础设施——它不做建造，但没它工人上不去。
- 关键洞察：建完楼，脚手架就拆掉。模型越强，harness 复杂度应越小。
  - Manus 六个月重写五次，每次都在删复杂度：复杂工具定义 → 通用 shell 执行；管理 agent → 简单结构化 handoff。
#### 5.2 协同进化原则
- 模型现在是带着特定 harness 一起 post-train 的；Claude Code 的模型就是用它的 harness 训出来的。
- 换工具实现就会掉分——紧耦合。
- "Future-proofing test"：若模型升级后 harness 不需要加复杂度，性能就随之提升，那么设计是好的。
#### 5.3 每个 harness 架构师的 7 个决策
- 单 agent vs 多 agent：Anthropic 和 OpenAI 都说先把单 agent 用到极致。多 agent 带路由开销、handoff 会丢 context；只有工具过载 ＞ 约 10 个重叠工具、或任务域明显分离时才拆。
- ReAct vs plan-and-execute：ReAct 每步都交织推理与行动，灵活但单步贵；plan-and-execute 分开。LLMCompiler 比顺序 ReAct 快 3.6x。
- Context window 管理策略：时间清理 / 对话摘要 / observation masking / 结构化笔记 / 子 agent 委派。ACON 研究：token 减 26–54%，准确率保持 95%+；优先保留推理轨迹而非原始工具输出。
- 验证循环设计：computational verification（测试、lint）给确定性 ground truth；inferential verification（LLM-as-judge）抓语义但加延迟。Martin Fowler Thoughtworks 团队框架：guides（feedforward，行动前引导）vs sensors（feedback，行动后观察）。
- 权限与安全架构：Permissive（快但险）vs Restrictive（安全但慢），选择取决于部署场景。
- 工具范围策略：工具越多往往性能越差。Vercel 从 v0 砍掉 80% 工具反而更好；Claude Code 靠 lazy loading 做到 95% context 削减；只暴露当前步骤最小必要工具集。
- Harness 厚度：多少逻辑放 harness、多少交给模型。Anthropic 押注薄 harness + 模型升级；图式框架押注显式控制。Anthropic 会随新模型版本内化规划能力，主动从 Claude Code 的 harness 中删除规划步骤。
#### 5.4 Harness 就是产品
- 同一个模型，不同 harness 设计，可以产生截然不同的表现；TerminalBench 证据：仅换 harness，agent 在排行榜上移动 20+ 位。
- harness 不是已解决的问题，也不是 commodity 层——硬工程在这里：把 context 当稀缺资源管理、设计能在错误复利前抓住它们的验证循环、搭既提供连续性又不幻觉的记忆系统、在造多少脚手架 vs 留多少给模型之间下架构赌注。
- 趋势：随模型变强，harness 在变薄，但不会消失——最强模型也需要东西去管 context、执行 tool call、持久化状态、验证工作。
- 结语："The next time your agent fails, don't blame the model. Look at the harness."

## 作者边界、反例与不确定性
- 原文称生产级 harness 有 12 个组件，但正文实际列出 11 个；第 12 项以 Lifecycle/整体治理层补足，属于原文自身未完全展开的清单。
- TerminalBench 证据在材料中只有结论式表述：同模型换 harness 排名移动 20+、从榜外到 rank 5；未给出具体模型、基线、harness 变体与评测设置，无法据此判断效应成立的条件。
- “模型越强 harness 越薄”“harness 不会消失”是作者的趋势判断，不是材料已证明的定律；Manus、Anthropic 删规划步骤等是支持性案例。
- 多 agent、厚/薄 harness、权限策略等均被呈现为取决于场景与架构赌注的选择，不存在统一最优解。
- 概念网络图为 Codex 据原文概念网络文字整理，非原文配图，可作为辅助，不增加作者原始论据。
