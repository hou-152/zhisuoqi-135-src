# 一次关于 Loop 的工程争论

## 一句话主旨
Loop 是 AI 编程的下一层抽象，但真正资产是它调用的 skill。

## 作者试图回答的问题
2026 年 AI coding 圈出圈的一句话——"不要再直接 prompt coding agents，而是设计会 prompt agents 的 loops"——在工程实践里到底指什么？作者连带的判断是：难点常不在模型调用，而在循环何时停止、如何观测、怎样验收。

## 三级论证骨架

### 一、争论起点：一句话出圈，但定义不清
#### 1.1 Steinberger 的核心说法与传播反差
- 2026 年 6 月 7 日，Steinberger 提出"工程师不应再只是 prompt coding agents，而应设计会 prompt agents 的 loops"。
  - 反差：几乎所有人都在引用 loop，但很多人无法说明它在工程实践里是什么。
#### 1.2 作者的位置与争论真主题
- 作者自己每晚运行 loop，让 agents 在睡眠时间给约三十个开源仓库打开 PR。
- 争论真主题不是"prompt 过时"，而是工程师位置变化：从循环内部的 prompt 发送者，移动到循环外部的系统设计者。
- 作者认为最准确的评论来自一条区分：不是 ralph 或 goal 这种单 agent 循环，而是持续编排 loop，负责监督其他线程或 agents。

### 二、Boris Cherny 的定义：model 成为 subroutine
#### 2.1 朴素定义
- Boris 在 WorkOS 的 Acquired Unplugged 活动上称：他不再直接 prompt Claude，而是写正在运行的 loops，由 loops 去 prompt Claude 并判断下一步。
- 作者给出的朴素定义：loop 是一个小程序，替你 prompt coding agent，读取 agent 的产物，判断是否完成；没完成就再次 prompt。
- 这个结构里，人类是循环的作者，模型是系统中的一个 subroutine。
#### 2.2 Boris 的三阶段演进
- 一年前靠 autocomplete 手写代码 → 随后同时跑五到十个 Claude sessions 并逐个 prompt → 现在写 loops，让几百个 agents 读取 GitHub、Slack、Twitter 并决定下一步构建什么。
- 强烈信号：Boris 称最近 30 天给 Claude Code 的贡献 100% 由 Claude Code 写出，落地 259 个 PR。
- 作者强调 Boris 并不是说工程师消失了：决定做什么、理解客户、协调团队仍更重要，变化只是抽象层级从"写代码"上升到"写会写代码的东西"。

### 三、loop 是一条从 ReAct 到编排的谱系
#### 3.1 回复混乱源于 loop 至少覆盖五种层级
- 第一阶段 2022 ReAct：模型推理、调用工具、读取工具结果、再重复，通常一模型一循环，并有人类监督。
- 第二阶段 2023 AutoGPT：给模型一个目标让它自我 prompt 和推进；失败模式是长时间空转，让很多人形成"agents are a toy"的印象。
- 第三阶段 2025 Geoffrey Huntley 的 ralph loop：一个简单到粗暴的 bash 循环，反复把同一个 prompt 文件喂给 agent。
#### 3.2 ralph 的真正创新与后续两个阶段
- ralph 的创新不是复杂性，而是上下文纪律：每次迭代重置到固定 anchor files，而非让对话上下文无限增长。
- 第四阶段 2026 春天，Codex 和 Claude Code 把 ralph 式模式产品化为 /goal：持续运行，直到小验证模型确认任务完成。
#### 3.3 第五阶段才是新东西
- loop 成为工作单元，而不是单次任务；可并发监督其他 loops；调度替代人类 kickoff；git-backed state 和 crash recovery 让它在基础设施时间里持续运行。
- 结论：single-agent ralph loop 已是旧帽子，新层级是 multi-agent orchestration loop。

### 四、为什么它不只是"cron 换皮"
#### 4.1 怀疑者的说法与作者的一半认同
- 若 loop 只是定时运行的东西，那确实就是 cron，Boris 的 loop 也可以真的跑在 cron 上——作者认为这只说对了一半。
#### 4.2 关键区别是 decision-maker
- 传统 cron job 执行固定脚本；agent loop 中间有一个会读取当前状态、选择下一步、执行、检查并决定是否继续的模型。
- 区别不在调度，而在 decision-maker：不是硬编码分支，而是模型每个 tick 根据状态做判断。
- 多个 loop 被堆叠、由一个 loop 分派和监督其他 loop、共享持久状态时，就表达了 cron 无法表达的动态编排。
- 作者的诚实表述：loop 不是魔法，也不只是 cron，它是 cron plus a decision-maker in the body，真正的工程难点是包住这个决策者，让它不会冲出边界。

### 五、实践入口与深水区
#### 5.1 最小入口与 Boris 的五条建议
- 最小入口是 Claude Code 的 /loop：让它 babysit 所有 PR，自动修复 build 问题，评论出现时用 worktree agent 修复。
- Boris 提出五条运行 Opus 数小时或数天的建议：开启 auto mode 减少权限中断；使用动态 workflow 编排大量 agents；用 /goal 或 /loop 持续推进；在 cloud 中运行 Claude Code；给 Claude 端到端自验证能力。
- 作者强调第五条最关键：一个 loop 的可信度取决于它检查自己工作的能力。
#### 5.2 面向普通用户的理解与深水区案例
- 面向普通用户：AI coding 正从 one-off prompts 转向 background operations，人类写意图和停止条件，loop 每个 tick 再去 prompt agent。
- 深水区是 Steve Yegge 的 Gas Town：二三十个 Claude Code instances 由 Mayor agent 协调，patrol agents 连续运行，状态存在 git 里，崩溃后还能恢复。
- 作者把 Gas Town 视为"持续编排 loop 监督其他线程"的现实版本，而不是概念幻灯片。

### 六、反馈和验证是 loop 能否工作的核心
#### 6.1 verification 是最快增长的子主题
- 作者反复强调，最快增长的子主题不是 orchestration，而是 verification。
- 如果 open loop 只会写代码、没有反馈，它会变成制造 confident mistakes 的机器。
#### 6.2 可靠 loop 必须把反馈放进循环内部
- 可靠 loop 必须写、运行、读取结果、修正。
- 作者引用 roborev 这类背景 commit review 工具作为方向：每个 commit 都被审查，结果在上下文仍然新鲜时反馈给 agent。
- 要点：loop 本身不是魔法，loop 里的 feedback 才是让它产生工程价值的部分。
- 因此设计 loop 不能只设计 prompt，还要设计验证门禁、失败回路、回滚策略、日志、状态和停止条件。

### 七、成本从写代码转移到管理 loop
#### 7.1 昂贵部分变成管理 agent loop
- 当模型能低成本写出大量代码时，昂贵的部分变成管理 agent loop。
- 一个工程师的讽刺说法：他今年交付的每个 AI agent 本质上都是 for-loop、一次 LLM call，以及包住 JSON parsing 的 try/catch，真正 agentic 的地方只是月底的 Anthropic 账单。
- Uber 对 Claude Code 和 Cursor 给工程师设下每人每工具每月 1500 美元上限，被作者用来说明成本现实。
#### 7.2 最怕的失败模式与三种 hard stop
- 生产环境最怕的失败模式是不会停止的 loop：无限迭代、无进展但持续消耗 token 或预算。
- 严肃的 loop 设计收敛到三种 hard stop：最大迭代次数、no-progress detection、token 或 dollar budget ceiling。
- 作者区分浪漫版本和生产版本：浪漫版本是让一千个 agents 一夜建公司；生产版本是写 loops，并把大量工作花在确保它们会停。

### 八、最终答案：loop 是管道，skill 才是资产
#### 8.1 结论落在 skill
- loop 是 plumbing，真正的资产是它调用的 skill。
- Steinberger 关于 loops 的另一半观点：如果一件事做超过一次，就把它变成自动化 skill；如果一件事很难，做完后也把它变成 skill，让下一次免费。
- 一个没有可复用技能的 loop 只是包住陌生 agent 的 while-true；能调用锋利、经过测试、命名清楚技能库的 loop 才会复利。
#### 8.2 对"WTF is a loop"的最终回答
- 不是 prompt engineering 死了，而是：不要再做循环里的那个人；写一次 loop，给它值得调用的技能和可检查自己的反馈，给它预算和停止边界，然后让它在基础设施时间里运行。
- Steinberger 和 Boris 描述的是同一种工程转向：从会话式 prompt，转向可调度、可验证、可恢复、可复用的 agent 操作系统。

- 明确的保留：loop 不是魔法，真正难点是包住循环里那个决策者，让它不出边界。
- 对 Boris 立场的澄清：Boris 并不是说工程师消失了；决定做什么、理解客户、协调团队仍更重要。
- 作者用"最准确""最清楚"等表述评价各方观点，属其本人判断，非客观排序。
- 作者未给出 loop 成熟度的量化标准，也未穷尽划分层级；Uber 预算上限、Boris 的 259 PR、Gas Town 规模均为作者转引案例，作者未独立验证。
