# 《2026 AI 工程五大趋势：从模型能力转向可靠系统》

## 一句话主旨
AI工程重心从模型能力转向让Agent在真实系统中长期可靠可控地工作。

## 作者试图回答的问题
核心问题：2026年AI工程由哪些趋势定义，行业重心发生了什么转移？
关联子问题：五个趋势各自是什么、如何运作；它们如何共同构成"可靠系统工程"；工程师的角色如何变化。

## 三级论证骨架
### 一、背景：三年内从 Prompt Engineering 到主流软件工程
#### 1.1 命名与关注点迁移
- 2023年6月 swyx 提出"AI engineer"命名这一交叉领域，当时还被称为 prompt engineering。
- 三年后，是否每家公司设立该职位已不重要；coding agents、harness、context management、model output evaluation、autonomous system orchestration 已进入主流软件开发。
  - 2023年会议关注 AutoGPT、BabyAGI、GPT-Engineer，讨论"如何移除人"；2026年转向 Claude Code、Codex、Gemini CLI、Cursor、Warp 及生产基础设施。

#### 1.2 判断：工程成熟而非热潮消退
- 从展示单次自治 demo 转向构建可被组织长期信任的系统。

### 二、趋势一：关注点从 Agent 转向 Agent 周围的系统（Harness）
#### 2.1 概念转向：从 Agent 分解到 Harness
- Lilian Weng 2023年将 Agent 分解为 planning、memory、tool use；2026年新文章将重点转到模型周围的 harness。
- Harness 负责 workflow、context、permissions、evaluation、persistent state、continuous improvement。
  - 原比喻："模型像发动机，harness 是方向盘、刹车、仪表盘和车架。发动机再强，没有完整车辆也不能可靠上路。"
- 判断：模型能力只是系统的一部分，可靠交付来自外围结构。

#### 2.2 完全自治被降格
- 完全自治不可靠，规模化场景中也未必可取；大会更常把 Agent 定位为增强 AI engineer，而非彻底替代人。
- Romain Huet（OpenAI）："software ate the world, AI ate software, AI engineers are eating the world"——人通过 Agent 放大交付范围。

#### 2.3 Capability Overhang 与外部系统的必要
- Thariq Shihipar（Anthropic）："models are grown, not designed"，能力 spiky 增长。
- 前沿公司也无法完全预测模型变化，因此外部评估、监控、控制系统更重要。
  - 原比喻："模型像植物突然长出新枝，人不完全知道下一步会长哪里。"

### 三、趋势二：Loop Engineering 成为新的控制层
#### 3.1 Inner/Outer Loop 分工
- 多位工程师把系统拆成 inner loop（Agent 与用户/环境交互执行主要工作）与 outer loop（研究、维护、改进执行系统）。
- Roland Gavrilescu（Introspection）用 autoresearch 描述 outer loop：读取反馈信号、evals、human input，持续研究 primary system。
- Addy Osmani："agents can run much more of the inner execution loop, but that outer loop is still engineering."
- Peter Steinberger（OpenClaw 作者）同样分工：Agent 运行 inner execution loop，他在 outer loop 设方向、做决定。
  - 原比喻：inner loop 像生产线本身；outer loop 像工程团队观察生产线数据、调整工艺，不亲自做每个零件，却决定系统怎样变好。

#### 3.2 Loop 可靠性的争议
- Dex Horthy（HumanLayer）："hype is outrunning discipline"，对比 Kubernetes 的 deterministic control loop。
- Geoffrey Huntley（Ralph Loop 作者）：开发者像 locomotive engineer，职责是让火车留在轨道上。

#### 3.3 Loop Engineering 的控制对象
- 人不必介入 Agent 每一步操作，但要设计反馈、失败检测、终止条件、升级路径、人工检查点。
- Inner loop 追求执行速度和自治；outer loop 追求方向、质量、系统改进。
- 非确定性模型不能直接套用传统控制循环：Agent 输出分布、工具调用、能力边界随模型变化。
- 判断：loop engineering 是对自治的新约束——不是把 Agent 锁死，而是让它能跑，同时保留可观测、可评估、可纠偏的边界。

### 四、趋势三：AI Engineering 进入企业
#### 4.1 FDE（Forward Deployed Engineer）的角色
- FDE 不只是部署模型，而是与组织共同实现 integrations、cloud agents、long-running agents、automations、基于 SDK 的应用。
  - 原比喻："不是交付一盒软件就走，而是工程师驻场理解真实流程，把 AI 接进去，直到客户自己能维护且确实愿意继续使用。"

#### 4.2 成功标准：strict ROI
- Natalie Meurer（Sierra）：每家企业都想知道怎样维护 agentic ecosystem 的全部能力，包括多团队贡献和大量集成。
- Pauline Brunet（Cursor）：成功标准设为 strict ROI——FDE 离开后，客户不会关闭系统；要求 Agent 真正进入工作流，而非停留在演示。

#### 4.3 Software Factory 的自动化边界
- Software factory 指长时间运行的 Agent 覆盖软件生命周期；企业须选择自动化哪些 repository 和环节，以及在 code review、高风险变更等位置何时引入人。
  - 原比喻："把写、测、审和部署组织成 Agent 生产线，但每家公司仍要决定哪些工位全自动、哪些必须人签字。"
- Enterprise adoption 仍集中在 early adopters；FDE 需找到组织内 champion；技术可用不等于组织具备治理、信任与变革条件。

#### 4.4 企业级 Context Engineering
- Prukalpa Sankar（Atlan）：业务系统中的 context 先流入 shared company brain，再通过 MCP、API、retrieval 流向 agents、copilots、apps。
- 企业难题不只是"给模型更多资料"，而是让数据在权限正确、版本可靠、来源可追踪的情况下流动。
- FDE 成为技术与组织之间的翻译者，需共同定义 ROI、治理、人机分工。
- 成败取决于系统能否在 FDE 离开后持续运行、被内部维护、融入正式责任结构。

### 五、趋势四：Coding Agent 取代 IDE 成为开发者接口
#### 5.1 能力迁移
- 2023年 AI 编程主要是 GitHub Copilot 自动补全几行代码；2026年 coding agent 能理解广泛目标、探索 codebase、修改多个文件、运行测试、调试失败并迭代，然后把结果交给开发者。
- Claude Code、Codex、Gemini CLI、Cursor、Warp 不再只是 IDE plugin，而成为开发者操作软件生产的主要接口。
- Andrew Qu（Vercel）：Agent 是"a new type of software"——基础设施像 web app，但 interaction、interface、outputs 更动态、更不可预测。
  - 原比喻："传统软件像固定售货机，Agent 更像能临场处理任务的员工；同样需要场地，却不能用完全固定的输入输出规则管理。"
- 一年前行业还未意识到 secure code execution、sandbox、long-running jobs 会如此重要。

#### 5.2 Factory 与 Orchestra：两种设计价值
- Software factory 强调 Agent 团队规模化执行；Conductor CEO Charlie Holtz 偏爱 orchestra 比喻——人站在乐团前挥指挥棒，不被工厂流程隔离。
  - Factory 追求自动化、吞吐、标准流程；orchestra 强调人的控制感、创造力、实时协作。
- Geoffrey Huntley 即使支持 loopmaxxing，也担心行业过度自动化，明年可能发现 factory 和 loop 大量失败。

#### 5.3 人未退出，接口迁移
- 判断：coding agent 取代 IDE 不等于开发者退出；人的接口从直接编辑每行代码迁移到目标设定、任务分解、审查、风险判断、多 Agent 调度。
- 好的开发体验应让人感到掌控和"in the flow"，而不是只给出看不见过程的自动化黑箱。

### 六、趋势五：所有 Agent 平台围绕 Skills 建设
#### 6.1 Skills 的定义与来源
- Anthropic 推广 agent skills 后，skills 成为大会最热门主题之一。
- Addy Osmani：编码 senior engineer 的 workflows、quality gates、best practices。
- Andrew Qu（Vercel）：skills 是"portable, on-demand knowledge"；Roland Gavrilescu：行业已从 agent tools 转向 agent skills。
- Philipp Schmid（Google DeepMind）：skills 与 declarative Markdown 实现"agents without code"——用文件扩展能力，减少过去常由 Python 编写的 orchestration code。
  - 原比喻："Skill 像给 Agent 的作业手册，不只告诉它知道什么，还写清楚按什么步骤做、做到什么标准才算完成。"

#### 6.2 Skills 的功能
- Skills 不只提供知识，还保存操作顺序、验收门槛、组织经验。
- Garry Tan（Y Combinator）：AI-native 公司把销售、支持、财务流程编码为 skills，雇工程师维护 skills、处理它们尚不能完成的工作。
- 判断：Skills 是 Agent 平台的组织记忆和可移植流程层，但不是"一写永用"的 prompt 文档。

#### 6.3 Skill Engineering 的风险与纪律
- Paul Bakaus（Impeccable）用 design skills 为 coding agent 提供界面设计词汇，并提出 skill engineering 作为独立学科。
- 警告：大多数 skill 和 model 不够有创造力；多人使用同一 skill 会向单一方向收敛，导致所有设计相似。
- Matt Pocock：管理混乱叫"skills hell"，类比 framework hell；建议写更少、更小的 skills，投入更多结构设计。
- 原句："Autonomy without structure creates as much slop as leverage."——Skills 提供 structure，但结构本身须被重新审视，不是堆积更多文件。
- 新模型发布后，Agent 像从初中升入高中，原 curriculum 需要重写；Skill 必须随模型能力、工具和工作流共同迭代，旧 scaffold 可能限制新能力。

### 七、综合：五大趋势构成同一套可靠系统工程
#### 7.1 五个层面的对应
- Harness 定义 Agent 周围的运行边界；loops 把执行与监督拆层；FDE 将系统嵌入企业；coding agent 成为交互入口；skills 保存可移植知识和流程。
- 对应五层面：运行时、控制、组织落地、人机接口、可复用能力。

#### 7.2 结论
- Agent 已能工作并开始规模化，工程问题从"是否可能"升级为可靠性、可维护性、治理、ROI、持续改进。
- AI engineer 职责从写 prompt 迁移到设计系统：选择自动化边界、构建反馈循环、管理 context、定义 evals、维护 skills、编排 Agent 团队。
- 2026年的关键信号不是 Agent 取代人，而是软件工程开始围绕非确定性智能组件重新组织。

## 作者边界、反例与不确定性
- Loop engineering 被标注为 frontier thinking，纪律未定型：作者与 Geoffrey Huntley 都警示下一年可能出现大量 factory 与 loop 失败案例。
- 完全自治被否：大会更常把 Agent 定位为增强而非替代；企业落地仍集中在 early adopters，技术可用不等于组织具备治理、信任与变革条件。
- Skills 有明确风险：同一 skill 导致输出趋同（Paul Bakaus 警告）、"skills hell"（Matt Pocock）、随模型升级需重写 curriculum——不是"一写永用"。
- 非确定性模型不能直接套用传统 deterministic control loop：Agent 输出分布、工具调用、能力边界随模型变化。
