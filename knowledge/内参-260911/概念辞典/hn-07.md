# 概念解析辞典

> 针对《Cursor：让 coding agent 连续自治运行数周的工程经验》（Cursor 官方博客 *Scaling long-running autonomous coding*，未署名中文编译）的概念提取

## 一、核心概念

### 1. **长时程自治编码（long-running autonomous coding）**

- **context**：全文的目标设定是让 agent 在无人值守下连续运行数周，处理"人类团队通常需要数月完成"的项目。作者的原话指向这个目标：

  > "running coding agents autonomously for weeks"

- **费曼一下**：这不是"你问一句它改一段代码"，而是把一个大工程交出去，让 agent 自己连轴转几周，期间没人盯着。时间尺度一变，原本不重要的问题——协调、漂移、责任归属——全都变成主要矛盾。它是全文所有工程努力围绕的总靶子。

### 2. **单 agent 的速度天花板**

- **context**：全文的起点问题不是 agent 做不对，而是做得不够快。作者在描述这个起点时写道：

  > "Today's agents work well for focused tasks, but are slow for complex projects."

- **费曼一下**：一个很强的工程师也架不住项目有三个月的量。瓶颈不在质量而在串行速度，所以下一步只能是并行——而并行立刻把问题从"能力"换成"协作"。这个概念钉住了全文的问题代际：从单体能力问题升级为多体协调问题。

### 3. **动态协调（dynamic coordination）**

- **context**：Cursor 的第一直觉认为提前规划会太僵硬，因为大项目的路径和分工在一开始都不明显。作者的判断是：

  > "planning ahead would be too rigid"

- **费曼一下**：不预先排班，大家到现场看着办，根据别人当下的动作决定自己做什么。听上去灵活，实际是把调度成本平摊给每一个执行者——每个人都得先花时间搞清楚周围在干什么。这个概念解释了 Cursor 为什么先走扁平路线，而不是一上来就分角色。

### 4. **共享文件加锁的协调机制**

- **context**：初版实现是所有 agent 地位平等，通过一个共享文件查看状态、认领任务、更新状态，用锁防止两个 agent 抢同一个任务。原文对此机制的描述是：

  > "All agents were peers coordinating through a shared file, claiming tasks, updating status, and using locks to prevent two agents from grabbing the same task."

- **费曼一下**：像一块公共白板加一支唯一的笔，谁写谁先拿笔。规则很简单，但只要有人拿了笔不还、或者拿着笔晕过去，整块白板就停摆。这个概念是全文机制迭代的第一块垫脚石，后续所有失败都从这里展开。

### 5. **锁竞争瓶颈（lock contention）**

- **context**：即使锁本身工作正常，它也成了瓶颈。作者用具体数字说明了问题的严重程度：

  > "Twenty agents would slow down to the effective throughput of two or three, with most time spent waiting."

- **费曼一下**：二十个人干活却只有一支笔，多数时间在排队。人手加得再多，产出也卡在那支笔的速度上——这是并行系统最典型的伪扩展，也是这张设计图的第一道裂痕。

### 6. **乐观并发控制（optimistic concurrency control）**

- **context**：第二版做的是"自由读、检查后写"——agent 可以读状态，但如果状态自上次读取后已改变，写入就失败。作者对它的评价是：

  > "This was simpler and more robust, but there were still deeper problems."

- **费曼一下**：不再抢笔，而是先写下来再检查"我看到的版本还是最新的吗"，不是就重来。机制上确实更干净，但它只解决了"谁能写"，没解决"谁该扛难活"。这个概念的重要在于：它把机制修得干干净净，却让下一个更深的问题浮出水面。

### 7. **无层级导致的风险规避（risk-averse agents without hierarchy）**

- **context**：这是整篇文章最重要的转折。作者在诊断问题的实质时写道：

  > "With no hierarchy, agents became risk-averse."

  agent 避开困难任务、只做小而安全的改动，没有 agent 为难题或端到端实现负责，工作长时间空转而无进展。

- **费曼一下**：一群地位相同、都能自选任务的人，最后往往都去挑最容易交差的那份。难题不是没人能做，是没人被指定要做——协调失败在这里已经从技术问题变成了责任归属问题。这个概念把诊断推高了一个维度，是整篇文章从"优化机制"转向"重构架构"的分水岭。

### 8. **Planner–Worker 角色分离**

- **context**：解法性架构。Planner 持续探索代码库并创建任务，Worker 领取任务后"全神贯注死磕这个任务直到完成，然后 push"。作者用一句话评价它的效果：

  > "This solved most of our coordination problems."

- **费曼一下**：把"想做什么"和"把它做完"拆成两种岗位。执行者不再需要环顾四周，专注度和吞吐同时上来；协调成本被集中到少数规划者身上，而不是摊在每个人头上。它是全网络的枢纽——向下派生递归规划，向上支撑长时程自治这个总目标。

### 9. **递归并行规划（sub-planner）**

- **context**：Planner 不是单点，它可以派生自己的同类。原文描述：

  > "The planner can spawn sub-planners for specific areas, making planning itself parallel and recursive."

- **费曼一下**：规划本身也会堵。所以让规划者按领域再派规划者，规划这件事也并行起来——否则执行端扩容再多，也会被上游那一个大脑限速。这个概念补上了架构中的最后一块潜在瓶颈。

### 10. **judge agent 与周期性 fresh start**

- **context**：每个周期结束时有一位裁判来决定是否继续，下一轮则从头开始。这个设计一直保留到文末：

  > "Periodic fresh starts are still needed to combat drift and tunnel vision."

- **费曼一下**：给长跑加上分段与裁判。跑久了状态会变形，与其修修补补，不如定期清空重来一轮——用"忘记"来对抗积累的偏移。这是长时程系统特有的维护动作，是架构自带的呼吸阀。

### 11. **漂移与隧道视野（drift & tunnel vision）**

- **context**：长时程自治的两种典型退化。作者用它评价模型差异时说 GPT-5.2 更好是因为：

  > "It follows instructions, stays focused, avoids drift, and implements things precisely and completely."

  同时它也解释了为什么需要周期性重启，以及为什么角色分离能防止"any single agent getting tunnel vision"。

- **费曼一下**：跑得太久，agent 要么慢慢偏离原本的目标（漂移），要么钻进一个局部越挖越深、看不见全局（隧道视野）。两者都不会报错，只会安静地浪费掉几天算力。它是长时程场景独有的退化力量，与总目标形成持续张力。

### 12. **模型—角色适配**

- **context**：Cursor 最终的结论是按角色选模型，而不是用一个通用模型包打天下：

  > "We now use the model best suited for each role rather than one universal model."

- **费曼一下**：不同模型的"性格"不同——有的适合长期死磕，有的适合快速交付；"编码专用"模型未必是更好的规划者。长时程自治的成败不只由架构决定，也由"把哪个模型放在哪个岗位"决定。这是唯一一个绕过架构、直接支撑总目标的元经验。

### 13. **减法式改进（removing complexity）**

- **context**：他们发现改进往往来自删减而非添加。最典型的是那个被删除的 integrator 角色，作者写道：

  > "We initially built an integrator role for quality control and conflict resolution, but it created more bottlenecks than it solved."

- **费曼一下**：发现问题就加一个角色，是系统复杂化最常见的路径。但每个新增的中间人都变成新的排队点。先问"能不能删掉一层"，常常比"再加一层"更有效。这个原则为后来的"结构适量"提供了具体证据。

### 14. **结构适量原则**

- **context**：这条原则把减法式改进上升为一般判断：

  > "The right amount of structure is somewhere in the middle."

  太少则 agent 冲突、重复劳动、漂移；太多则系统脆弱。作者同时提到，直接照搬分布式计算与组织设计的成熟模型并非都适用于 agent。

- **费曼一下**：管得太松，大家互相踩脚；管得太死，一个环节坏掉全线停摆。多 agent 系统的设计不是"越有秩序越好"，而是找到那个中间剂量——而且这个剂量不能从人类组织学直接抄。这条原则为 Planner-Worker 架构提供了设计哲学上的支撑。

### 15. **prompt 主导论**

- **context**：全文最后一条、也许是最重的一条元经验：

  > "The harness and models matter, but the prompts matter more."

  让 agent 协调良好、避免病态行为、长期保持专注，靠的是大量 prompt 实验。

- **费曼一下**：同一套系统、同一批模型，说话方式变了，行为就变了。当执行力不再稀缺，稀缺的是把意图表达清楚的能力。这条结论与模型—角色适配并列，但它更像一个反直觉的杠杆：最便宜、最容易被低估的投入，反而决定了系统行为的大部分。
