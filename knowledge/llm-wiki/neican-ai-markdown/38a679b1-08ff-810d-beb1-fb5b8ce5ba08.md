# Tokenmaxxing 三个月失败，说明 AI 生产力转化仍有距离

> 文章讨论短期堆 token、堆调用量并不能自动带来组织级生产力。它适合提醒我们区分 AI 使用热度、真实流程改造和可持续产出。

## 导读

token-maxxing、token 经济学、agent 范式

## 核心观点

Tokenmaxxing 在三个月内从硅谷开发者的身份展示，扩散为企业 AI 使用热潮，又迅速被 Amazon、Uber、Microsoft 等公司踩刹车。文章的核心判断是：它失败不是因为 AI 没有价值，而是因为 token 消耗只是上游活动指标，无法自动转化成有用功能、业务结果和宏观生产率。

更深层的原因有四组：Agent 太贵且低效；组织没有准备好吸收 AI 上游产出；Tokenmaxxing 本质上重演了通用技术的生产率悖论和 J 型曲线；即使供给成本下降，市场需求也存在天花板。激进烧 token 是企业为寻找瓶颈支付的一笔试错成本，但在工作流、评测、责任体系和真实需求尚未成熟前，它必然先失败。

## Tokenmaxxing 从效率信号变成了身份符号

- 文章开头把 Tokenmaxxing 放在生成式 AI 爆发三年半后的分歧点上：市场仍然乐观，但怀疑也在累积。
- 3 月 20 日左右，纽约时报的 Kevin Roose 观察到硅谷开发者开始炫耀 token 用量。OpenAI 工程师一周用掉 2100 亿 token，约等于 33 个维基百科；Claude Code 工程师单人一个月可以烧掉 15 万美元 token。
- 最初的含义是“token 利用最大化”：开发者通过 Claude Code 等 AI 编程工具、多线程并行工作，把模型调用推到极高强度。
- 但它很快被扭曲为“AI 超级个体身份”的标识物。token 用得越多，似乎越能证明一个人懂 AI、效率高、掌握了并行工作。
- 早期能承担这种账单的主要是前沿模型公司和 AI 创业团队，因为它们有公司默认的不设限额度。

## 四月之后，Tokenmaxxing 被企业领导层背书并产业化

- 进入四月，Tokenmaxxing 不再只是开发者文化，而被互联网公司广泛接纳。
- 黄仁勋在 GTC 上说，如果一名年薪 50 万美元的工程师在 AI token 上的支出低于 25 万美元，将“令人非常担忧”。
- Y Combinator CEO Garry Tan 也称自己团队 tokenmaxxing 的时间比大多数人都长。
- Meta 内部甚至一度流传“token 使用量可能影响裁员决策”的说法。
- 这种领导层背书让 token 消耗从成本项变成组织激励：越多使用 AI，似乎越代表公司进入新生产力范式。
- 不止科技公司，Disney、Visa、阿里、腾讯、字节等公司也开始把 AI Coding 工具和 token 使用额度提供给广泛员工。

## 不到两个月，企业开始发现 token 消耗和业务产出脱钩

- Amazon 关闭内部 AI 使用排行榜 Kirorank，因为员工为了提高排名，让 AI agent 执行没有实际价值的任务，只是把 token 消耗刷上去。Dave Treadwell 后来提醒员工不要为了用 AI 而用 AI。
- Uber 的 Andrew Macdonald 公开谈到，公司看不到 token 消耗和“更多有用的消费者功能”之间的直接对应关系。Uber 95% 的工程师每月都使用 Claude Code，70% 的提交代码来自 AI，每人每月 API 调用费 500 到 2000 美元，但到 2026 年 4 月已烧光全年 Claude Code 预算。
- Microsoft 也计划取消 Experiences + Devices 部门大部分 Claude Code 内部授权，要求工程师迁回 GitHub Copilot CLI，核心原因是 token 账单开始难以控制。
- 这些案例说明：token 是活动量，不是产出量。它可以衡量模型被调用了多少，却不能直接说明客户问题解决了多少、产品功能交付了多少、公司资产沉淀了多少。

## 行业开始寻找 token 之外的效率口径，但新指标仍不稳定

- 百度提出 DAA（日活智能体数），想用每天有多少 Agent 真正在干活替代 token 消耗。但文章认为这只是“下了一层”，与 token 用量仍高度相似。
- Devin 选择“节省人类工时”作为效率标的，Uber 试图把 token 与 ROI 挂钩，Amazon 把北极星指标还原到“客户/业务问题解决数”。
- 这些指标方向更接近真实产出，但难题没有消失：token 消耗如何与传统目标挂钩？试错和构建成本的容忍度如何设定？自动化批量生产的工作流算单个功能交付，还是基础设施建设？
- 6 月 14 日，Satya Nadella 提出“Token 资本”，把 token 使用目标转向企业拥有的 AI 能力资产，包括工作流、私有评测、组织记忆、反馈闭环和可迁移知识。
- 文章认为这个说法抓住了 Harness 演进方向，但也有自我包装成分：未来理想的 Harness 本来就会在用户正常工作时自动沉淀任务轨迹、评测信号和组织知识。到那时，只要不是瞎用，token 积累自然会带来系统沉淀。
- 因此，“Token 资本”也可以理解为 Microsoft 对模型厂商借 Harness 进入云业务的一种反向叙事：不要只买最强模型，要在 Azure、Copilot 和 agent platform 上搭企业学习系统。

## 第一层失败原因：Agent 用不起

- Tokenmaxxing 最直接的问题是太贵。文章把成本压力拆成三部分。
- 第一，前沿模型公司面临 IPO 和利润压力。Epoch AI 估算，如果从收入中扣除计算成本，OpenAI 约 60 亿美元销售额对应毛利润约 20 亿美元，再扣除营销、行政和分给 Microsoft 的收入，净利润很可能为负。若算上 GPT-5 约 50 亿美元研发成本，模型四个月生命周期很难盈利。
- 第二，订阅制被重度用户打穿。OpenClaw 等自动化 Agent 让订阅用户的 token 消耗飙升，远超人类聊天式订阅模型。Anthropic 在 2026 年 4 月前后调整订阅策略，Claude 订阅额度不再覆盖 OpenClaw 这类第三方 Agent 工具。Google Gemini 也开始按复杂度计量。
- 第三，Agentic Coding 的 token 消耗在 Harness 加持下本身就很高。Google 和 Microsoft 主导的研究显示，agentic coding 的 token 消耗约为普通代码问答和代码推理任务的 1000 倍。
- 成本主要不是输出 token，而是输入 token。Agent 为了保持真实状态，会在 Setup、Explore、Fix、Validate、Closeout 各阶段反复读上下文，其中 Explore 和 Fix 约占 2/3 的 rounds，缓存阅读 token 又是最大项。
- 文章用“干烧柴火，饭不熟”总结这种低效：上下文反复输入，任务没有成比例推进；不同尝试之间 token 消耗可差 30 倍，模型也会系统性低估真实用量。

## Effective Feedback Compute 揭示了 Agent 行动低效

- 哈工大论文《Scaling Laws for Agent Harnesses via Effective Feedback Compute》进一步量化了这种低效。
- Effective Feedback Compute（EFC）衡量的是 Agent 每次行动是否获得真正能影响下一步动作的新证据。
- EFC 转化率 η 表示原始计算预算中有多少变成有效反馈。文章用“花 100 块钱取证，只有 10 块钱买到真正能改变下一步的线索”解释这个概念。
- 在复杂 Terminal 任务和 SWE 任务中，几乎所有 Harness 的 EFC 转化率都很低，接近 0.1；越复杂的 Harness，在复杂任务中有效反馈效率越低。
- 多 Agent 系统会进一步放大问题。Agent Swarm 让 300 多个子 Agent 分布式做任务，每个都独立积累上下文并汇报，可能成为新的 token 杀手。
- 因此，Agent 的低效、长程任务的上下文需求、多 Agent 系统的协同成本，一起铸成了 1000 倍 token 消耗。

## 第二层失败原因：组织的混乱

- Tokenmaxxing 最初主要发生在开发团队，后来随着 OpenClaw、Skill 等更适合一般办公的 Agent 形式出现，被扩散到更多非编程场景。
- 文章提出关键问题：当下 Agent 即使结合 Skill，也未必适合在非编程工作中大规模铺开。
- Joshua Bengio 对模型能力的评价是“能力参差不齐”。当前后训练过分强化可验证奖励（RLVR），使模型在有明确答案的任务上表现更好，在设计、写作等缺乏明确答案的任务上提升更难。
- Joshua Gans 的《Artificial Jagged Intelligence》把这个问题称为“锯齿状智能”：企业任务不是平滑平面，不同业务领域、工具环境、工作流长度、验收方式都会让 Agent 表现剧烈变化。
- 真正决定部署价值的，不是模型在平均 benchmark 上得分多高，而是组织最常用、最关键、最不能出错的任务是否落在模型弱区。
- 如果一个组织 70% 的 Agent 调用集中在客服查询、合同审查、ERP 录入、CRM 更新或遗留代码修改中的某些高频工作流，而这些工作流刚好是模型弱区，更多 token 只会让 Agent 在弱区跑得更久，制造更多返工。

## 行业任务的真实通过率说明 Agent 还没有准备好

- UC Berkeley RDI 与 250 多名行业专家的《Agents' Last Exam》测试了 55 个子领域、13 个行业集群、1400 多个真实专业任务。
- 这些任务来自真实从业者日常工作，例如 3D 建模、达芬奇绿幕抠像、视频合成等，强调长周期、经济价值和可验证结果。
- 只看最难一档任务，当前表现最好的配置 Codex + GPT-5.5 完整通过率也只有 8.6%；主流系统平均完整通过率仅 2.6%。
- 分领域看，Agent 能力也不均匀。数学计算和农业成功率中值可达 55%-85%，商业和法律降至 50%-55%，教育低至 25%。
- 研究团队对 Claude Code + Opus 4.7 的失败案例归因：75% 来自理解和策略层面，只有 22% 是执行错误。文章总结为：Agent 不是“手脚不灵”，而是“脑子里没有行业 know-how”。
- Skill 能缓解问题，但越贴近真实业务，越需要隐性专业判断、本地规则、专业软件环境和可验证输出。通用 Skill 到企业内部往往需要 fork。
- 这也解释了 Nadella 为什么强调 token 资本：企业需要沉淀这些 know-how。但悖论是，在没有划定 AI 强弱和薄弱环节前，不烧 token 去试，几乎不可能构建有效沉淀；烧，又烧不起。

## 脆弱链会从写代码转移到审核、测试、发布和采用

- 即使任务适合 AI，组织链条也未必能吸收 AI 的上游产出。
- Coding Agent 是当前 Agent 最擅长的领域，但软件生产不是只写代码。代码之后还有审核、合并、测试、集成、发布、上架和用户采用。
- MIT《Writing Code vs. Shipping Code》用 10 万多名 GitHub 开发者数据，比较 AI 工具采用前后变化。自动补全让 commits 累计增加约 40%，交互式 coding agents 增加约 140%，自主 coding agents 增加约 180%。
- 但效应传导到项目数只剩约 50%，传导到 releases 只剩约 30%。写代码变快，不等于交付代码变快。
- AI 把上游写代码加速后，设计、审核、测试、产品决策、发布流程、应用商店审核和用户采用没有同步加速，上游红利在下游被稀释。
- Review 和测试也可以用 AI，但 token 账单甚至可能达到写代码的十倍以上。如果不用 AI，人的带宽会卡死；如果用 AI，又可能继续放大成本。
- CMU《AI IDEs or Autonomous Agents?》发现采用自动化 Coding Agent 后，代码中需要人处理的警告上升约 18%，AI 写的代码理解难度上升约 39%。更多问题、更难懂的代码，会把人的心流写作时间替换成高强度 review。

## 简单问题上的虚耗让组织产生效率幻觉

- Stanford《The efficiency-gain illusion》设计了 24 个简单任务，覆盖信息查找、信息处理、流程执行和内容生成。
- 任务包括回答黑白混合是什么颜色、说出奥运奖牌得主、找同义词、总结短文、找拼写错误、计算 27 + 56 等。
- 这些任务在企业里对应大量小颗粒度日常工作。很多时候，人自己做比打开 AI、写 prompt、等待、阅读、确认更快。
- 但实验中，哪怕是简单颜色回忆或 27 + 56，也有近 40% 的人要用 AI。
- AI 不是没有能力，而是固定调用成本超过任务收益。它把原本十几秒完成的小动作，变成 prompt、等待、阅读、验证、修改的一串流程。
- 参与者先用过 AI 后，后面更容易继续用 AI，而且对 AI 节省时间的判断更失准。这就是组织里的效率幻觉：使用率上升，员工也觉得先进，但大量小任务变慢，既花 token，又没有提效。

## 重复开发成为技术之外的大型 token 浪费项

- OpenClaw、Cowork 等自动化 Agent 把“生产一个可用模块”的边际成本降到接近于零，开发者和 Agent 都更倾向直接生成新实现，而不是检索、理解、比较和复用已有实现。
- 组织没有同步解决“发现已有模块、判断优劣、追踪来源、复用依赖”的问题。
- Skill 市场已经暴露这种乱象。南洋理工大学《SkillClone》分析超过两万个 Skills，发现 75% 非常近似，去重后只有 5,642 个有不同理念和目标；40% 的相似 Skill 不是同一作者产出，说明是广泛重复建设。
- CMU 对 40,285 个公开 Skills 的测量研究也发现明显意图同质化：代码审查、文档生成、网页抓取等功能大量重复，只是名称、提示词和实现细节不同。
- 代码领域同样如此。萨斯喀彻温大学研究了 8,106 个由 Codex、Claude Code 等 Agent 提交的 fix-related PR，其中 26.1% 被关闭且未合并。人工分析 326 个未接纳修改后发现，最常见失败原因是“同一问题已被另一个 PR 解决”，占 22.1%。
- 这说明更快的代码生产速度、模型倾向带来的更一致解法、缺乏全局协调，会让重复造轮子加剧。

## 第三层失败原因：Tokenmaxxing 重演生产率悖论

- 文章把 Tokenmaxxing 放回经济学问题：电力、计算机、互联网等通用技术都经历过“技术能力快速提升，但宏观增长没有同步出现”的阶段，这就是生产率悖论。
- 对这个问题的重要解释是 J 型增长曲线理论及其底层的可替代性理论。
- 可替代性理论认为，复杂产品由一组互补要素共同决定，任何一个要素都可能成为瓶颈。Agent 技术瓶颈、流程瓶颈、组织瓶颈都会让局部效率提升被稀释。
- 代码生产效率提高一百倍，如果企业连需求都说不清楚，整个项目效率很难提升。Agent 一天生成一千个方案，如果人类只能审核十个，多出的九百九十个不是产出，而是待处理库存。
- J 型理论认为，技术进步带来的增长往往要等企业同步改变设备、流程、技能和组织结构后才会出现。
- 在下探阶段，企业一边支付技术成本，一边支付组织改造成本，统计生产率甚至可能下降。Tokenmaxxing 就是企业支付这笔投入、趟出瓶颈的过程。
- 它必然失败，但失败并非毫无意义：它帮助企业发现哪些任务不适合当前 Agent，哪些流程需要重构，哪些评测和责任体系必须补齐。

## 第四层失败原因：需求有天花板

- 文章最后提醒，不是所有技术革新都会带来 J 型增长，因为供给侧改善还会遇到需求天花板。
- Cornell 研究《AI and the Quantity and Quality of Creative Products》发现，LLM 兴起后 2022 到 2025 年新书发布量接近增长三倍，但整体图书阅读量只提高约 7%。
- 内容供给确实提高了，但注意力没有同步扩张，而且新增书籍平均质量下滑，高质量书籍仍以人类写作为主。注意力市场的需求天花板很低。
- 编程领域也有类似问题。MIT《Writing Code vs. Shipping Code》显示，AI 推动四大主流 App 商店的新 app 数量增长，但没有带来总使用量增长。市场上 app 变多，用户没有因此多用软件。
- 软件开发的需求天花板可能高于内容，但关键在于“有效需求”。一个内部软件预计创造一万元价值，传统开发要五万元时，需求不会表现为订单；AI 把总成本降到五千元后，交易才第一次成立。
- AI 创造新市场的方式，是让原本不划算的任务跨过盈亏门槛。但能释放多少需求，取决于门槛附近积压了多少任务。
- Coding Agent 可能释放内部工具、一次性软件、遗留系统维护和小流程自动化需求，但前提是整体成本真的降到用户愿意接受的水平。Tokenmaxxing 阶段，token 成本本身仍高，降本很难完成。
- 真正难的仍是识别尚未满足、用户愿意付费、现有产品没有解决、且能通过软件解决的问题。Agent 目前在寻找新需求和给出低成本方案方面还不够强。

## 结论：激进 Tokenmaxxing 会失败，但它暴露了 AI 生产力转化的真实路径

- 文章并不是否定 AI，而是否定用 token 消耗替代生产力指标。
- Tokenmaxxing 的失败揭示出 AI 生产力转化至少需要四个条件：Agent 成本和有效反馈效率改善；组织能识别适用任务和弱区；下游审核、测试、发布、采用链条同步加速；市场上存在可被降本释放的有效需求。
- 在这些条件成熟前，更多 token 往往只会制造更厚账单、更多半成品、更多待审核库存和更多重复建设。
- 生产力爆发仍可能发生，但它不会来自“烧得更多”本身，而来自企业把数据、流程、人员、评测和责任体系重组到能稳定吸收 AI 的状态。
- 所以文章最后的判断是：我们离真正转化成生产力爆发还需要时间，可能等待 AI 能力突破人的瓶颈，也可能等待组织真正吸纳 AI。在此之前，激进 Tokenmaxxing 必然失败。

## 概念网络

### 关键概念

#### Tokenmaxxing

**context**：文章用 Tokenmaxxing 指代把 token 使用推到最大化的 AI 使用文化。它最初来自硅谷开发者炫耀 Claude Code 等工具的高强度使用，后来被扭曲成“AI 超级个体身份”的标识物。

**费曼一下**：这就像把电费当成工厂生产力。机器转得越久、电表跑得越快，看起来很忙，但关键是最后有没有生产出能卖出去的东西。

#### Token 资本

**context**：Satya Nadella 提出 token 使用的目标应该是企业拥有的 AI 能力资产，包括工作流、私有评测、组织记忆、反馈闭环和可迁移知识。

**费曼一下**：不是每一次模型调用都算浪费。如果调用过程沉淀成公司以后还能复用的流程、知识和评测，它就像研发投入。但如果只是刷榜，那只是账单。

#### AI Harness

**context**：文章多次用 Harness 指代把模型、工具、上下文、反馈、任务轨迹和自动化流程组织起来的系统。Harness 为了让 Agent 不跑偏，会反复送入上下文，也可能自动沉淀组织知识。

**费曼一下**：模型像发动机，Harness 像整辆车。它决定发动机什么时候看地图、什么时候踩油门、什么时候回头检查路线。车设计不好，再强的发动机也会耗油空转。

#### Agentic Coding 的 1000 倍消耗

**context**：Google 和 Microsoft 主导的研究称，agentic coding 的 token 消耗约为普通代码问答和代码推理任务的 1000 倍，主要花在反复输入上下文，而不是输出代码。

**费曼一下**：让 AI 自己修代码，不是问它一个问题，而是让它反复找文件、读日志、改补丁、跑测试、再读上下文。它像一个不断翻资料的实习生，资料费可能比写出来的代码还贵。

#### Effective Feedback Compute（有效反馈计算）

**context**：EFC 衡量 Agent 花出去的计算里，有多少变成真正能影响下一步动作的新证据。复杂任务中许多 Harness 的 EFC 转化率接近 0.1。

**费曼一下**：如果花 100 块侦查，只有 10 块买到了真的有用线索，剩下 90 块只是绕圈子。EFC 就是在算 AI 的每次行动有没有带来下一步可用的新信息。

#### 能力参差不齐的智能

**context**：文章借 Joshua Bengio 和 Joshua Gans 的观点说明，模型能力不是平滑分布的。它在有明确答案的任务上更强，在设计、写作、行业 know-how 等任务上更弱。

**费曼一下**：AI 不是一个所有科目都平均 90 分的学生，而是有些题很强、有些题很弱。企业最常用的题如果刚好在弱项里，多花 token 也不会自动变好。

#### 组织弱区

**context**：真实企业的 Agent 调用可能集中在客服、合同、ERP、CRM、遗留代码等少数高频工作流。如果这些工作流落在模型弱区，更多 token 只会带来更多返工。

**费曼一下**：公司不是平均使用 AI，而是在几个关键流程里反复用。只要关键流程卡住，整体收益就卡住，就像水管最窄的一段决定水流。

#### Skill 的本地化

**context**：文章认为 Skill 能缓解模型缺少行业 know-how 的问题，但真实业务需要隐性判断、本地规则、专业软件环境和可验证输出，通用 Skill 到企业内部往往要 fork。

**费曼一下**：通用 Skill 像一本公开菜谱。公司真正要用时，还要改成自家厨房的锅、火候、食材和出餐标准，否则做不出稳定结果。

#### 脆弱链的转移

**context**：AI 加速 coding 后，瓶颈会转移到审核、合并、测试、发布和用户采用。MIT 研究显示 commit 增长可以很高，但传导到 releases 会大幅衰减。

**费曼一下**：AI 把切菜速度提高三倍，但炒菜、装盘、上菜没变快，厨房只会堆满半成品。效率提升会跑到下一段链条前停住。

#### 效率幻觉

**context**：Stanford 研究显示，在许多简单任务上，人自己完成比调用 AI 更快，但用过 AI 的人更容易继续使用 AI，也更容易高估节省时间。

**费曼一下**：AI 让人感觉自己更先进，但有些小事本来十秒能做完，调用 AI 反而变成一分钟流程。感觉更现代，不等于真的更快。

#### 重复造轮子

**context**：OpenClaw、Cowork 等 Agent 降低了生产模块的边际成本，却让开发者和 Agent 更倾向直接生成新实现。Skill 市场和 AI PR 都出现大量重复建设。

**费曼一下**：当造一个轮子太便宜，大家就懒得找旧轮子。结果仓库里堆满相似轮子，真正浪费的是发现、比较、维护和选择的成本。

#### 生产率悖论

**context**：文章把 Tokenmaxxing 放入电力、计算机、互联网等通用技术的历史脉络：技术能力快速提升后，宏观增长不一定立刻出现。

**费曼一下**：新技术刚出现时，大家都买设备、改流程、学用法，但产出还没起来。账单先涨，效率后到，这就是生产率悖论的直觉。

#### J 型增长曲线

**context**：J 型理论认为，技术进步带来的增长要等企业同步改变设备、流程、技能和组织结构后才会显现。前期投入可能让统计生产率先下降。

**费曼一下**：像挖地基盖楼，前面看起来是在往下挖，不是在往上建。只有地基、管线和结构都到位，楼才开始往上长。

#### 有效需求

**context**：文章区分欲望和有效需求。用户想要某种软件，不代表市场会提供；只有愿意支付的最高价格高于交易总成本，需求才会变成订单。

**费曼一下**：想要不等于会买。AI 真正创造新市场，是把原来“不划算”的小软件、小自动化、小维护任务，降到值得买、值得做的成本线以下。

### 概念网络

这篇文章的整体概念网络可以看成一条从“错误指标”到“真实生产力转化条件”的链条。

最上游是 **Tokenmaxxing**。它把 token 消耗误当成 AI 掌握程度和生产力信号，形成一种带有身份展示意味的组织激励。企业领导层背书后，token 使用量进一步被放大，开始进入排行榜、预算和内部文化。

随后出现第一层校正：**Token 资本** 和各种新指标试图把 token 从消耗量重新解释为资产沉淀。这里的关键中介是 **AI Harness**。如果 Harness 能把每次调用沉淀成工作流、私有评测、组织记忆和反馈闭环，token 才可能成为资本；如果不能，它就只是成本。

但 Harness 自身带来第二层问题：**Agentic Coding 的 1000 倍消耗** 和低 **Effective Feedback Compute**。Agent 为了完成长程任务，会反复读取上下文、探索、修复和验证，消耗大量输入 token。只有当这些行动产生真正影响下一步的新证据时，计算才有效。EFC 过低说明很多 token 只是空转。

第三层是能力与组织的错配。模型是 **能力参差不齐的智能**，企业又存在自己的 **组织弱区**。当高频流程恰好落在模型弱项里，更多 token 不会带来线性改善。**Skill 的本地化** 是补救路径，但它本身需要企业规则、专业判断和可验证输出的长期沉淀。

第四层是生产链条瓶颈。即使上游写代码变快，**脆弱链的转移** 会把瓶颈推到 review、测试、发布和用户采用。与此同时，日常小任务中的 **效率幻觉** 会让组织把 AI 使用率误读为效率提升，**重复造轮子** 又会把低边际生成成本转化成重复建设和协调成本。

第五层是经济学解释。Tokenmaxxing 重演了 **生产率悖论**：通用技术能力提升初期，组织需要先支付技术、流程、技能和结构改造成本。只有这些互补要素同步改变后，才可能走过 **J 型增长曲线** 的下探阶段，进入真正的生产率提升。

最底层是需求约束。就算供给侧效率提高，市场仍然受 **有效需求** 限制。AI 能创造新市场，前提是它把原来不划算的任务降到值得购买的成本线以下；如果只是生产更多 app、更多内容、更多半成品，而用户时间、支付意愿和真实问题没有同步扩大，供给增长就会撞上需求天花板。

因此，文章的网络结论是：Tokenmaxxing 失败不是 AI 生产力失败，而是把“算力消耗”误认成“生产力转化”的失败。真正的转化路径要同时穿过 Harness 效率、组织吸纳、流程瓶颈和有效需求四道门。
