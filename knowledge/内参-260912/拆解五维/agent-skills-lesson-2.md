# 五维拆解 · agent-skills-lesson-2

## ① 概念 ×3
- **技能与 SKILL.md 的两段结构**：技能是一个目录，目录中包含 SKILL.md 文件，而不是一段单独的提示词。；SKILL.md 被两组破折号分成两半：前半是元数据（名称、描述），后半是说明/指令。；第二组破折号之后的所有内容，是 Claude 激活技能后需要执行的指令。
- **名称与描述的分工（描述即匹配条件）**：名称代表技能的身份；描述告诉 Claude 何时使用该技能，是匹配条件。；发送请求时，Claude 把消息与所有可用技能的描述进行比对，匹配是语义上的，允许意图重叠（如“解释这个函数的作用”匹配“用图表解释代码”）。；描述写的是使用场景而非技能内容摘要，所以命名与描述要能区分彼此。
- **启动仅加载元数据、确认后才完整加载**：Claude Code 启动时扫描技能位置，但只加载技能名称和描述，不加载完整内容。；请求匹配命中后，Claude 先给出确认提示；确认前完整内容尚未进入上下文。；确认后 Claude 读取整个 SKILL.md 并执行其中指令；因此新增、修改、删除技能后都必须重启 Claude Code 才生效。

## ② 阅读 ×1（三层梯度）
> 只写一个 SKILL.md，就能让 Claude 在合适的时机自动套用你的固定格式——关键全在名称与描述怎么被匹配、何时才被加载。

- **直觉**：技能像一柜贴标签的工具：平时你只扫标签，不翻说明书；真要用哪个，才把说明书抽出来，而且抽之前先问你一声。
- **机制**：技能=目录+SKILL.md；前半放名称和描述，后半放指令。启动时只把名称和描述放进可用列表，请求来了拿语义匹配描述，命中先要确认，确认后才读整份 SKILL.md 执行；所以改动要重启才生效。
- **边界**：这套机制在几处讲不完整：优先级列表前后不一致（一处排企业版→个人版→项目版→插件版，后文只列企业级、个人、插件，未提项目版路径）；未说明确认提示能否跳过、匹配失败怎么办、多个技能同时匹配时如何选；命名撞车时个人技能会被企业级同名技能压过。

## ③ 决策 ×3
- **情境**：你有一件每周都要重复、格式固定的写作任务（如写 PR 描述、周报、代码审查意见），想让它自动照模板产出。
  - 做法：把它做成个人技能：在 ~/.claude/skills 下建一个与技能同名的目录，写 SKILL.md，描述里写清“什么时候用它”，正文写清执行步骤与输出格式，然后重启 Claude Code 并在可用技能列表里确认。
  - 适用条件：适用于你希望在所有项目通用、且任务是格式固定可复述的；若只是项目内部专用，材料未给出项目版路径，别想当然照搬个人版路径。
- **情境**：团队成员各自起了同一个技能名（如都叫 review），你想知道最终生效的是谁、要不要改。
  - 做法：按材料给出的优先级判断：企业版最高，其后个人版、项目版，插件版最低；公司可用企业级技能强制统一标准，个人定制不会覆盖它，要避免撞车就改用 frontend-review、backend-review 这类描述性名称。
  - 适用条件：适用于你已知该名字存在同名技能；材料自身对项目版位置与路径说明不一致，涉及项目版时不要当作确定结论使用。
- **情境**：你改好了 SKILL.md，测试时却发现 Claude 的行为跟改动前一模一样。
  - 做法：先确认是否已重启 Claude Code——技能在启动时加载，创建、修改、删除后都要重启；删除技能是删掉它的配置目录，不是改内容。
  - 适用条件：适用于行为没变化、且你确定改的是正确的 SKILL.md；若重启后仍不匹配，材料未说明匹配失败时的处理方式，需要自行记录现象而不能引用材料下结论。

## ④ 实验 ×5
1. **做**：用手写一个最小个人技能：建目录 ~/.claude/skills/<技能名>/SKILL.md，只写 name 和 description，第二组破折号后留空或只写一句废话，重启 Claude Code。
   - 观察：技能名称是否出现在可用技能列表里；不触发它时，Claude 是否表现得完全不知道那后半句废话。
   - 结论：验证“启动时只加载名称和描述、不加载完整内容”这一条。
2. **做**：照材料的 pr-description 示例原样创建技能：描述写“创建 PR、写 PR 或用户要求总结变更时使用”，正文要求先跑 git diff main...HEAD，再按 What / Why / Changes 三段输出；在分支上做几处改动，然后说“为我的更改编写 PR 描述”。
   - 观察：是否出现“正在使用 PR 描述技能”的迹象；输出是否稳定落在 What / Why / Changes 三段格式上。
   - 结论：验证描述作为匹配条件能命中、且确认后正文指令被完整执行。
3. **做**：做一次对照：先用材料给的描述原句（含“Use when creating a PR…”这类触发场景）测试一次请求；再把描述改成只写“帮助处理代码相关任务”这种含糊说法，重启后用同一句请求再测一次。
   - 观察：两次是否都弹出加载确认、以及哪一次更容易被匹配到、匹配是否变得容易被别的技能抢走。
   - 结论：验证描述写的是“何时使用”而非内容摘要，描述含糊会削弱语义匹配的准确性。
4. **做**：在同一个请求上分别做两种处理：弹出确认时接受，与直接不确认（或另发一条无关请求），对比两次之后 Claude 的回答。
   - 观察：未确认时 Claude 是否并未按你的模板格式作答；确认后是否读入了整份 SKILL.md 的指令。
   - 结论：验证确认提示是加载边界：确认前完整内容未进入上下文。
5. **做**：记录一次撞车现象：若你能访问某个更高优先级的同名技能，就创建一个同名的个人技能；否则创建两个仅命名不同（如 review 与 frontend-review）的技能，各写一句可区分的正文指令，重启后分别请求并记录哪个生效。
   - 观察：同名情况下哪一个版本被采用；不同命名时请求是否被引向预期的那个技能；以及项目版是否出现在你实际能观察到的位置。
   - 结论：验证企业版→个人版→项目版→插件版的优先级，并记录材料未说清的项目版与多技能同时匹配情形。

## ⑤ 费曼验收
**AI 示范**：技能是一个目录，里面放 SKILL.md：两行 --- 把文件分上下半，上半是名片（名称+描述），下半是说明书（具体怎么做）。Claude 启动只读名片，靠语义匹配把你的请求和描述对上，命中后先问你要不要加载，你确认了才读整份说明书去执行。

**判定要点**（引擎用）：
- 技能与 SKILL.md 的两段结构：点明技能是“目录 + SKILL.md”，不是单独一段提示词；说出 SKILL.md 分元数据段与指令段，并指出分界是第二组破折号；说出破折号之后的正文是激活后才执行的指令
- 名称与描述的分工（描述即匹配条件）：说清名称是身份标识、描述是“何时使用”的匹配条件；指出匹配对象是描述而不是完整技能内容，且匹配是语义的、允许意图重叠；举例或说明描述应写使用场景
- 启动仅加载元数据、确认后才完整加载：说出启动时只加载名称和描述、不加载完整内容；说出命中后先有确认提示，确认后才读取整个 SKILL.md 并执行；由此推出创建/修改/删除技能后需重启 Claude Code 才生效
