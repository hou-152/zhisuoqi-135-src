# 五维拆解 · agent-skills-vs-features

## ① 概念 ×3
- **Skills（按需加载的特定任务专业知识）**：当 Claude 将某个请求与某个 skill 匹配时，该 skill 的指令才加入对话；例如编写新代码时 PR 审查清单不需要出现在上下文中，只在请求审查时才激活。；skill 激活时，其指令加入现有上下文，即 Skills 是为当前对话添加知识，而不是在独立环境中执行任务。；Skills 是请求驱动的，根据请求内容激活；适用于特定任务的专业知识、只在某些情况下才相关的知识，以及会使每次对话都变得杂乱的详细流程。
- **按需加载与始终加载（加载模型）**：CLAUDE.md 会加载到每次对话中，最适合始终生效的项目标准，例如让项目使用 TypeScript 严格模式。；Skills 按需加载，最适合特定任务的专业知识；判断依据是内容是否只在某些情况下才相关。；始终加载适用于任何请求都必须遵守的项目级标准、类似「永远不要修改数据库架构」的约束、框架偏好与编码风格。
- **功能组合（结合使用，而非硬塞）**：每种功能都各有专长，当其他选项更合适时，不要把一切硬塞进 skills 中，而且可以同时使用多种功能。；一个典型配置可能同时包含：CLAUDE.md 作为始终生效的项目标准、Skills 作为按需加载的特定任务专业知识、Hooks 作为事件触发的自动化、Subagents 作为隔离的委派执行上下文、MCP servers 作为外部工具和集成。；当有知识应在相关主题出现时被自动应用，就用 skills，并与其他功能结合使用以实现全面自定义。

## ② 阅读 ×1（三层梯度）
> 同一套自定义能力里，几乎每个「该用哪个」的纠结都源于一个判据没想清楚：这东西该始终生效，还是只在被请求时才生效。

- **直觉**：把这几种功能想成不同角色的分工：一直贴在桌上的项目守则、需要时才翻开的手册、被叫去单独房间干活的同事、一有事件就响的传感器、通往外部工具的插头——它们不是互相替代的关系。
- **机制**：核心是三组对照：加载时机上，CLAUDE.md 每次对话都加载，Skills 按请求匹配后才加载并把指令加入现有上下文；作用位置上，Skills 为当前对话添加知识，Subagents 在隔离的执行上下文中接收任务、独立完成再返回结果，还可拥有与主对话不同的工具访问权限；触发方式上，Hooks 由文件保存、工具调用等事件触发，Skills 由请求内容触发。
- **边界**：Skills 是按需加载的，因此不会始终生效，也不承担执行委派；当其他选项更合适时不要把所有事情硬塞进 skills。原文把 MCP servers 与 skills 归为完全不同的类别，但没有给出两者的具体取舍标准，也没有展开 MCP 的使用场景，这部分不能替原文下判断。

## ③ 决策 ×3
- **情境**：你手头有一堆项目规范、团队约定和零散检查清单，纠结哪些该放进每次对话都生效的配置，哪些该做成单独的知识包。
  - 做法：用「是否始终适用」做分流：无论什么请求都必须成立的标准与约束放进始终加载的配置；只在某些任务下才相关的详细流程，做成按请求匹配才激活的按需知识。
  - 适用条件：适用于触发前提是「任何请求下都要成立」的规则。如果某条内容你自己都说不清何时会用到，先不要放始终加载；若它其实是由某个动作事件引发（比如每次保存文件），则应考虑事件驱动的自动化，而不是任何一种按需知识。
- **情境**：接到一个大任务，需要反复搜索、试错，主对话的上下文越来越杂，你还在纠结要不要把新学到的知识也塞进同一个对话。
  - 做法：把这类工作交给在隔离上下文中运行的委派方式：给它一个任务，让它在独立环境里做完再返回结果，需要不同工具访问权限时尤其如此。
  - 适用条件：适用于目标是「把工作交出去执行」且希望与主上下文隔离。如果目标只是为当前任务增强知识、且这份专业知识贯穿整个对话过程，那就该走给当前对话添加上下文的路子，而不是委派。
- **情境**：你希望某个动作每次都自动发生，比如保存后自动检查、在调用某个工具前先验证输入。
  - 做法：把它做成由事件触发的自动化，让它在事件发生时运行，而不是写成一份期待被请求激活的知识。
  - 适用条件：仅当触发点是一个明确事件、且不依赖对请求内容的判断时才成立。如果你真正想影响的是 Claude 处理请求的方式或推理所依据的指导原则，那属于请求驱动的知识，放错位置会导致它在该触发时没触发。

## ④ 实验 ×5
1. **做**：把你项目里现有的规范、约定、检查清单全部列成一张表，逐条标注「始终生效」还是「只在某些情况相关」，并为每条写一句判断理由。用任意文本编辑器即可完成，不依赖任何付费工具。
   - 观察：有多少条其实只在少数场景相关，却一直占据着每次对话的位置；标注时你犹豫的是哪些条目。
   - 结论：验证「始终加载 vs 按需加载」这条分流判据是否真的可操作，以及你的配置里是否存在把一切硬塞进同一处的情况。
2. **做**：从上一步的表里挑一条「只在某些情况相关」的内容（例如一份审查清单），把它整理成一份独立的按需知识：在写新代码时不提及它，只记录结果；在明确提出对应请求时再提及，再记录一次。
   - 观察：两次分别有没有被激活，激活后是否加入了当前对话的上下文，以及未激活那次回答里是否白白掺进了这份清单。
   - 结论：验证按需知识确实是请求驱动、只在匹配时进入上下文的，而不是始终生效的规则。
3. **做**：做一次对照复现：把同一份任务知识准备两份，一份放在始终加载的位置，一份放在按需激活的位置，然后用同一类请求各问一次，逐字对比两次输出中出现了什么。
   - 观察：两份配置下，上下文里分别多出了哪些内容，答案在处理方式、详细程度上有没有差异。
   - 结论：验证加载时机的选择会实际改变 Claude 处理请求的方式，而不只是文件组织上的形式差别。
4. **做**：用免费工具做一次事件驱动验证：写一个本地脚本或命令，把它绑定到「文件保存」这个动作上，反复保存几次文件，观察它是否在没有你提出任何请求的情况下自行执行；再把同一件事作为「我知道何时该做」的知识记录下来，对比两种触发方式。
   - 观察：脚本在未被请求时是否被执行、执行了多少次；而单纯记录下来的知识在同样几次保存中是否什么也没发生。
   - 结论：验证事件驱动与请求驱动不是一回事：前者由动作触发，后者由请求内容触发。
5. **做**：为你的项目写一份配置清单，分别列出：始终生效的标准、按需加载的任务知识、事件触发的自动化、隔离上下文的委派工作、外部工具与集成各自负责什么；最后补一段结论，说明为什么某项内容最终没有被放进按需知识里。
   - 观察：清单里有没有职责空缺或同一件事被两个位置重复承担的情况，你的结论段是否给出了明确理由。
   - 结论：验证「各功能各有专长、结合使用而非硬塞」是否在你的实际配置中成立。

## ⑤ 费曼验收
**AI 示范**：这几种自定义不是互相替代：有的每次对话都加载，用来放始终生效的标准；有的按请求匹配才激活，把指令加进当前对话；有的在隔离上下文里替你把活干完再交结果；有的由保存、工具调用这类事件触发；还有的负责接外部工具。各管一摊，组合起来用，别都塞进同一个地方。

**判定要点**（引擎用）：
- Skills（按需加载的特定任务专业知识）：说清它的加载时机是被请求内容匹配之后，而非每次对话都进入；说清它给当前对话补充知识，而不是在隔离环境里执行任务；举出至少一个「只在某些情况才相关」的例子，说明它不该一直占用上下文
- 按需加载与始终加载（加载模型）：能指出另一类方式是每次对话都会加载的；给出「始终适用」这类内容的典型形态，并说明它与只在特定任务下相关内容的分界；给出的判断依据落在「是否任何请求都必须成立」上，而不是凭感觉挑
- 功能组合（结合使用，而非硬塞）：明确表达这些能力解决的是不同问题、不是互相替代关系；能列出至少三种不同职能并各自对应到恰当的位置；指出「当其他选项更合适时不要再硬塞」这一边界，而不是宣称某一种方案能包办全部
