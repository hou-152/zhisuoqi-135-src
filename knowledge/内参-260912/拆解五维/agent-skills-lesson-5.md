# 五维拆解 · agent-skills-lesson-5

## ① 概念 ×3
- **技能分发三通道：仓库、插件、企业托管**：仓库提交：把技能放在 .claude/skills 中，通过 Git 自动共享，任何克隆该仓库的人自动获得、无需额外安装；推送更新后每个人在下次拉取时获得更新。；插件：在插件项目中创建遵循与 .claude 目录类似文件结构的 skills 目录（每个技能一个文件夹，内含 SKILL.md），分发到市场后其他用户自行发现并安装；适合不是过于特定于某个项目、对直接团队以外社区成员也有用的技能。；企业托管设置：管理员在整个组织范围内部署技能，企业技能优先级最高、会覆盖同名的个人、项目和插件技能，并支持 strictKnownMarketplaces 控制插件安装来源；适用于关键词是“必须”的强制性标准、安全要求、合规工作流程和编码实践。
- **子代理的技能隔离**：子代理不会自动看到您的技能：把任务委派给子代理时，它会以全新、干净的上下文开始。；内置代理（Explorer、Plan、Verify）完全无法访问技能，只有在 .claude/agents 中定义的自定义子代理才可以。；自定义子代理可以使用技能，但只有在您明确列出它们时才可以。
- **skills 字段的显式授权**：在 .claude/agents 的代理 markdown 文件前置元数据中写 skills 字段，列出要加载的技能（示例中为 accessibility-audit, performance-check）。；前提是这些技能已存在于 .claude/skills 目录；可用 /agents 命令交互式创建新子代理，或把 skills 字段添加到现有代理的 markdown 文件中。；委派给该子代理时它会加载这些技能并应用于每次审查，用于在委派工作中强制执行标准而不依赖提示。

## ② 阅读 ×1（三层梯度）
> 同一个技能，一个人用只是方便，一群人用才变成标准——而技能往哪儿放，决定了谁能拿到、谁说了算，也决定了子代理为什么空着手干活。

- **直觉**：技能放在哪，谁就能拿到：放进 .claude/skills 跟着仓库走，谁克隆谁有；做成插件上市场，别人自己发现自己装；企业托管则是组织统一配发。子代理像一个新来的外包同事，你不把工具清单写给他，他就空手干活。
- **机制**：.claude/skills 是技能存放处，Git 就是分发管道，.claude 目录里的代理、钩子、技能和设置都随版本控制并走正常 Git 工作流。插件把同样的目录结构（skills 目录，每个技能一个含 SKILL.md 的文件夹）搬到市场分发。企业托管由管理员部署，优先级最高可覆盖同名技能，并用 strictKnownMarketplaces 限定插件只能从白名单来源安装。子代理委派时上下文全新干净，所以必须在代理前置元数据的 skills 字段里点名，技能才会被加载并在每次委派时应用。
- **边界**：材料只交代了企业技能覆盖同名的个人、项目和插件技能，这三者彼此之间的先后次序并未说明。插件不适合过度绑定某个项目的技能；企业层只该用于带“必须”的强制标准，用它会压掉个人与项目的定制。内置代理无论怎么配都无法访问技能，配置只对 .claude/agents 中的自定义子代理有效；而且技能本身必须先存在于 .claude/skills，skills 字段才落得下地。

## ③ 决策 ×3
- **情境**：团队刚打磨出一个 PR 审查技能，希望每个人拉下代码就自动用上，不想让人人再手动装一遍。
  - 做法：把技能提交进仓库的 .claude/skills，靠 Git 自动共享：克隆即获得，推送更新后大家在下次拉取时同步。
  - 适用条件：适用于技能主要服务这个仓库、这个团队，且愿意随版本控制一起演进。如果技能并不特定于某个项目、对直接团队以外的社区成员也有用，才考虑走插件市场那条路。
- **情境**：公司要求所有仓库的安全与合规检查必须统一，不允许各团队自行改写规则。
  - 做法：用企业托管设置在整个组织范围内部署技能，借助最高优先级覆盖同名的个人、项目和插件技能，并用 strictKnownMarketplaces 限定插件只能从批准的来源安装。
  - 适用条件：判断标准是“必须”——强制性标准、安全要求、合规工作流程和编码实践才值得动用这一层。代价是覆盖会压掉个人和项目的定制，非强制的一致性问题不必走这条路。
- **情境**：你把前端审查任务委派给子代理，结果它完全没用上你已经写好的无障碍审计技能。
  - 做法：在 .claude/agents 的自定义子代理 markdown 前置元数据的 skills 字段里明确列出该技能（可用 /agents 交互创建），并先确认技能已存在于 .claude/skills。
  - 适用条件：只对自定义子代理有效，内置的 Explorer、Plan、Verify 配了也用不了。如果只是偶尔一次用到某规则，用提示重申即可；只有在希望把标准固化、委派时不依赖提示，才值得绑定成技能。

## ④ 实验 ×5
1. **做**：在本机任意一个 Git 仓库里建出 .claude/skills/<技能名>/SKILL.md 的目录结构，提交并推送；让另一位同事（或另一份克隆）执行 pull，全程不做任何额外安装。
   - 观察：对方拉取后是否自动拥有了这个技能；你再次推送修改后，对方下次拉取是否同步到新版。
   - 结论：验证“仓库提交是最简单的共享方法”：克隆即获得、无需额外安装，更新随正常 Git 工作流在下次拉取时到达。
2. **做**：只用纸笔或一张表格，画四个同名技能分别放在个人、项目、插件、企业四层，按材料给出的规则逐一标注谁生效。
   - 观察：哪些冲突有明确答案，哪些组合材料根本没有交代次序。
   - 结论：验证企业技能最高优先级、覆盖同名个人/项目/插件技能，同时确认“其余三类彼此次序”在材料中是未说明的边界所在。
3. **做**：在一个插件项目里复刻第 1 步的结构：建 skills 目录，每个技能一个文件夹、内含 SKILL.md，然后把它与 .claude 目录结构并排比对。
   - 观察：两者的文件结构有哪些相同之处，差别出现在分发方式而非目录约定上。
   - 结论：验证插件的目录结构遵循与 .claude 类似的约定，而它的与众不同之处在于“分发到市场，其他用户自行发现并安装”。
4. **做**：用 /agents 创建一个自定义子代理，前置元数据先只写 name、description、tools，不写 skills；把同一个任务委派给它并记录结果。然后在该代理文件中补上 skills 字段（列出已存在于 .claude/skills 的技能），再次委派同一任务，做前后对照。
   - 观察：第一次委派时技能是否被加载、输出是否体现该技能；第二次委派时加载行为与输出质量有什么变化。
   - 结论：验证子代理以全新干净上下文开始、不自动继承技能，只有在前置元数据中显式列出后才会加载并应用于每次委派。
5. **做**：把同一个审查任务分别委派给内置代理（Explorer／Plan／Verify）和一个已用 skills 字段授权的自定义子代理，各自记录是否加载技能、结果是否遵守你设定的标准。
   - 观察：内置代理是否出现任何加载技能或遵循技能标准的迹象，自定义子代理是否稳定复现同一套标准。
   - 结论：验证内置代理完全无法访问技能是一道配置打不开的硬边界，要在委派中强制执行标准只能走自定义子代理这条路。

## ⑤ 费曼验收
**AI 示范**：技能共享三条路：放进 .claude/skills 跟仓库走，克隆即得；做成插件上市场，别人自己装；企业托管优先级最高，覆盖同名技能并限定插件来源。但子代理从零开始，默认看不见技能，必须在代理文件 skills 字段点名才会加载；内置的 Explorer、Plan、Verify 完全用不了。

**判定要点**（引擎用）：
- 技能分发三通道：仓库、插件、企业托管：能分别说出三种分发方式各自的载体与到达使用者的路径，而不是只笼统说“共享技能”。；讲到企业层的两个特征：优先级最高、可控制插件可从哪里安装。；给出各自的适用判断依据（最简单／面向直接团队以外／带“必须”的强制与合规）。
- 子代理的技能隔离：明确指出子代理不自动继承技能，并给出原因是委派时以全新、干净的上下文开始。；区分内置代理与自定义子代理的访问权限差异，说明前者对技能完全不可用、后者也需满足附加条件。
- skills 字段的显式授权：指出授权发生在自定义子代理文件的前置元数据中，且以列出技能名的方式完成。；说明生效前提是技能已存在于 .claude/skills，并指出加载后的效果是每次被委派时都应用。；点出这一做法的价值在于把标准固化下来，不必在每次委派时靠提示重申。
