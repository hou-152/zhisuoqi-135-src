# 五维拆解 · agent-skills-api

## ① 概念 ×3
- **代理技能（Agent Skills）**：模块化功能，每个技能包含指令、元数据和可选资源（脚本、模板），Claude 在需要时自动使用。；是文件系统上的可重用资源，赋予 Claude 特定领域专业知识（工作流程、上下文、最佳实践），把通用代理转变为专家。；与提示不同：提示是对话级、针对一次性任务的指令；技能按需加载，不必在不同对话中重复相同指导。
- **渐进式披露（Progressive Disclosure）**：分层加载：Level 1 元数据启动时始终加载（每技能约 100 tokens，只有 name 与 description）；Level 2 指令在技能触发时加载（低于 5k tokens，SKILL.md 正文）；Level 3+ 资源按需加载（访问前零成本）。；引用文件被读取时才进入上下文；脚本通过 bash 运行，只有输出进入上下文，脚本代码本身从不进入上下文。；结果：保证任一时刻只有相关内容占用上下文窗口，可安装多个技能而不造成启动开销，未使用的捆绑内容没有上下文惩罚。
- **SKILL.md 与 YAML 前置元数据**：每个技能都必须有 SKILL.md，含 YAML frontmatter，必需字段是 name 和 description，正文承载工作流程与指南。；description 必须同时说明技能做什么和 Claude 何时使用它，因为 Claude 正是依据这段元数据判断是否触发技能。；字段约束：name 最多 64 字符、只允许小写字母/数字/连字符、不能含 XML 标签、不能含保留词 anthropic 与 claude；description 非空、最多 1024 字符、不能含 XML 标签。

## ② 阅读 ×1（三层梯度）
> 如果不想再把同一套流程说明反复粘贴进每个对话，就要弄清：技能凭什么按需加载，又凭什么只花约一百词就待在启动提示里。

- **直觉**：把技能想成给新同事的入职指南：平时只先交给他一张技能清单，真遇到做 PPT 或填 PDF 表格，才去翻对应手册、附件和工具。Claude 不会预先吞下全部内容，只在相关任务出现时才按需读文件。
- **机制**：技能是虚拟机上的目录。启动时系统提示只带 YAML 里的 name 与 description（约 100 tokens/技能）；请求匹配 description 后，Claude 用 bash 读 SKILL.md（正文不足 5k tokens）；指令引用 FORMS.md 或数据库 schema 时再读，提到脚本就用 bash 运行、只接收输出。三类内容各有所长：说明用于灵活指导，代码用于可靠性，资源用于事实查找。
- **边界**：「按需加载」不等于随处可用：API 沙箱无网络访问、无运行时包安装，只能用预装依赖；自定义技能不跨产品面同步，共享范围也不同（claude.ai 个人独有、API 工作区范围、Claude Code 个人或项目级）；Agent Skills 不在 ZDR 覆盖范围内。当任务需要联网、装包、跨面上传复用或受 ZDR 保护时，这套机制就不成立。

## ③ 决策 ×3
- **情境**：你在多个对话里反复粘贴同一套规范、步骤或组织经验，每次都从头写一遍。
  - 做法：把它打包成技能：SKILL.md 里放工作流程，YAML 的 description 同时写清「技能做什么」和「什么时候该用它」，让 Claude 在相关请求出现时自动加载。
  - 适用条件：适用条件：这类任务反复出现、指导可复用、来源可信。若只是当下一次性的特殊要求，或内容只对这一次对话有效，直接写在提示里更省事。
- **情境**：你想给技能附上大量资料（完整 API 文档、数据库结构、模板、示例）或一段必须精确执行的代码，又担心占满上下文。
  - 做法：把资料放成 Level 3 资源，只在指令引用时才读取；把重复性操作写成脚本交给 bash 运行，只让输出（如「Validation passed」或具体报错）消耗 token。
  - 适用条件：适用条件：资料确实只按需被引用、脚本输出足够表达结果。若每次任务都必须先读完整份资料才能判断，那它就不再是「按需」，应改用别的方式组织。
- **情境**：同事发来一个来源不明的技能包，或你打算让技能从外部 URL 取数据后直接投入使用。
  - 做法：像安装软件一样对待它：只从可信来源（自己创建或来自 Anthropic）使用；必须用时先彻底审计包内所有文件（SKILL.md、脚本、图片、资源），查找异常网络调用、文件访问模式或与声明目的不符的操作。
  - 适用条件：适用条件：任何要接入敏感数据或关键操作的环境都应如此，生产系统尤其。注意组织级 Skill content scanning 只覆盖 claude.ai 和 Claude Cowork 上传的自定义技能，不覆盖通过 Skills API 或 Claude Console 上传的；即使可信技能，外部依赖变化也可能把它污染。

## ④ 实验 ×5
1. **做**：在本地建一个技能目录：pdf-processing/SKILL.md 与同目录的 FORMS.md，手动模拟一次「读取」路径——先只读 SKILL.md，再判断当前任务是否需要 FORMS.md，最后记录这次任务实际读了哪几个文件。
   - 观察：哪些文件被真正读取、哪些始终留在硬盘上没有被打开。
   - 结论：验证按需文件访问：只读任务需要的文件，其余文件在被引用前不消耗上下文。
2. **做**：为同一个技能写两版 description：A 版只写「做什么」，B 版同时写「做什么 + 何时使用」；再准备 6 个请求（3 个相关、3 个不相关），逐个对照两版描述判断会不会触发。
   - 观察：两版各自出现多少次漏触发和误触发，差异出现在哪些请求上。
   - 结论：验证触发判断依赖 description 同时说明功能与使用时机，只写功能的描述会产生偏差。
3. **做**：把一段校验脚本（例如 fill_form.py 十行代码）分别统计两种路径的量级：脚本源码的字符/词数，与它正常执行后的输出（如一行「Validation passed」或一条报错）的字符/词数。
   - 观察：源码量与输出量之间的倍数差距，以及输出是否足以判断执行结果。
   - 结论：验证脚本代码本身不进入上下文、只有输出消耗 token，因此比让 Claude 临时生成等效代码更省。
4. **做**：为同一个技能做一张加载成本阶梯表：分别统计 Level 1（name + description）、Level 2（SKILL.md 正文）、Level 3（被引用文件）的字符/词数，并换算成大致 token 量。
   - 观察：启动时固定付出的那一层有多小，触发后才付出的那层有多大，未被访问层是多少。
   - 结论：验证启动成本约为每技能一百 tokens 的量级，因此可以安装多个技能而不造成启动上下文开销。
5. **做**：列出你计划让技能做的事（联网抓取外部数据、运行时 pip install 新包、把同一个技能同时用在 claude.ai 和 API、要求数据受 ZDR 保护），逐条对照运行时限制、跨产品面同步与数据留存边界，标出哪些在该产品面不成立。
   - 观察：哪些计划项被边界直接否掉，哪些只在某个产品面可行（如 Claude Code 有完整网络权限，API 沙箱没有）。
   - 结论：验证技能能力取决于所在产品面，「一次上传处处可用」不成立，规划技能前必须先对齐边界。

## ⑤ 费曼验收
**AI 示范**：技能不是一次性提示，而是文件系统里的文件夹：指令、脚本、资料打包在一起。启动时 Claude 只看到名字和描述；请求匹配描述后，才用 bash 读 SKILL.md，再按需读附件、跑脚本——脚本代码不进上下文，只有输出进入。这就是渐进式披露。

**判定要点**（引擎用）：
- 代理技能（Agent Skills）：说清它是可复用、按需加载的模块化能力包（含指令、元数据与可选资源），而不是一次性的对话级提示；说清它的作用是把通用代理变成特定领域专家，承载工作流程、上下文与最佳实践；提到「一次创建、自动使用」，从而免去在不同对话里重复同一套指导
- 渐进式披露（Progressive Disclosure）：说清内容分阶段进入上下文：先元数据、触发后读指令、资源被引用时才读取；给出层级间的成本差异（元数据约百词、指令不足 5k、未访问资源为零）；说清脚本通过 bash 运行，只有输出进入上下文，代码本身不进入
- SKILL.md 与 YAML 前置元数据：说清每个技能必须有 SKILL.md，其 YAML 前置元数据中 name 与 description 为必需字段；说清 description 同时承担「做什么」与「何时触发」两件事，是 Claude 判断是否触发技能的依据；至少说出一条格式约束（name 的字符与保留词限制，或 description 的非空与长度上限）
