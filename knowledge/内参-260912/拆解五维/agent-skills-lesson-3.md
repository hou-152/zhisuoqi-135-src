# 五维拆解 · agent-skills-lesson-3

## ① 概念 ×3
- **description（必填字段）**：description 是必填字段，最多 1024 个字符；它告诉 Claude 何时使用该技能，Claude 用它来进行匹配，因此是最重要的字段。；好的描述应该回答两个问题：这项技能有什么作用？Claude 应该在什么情况下使用它？；若技能没有在预期的时间触发，应添加更多与实际请求措辞相匹配的关键词；指示要明确，不能写成“帮忙处理文件”这类含糊说法。
- **allowed-tools（可选字段）**：allowed-tools 是可选字段，用于限制 Claude 在技能激活时可以使用的工具，适用于只读或对安全性要求较高的工作流程。；示例中设为 Read, Grep, Glob, Bash，技能激活时 Claude 无需请求许可即可使用这些工具，不能编辑，也不能写作。；如果完全省略 allowed-tools，该技能不会限制任何内容，Claude 使用其正常的权限模型。
- **逐步披露（progressive disclosure）**：技能与对话共享上下文窗口，激活时会加载 SKILL.md 内容；把全部内容塞进一个 2000 行的文件会占用大量上下文空间，而且维护起来很麻烦。；做法是把必要的说明留在 SKILL.md，把详细参考资料放在单独文件，Claude 只在需要时才阅读，并在 SKILL.md 中链接支持文件、附上何时加载的清晰说明。；经验法则是 SKILL.md 最好控制在 500 行以内，超过就考虑拆分成单独的参考文件；技能目录中的脚本无需加载内容即可运行，只有输出会消耗令牌。

## ② 阅读 ×1（三层梯度）
> 技能写得再好，description 里没写清“什么时候用它”，Claude 就永远不会把它叫出来——这一课讲的正是决定技能生死的那个字段。

- **直觉**：SKILL.md 前置元数据里有两个必填字段：name 管身份（小写字母、数字、连字符，最多 64 字符，要和目录名一致），description 管触发（最多 1024 字符）。材料把“最重要”直接给了 description，因为 Claude 靠它做匹配判断这个技能相不相关。
- **机制**：Claude 拿当前请求去比对 description，决定是否激活技能；激活后 SKILL.md 内容被载入与对话共享的上下文窗口，同时 allowed-tools 白名单生效——表内工具免请求许可，白名单外的编辑、写作被挡死。为控制上下文占用，细节被移到支持文件按需读取（例如 architecture-guide.md 只在有人问系统设计时才被读），脚本则只运行不被读入，只有输出消耗令牌。
- **边界**：500 行只是“一个好的经验法则”，不是硬性上限；完全省略 allowed-tools 就等于不设任何限制，回到正常权限模型；脚本省掉的是脚本正文进入上下文，而不是省掉脚本本身。description 没触发时作者给的补救办法只有一条：补上与实际请求措辞相匹配的关键词——若请求本身不落在技能范围内，加词也救不回来。

## ③ 决策 ×3
- **情境**：你写好的技能在该用的时候没被触发，你以为是自己配置出错。
  - 做法：先回头改 description：补上更多与你实际请求措辞相匹配的关键词，并把“技能有什么作用、Claude 应在什么情况下使用它”这两个问题答清楚。
  - 适用条件：适用于该技能确实应该在这个时机被使用、只是措辞没对上；如果这个请求本来就不属于该技能的职责范围，改描述的效果有限，应该换技能或改职责边界。
- **情境**：团队里有一个只做排查、审计或巡检的工作流，你希望它绝对不能改动文件。
  - 做法：给该技能设置 allowed-tools 白名单，例如只列 Read, Grep, Glob, Bash，让激活期间只能读、不能编辑也不能写作。
  - 适用条件：适用于只读任务、安全要求较高或需要设安全护栏的场景；如果这个技能本身就需要写文件或改代码，就不要用这套白名单，或者接受省略 allowed-tools 后 Claude 使用正常权限模型。
- **情境**：你的 SKILL.md 越写越长，参考资料、示例、脚本说明全堆在一个文件里。
  - 做法：把必要说明留在 SKILL.md，把详细参考资料拆到单独文件，并在 SKILL.md 里链接它们、写清什么时候才加载哪个文件。
  - 适用条件：当那部分细节只在少数场景下才相关时，拆分才能省下上下文；如果内容每次激活都必须用到，拆出去只会多一次读取，留在主文件反而更直接。

## ④ 实验 ×5
1. **做**：为同一个技能写两版 description：一版是“帮忙处理文件”这种含糊说法，一版明确写出这项技能有什么作用、Claude 应该在什么情况下使用它；然后分别用你平时真实会说的那句话去请求。
   - 观察：两版描述下技能是否在预期时机被触发，以及触发时你用的措辞与描述中的关键词是否吻合。
   - 结论：description 是 Claude 做匹配的依据，措辞贴近真实请求才能被正确匹配。
2. **做**：复现材料中的前置元数据示例：name: codebase-onboarding、description: Helps new developers understand the system works.、allowed-tools: Read, Grep, Glob, Bash、model: sonnet，然后在技能激活状态下要求它修改或新建一个文件。
   - 观察：白名单内的读取、检索、搜索类操作是否免请求许可直接执行，编辑与写作类操作是否被挡住。
   - 结论：allowed-tools 是激活期间的权限白名单：表内免许可，表外的编辑与写作被禁止。
3. **做**：把上一个实验的前置元数据里 allowed-tools 一行整个删掉，保持其他字段和请求不变，重复同一次操作。
   - 观察：技能是否还会阻止写文件、是否回到正常的权限请求流程。
   - 结论：完全省略 allowed-tools 不等于设限，而是不限制任何内容，Claude 使用其正常的权限模型。
4. **做**：挑一份超过 500 行的 SKILL.md，拆成“精简主文件 + 一个单独的参考文件”，主文件里只留必要说明、链接和“何时加载该参考文件”的说明；同一个技能分别在被问及参考内容与不被问及参考内容时各问一次。
   - 观察：两次提问中参考文件是否被读取，以及激活后主文件变短对上下文占用和维护难度的影响。
   - 结论：逐步披露能让上下文里出现的是目录而不是整份文档，500 行是可操作的经验边界。
5. **做**：在技能目录里放一个脚本，在 SKILL.md 中把指令写成“告诉 Claude 运行这个脚本”，而不是“读取这个脚本”，执行一次并记录 token 消耗。
   - 观察：脚本正文是否被载入上下文，消耗是否只发生在脚本的输出上。
   - 结论：脚本是运行的对象而不是阅读的对象，只有输出会消耗令牌，从而保持上下文高效。

## ⑤ 费曼验收
**AI 示范**：description 最重要：说清技能做什么、何时用，措辞贴近实际说法，Claude 靠它匹配。allowed-tools 是可选工具白名单，设了就只给这几把工具，省略则完全不限。SKILL.md 控在 500 行内，厚资料放旁边按需加载；脚本只运行，只有输出耗 token。

**判定要点**（引擎用）：
- description（必填字段）：能说出该字段必填、有字符数上限，并且是 Claude 用来做匹配、决定是否启用技能的依据。；能说出好的描述必须同时回答“技能有什么作用”和“Claude 应在什么情况下使用它”两个问题。；能说出技能未在预期时机触发时的排查方向是补充与实际请求措辞一致的关键词，并指出含糊指令不可取。
- allowed-tools（可选字段）：能说出它是可选字段，作用是限制技能激活期间可用的工具，面向只读或高安全要求的工作流。；能举出白名单生效时的效果：表内工具免请求许可，同时不能编辑、不能写作。；能说出省略该字段并不等于设限，而是不限制任何内容并回到正常权限模型。
- 逐步披露（progressive disclosure）：能指出技能激活会把 SKILL.md 载入与对话共享的上下文窗口，因此大文件既占空间又难维护。；能说出做法：主文件只留必要说明，详细资料放单独文件并附上何时加载的链接说明，行数控制在经验边界以内。；能区分脚本与文档的差别：脚本运行而不把内容读进上下文，只有输出消耗令牌。
