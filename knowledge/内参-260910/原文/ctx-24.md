## 核心观点

- AI 领域的对话正在从「提示词工程」（prompt engineering）转向一个更宽、也更有力量的概念：**上下文工程**（Context Engineering）。Tobi Lutke 的定义被作者认为说到了点上——它是「为任务提供全部上下文，使其对 LLM 而言变得看似可解的艺术」。
- 随着 agent 兴起，真正要紧的问题变成了：我们往那块**有限的工作记忆**（limited working memory）里装什么信息。决定一个 agent 成败的主要因素，是你给它的上下文的质量。
- 全文最锋利的一句判断：**大多数 agent 的失败已经不再是模型失败，而是上下文失败**（Most agent failures are not model failures anymore, they are context failures）。这句话把归因权从模型手里拿了回来，交还给做系统的人。
- 廉价 demo 与「魔法级」agent 的差距，不在更聪明的模型或更巧妙的算法，而在于**为正确的任务提供正确的上下文**。
- 上下文工程的定义：设计并构建**动态系统**，在正确的时间、以正确的格式，提供正确的信息与工具，让 LLM 拥有完成任务所需的一切。
- 构建强大可靠的 agent，正在越来越少地关于「找到一个魔法提示词」或「等模型升级」，越来越多地关于上下文的工程化——这是一个**跨职能挑战**（cross-functional challenge）。

## 术语转向：从提示词工程到上下文工程

- Context Engineering 是 AI 世界正在获得关注度的新术语，讨论的重心正在从 prompt engineering 迁移出去。
- 作者引用 Tobi Lutke 的说法作为起点：它是「the art of providing all the context for the task to be plausibly solvable by the LLM」——注意关键词是 **plausibly solvable（看似可解）**，不是「更聪明」。信息不全的任务，模型只能猜。
- 转向的直接推力是 agent 的兴起：一旦模型要跨多步、调工具、持续工作，「往有限的工作记忆里装什么」就成了首要工程问题。
- 观察结论前置：agent 成败的主要决定因素是上下文质量；失败模式的归因也随之改变——不再是模型不行，而是上下文不行。

## 什么是上下文：模型生成响应之前看到的一切

要理解上下文工程，必须先扩展对「上下文」的定义。它不只是你发给 LLM 的那条单一提示词——把它想成**模型在生成响应之前看到的一切**（everything the model sees before it generates a response）。

原文把「上下文」拆成七类构成：

- **Instructions / System Prompt**：定义模型在一次对话中行为方式的初始指令集，可以也应该包含示例与规则。
- **User Prompt**：来自用户的即时任务或问题。
- **State / History（短期记忆）**：当前对话，包括把事情推到此刻的用户与模型的历次回应。
- **Long-Term Memory（长期记忆）**：跨越许多次先前对话积累起来的持久知识库——学到的用户偏好、过往项目的摘要、被要求记住以备将来使用的事实。
- **Retrieved Information（RAG）**：外部的、最新的知识，来自文档、数据库或 API 的相关信息，用于回答具体问题。
- **Available Tools**：它可以调用的全部函数或内置工具的定义（例如 check_inventory、send_email）。
- **Structured Output**：对模型响应格式的定义，例如一个 JSON 对象。
- 这份清单的意义在于：上下文是一个**装配结果**，七类来源各有各的获取路径与成本，而它们共享同一块有限空间。

## 廉价 demo 与「魔法级」agent：同一封邮件的两种回复

- 作者用一个极简场景做对照实验：AI 助理被要求根据一封邮件安排会议，邮件原文只有一句 —— 「Hey, just checking if you're around for a quick sync tomorrow.」
- **「廉价 demo」型 agent**：上下文贫乏，只看到用户的请求，别的什么都没有。它的代码可能完全能跑——调用 LLM、拿到响应——但输出无用且机械：「Thank you for your message. Tomorrow works for me. May I ask what time you had in mind?」
- **「魔法级」agent**：由丰富的上下文驱动。关键的认知转换在这里——**代码的首要职责不是弄清楚「怎么」回应，而是「收集」LLM 完成目标所需的信息**。在调用 LLM 之前，你会把上下文扩展到包含：
- 你的日历信息（显示你已被排满）。
- 你与此人过往的邮件（据此判断合适的非正式语气）。
- 你的联系人列表（识别出对方是关键合作方）。
- send_invite 或 send_email 这类工具。
- 于是同一个模型能生成这样的回复：「Hey Jim! Tomorrow's packed on my end, back-to-back all day. Thursday AM free if that works for you? Sent an invite, lmk if it works.」
- 这个对照要证明的事：魔法不在更聪明的模型或更巧妙的算法里，而在于为正确的任务提供了正确的上下文。差距全部来自「调用之前装进去的东西」。

## 上下文工程的定义与四条特征

- 与提示词工程的分界：prompt engineering 聚焦于在一个文本字符串里打磨出完美的指令集；context engineering 的范围要宽得多。
- 作者给出的定义：**上下文工程是设计并构建动态系统的学科，这些系统在正确的时间、以正确的格式，提供正确的信息与工具，从而给 LLM 完成一项任务所需的一切。**
- 四条特征（原文以并列条目给出，是全文最可操作的部分）：
- **A System, Not a String（是系统，不是字符串）**：上下文不是一个静态的提示词模板，它是**在主 LLM 调用之前运行的那个系统的输出**。
- **Dynamic（动态）**：即时生成，为当下任务量身定制。这次请求可能是日历数据，下次是邮件或一次网络搜索。
- **About the right information, tools at the right time（正确的信息与工具，在正确的时间）**：核心工作是确保模型不缺关键细节（「Garbage In, Garbage Out」）。这意味着**同时提供知识（信息）与能力（工具）**，且只在需要且有用时提供。
- **Where the format matters（格式很重要）**：你如何呈现信息是有影响的。**一份简洁的摘要优于一堆原始数据的倾倒；一个清晰的工具 schema 优于一句含糊的指令。**
- 这四条合起来把「上下文」从文本对象改写成了系统对象：它有生产者、有触发时机、有格式契约。

## 对构建可靠 agent 的含义

- 重心迁移：构建强大而可靠的 AI agent，越来越少地关于寻找一个魔法提示词或等待模型更新，越来越多地关于**上下文的工程化**——在正确的时间、以正确的格式提供正确的信息与工具。
- 这是一个**跨职能挑战**：需要理解你的业务用例、定义清楚你的输出、并把一切必要信息结构化，好让 LLM 能够「完成任务」。
- 归因结论再次收束：agent 的失败不只是模型失败，它们是上下文失败。这条判断既是诊断工具，也是责任划分——它把改进的着力点放在可被工程化的一侧。

## 概念网络

### 关键概念

### 上下文工程（Context Engineering）

**context**：全文的中心概念，被明确定义为「设计并构建动态系统的学科，这些系统在正确的时间、以正确的格式，提供正确的信息与工具，从而给 LLM 完成一项任务所需的一切」。作者用它替代 prompt engineering 作为 AI 的「新技能」，并指出这正是决定 agent 成败的地方。

**费曼一下**：以前我们琢磨的是「这句话该怎么问」，现在要琢磨的是「回答这个问题之前，得先把哪些资料和工具摆到桌面上」。它更像给一个新来的助理准备工作台，而不是给他下一道指令。

### 上下文（Context）：模型生成之前看到的一切

**context**：作者要求先扩展定义——上下文「不只是你发给 LLM 的那条单一提示词」，而是「模型在生成响应之前看到的一切」，并拆成七类：系统提示、用户提示、短期记忆（State / History）、长期记忆、检索信息（RAG）、可用工具、结构化输出定义。

**费曼一下**：模型答题时能看到的整张桌面就是上下文——题目、规则、笔记本、参考书、计算器、答题卡格式，全都算。只盯着「题目怎么写」，等于只擦干净了桌面的一角。

### 有限的工作记忆（limited working memory）

**context**：随着 agent 兴起，「我们往这块有限的工作记忆里装载什么信息」变得更加重要。这是上下文工程之所以是「工程」的物理前提——空间有限，所以必须做取舍。

**费曼一下**：模型的注意力像一张放不大的桌子。资料再多也只能摊开一部分，所以问题从「有没有资料」变成「这一刻该把哪几份摊在最上面」。

### 上下文失败，而非模型失败（context failures, not model failures）

**context**：全文最有力的归因判断，出现两次——「大多数 agent 的失败已经不再是模型失败，而是上下文失败」「agent 的失败不只是模型失败；它们是上下文失败」。它是从「换个更强的模型」转向「修好装配上下文的系统」的开关。

**费曼一下**：助理办错事，先别急着换人。多半是你没告诉他日程满了、没给他通讯录、没给他发邀请的权限。同一个人，材料给全了，表现就换了一个档。

### 系统而非字符串（A System, Not a String）

**context**：上下文工程四条特征的第一条，也是它与提示词工程最锋利的分野：上下文「不是一个静态的提示词模板」，而是「在主 LLM 调用之前运行的那个系统的输出」。

**费曼一下**：提示词是一张写好的卡片，谁来都念同一张。上下文是一条流水线的产品——每次调用之前先跑一遍，产出这一次专属的那份材料。

### 动态装配（Dynamic）

**context**：第二条特征，指上下文「即时生成、为当下任务量身定制」；原文给出的对比是「这次请求可能是日历数据，下次是邮件或一次网络搜索」。

**费曼一下**：不是准备一个万能资料包，而是每次接到任务后临时抓取：今天要排会就调日历，明天要回客户就调往来邮件。资料的清单本身是随任务变的。

### 正确的信息与工具，在正确的时间

**context**：第三条特征，核心工作是「确保模型不缺关键细节」，作者用「Garbage In, Garbage Out」点明后果；同时强调这意味着提供知识（信息）与能力（工具）两样东西，且**只在需要且有用时**提供。

**费曼一下**：既要给资料，也要给工具，还要挑时候给。全部一次性塞过去不是慷慨，是把桌子占满；关键细节漏掉一条，后面全是无用功。

### 知识与能力的双供给（information and tools）

**context**：作者在第三条特征中特意区分的两类供给物——knowledge（information）与 capabilities（tools）。在七类上下文构成中，它们分别对应 RAG / 记忆一侧与 Available Tools 一侧，如 check_inventory、send_invite。

**费曼一下**：光告诉助理「你老板明天满档」，他也只能干看着；还得给他一个能发邀请的按钮。知道什么和能做什么，缺一样任务都落不了地。

### 格式即上下文（where the format matters）

**context**：第四条特征——「你如何呈现信息是有影响的」，并给出两条可直接执行的判断：「一份简洁的摘要优于一堆原始数据的倾倒」「一个清晰的工具 schema 优于一句含糊的指令」。七类构成里的 Structured Output 也属于格式层面的上下文。

**费曼一下**：同样的信息，摆放方式不同，效果差很远。给人一份两行的摘要，比甩过去一整个数据库导出更管用；工具说明写清参数，比嘴上交代一句强。

### 廉价 demo 与「魔法级」agent

**context**：全文的示范性对照——同一封「明天有空快速对齐吗」的邮件，上下文贫乏的 agent 只能回出礼貌而机械的「Tomorrow works for me. May I ask what time you had in mind?」；被日历、往来邮件、联系人列表与发邀请工具喂饱的 agent，回出的是「Tomorrow's packed on my end... Thursday AM free if that works for you? Sent an invite」。作者用它证明「魔法不在更聪明的模型或更巧妙的算法里」。

**费曼一下**：这是判断一个 AI 产品成色的照妖镜。看它回答得体不体面，其实是在看它回答之前被喂了多少东西。代码水平相同，上下文水平不同，成品一个像玩具，一个像同事。

全文的思想网络由一次**定义扩张**发动。作者先把「上下文」从「你发出的那条提示词」扩张为「模型生成响应之前看到的一切」（C2），这一步是整篇文章的地基：只有当上下文被重新划界为七类构成的装配结果，「工程化」才有对象可言。因此 C2 是**支撑**关系而非并列关系——它不解释上下文工程是什么，它让上下文工程成为可能。

与 C2 构成直接**张力**的是有限的工作记忆（C3）。上下文的可选内容原则上无边界（历史、长期记忆、检索、工具、格式定义都能往里放），但模型的工作记忆是有限的。这组「无边界的候选 × 有限的容量」是全文的动力源：正因为装不下全部，才需要有人决定装什么、何时装、以什么形状装。取舍的必然性把「上下文」从素材问题变成了设计问题。

从提示词工程（C11）到上下文工程（C1）是一条**演化**链条，而不是替换或否定。两者的分野由「系统而非字符串」（C5）这条特征最清晰地标出：C5 与 C11 之间是**对立**关系——一边是静态模板，一边是主调用之前运行的另一个系统的输出。C5、动态装配（C6）、正确的信息与工具在正确时间（C7）、格式即上下文（C8）四者是 C1 的**层级**展开：它们不是四个独立主张，而是同一个定义的四个面——系统性回答「谁生产」，动态性回答「何时生产」，C7 回答「生产什么」，C8 回答「以什么形状交付」。

C7 之下再分出知识与能力的双供给（C9），是一层**支撑**细化。作者特意把 knowledge（信息）与 capabilities（工具）并列，是为了防止上下文工程被窄化成「检索更多资料」——只给资料而不给 send_invite 一类能力，任务同样落不了地；而「只在需要且有用时提供」又把这条特征拉回到与 C3 的张力上，形成闭环。

网络的收口处是归因判断 C4：上下文失败而非模型失败。它在结构上有两重身份。向上，它**支撑**C1 的必要性——如果失败大多源于模型，改进的着力点就该在模型侧，上下文工程也就不成学科；向下，廉价 demo 与魔法级 agent 的对照（C10）**印证**它：同一个模型、同一封邮件，只因调用前装进去的东西不同，产出便从机械客套变成得体协作。这条从「诊断」到「实证」再回到「学科正当性」的回路，是全文说服力的真正来源，也是「魔法不在更聪明的模型里」这句结论能站住的原因。

## 费曼 x3

agent 做不好的时候，人的第一反应几乎总是怀疑模型。换个更新的版本，加一段更严厉的系统提示，期待下一次输出忽然聪明起来。但卡住的地方常常不在推理能力，而在它下判断时手里握着的东西太少。Tobi Lutke 那句定义值得反复读：这是为任务提供全部上下文、使其对 LLM 而言变得看似可解的艺术。可解——不是更聪明，是可解。信息不全的任务，再强的模型也只能猜。

正因如此，「大多数 agent 的失败已经不再是模型失败，而是上下文失败」这句话才有重量。它把归因权从模型手里拿回来，交给做系统的人。一封「明天有空快速对齐吗」的邮件，信息贫乏的 agent 只能回一句礼貌而机械的「明天可以，你想几点」；而在调用模型之前先把日历、与此人的往来邮件、联系人身份，以及发邀请的工具装进上下文，同一个模型就能回出「明天满档，周四上午行吗，邀请已发」。差距不在算法，在装进去的东西。

上下文工程与提示词工程的分野，最锋利的一句是：它是系统，不是字符串。提示词是静态模板，上下文是另一个系统在主调用之前跑出来的产物，按当下任务动态装配——这次是日历，下次是邮件或一次搜索。它同时供给两样东西，知识和能力，信息和工具，而且只在需要且有用时供给。

还有一条容易被跳过：格式本身就是上下文的一部分。一份简洁的摘要胜过一堆原始数据的倾倒，一个清晰的工具 schema 胜过一句含糊的指令。同样的信息换个呈现方式，模型的表现就不一样——这解释了为什么「垃圾进，垃圾出」在 agent 时代不是老话，而是日常事故的根因。

于是构建可靠 agent 的重心悄悄挪了位置：从寻找魔法提示词、等待模型升级，挪到设计那个决定「什么信息、什么工具、什么格式、什么时机」的系统。这是一件跨职能的活，要懂业务场景，要定义清楚输出，要把必要信息组织成模型能用的形状。写代码的人真正的任务，不再是想清楚怎么回答，而是把回答所需的东西凑齐。
