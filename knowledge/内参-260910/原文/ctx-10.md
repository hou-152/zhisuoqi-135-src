## 核心观点

- Linear 联合创始人兼 CEO Karri Saarinen 的中心主张：把 AI 装进软件开发，靠的不是抢着上功能，而是先深入理解工作流。Linear 不去做又一个 chatbot，而是要成为“引导 agent、承载组织上下文的系统”——一句话，成为 agent 的骨架。
- 对“SaaS 已死”的回应：这个时代的完美生意恰恰仍是 SaaS。Linear 是工作被发起、信息被记录的“粘性界面”，却不用为 token 买单——token 成本由 OpenAI、Anthropic 和各家 coding agent 承担。方向上护城河确实在蒸发，但“人人自己 vibe code 出一个 CRM”的叙事过于简化。
- 度量与质量：agent 写了多少代码、合并了多少 PR、烧了多少 token，都是虚荣指标，只量出产出、量不出价值。真正该看的是产品是否变好、bug 是否更少、用户是否真的喜欢。Linear 靠“零 bug 政策 + 一周 SLA”，让 coding agent 先做第一遍修复。
- 节奏哲学：执行要快，决策要慢。不要用 AI 去“speed-run”决策；先花时间找对问题和方法，一旦定了再全速迭代。设计与产品常需要“概念性工作”——像一辆“概念车”，产出的是理解，而不是可发货的功能。
- 人的位置：agent 会接管执行、甚至部分自主决策，但产品构建仍是手艺与艺术，靠直觉而非 A/B 测试。人的角色转向定义策略、设定目标、判断什么值得做；你把自己的思考说得越清楚，就越能把它 codify 给 agent。

## 理解优先于跟风：Linear 为什么没有抢着上 AI

- Karri 的方法论来自设计背景：先理解问题，再动手。他观察到科技圈的通病是“不去理解就跳进去做”——“我能做这个，那我现在就做”，却不问“该不该做、它是否真的帮到你”。（04:17 高亮：人们往往不试图理解事物，而是直接跳进去做。）
- 早期 AI 浪潮里，“每家公司都冲进这一刻”，宣称“我们现在是 AI 公司了，因为集成了 chatbot”。Linear 内部也试过，然后发现“这其实没什么用”——找不到真正需要它的工作流。
- 于是他们花了大约两年去理解工作流：“人们到底想怎么用这些东西。”使命从未改变：让 Linear 承担运营一个产品团队的负担——搞清楚该做什么、什么时候做，让人（或 AI）去建。AI 反而让使命更好，因为能自动化更多负担，把品味、手艺、思考留给人。
- 落地做法之一：发布 agent 平台——一个开放平台，文档很好，agent 能自己读文档、自建集成。因此如今大多数 coding agent 都接入了 Linear：OpenAI 把它 codex 那类云端 agent 接了进来，只因为 Linear 就摆在那儿、随手可用。
- 世界观：不会只有一个 agent，每个人都会有很多 agent，公司也会自建 agent（05:30 高亮）。客户 Coinbase 和 RAMP 就自建了 homegrown coding agent 并接入 Linear。Linear 因此成为“引导 agent、构建上下文的系统”，但不试图拥有这个市场的一切，可以和别的公司共处。
- 现在也在往 Linear 里加一个聊天界面，但重点是“工具 + 技能 + 理解”：比如综合客户请求，因为 Linear 本就是客户问题、请求汇聚之处，Linear agent 能原生地看穿其中的模式。目标是给组织带来清晰与上下文，供 AI 构建工作流时使用。
- 更深的问题：当 AI 建得更多、执行得更多，问题变成“如何富有成效地驾驭它”。你可以派一百万个 agent 去干活，但它们该干什么？如果不想清楚，很多工作其实没用。你需要一个决策过程去判断“这真的重要吗、我们该做吗”——Linear 正是建立这种意图与上下文、再交给 agent 去建的地方。

## “SaaS 已死”是一个过度简化的叙事

- 现象：股市认为 SaaS 已死。两年前一批公司（包括很多 SaaS）冲进 chatbot，很大程度上是“我们知道这事正在发生，至少得显得在做点什么”。如今公开市场开始反过来要求这个。
- Linear 的处境：没有来自投资人的压力（这是“挑对投资人”的好处，他们信任团队做正确判断）。内部确有压力，但结论是“我们现在就是看不到这么做的价值”，得先找到真正帮到这些公司的价值。
- 市场噪音：现在节奏快了很多，每隔几周就有变化。“这周有人在搞某种 loop，几周后大家又说 loop 是个坏主意。”这些是该读、该理解的信号，但很多没有在真正重要的大型组织语境里被测试过；没测过，就无法预测事情究竟会怎么变。
- 对 SaaS 叙事的判断：方向上大概正确——对投资人而言，未来现金流更不确定，因为格局在变，不能指望一切照旧。但“人们会自己攒出一个 CRM 工具”太简化，他不认为会那样发生。
- 更可能的图景：会冒出新公司；很多上市公司并不是最灵活或最稳健的方案，只是大公司在用的大方案，带着某种惯性。上市公司受伤最重，因为它们的护城河正在消失。即便对 Linear，也要重新活在“第一天”（day one）的世界里，不能再依赖过去的决定，要以全新眼光重看这些问题：当 agent 进入产品开发流程，会冒出哪些新问题、如何帮上忙。不该被过去的产品绑住，而要看未来的产品该是什么样。
- 这对存在了几十年的大公司更难；成长型公司或创业公司能做得好得多。

## AI 时代的工程工作流与质量度量

- 团队规模：约 120 人，约一半（60 人）在产品团队。
- 转型过程：曾有一段时间，公司需要鼓励大家更多地用这些工具——人有惯性，一直用老办法，就越来越不愿尝试新工具。如今几乎所有工程、有时连设计和 PM 也都在用 agent 编码工具。
- 虚荣指标：Karri 常在 Twitter 上调侃——如今最大的虚荣指标是“你多少代码是 agent 写的、你合并了多少 PR”。这度量的是产出，但产出做了什么？是否真的产生价值、改进产品？高活动量有时是负的——它可能引入不必要的复杂性或 bug。所以“活动并不总是正向的，有时是负向的”。
- 激励错配：市场上有一批“token 卖家”式的大公司，其商业模式就是让你花更多 token（你花得越多，它们的收入和市场份额越高）。于是有大量“你应该花更多 token”的激励，却没人说“你该想清楚、花得好”。但花更多 token 从来不等于产品更好。
- 更好的度量：仍是经典的利润、营收、用户喜爱——尽管这些是滞后指标。token 使用量可以按人或按团队看，但别推到极端、当成唯一指标，只把它当信号。真正要问的是：产品在改进吗？新功能有好评吗？bug 更少吗？bug 是可度量的（前提是你诚实地跑一个真正记录 bug 的跟踪流程）。
- 零 bug 政策：Linear 有一个 team triage，所有 bug 都进去，一周 SLA 内必须修完。现在 coding agent 能先做第一遍修复，然后 @ 那位工程师；工程师若不喜欢或想改，也能在 Linear 里改、在 Linear 里 review 代码。这形成了一个很顺的工作流。
- Karri 的态度：“现在有了 agent 和 AI，你为什么还会有 bug？没有借口了。”根子在一个选择：你到底在乎产出的质量，还是只想要更多产出。Linear 选质量，而 AI 提供了在不拖慢团队的前提下维持这一标准的杠杆。

## 决策要慢、执行要快

- 表面矛盾：Karri 一边强调“要慢下来思考”，一边又用让人更快的工具。他的解法是：在执行上要快，在“决定做什么”上要慢。
- 危险所在：用 AI 去“speed-run”决策，甚至干脆不做决策。有人现在就是有想法立刻建，结果一群人盯着一个“没人真正知道为什么存在、该不该做”的东西。每个新原型都显得有点用，但你没有一个好的方式给它定位——它相对于其他事到底有多有用？现在就该投入吗？
- 原则（23:25 高亮）：“我不想让找问题这件事变快。你应该花时间去找对的问题、对的方法；一旦你定了，就可以走得更快。”Linear 流程不多，但核心是“我们要承诺做这件事”；一旦承诺了某个修复或项目，就要让循环变快、全速改进。
- 缩短循环的实例：他们大量用 Slack，配上 Slack agent 讨论，一旦决定“我们该做这个”，就直接 @ Linear：“能把这段对话变成 issue 吗？”于是事情立刻变得可执行，而不是“我们得先开个会、再立项、再分派人”。所有这些工具的共同模式：缩短某个循环，让你能立刻做，而不用等下周或别的时间——立刻做的成本其实很低。

## 概念性工作与迭代式地理解问题

- Dan 的自述共鸣：作为产品构建者，他常常“不做出来就不知道自己在做什么”，得先做五个自己都说不清的东西，然后才恍然“啊，就是这个”，才真正理解它。Karri 认可这是一种“通过做来理解”的工作流。
- “概念性工作”：在设计里，有时输出本身就是一个“概念”——不一定要交付。“我们不必真的把它发出去，但我走过了理解这个问题的过程，我现在有了一个关于它的概念。”
- “概念车”比喻：在大公司里，他用“概念”这个词是为了不吓到人。就像概念车——“这辆车不会量产，但这里有些能影响下一辆车的想法”。当你看到某个非常不同的东西，恐惧会冒出来：“如果改这个，还有什么会跟着坏？”但此刻的重点不是去决定那个，而是先决定“这个新概念有没有价值、是否重要到值得推进”，问题以后再处理。这是在切分“你现在到底在做哪一个决策”。
- 实践：他会在公司里彻底重做某个界面，说“我觉得这个项目该长这样”，和现状完全不同。有人说“这挺有意思”，有人说“它在这条那条上行不通”，他回“没关系”。产出可能只是一个 Figma 设计或原型。即使有了所有这些工具，产出也不该总是“我们发了个东西”；有时产出是内部的——“现在我们更懂这个问题了”，之后就能更好地把它做成可发货的东西，但要先想再做。
- 思考本身可以包含“构建”：设计、写作、谈论都算思考；你构建东西的目的不是第二天就发它，而是把它理解得更好。
- AI 带来的新难点：工具一直在变、LLM 本就不确定，你不总能判断某个东西究竟有多有用。某个时刻你就得决定“我觉得该试”，除了内部试，也得拿给客户试，放进某种 beta。每个阶段都要心里有一个明确目标，并诚实面对这个阶段的真实目标——如果放 beta，目标应是理解工作流、理解人们怎么用、想要它在哪里更好，而不是尽快发货。

## 构建 agent-native 的上下文骨架（含产品演示）

- 产品策略在变。Linear 现在加两类东西：一是 Linear agent（拥有你的工作，以及组织和你所建产品的上下文，可用于 PM 工作流，设计师也能用它来理解问题）；二是 coding agent（能真正开始写代码，你可以在线看 diff，它像一个“conductor 环境”，你能看到变更、引导它）。
- 隐喻的转变：历史上人们把 issue tracking 想成厨房的点单系统——有人点了鱼，一张票进厨房“做鱼”。Linear 从不这么看；对他们，Linear 更像一个“可依赖的骨架”：收集信号、收集问题、收集决策（“我们该做这件事”）。这需要去教育用户。这类产品是为了改进团队的工作流，而不是给组织各部门当一个“奇怪的工单系统”。工单本身可能随 agent 消失——agent 既能开票也能完成票；但收集上下文、把工作塑造成可执行、并为 agent 提供来自环境的好上下文，仍然有价值。
- 为什么要自建 coding agent：一个教训是“当我们自己不掌控 agent 时，事情很难办”。他们想尽量支持所有公司、所有 agent，但一旦有了想法却没法自己实现，得靠对方去做。自建 coding agent 是为了更顺滑的端到端工作流：你在 Linear 里起一个任务，问 agent“这东西已经存在了吗？”不存在就建 issue、开一个 work stream、开始写代码，然后看 diff 涌出来、review、合并，或者看原型。
- 上下文注入的价值：用 Claude、ChatGPT 或 codex 这类工具的问题是“我必须非常显式地告诉 agent 每次要带什么上下文”。而 Linear 的价值在于“上下文本就活在那里”，可以聪明地把它作为 work stream 的一部分注入进去，更自然，也不会去刷屏塞满上下文窗口。Linear 像是“产品里正在发生什么、以及它潜在的未来状态”的多人/组织级上下文。你仍然可以跑本地 agent，但有些场景应该直接把 bug 修复或小任务自动化，让它在 Linear 里、在一个 sandbox 里后台跑，而你自己的电脑照常干别的活。
- 演示（Karri 的真实 Linear 实例）：在新建 tab 里，除了经典的“你想做什么”输入框，还有另一个界面——你可以在某个项目的上下文里直接干活。这里会有 skills：组织级指引和个人级指引，可以有个人技能或组织技能。
- 演示细节一（Linear way skill）：Karri 做了一个“Linear way skill”——喂进公司 blog 里关于产品开发的材料，让它“act like a linear product teammate”，并带一个固定格式（从“底层需求”开始）。用它来快速理解一个功能请求。比如“multiple assignees per issue”（同一 issue 多人被指派），这是几百人提过的请求；他让 agent 去综合、去解释人们想要它的不同原因，先讲清楚核心问题。
- 演示细节二（multiple workspaces）：agent 走查后说“确实有真实需求，但比听起来更复杂”——公司可能想要一个地方统一管理计费与治理，但又有多个不同部门，想切分 workspace，同时保留某种总体控制。它解释了缺什么、好在哪，并给出几条产品方向建议，把一件很复杂的事变成可讨论、可执行的东西。模型现在用 Claude（问是 Sonnet 还是 Opus，Karri 说自己也不确定），未来最终会用多个模型。
- 演示细节三（dark theme 微例子）：想做一个更黑的新暗色主题，可以直接 task 一个 coding agent；它会去看代码库、理解代码库，先把它变成一个 issue、委派给 Linear，spin up 一个 sandbox 开始干。一个好处是：团队知道你在做这个（“FYI，我在做这个”），而且这个 agent session 对所有人可见。
- 共享 / 多人 agent 会话：session 对我和对他都可见，一旦完成，两人可以跳进同一个 chat 一起看。他们曾“意外”发现这很有用：head of product（Anon）和 head of design（Connor）一起在 inbox 上来回改——PM 和设计师来回“不，这里不太对，修一下这个”，两人都能看同一个 preview link。代码评审同理：工程师进来说“这里不对”，可以直接让 agent 去修，而不是叫另一位工程师去修。这大大压缩了协作循环，让多个人一起用 agent 做同一件事。（那次是后端改动，没有客户端 review；若是面向客户的东西，可以打开 preview link 看它 live 的样子。）

## 商业模式：粘性界面 vs token 成本

- Dan 的观察：这是这个时代的完美生意——它仍是 SaaS，没有 AI token 成本，但你控制了所有 AI 的入口。别的所有 coding agent、OpenAI、Anthropic 都得去应付全部 token 成本；而你是那个粘性界面，因为一切都从这里被发起、所有信息在这里被记录，你却不用为实际的 token 付一分钱。而现在你在加一层、要开始为 token 付费，而你可能更愿意这样——因为两者更紧的集成，能做更有趣、更强的事。
- Karri 的商业考量：这还得看未来更多。coding agent 那一侧确实必须提供 usage-based billing，因为它可能变得很贵；基础的 Linear agent 功能（帮你回答问题的那类）则应更多地包含进平台价值里。得看实际用量有多少，但 Linear 仍会是一个相当聚焦的平台——不该在这儿跑随便什么东西，应该清楚你在 Linear 里该做什么、跑哪些工作流或工作负载。
- 定位：不做一个非常通用的 agent 平台，而是做“产品上下文 / 产品记忆平台”——你可以把 agent 集成进来，也可以从别的工具里调用 Linear agent，或把别的工具带进 Linear。它是围绕你的产品工作的一种方式、是一个通往“产品思考”的 API；不像普通工具那样每次都得叫它去 fetch、去找某样东西，因为普通工具对“你一般在做什么、已有哪些上下文可用”并没有理解。

## 产品开发的未来与人机协作

- 增加表面积的取舍：Dan 指出，这把产品的表面积扩大了很多，很多东西别处已经有了、很多大公司正拼命建 AI coding agent，Linear 却要重建不少。Karri 的回应：要不断问自己“我们的优势、独特优势到底是什么”。他不认为 Linear 要解决所有 coding 需求，也不必。价值在于“坐在工作来源的上游（upstream）”：work 进来、bug 进来，会自动 spawn 成 agent、甚至被委派给 agent，工程师可能根本看不到它们，或者看到时已经有一个 fix 在建了。这不是那种“帮我建个新产品”的 agent——那不是 Linear 该待的地方；而是“你是一家大公司，有海量请求和 bug 涌来，我们如何自动帮你缩减这个工作流”。
- 反“大杂烩产品”：不想做那种什么都为所有人做的 kitchen sink 产品。公司常常因为企业买家和 checklist 陷进这种状态——只为了把勾打到 checklist 上正确的位置，但这些并不创造好的产品体验。Linear 的做法始终是找工作流里“自然的下一步”：从一个 issue 出发，自然的下一步是“有人得修它”，那就帮人更快地修——一个选择是做 cloud agent 来修；但 agent 修完，你怎么知道它好？你得看代码、看 diff、跑 build。所以他们始终聚焦于工作流、聚焦于“如何帮公司把产出做得更好更快”，而不是去拥有每一个表面。
- 五年后什么会变（Dan 的收官问题）：会有更多“自动驾驶”的方面——你能设一些规则或指引，Linear 也在建“项目记忆”之类的东西。一个常见工作流是：有一个正在进行的 project（往往对应一个功能、界面的一部分或产品的一部分），有大量反馈和请求涌进来；有机会把它变得更像产品/功能本身——project 像一个 agent，基于它收到的输入自己做决策，仍可要求一定量的人类输入，但能自动运行。它会说“我看到这些模式，它们指向这个解法，这个解法似乎对人们管用，我做了个试制品发给一些客户，反馈不错”。也就是基于某种上下文和一套规则/指引，自己去做事。
- 五年后什么会不变（人的位置）：即便在 agent 做部分思考、部分自动运行的世界里，人反而要更明确地表达“想要什么、什么值得做、我们该做哪些领域”。很多东西仍然是人在开会、讨论、写 issue、写文档、读文档——仍需要人去理解这些，不能把思考纯粹外包给 AI agent。你越能澄清自己的思考和策略，对团队越好，对 agent 也越好——因为只有这样，才能把这些策略 codify 进那些自主运行的东西里。
- Karri 的信念：他不认为、也不太相信“我们在替代人类”（也许是他不想相信）；但事情会变、角色会变（工程到底做什么、需要多少工程师、未来的岗位是什么）。他仍看不到 agent/AI 如何做所有的思考、选择与决策。产品构建仍像一门手艺或艺术——他们谈“直觉”，基于对问题的理解来决定，几乎不把数据当决策依据（有时只当一个信号）。他个人从不相信 A/B 测试和纯数据驱动的产品开发——那对 agent 也许好用，但不适用于所有产品。（51:07 高亮：产品构建仍是手艺或艺术，仍需人的手感去判断什么有趣、什么让产品变好。）最好的产品也不必是那样造出来的；你仍需要那份人的手感，去判断什么有趣、什么能让它更好。

## 概念网络

### 关键概念

### 代理原生（agent-native）

**context**：文中反复出现的核心定位词。Linear 被描述为“成功转型为 agent-native”的少数公司之一——不是给旧产品外挂一个 chatbot，而是把产品从底层改造成“供 agent 使用、并为 agent 提供上下文与集成”的形态。它的 agent 平台文档很好，agent 能自己读文档、自建集成，因此大多数 coding agent（含 OpenAI 的 codex）都接了进来。

**费曼一下**：普通软件是给人用的，界面、按钮、说明都围着人转。agent-native 软件是给 AI 用的——它默认读者是一个 agent，于是把“该带什么上下文、能调哪些能力、怎么完成任务”都摆好。就像同一栋楼，一种是为行人设计的商场，另一种是为无人车设计的仓库：后者的通道、标识、货架都按机器的读取方式重排过。

### 上下文骨架（Linear 作为引导 agent 的系统）

**context**：Karri 用来概括 Linear 新使命的说法——“Linear 成为引导 agent、构建这种上下文的系统”。它和一个被推翻的旧隐喻对立：过去人们把 issue tracking 当成厨房点单系统（点了鱼，票进厨房“做鱼”），而 Linear 把自己看作“可依赖的骨架”，负责收集信号、问题和决策。

**费曼一下**：当你能同时指挥一百万个 agent 干活，真正稀缺的不是“手”，而是“该干什么”的清晰指令和背景。骨架就是那套让所有 agent 站得住、对得齐的中轴：它不亲自砌砖，但决定了砖往哪儿砌。工单系统只管“把菜端出去”，骨架管的是“这家店为什么做这道菜、接下来该上什么”。

### “SaaS 已死”叙事与护城河蒸发

**context**：文章标题直接回应的市场情绪——股市认为 SaaS 已死（即所谓 “SaaSpocalypse”）。Karri 认为方向上大概正确：对投资人而言，未来现金流更不确定，护城河在消失，上市公司受伤最重。但他判断“人们会自己攒出一个 CRM”这种版本过于简化，更可能是冒出更灵活的新公司，而笨重的大方案被惯性拖住。

**费曼一下**：“SaaS 已死”像一句好用的口号，但它把两件事混为一谈。真命题是：当 AI 让软件更易被替代，靠锁定和惯性收租的旧护城河确实在退潮。假命题是：所以每家公司都会自己写掉所有软件。退潮冲垮的是站在浅滩、动作迟缓的大船，而不是所有船；灵活的新船反而能借这股水位变化重新出海。

### 粘性界面与 token 成本转移（“坐在上游”的卡位）

**context**：本篇的商业模式核心洞察，也是标题“把上下文变成骨架”的另一面。Dan 点破：Linear 是“这个时代的完美生意”——仍是 SaaS，是工作被发起、信息被记录的粘性界面，却不用为 token 付费，token 成本由 OpenAI、Anthropic 和各家 coding agent 承担。Karri 补充其战略价值在于“坐在工作来源的上游”：bug 与请求一进来就自动 spawn 给 agent，工程师甚至看不到，或看到时已有 fix。

**费曼一下**：想象一个繁忙的港口。真正烧钱的是跑远洋、烧油的货轮（那是各家大模型和 coding agent 在付 token）；而港口只管调度、收记录、盖章放行，成本低却掌握一切从哪儿开始、往哪儿去。谁守住了“工作从这里发起”的入口，谁就既省了油钱，又拿到了指挥权——这就是上游卡位的杠杆。

### Token 卖家的激励错配

**context**：Karri 对“花更多 token=更好”思路的批评。他指出市场上有一批“token 卖家”式的大公司，其商业模式就是让你花更多 token（你花得越多，它们收入和市场份额越高），于是激励都在喊“多花 token”，没人喊“想清楚、花得好”。但在他看来，花更多 token 从来不等于产品更好，活动量甚至可能是负向的。

**费曼一下**：卖油的人不会劝你少开车。当你的供应商靠你的消耗量赚钱，它给你的所有“最佳实践”都会悄悄偏向“多烧一点”。识别这种激励错配，你才不会把“烧得多”误当成“做得好”——耗油量是成本，不是里程，更不是你到没到目的地。

### 虚荣指标（vanity metrics）

**context**：Karri 常在 Twitter 上调侃的对象——“如今最大的虚荣指标是你多少代码是 agent 写的、你合并了多少 PR”。这类指标度量产出，却不度量价值：产品是否改进、是否解决了用户问题。他主张用滞后但真实的指标（利润、营收、用户喜爱）以及可度量的 bug 数作为反平衡，而不是把 token 使用量推成唯一指标。

**费曼一下**：体重秤上多出的数字，可能是肌肉，也可能是脂肪，还可能是没上厕所。只盯着“产出了多少”，就像只盯着体重秤——数字在动，却说不清你到底变好还是变差。虚荣指标让人感觉良好、便于汇报，但真正该问的是那个不好看的、滞后的问题：产品真的更好了吗？

### 零 bug 政策与一周 SLA

**context**：Linear 的内部质量制度，也是它把 agent 用在刀刃上的样板。所有 bug 进一个 team triage，一周 SLA 内必须修完；如今 coding agent 能先做第一遍修复，再 @ 工程师复核，工程师能直接在 Linear 里改代码、review 代码。Karri 由此说“现在你为什么还会有 bug？没有借口了”——它最终是一个“在乎质量还是只要产出”的选择。

**费曼一下**：把“修 bug”从一件靠人排队、容易拖延的苦差，变成一条有硬期限、有机器先跑一遍的流水线。agent 负责脏活累活的第一版，人只做最后的质量把关。当修复的启动成本被压到接近零，“留着 bug”就从“没空”变成了一个明摆着的选择题——而他们选择不留。

### 决策慢、执行快

**context**：Karri 化解“又要慢思考、又用快工具”这一表面矛盾的原则：在执行上要快，在“决定做什么”上要慢。他警告用 AI 去“speed-run”决策的危险——有想法就立刻建，最后得到一堆没人知道为何存在的东西。（23:25 高亮：我不想让找问题变快；先花时间找对问题和方法，定了再加速。）

**费曼一下**：开车时你可以踩到底，但选目的地绝不能靠掷骰子。把油门和方向盘分开：方向（做什么）要反复确认、慢慢定；一旦定了方向，速度（怎么做）越快越好。AI 是极强的油门，如果你用它来替你选方向，只会更快地开到错误的地方。

### 概念性工作与“概念车”

**context**：Karri 从设计背景带来的方法——有些工作的产出是一个“概念”，而非可交付的功能。他用“概念车”作比：这辆车不会量产，但其中的想法能影响下一辆车。这样做是为了先只决定“这个新想法有没有价值、值不值得推进”，把“会不会打破现有系统”的恐惧和问题推到以后，切分“你现在到底在做哪个决策”。

**费曼一下**：概念车在车展上惊艳全场，却从不真的开上路——它的任务是探路，不是载客。产品里的“概念”也一样：你做一个大胆的原型，不是为了明天上线，而是为了看清“这个方向到底值不值得走”。把“探索的决定”和“交付的决定”分开，你才敢想得足够远，而不被“这会不会搞坏现有东西”提前吓退。

### 缩短循环（shortening the loop）

**context**：Karri 用来概括所有有效 AI 用法的共同模式——“它们都在缩短某个循环，让你能立刻做，而不用等下周”。典型例子：在 Slack 里用 agent 讨论并达成一致后，直接 @ Linear 把对话变成 issue，省去“开会—立项—分派”的迟滞；把“想到”和“做到”之间的距离压到最短。

**费曼一下**：很多好主意不是死于反对，而是死于拖延——等下次开会、等有空再说，然后就没有然后了。缩短循环，就是趁热把念头当场钉成一件可执行的事。当“立刻做”的成本低到几乎为零，主意的存活率就大幅上升；AI 最朴素也最可靠的价值，往往就是把这段等待时间抹掉。

### 产品记忆平台（product memory platform）

**context**：Karri 给 Linear 的定位，用来和“通用 agent 平台”划清界限。Linear 不追求让你在上面跑随便什么东西，而是做“产品上下文 / 产品记忆”的所在地——它是围绕产品工作的方式、是一个通往“产品思考”的 API。相比之下，用 Claude、ChatGPT 或 codex 时，你每次都得显式告诉它带什么上下文，因为它不知道你一般在做什么。

**费曼一下**：通用 agent 像一个每天失忆的临时工，你每次都得从头交代背景。产品记忆平台像一个跟了你多年的老同事，你只说半句，他就知道你指的是哪个项目、上次卡在哪、客户要什么。价值不在“更聪明的大脑”，而在“共享且长期沉淀的记忆”——上下文本就活在那里，不必每次重新搬运。

### 大杂烩产品陷阱（kitchen sink product）

**context**：Karri 明确要避开的反面——那种“什么都为所有人做”的产品。公司常因企业买家和采购 checklist 陷进这种状态：只为把勾打到正确位置而堆功能，但这些并不创造好的产品体验。Linear 的对策是只沿工作流找“自然的下一步”（从 issue 到“有人得修它”到“帮他更快修”），而不是去拥有每一个表面。

**费曼一下**：把厨房所有电器都塞进一个盒子，你得到的不是全能厨具，而是一个谁都不好用的怪物。企业软件最容易这样死：为了在招标表上多打几个勾，功能越堆越多，体验越用越糟。克制的产品只做工作流里“下一步顺理成章要做的事”，宁可不拥有所有表面，也不把自己堆成一个大杂烩。

### 第一天心态（day one）

**context**：Karri 面对护城河消失时给自己立的姿态——“我们要重新活在 day one 的世界里，不能再依赖过去的决定”。它要求以全新眼光重看问题：当 agent 进入产品开发流程，会冒出哪些新问题、该如何帮忙，而不被过去的产品形态绑住。他认为这对存在数十年的大公司尤其难，成长型公司反而更容易做到。

**费曼一下**：公司待久了，会把“我们一向这么做”当成物理定律。day one 心态就是强迫自己假装今天才创业：既有的决定、既有的产品都不是理所当然，一切都要重新问一遍“如果从头来，还会这样吗”。当外部世界剧变，最危险的不是没经验，而是把过去的经验误当成不变的地基。

### 共享 / 多人 agent 会话

**context**：Linear 演示里的一个关键差异化能力——agent session 对团队可见，多人可以跳进同一个 chat 一起看、一起改。文中的真实例子：head of product（Anon）和 head of design（Connor）一起在 inbox 上来回改，都能看同一个 preview link；代码评审时，工程师可以直接让 agent 修，而不必转手叫另一位工程师。Karri 说这“压缩了协作循环”。

**费曼一下**：大多数人用 AI 是各自对着自己的私密聊天窗口干活，成果和过程别人看不见。共享会话把这块“单人操作台”改成“公共工作台”：谁发起的、改到哪一步、预览长什么样，全组一目了然。于是 PM、设计师、工程师不再靠转述彼此的意图，而是围着同一个 agent 直接协作——协作的往返一下子短了。

### 组织级技能与指引（skills / Linear way skill）

**context**：Linear 演示中的功能——在产品里内置 skills，分组织级指引和个人级指引。Karri 亲手做了个“Linear way skill”：喂进公司 blog 里关于产品开发的材料，让 agent “act like a linear product teammate”，并按固定格式（从“底层需求”开始）去综合功能请求，比如把“多人指派同一 issue”“multiple workspaces”这类几百人提的诉求，变成可讨论、可执行的东西。

**费曼一下**：技能就是把“我们这家公司是怎么想事情的”写下来、喂给 agent，让它像一个懂行的老员工那样开口，而不是一个只会通用套话的外人。你把团队的判断口径、常用格式、看问题的顺序固化成一份可复用的“上岗手册”，agent 一加载就自带你们的品味——这比每次临时提示要稳定得多。

### 自动驾驶产品与项目记忆（self-driving / project memory）

**context**：Karri 对五年后“会变的部分”的预测。Linear 在建“项目记忆”之类的东西：一个 project（往往对应一个功能）可以像 agent 一样，基于涌入的反馈和请求自己做决策，仍可要求一定量的人类输入，但能自动运行——它会说“我看到这些模式，指向这个解法，我做了个试制品发给客户，反馈不错”。这是基于上下文和一套规则/指引的自动运转。

**费曼一下**：今天的项目是一块被动的白板，人往上贴需求、派任务。自动驾驶的项目更像一个有记忆、会主动的助手：它记得这个功能一路收到过什么反馈，自己从中看出模式、提出方案、甚至小范围试水，只在关键处停下来问你一句。人从“事事亲自推”变成“设好规则、在岔路口把关”。

### 人的手感与产品手艺（反数据驱动）

**context**：Karri 对五年后“不变的部分”的信念，也是全篇的落点。他不相信 AI 会替代人类：产品构建仍是一门手艺或艺术，靠“直觉”和对问题的理解来决定，几乎不把数据当决策依据。他个人从不信 A/B 测试和纯数据驱动的产品开发——那也许适合 agent，但不适合所有产品。（51:07 高亮：产品构建仍是手艺或艺术，仍需人的手感判断什么有趣、什么让产品变好。）

**费曼一下**：数据能告诉你“哪个按钮点击更多”，却告诉不了你“这个产品该有怎样的灵魂”。A/B 测试擅长在既定选项里择优，不擅长凭空想出那个更好的选项。当 agent 接管了执行和择优，人剩下的、也最不可替代的，恰恰是那份说不清道不明的手感——判断什么有趣、什么值得做、什么能让产品真正变好。

这篇访谈的骨架，是一个把“理解优先于跟风”贯彻到底的产品哲学。它的起点是一次方法论选择：Karri 拒绝为了“显得是 AI 公司”而外挂 chatbot，转而先花两年理解工作流。由此长出全篇最核心的定位——把 Linear 做成“代理原生（agent-native）”的“上下文骨架”。这两个概念是一体两面：agent-native 是产品形态（为 agent 而非人重排），上下文骨架是它承担的角色（不亲自干活，而是决定一百万个 agent 该干什么）。它同时否定了一个旧隐喻：issue tracking 不是厨房的“工单系统”，而是收集信号、问题与决策的中轴。

这套定位之所以成立，靠的是一个商业模式支点：“粘性界面与 token 成本转移”。因为工作从 Linear 发起、信息在 Linear 沉淀，它既能把烧钱的 token 成本转移给上游的大模型和 coding agent，又能“坐在上游”卡住入口——bug 一进来就自动 spawn 给 agent。这正是对“SaaS 已死”叙事的精确回应：护城河蒸发是真的（所以上市公司受伤最重），但“人人自造 CRM”是假的；能借水位变化重新出海的，是抱着“第一天心态”、不被旧决定绑住的灵活公司。于是，商业洞察（粘性界面）、市场判断（SaaS 叙事）与心态要求（day one）在“为什么 Linear 反而是完美生意”这一点上收束到一起。

网络的第二条主线是关于“质量与节奏”，它为第一条主线提供了纪律。“虚荣指标”和“token 卖家的激励错配”是一对因果：正因为供应商靠消耗量赚钱、拼命鼓励多烧 token，才更需要警惕“agent 写了多少代码”这类只量产出、不量价值的数字。对它们的反平衡，一边是可度量的“零 bug 政策与一周 SLA”（用 agent 做第一遍修复，把质量变成硬约束），另一边是“决策慢、执行快”这条元原则——它进一步派生出两个操作性概念：向前看是“缩短循环”（把想到与做到之间的等待抹掉，让执行飞快），向内看是“概念性工作与概念车”（把探索的决定和交付的决定切开，让决策足够慢、足够深）。速度与审慎因此不再矛盾，而是被分配到了循环的两端。

第三条主线把定位落成产品与战略的取舍。“产品记忆平台”与“大杂烩产品陷阱”是一组对立选择：Linear 用“只做工作流里自然的下一步”来抵抗“为 checklist 堆功能”的诱惑，宁可不拥有每个表面，也要守住聚焦。而“共享/多人 agent 会话”和“组织级技能与指引”是这块聚焦地基上长出的两种具体杠杆——前者把单人操作台改成公共工作台、压缩协作往返，后者把“公司怎么想事情”固化成 agent 自带的品味；两者都在把散落的上下文变成骨架的一部分，回扣了 agent-native 的初衷。

最后，全篇在时间轴上收尾：向前是“自动驾驶产品与项目记忆”，让 project 自己看模式、提方案、小范围试水，代表“会变的部分”；向后是“人的手感与产品手艺”，代表“不变的部分”。这两者不是对立而是分工——正因为 agent 会接管越来越多的执行与择优，人越要把“想要什么、什么值得做”说得更清楚，才能把策略 codify 进那些自主运行的东西里。于是整张网络回到它的第一因：无论工具多快，真正稀缺的仍是人对“该做什么”的清晰判断，而 Linear 的全部设计，都是为了把这份判断收集、沉淀，并放大给一群随时待命的 agent。
