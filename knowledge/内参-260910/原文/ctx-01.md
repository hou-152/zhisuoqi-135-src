## 核心观点

- 上下文工程不是 agent 时代的新发明。作者主张它至少已有二十多年历史：从 1990 年代的普适计算、上下文感知系统、人机交互框架，一路演化到今天由智能体驱动的人机协作范式。把它当成 2023 年才出现的技巧，会切断它与几十年 HCI 积累的联系。
- 上下文工程的本质是**熵减**。人与人交流时，听者会用共有知识、情绪线索、情境感知去主动补全没说出口的部分；机器目前做不到这一点，所以人必须替它"预处理"上下文，把高熵的意图压缩成机器能理解的低熵表示。这份"力气"（effort）就是上下文工程的核心。
- 机器越聪明，这门手艺越自然，人机交互的成本越低。因此驱动范式跃迁的根本变量是机器智能水平，而不是某项具体技术。
- 论文给出统一的形式化定义：上下文是所有相关实体的表征信息之并集；上下文工程则是把原始上下文 C 和目标任务 T 映射为一个上下文处理函数的系统性过程。这个定义刻意不绑定任何时代或技术。
- 按机器智能划分四个阶段：1.0 原始计算（1990s–2020）、2.0 智能体（2020 至今）、3.0 人类级智能（未来）、4.0 超人智能（推测）。每一阶段的设计权衡和人机分工都不同。
- 今天把 context 窄化成"对话历史 / 系统提示词"，作者判定为**一种倒退**（a step backward）——1.0 时代的理论视野反而更宽、更整体。
- 全文的实践部分围绕三个维度展开：上下文的收集与存储、管理、使用；并在每个维度下比较典型做法及其代价。
- 一句贯穿全文的话来自作者自题："A person is the sum of their contexts."（一个人是其全部上下文之和），呼应马克思"人的本质是一切社会关系的总和"。

## 被误解的新学科：这门手艺有二十年历史

- 近年来 LLM 与智能体兴起，上下文窗口里放什么会显著影响模型表现，加上多步推理和长时程任务的需求，把"如何让机器理解人的意图"推成了中心问题。
- 现有实践已经很多：提示工程、检索增强生成（RAG）、工具调用、长期记忆机制。这些技术扩展了机器吸收高熵上下文的能力，也实质影响了交互系统的设计。
- 但领域被普遍误解：上下文常被窄化为对话历史、系统提示或以 agent 为中心的环境输入。作者反对这种窄化——普适计算、上下文感知系统、HCI 的早期研究已经奠定了至今仍然有效的原则与方法。
- 论文的三项贡献：把上下文工程放回更长的历史里；给出熵减视角的本质判断 + 四阶段演化模型的理论框架；通过比较典型实践提出通用设计考量。

## 四阶段模型：从被动执行者到体贴的主人

- **Era 1.0 原始计算（1990s–2020）**：机器只能处理结构化输入和简单环境信号，缺乏对意义与意图的理解。交互靠菜单选择、传感器数值这类刚性预定义格式，所有上下文都必须被显式准备好。
- **Era 2.0 智能体（2020 至今）**：以 GPT-3 发布为转折点。机器能理解自然语言、推断部分隐含意图，上下文不再限于显式信号，可以容纳歧义与不完整信息；agent 会主动对上下文缺口做推理。
- **Era 3.0 人类级智能（未来）**：系统能像人一样吸收高熵信息，可解释的上下文范围扩展到社交线索、情绪状态、更丰富的环境动态，AI 成为有知识、有效率的同侪。
- **Era 4.0 超人智能（推测）**：机器获得"上帝视角"，比人更懂人的意图。主客关系反转——机器不再被动适配人定义的上下文，而是主动为人构造上下文、揭示隐藏需求、引导人的思考。围棋职业棋手正在向 AI 学习超人策略，就是苗头。
- 图上还有一条辅助线索：随着阶段推进，上下文的角色从"翻译"变为"指令"，再变为"场景"和"世界"；机器角色从被动执行者（Passive Executor）走向主动智能体、可靠协作者、体贴的主人（Considerate Master）；人机交互成本单调下降。

## 1.0 时代：意图翻译者、Dey 定义与 Context Toolkit

- 1.0 时代的分工是：人负责提供上下文，原始计算机负责接收。设计者充当**"意图翻译者"**（intention translators），把复杂的人类意图转换成结构化、机器可读的格式。
- 技术背景是 1980–90 年代从 CLI 到 GUI 的迁移。图形界面让计算机更普及，但没有消除认知负荷，只是重新分配了它。
- 1991 年 Weiser 提出普适计算（Ubiquitous Computing），设想计算无缝融入日常环境；由此衍生出上下文感知计算（Context-Aware Computing），追问系统能否感知用户状态、环境与任务并动态调整行为。
- 理论基石是 Dey 2001 年的定义：上下文是"任何可用于刻画一个实体所处情境的信息"，实体包括人、地点、对象，也包括用户和应用本身。这个定义强调上下文的多维性。
- 作者的判断：那个时代的理论"broad and deep"，强调对上下文的整体理解；今天的窄化（只盯聊天记录）是退步，回看 1.0 的基础理论有助于纠偏。
- 核心实践是从键鼠输入转向分布式、以传感器为中心的范式。Dey 的 Context Toolkit 提供了模块化可复用框架，围绕五个抽象组织：Context Widgets（封装传感器、暴露标准接口）、Interpreters（把原始数据升为高层含义）、Aggregators（整合多来源上下文）、Services（应用级访问）、Discoverers（动态注册与发现）。
- 这套"关注点分离"的架构，为可扩展的上下文感知系统打下了实践基础，尽管在表达力和扩展性上受限。

## 2.0 时代：从 context-aware 到 context-cooperative

- **采集端**：传感器依然中心，但智能手机、可穿戴、环境设备极大扩展了上下文的多样性与覆盖面；2.0 强调的不只是传感器种类多，还有从单个传感器里抽取更多维信号的能力。论文给出一张多模态采集器分类表，覆盖个人计算（手机、电脑、手表）、沉浸式技术（VR/AR、智能音箱、智能眼镜）、生理感知（脑机接口、皮肤传感器、眼动仪）、环境系统（家庭 IoT、车机、在线行为追踪）。
- **容忍度**：在达到人类级智能之前，衡量系统智能的最好尺子是它对**原始上下文的容忍度**（tolerance for raw context）——能不能直接吃下高熵输入。1.0 只能吃 GPS 坐标、时间、预定义状态；2.0 能吃自由文本、图像、视频这些接近人类自然表达的信号。
- 这不只是"多了几种输入类型"，而是系统理解混乱、模糊、不完整数据能力的深层提升。上下文可以以原生形态直接摄入，不再需要重度预处理。
- **理解与使用**：1.0 系统跑的是"条件—动作"规则，例如"若位置是办公室，则手机静音"——它响应你在哪里，不响应你在做什么。2.0 系统则主动解释用户在做什么并协作达成共同目标，例如分析你已写的段落和当前写作意图，建议下一节该写什么。
- 作者据此提出术语升级：从 context-aware 走向 **context-cooperative**（上下文协作）。系统不只是感知环境，而是嵌入你的工作流。

## 收集与存储：最小充分性与语义连续性

- 两条基本原则：**最小充分性原则**（Minimal Sufficiency）——只收集和存储任务所需的信息，上下文的价值在于充分而非体量；**语义连续性原则**（Semantic Continuity）——上下文的目的是维持"意义的连续"，而不仅是"数据的连续"。
- 1.0 的做法：单设备采集（GPS、时钟、键鼠事件、应用日志），本地存储为日志文件或简单数据库，临时状态放内存缓存、关机即丢。少数系统尝试上传中心服务器，但受制于高延迟和不稳定网络。整体优先"单机可用"，而非跨设备同步或数据保护。
- 2.0 的做法：采集分布到手机、可穿戴、家庭传感器、云服务、第三方 API；多模态信号被整合成连续的上下文流。存储采用分层架构，按用途决定策略——高频短时数据进内存或边缘节点，中期数据进本地嵌入式数据库（SQLite、LevelDB、RocksDB）或系统级安全存储，长期与跨设备同步交给云。
- 代码 agent 是典型压力场景：任务跨会话、跨长时间，光靠上下文窗口不现实。做法是周期性把任务状态与进度写进长期记忆，中断后可恢复。论文点名 Claude Code 的结构化笔记做法：周期性地把关键信息写出上下文窗口、需要时再取回，这种轻量但持久的记忆让 agent 能跟踪进度、避免信息丢失，也支撑了在宝可梦游戏里跨数千步管理策略、重置后无缝续跑这类长时程活动。
- 3.0 的展望是**人类级上下文生态**：系统可采集触觉、气味、味觉，从语调、停顿、目光甚至沉默里读出意图与情绪；所有上下文汇成长期的"个人数字记忆"（personal digital memory）。存储不再只是保存数据，而是能自主组织、提炼上下文的动态认知基础设施，具备类人的"遗忘"和"回忆"能力。

*原文配图｜多模态上下文处理流程，编码器到投影层再到拼接均值与交叉注意力* ｜ [原图](https://neican-res.candobear.com/article-images/ea0cb549e7b16d8afc59334483320cb2c57441a83212bae24bd76c486e25358e.jpg)

- 文本上下文处理的四种常见设计，各有代价：
- **打时间戳**：简单、维护成本低，聊天机器人和行为监控常用；但只保留时序、没有语义结构，难以捕捉长程依赖，序列线性增长带来存储与推理的扩展性问题。
- **按功能与语义打标签**：给每条信息标上"目标""决策""动作"等角色，还可加优先级、来源等维度，便于检索与管理；但略显刚性，可能限制灵活推理与创造性综合。
- **压缩成问答对**：适合搜索引擎、FAQ 类场景，检索效率高；但打断了原有的思路流动，不适合需要整体理解的总结与推理任务。
- **压缩成层级笔记**：树形结构、概念逐层细化，呈现清晰；但它反映的是信息如何分组，而不是想法如何逻辑相连——因果、证据与结论这类关系往往丢失，也无法记录理解随时间的演化与修正。
- 多模态处理的三种策略：把各模态编码后经投影层映射到**同一可比向量空间**；把各模态 token **拼进同一个 Transformer 做联合自注意力**，实现细粒度跨模态对齐（现代多模态 LLM 的主流）；用**交叉注意力**让一种模态去关注另一种模态的特定部分（一方作 query，另一方作 key 与 value）。
- 交叉注意力的传统设计通常要预先指定哪些模态交互，而人脑能在感官与记忆通道间灵活整合，不依赖这种固定映射——这是差距所在。

## 管理（二）：分层记忆与上下文隔离

- Karpathy 的操作系统类比被引作框架：LLM 像 CPU，上下文窗口像 RAM——快但容量有限的工作记忆；正如操作系统决定什么数据进 RAM，上下文工程决定什么信息进窗口。
- 分层的核心洞见是：**不同类型的信息需要不同的保留策略**。近期上下文需要快速检索但可能很快失效，重要模式与习得知识则应跨会话留存。LeadResearcher 在处理超长上下文（>200k tokens）时把研究计划存进持久记忆，防止关键信息因窗口限制丢失。
- 论文给出形式化定义：短期记忆是时间相关性权重超过阈值的上下文子集；长期记忆是重要性权重超阈值、且时间相关性已衰减的、经过处理与抽象的子集；记忆迁移函数刻画从短期到长期的巩固过程，受重复频率、情绪显著性、与既有知识结构的关联度支配。
- 论文的两层模型是为了讲清楚，真实实现常有更多中间层：工作记忆、情节缓冲、领域专用缓存等。
- **上下文隔离**（context isolation）是另一条路径：subagent 既绕开窗口限制，又降低上下文污染风险。Claude Code 的 subagent 系统是范例——每个 subagent 有自己独立的上下文窗口、定制系统提示、受限工具权限；任务匹配时主系统委派出去，subagent 独立运行而不污染主对话。
- 隔离可以沿功能维度（分析、执行、验证）或层级维度（规划、实现、评审）切分，每个隔离单元只拿到完成职责所需的最小权限，同时提升可靠性与可解释性。
- 与 RAG 这类静态检索不同，LeadResearcher 先做计划；信息不足时可追加搜索、调整关键词、创建新子任务，subagent 并行工作，主 agent 汇总中间结果并决定下一步——这个反馈回路帮助系统收敛到高质量答案。
- **轻量引用**（lightweight references）配合隔离：大块信息存外部，窗口里只放简短引用。HuggingFace 的 CodeAgent 用沙箱存放庞大输出、按需取回；schema 化状态对象同理，文件与日志留在外部存储，只暴露选定字段。两者都在降低 token 开销的同时保留完整上下文的可达性。

## 管理（三）：self-baking，把记忆变成学习

*原文配图｜自烘焙的四种代表设计，自然语言摘要、结构化存储、向量与固定 schema* ｜ [原图](https://neican-res.candobear.com/article-images/9b4be486987a69026746ba3d8da9a2f9a2f1ade8ada646f12b5bd042de5ff190.jpg)

- 原始上下文——对话轮次、工具输出、检索文档——积累极快。不处理就会淹没系统，让人无法分辨什么对未来推理真正重要。
- 因此可扩展 agent 的关键能力是**上下文抽象**，论文称之为 **self-baking**：agent 有选择地"消化"自己的上下文，转成持久的知识结构。这对应人的认知过程——情节记忆生成语义记忆，重复动作沉淀为习惯。
- 一句判词值得记住：self-baking 是**记忆"存储"与"学习"的分界**。没有它，agent 只是回忆；有了它，agent 才是在积累知识。
- 四种代表设计：
- **层级记忆组织**：原始上下文在底层保留细节，随着量增大逐层摘要成更抽象的表示向上传递，新信息从最低层进入、逐步"烘焙"上行，同时保留回溯原始细节的链接。
- **加自然语言摘要**：保留完整原始上下文，周期性生成压缩视图；摘要多了还可做多级摘要或按时间/重要性丢弃。简单灵活，但纯文本缺结构，难以理解事件之间的联系或做更深推理。
- **按固定 schema 抽关键事实**：在原始上下文之上加结构化解释，形式可以是实体图（节点带属性、状态与关系）、事件记录模板，或任务树。CodeRabbit 是具体例子——代码评审前先构造结构化案卷，把跨文件依赖、历史 PR 信息、团队规则编码成显式 schema，让 AI 在完整系统上下文上推理，而不是只看孤立的文件变更。代价是多层易不一致，且设计可靠的抽取器本身很难。
- **渐进压缩成语义向量**：把信息编码成稠密向量，可压缩、可构造多尺度层级记忆；旧 embedding 周期性池化或与长期状态融合再编码，形成更抽象稳定的语义记忆。紧凑灵活、利于语义检索，但表示不可读，难以编辑或检查记忆的具体部分。

## 使用（一）：系统内与跨系统的上下文共享

*原文配图｜跨 agent 上下文共享的三种模式，提示嵌入、结构化消息与共享记忆* ｜ [原图](https://neican-res.candobear.com/article-images/be2dea65f48ac30657ac7ba6e9c11d82358c0176b2fba5ab1e63b17ca9a63a82.jpg)

- 多 agent 系统能工作的一个务实理由：它让整个流程消耗的 token 超过单个 agent 所能承受，等于扩展了系统总容量。随之而来的关键问题是 agent 之间如何共享上下文。
- 系统内共享的三种模式：
- **把前序上下文嵌进提示**：上一个 agent 把思考过程整理成文本，下一个读了继续。AutoGPT、ChatDev 用提示作通信通道。
- **交换结构化消息**：按固定 schema 传递任务类型、输入数据、输出结果、推理步骤。Letta、MemOS 用这种方式保持清晰与一致。
- **用共享记忆间接通信**：agent 把信息留在共享空间（常组织为 memory blocks，带谁写的、何时、什么类型这类元数据），稍后各自查看。MemGPT、A-MEM 属此类。更结构化的版本是"黑板"，按主题、任务或目标分区，每个 agent 只盯与自己专长相关的分区，减少混乱并支持异步协作。还有图结构记忆：TME 把推理过程表示为任务图（节点是步骤及其输入输出与执行状态，边是依赖），G-Memory 把记忆建成语义图（节点是洞见、查询、中间结果，边是追问、精化、因果关系）。
- 跨系统共享（例如 Cursor 与 ChatGPT 之间）更难：同一系统内部组件格式兼容、规则相近，跨系统则各有各的格式、结构与逻辑，挑战是让共享上下文在边界之外仍可解释。
- 两条路线：**用适配器转换**（各自保留格式，每条连接单独建一个转换器，自由但成本随连接数增长）；**约定共享表示**（一开始就统一，避免两两翻译）。共享表示又有三种形态——共享数据格式（JSON schema 或定义良好的 API）、人类可读的自然语言摘要、语义向量。
- 权衡是清楚的：标准 schema 精确但需要严格协调；自然语言灵活易生成但难以可靠解析；语义向量紧凑通用但可解释性差。选择取决于涉及哪些系统和沟通目标。

## 使用（二）：上下文选择是"注意力之前的注意力"

- 即使窗口变长，LLM 仍受限于输入 token 的质量。核心问题变成：当前这一步应该选哪一部分可用上下文？
- 上下文可能来自草稿区、记忆、工具定义或 RAG 检索，但并非同等有用。无关或嘈杂的记忆片段会干扰推理、抬高推理成本。经验观察是：AI 编程表现常在上下文窗口填充度超过约 **50%** 后开始下降——上下文过多和过少都会损害效果。
- 缺乏稳健过滤，agent 会被自己的记忆淹没，形成现代版的"上下文过载"。因此有效的上下文选择是一种 **attention before attention**（注意力之前的注意力）——决定什么值得被注意。
- 记忆选择要考虑的因素：
- **语义相关性**：把查询和候选条目都编码成稠密向量做最近邻检索（如 FAISS），不依赖精确关键词也能找到语义相关项，是 RAG 与 Letta 一类系统的常规做法。
- **逻辑依赖**：当前任务直接依赖此前步骤的产出（规划决策、工具输出、推理链）。MEM1 显式记录推理轨迹，把新步骤存进记忆槽并链接到它依赖的早期步骤，逐渐形成依赖图；新查询到来时沿图遍历，只取处于相关依赖链上的上下文，让记忆反映任务的逻辑流而不只是表面相关。
- **新近性与频率**：越新、越常被访问的条目越可能再次被取用；系统给新条目更高优先级、让旧条目自然衰减，反复访问的条目累积更高重要性。
- **信息重叠**：多条信息表达同一含义时，过滤掉更旧或更粗的；现代系统用主动记忆管理，主动决定何时合并、更新、删除冗余条目。
- **用户偏好与反馈**：自演化记忆一类系统跟踪用户如何与信息互动，据此调整记忆条目的权重。
- 常见过滤策略：RAG 先切块（固定行/token 窗口，或用 AST 分割尊重函数、类、模块边界以保持语义完整），再走三类检索——基于 embedding 的语义检索、不解释语义的非语义检索（如 Grep 的字符串或正则匹配）、依托知识图谱与依赖关系（如函数调用图）的结构化检索。由于候选常重叠或含噪，许多系统加一层重排（有时由 LLM 驱动），用效率换准确率，Windsurf 等实现在设计取舍上各不相同。

## 主动推断用户需求

- 当前上下文使用大多是被动的，但用户往往难以（或不合理被要求）完整表达自己的需求与偏好。上下文工程应让 agent 变得**主动**：推断未明说的潜在需求、偏好与目标，并主动发起有帮助的交互。
- 类比人类助理逐渐学到"这位用户偏好可视化摘要""晚上适合头脑风暴"——这些洞见不是预设的，必须从累积的交互上下文中挖掘、抽象并验证。
- 三种常见形态：从对话历史与个人资料中**学习并适配用户偏好**，固化为不断演化的用户画像，并从用户是否继续对话、对建议如何反应这类间接信号中学习，有时也直接询问或给多个选项来收集显式反馈；**从相关问题序列推断隐藏目标**（先问 Python 装饰器再问性能调优，可能反映提升软件设计效率的更大目标），可用思维链做多步推断；**在用户卡住时主动提供帮助**，检测到犹豫或反复尝试时递上可视化、检查清单一类工具。

## 终身上下文的四道坎与"语义操作系统"

- 当"普通"的上下文工程变成**终身上下文工程**，问题升级：如何在语义一致的前提下可靠存储？数据规模上去后如何准确处理与管理？新设计出来后如何端到端评测？整条管线建起来后如何保持稳定？
- **挑战一，存储瓶颈**：在严格资源约束下尽可能多地保留相关上下文，目前没有统一方案；需要能同时支持高压缩、高精度检索与低延迟访问的基础设施。
- **挑战二，处理退化**：Transformer 全局注意力的 O(n²) 复杂度带来推理延迟、显存与 I/O 压力；同时随着输入变长，注意力被摊薄，模型难以保持对相关信息的聚焦、难以捕捉长距离依赖；检索系统被大量"语义相似但无关"的片段淹没，返回干扰而非证据；上下文越多，片段之间的矛盾越难被发现与调和。
- **挑战三，系统不稳定**：记忆累积后，小错误的影响面被放大，原本局部的错误开始扩散；缺少清晰边界与校验机制时，长时程或高安全要求的任务反而更脆弱。
- **挑战四，评测困难**：今天的基准多数只测"能不能检索到"，不检查信息是否仍然相关、准确、有用；系统很少具备检测矛盾、回滚错误更新、追溯推理步骤的能力。决策越依赖长记忆链，越难看清答案是怎么来的，也就越难信任和改进。
- 结论是一个方向性主张：终身上下文工程不能靠"扩大窗口"或"提高检索准确率"解决，它需要一个能随时间生长的**语义操作系统**——既是大规模高效的语义存储与记忆库，又具备类人的主动添加、修改、遗忘能力；同时需要替代 Transformer 扁平时序建模的新架构；还必须能自我解释，追溯、纠正、诠释推理链上的每一步。
- 一句范式判断：上下文不再是被动累积的，而是作为认知的核心要素被主动管理与演化。

## 工程实践：KV 缓存、工具设计、保留错误、复述目标

- **KV 缓存**：缓存过去 token 的注意力键值，避免重算，命中率直接决定延迟与成本。要提高命中率，一要保持前缀提示稳定（系统提示开头哪怕一个时间戳变动也会让整段缓存失效），二要强制 append-only 与确定性更新（改写或不一致序列化会破坏复用），三是在服务框架不支持自动增量前缀缓存时手动插入缓存检查点并谨慎放置。此外常用缓存预热与预测性加载。
- **工具设计**：关键在描述与规模。描述要精确、定义清晰，含糊或重叠的描述常导致失败；模型本身也能作为提示工程师改写这些描述实现自我改进。规模上，工具集过大会降低可靠性，交互中动态加载工具还会破坏 KV 缓存一致性、扰乱对早前动作的引用。实测数据：DeepSeek-v3 在超过 **30 个工具**后表现下降，超过 **100 个**几乎必然失败。更稳的做法是保持工具列表稳定，在解码层加约束（例如遮蔽 token logits 屏蔽非法选择）。
- **上下文内容**：不要替 agent 掩盖错误——把失败留在上下文里，模型才能观察自己的失误、学会纠正。agent 场景中传统 few-shot 反而有害：上下文里全是相似的动作—观察对，模型倾向照抄既有模式。Manus 的对策是引入受控的小扰动（替换序列化模板、变换措辞、微调顺序与格式），打破重复模式、重新聚焦注意力。
- **多 agent 实践**：主 agent 拆解查询并分派子任务时，必须给清晰的目标、输出、工具指引和边界，含糊指令导致混乱或遗漏；由于 agent 不擅长判断工作量，提示里可以写简单的调节规则（简单任务 1 个 agent，复杂任务更多）；搜索策略宜从广泛探索走向聚焦分析；显式写下推理过程的 extended thinking 模式能提升准确率与效率。
- **小技巧**：复杂任务里维护一个 todo.md 列出子目标并随进展勾选；但长任务中模型会遗忘早期目标，实用解法是在更新清单时用自然语言**复述**这些目标，把关键目标重新拉回模型的近期上下文和即时注意力范围内。

## 三个应用场景

- **CLI**：Google 的 Gemini CLI 是代表。核心机制是 GEMINI.md 文件——一份记录项目背景、角色定义、所需工具与依赖、编码规范的 Markdown 规格；这些文件可存在于用户主目录、项目根目录或子目录，通过文件系统层级实现信息的继承与隔离。收集上分两类：启动时自动加载系统提示、项目环境、祖先与后代 GEMINI.md 等静态信息，交互中增量累积对话历史这类动态上下文。管理上文件系统本身就是轻量数据库，并用 AI 生成的摘要替换长交互历史来压缩上下文；摘要遵循预定义格式（总体目标、关键知识、文件系统状态、近期动作、当前计划），保证一致性。社区还提议引入人工精修，做协作式的上下文管理。
- **Deep Research**：以 Tongyi DeepResearch 为例，四步循环——按查询搜网、从相关页面抽取关键信息、生成新的子问题引导下一轮、把多来源证据整合成答案；循环持续到不确定性降低、证据链完整。它面对的独特挑战是交互历史极长，直接堆叠所有观察、思考、动作会迅速撑爆窗口。解法是周期性调用专门的摘要模型，把累积历史压成紧凑的推理状态，既保留关键证据，也标出缺失信息与下一步方向；后续搜索与推理基于这些"上下文快照"而非完整原始历史，从而建立起"收集累积 → 周期压缩抽象 → 基于摘要推理复用"的清晰上下文生命周期。
- **脑机接口**：BCI 直接采集神经信号，带来两个优势——可采集注意力水平、情绪状态、认知负荷这类外部行为难以观察的上下文维度；采集更便捷，减少显式用户操作。当前技术对脑信号的理解仍粗糙，噪声与不稳定是显著挑战，但它指向一个方向：把上下文采集从外部环境延伸到用户的内在认知状态。

## 未竟之处与"数字存在"

- **采集仍然受限低效**：多数 agent 系统仍依赖显式用户输入，而用户有时说不清自己的意图，重要上下文因此缺失。出路是更自然、更多模态的采集方式，加上更能推断需求、补全缺口的模型。
- **大规模上下文的存储与管理**：交互累积后规模与复杂度快速增长，如何组织才能既可扩展又支持有效选择与检索，仍无好答案。
- **模型对上下文的理解有限**：系统在复杂逻辑和图像中的关系信息上仍然吃力；机器智能越低，上下文工程要花的"力气"越大，导致大量可用上下文没被充分理解与利用。方向是加强语义推理、逻辑解释与多模态对齐，减少对人力上下文工程的依赖。
- **长上下文的性能瓶颈**：Transformer 的二次复杂度使其在长上下文下低效。Mamba 及 LongMamba 等变体提升了效率与扩展性，但在输入远超训练长度、或关系与逻辑依赖横跨全文时仍显弱；LOCOST 能处理数十万 token 的文档，但在需要细粒度长跨度推理的任务上仍落后于 Transformer。需要的是新架构，而不是把长上下文仅仅当作"更长的输入"。
- **选择相关且有用的上下文**：现有相关性估计与过滤机制表现有限，有用信号会被漏掉，噪声与冗余会残留；方向是更精确、自适应的选择策略，持续判断该保留、丢弃还是强调什么。
- **数字存在（Digital Presence）**：马克思那句"人的本质是一切社会关系的总和"在以上下文为中心的 AI 时代获得了新的计算含义——人越来越不是由肉身或有意识的活动定义，而是由自己生成的数字上下文定义：对话、决策、交互痕迹。这些上下文可以持续、演化，甚至在人离开之后仍通过 AI 系统与世界互动。**人的心智也许无法上传，但人的上下文可以**——上下文本身由此成为一种持久的知识、记忆与身份形式。
- **结论**：上下文工程不是 LLM 时代的突发发明，而是被机器智能进程塑造的、长期演化的学科；其核心挑战始终是在不同的熵水平下弥合人类意图与机器理解。作者给出的轨迹是人类逐步从显式上下文管理中脱身；当机器理解接近乃至超越人类认知，形成对我们意图的"上帝视角"时，AI 系统不仅能理解我们，还可能照亮并扩展我们对自己的理解。

## 概念网络

### 关键概念

### 上下文工程（context engineering）

**context**：论文给出的形式化定义是 CE: (C, T) → f_context——把原始上下文 C 与目标任务 T 映射为一个上下文处理函数，这个函数由一组可灵活组合的操作构成（采集、存储管理、统一表示、多模态处理、self-baking、选择、跨系统共享、依反馈动态适配）。作者刻意让定义不绑定任何具体技术或时代：无论接收方是 1990 年代带图形界面的原始计算机，还是 2025 年的 agent，根本挑战都是"如何让上下文与意图被准确理解"。

**费曼一下**：它不是"写好提示词"的高级说法，而是"如何把人脑里的情境和目的，整理成机器接得住的形状"这个问题的统称。技术会换，问题不换。

### 熵减（entropy reduction）

**context**：论文对上下文工程本质的判断。人交流时听者会主动降低信息熵——用共有知识、情绪线索、情境感知补上没说的部分；机器目前缺这个能力，所以人必须替它预处理，把高熵的上下文和意图压缩成低熵表示。这份"effort"就是上下文工程的核心成本，且与机器智能水平成反比。

**费曼一下**：跟人说话可以省略一半，跟机器说话不能。省略掉的那一半，得有人补上——现在补的是你。机器越笨，你补得越多。

### 上下文（Dey 的定义与形式化）

**context**：Dey 2001 年的经典定义是"任何可用于刻画一个实体所处情境的信息"，实体包括与用户—应用交互相关的人、地点、对象，以及用户和应用本身。论文把它形式化为：对每个实体有一个情境表征函数 Char，上下文 C 是所有相关实体表征信息的并集。以 Gemini CLI 为例，相关实体包括用户、应用、终端环境、外部工具、记忆模块和后端模型服务。

**费曼一下**：上下文不只是"聊天记录"。你是谁、你在哪个目录、手边有什么工具、系统怎么配置，全都算。论文认为今天把它窄化成对话历史，是把一个宽概念用窄了。

### 四阶段演化模型（1.0 到 4.0）

**context**：按机器智能水平划分：1.0 原始计算（1990s–2020，结构化输入、刚性格式）；2.0 智能体（2020 至今，理解自然语言、容纳歧义）；3.0 人类级智能（未来，能读社交线索与情绪）；4.0 超人智能（推测，机器获得"上帝视角"、主客关系反转，主动为人构造上下文）。每一阶段的设计权衡与人机分工都不同。

**费曼一下**：一把用"机器有多聪明"当刻度的尺子。刻度往右走，人要做的翻译工作就往下降；到最右端，反过来是机器给人提供上下文。

### 意图翻译者（intention translator）

**context**：1.0 时代设计者的角色定位——把复杂的人类意图转换成结构化、机器可读的格式。当时机器只能执行预定义程序逻辑，无法理解自然语言语义、无法推理、无法有效处理错误，因此设计者必须把复杂目标拆成简单结构化组件、设计清晰的交互路径、加上反馈机制。

**费曼一下**：那个年代做产品设计，本质是当人机之间的口译。今天模型能自己听懂一部分，但只要它听不懂的部分还在，这个岗位就还在，只是换了名字。

### 原始上下文容忍度（tolerance for raw context）

**context**：论文提出的智能度量：在达到人类级智能之前，系统的智能主要由它的"类人度"决定，而类人度最好的衡量方式是它能消化多高熵的原始输入。1.0 只能吃 GPS 坐标、时间、预定义状态这类简单结构化信号；2.0 能吃自由文本、图像、视频这类接近人类自然表达的信号，因此上下文可以以原生形态直接摄入，无需重度预处理。

**费曼一下**：判断一个系统聪明不聪明，看它能不能直接吃"生的"东西。要你切好摆盘才吃的是弱的，端上一堆乱七八糟也能吃的是强的。

### 上下文协作（context-cooperative）

**context**：论文用来标记 2.0 与 1.0 分野的术语。1.0 的上下文感知系统跑"条件—动作"规则："若位置是办公室，则手机静音"——它响应你在哪里，不响应你在做什么。2.0 系统则主动解释用户正在做什么并协作达成共同目标，例如分析你已写的段落和写作意图，建议下一节内容。作者由此提出：从 context-aware 走向 context-cooperative。

**费曼一下**：从"感应到你进屋就开灯"，变成"看你在写论文就帮你想下一段"。前者响应状态，后者参与工作。

### 最小充分性与语义连续性原则

**context**：论文给上下文收集与存储定的两条基本原则。最小充分性原则：只收集和存储支撑任务所必需的信息——上下文的价值在于充分（sufficiency），不在于体量（volume）。语义连续性原则：上下文的目的是维持意义的连续，而不只是数据的连续。

**费曼一下**：不是存得越多越好，是存得刚好够用最好；也不是把每个字都留着就叫记得住，得让意思接得上。

### 分层记忆架构

**context**：借 Karpathy 的操作系统类比——模型是 CPU，上下文窗口是 RAM（快但容量有限的工作记忆），上下文工程决定什么进 RAM。论文形式化定义了短期记忆（时间相关性权重超阈值的子集）、长期记忆（重要性超阈值且时间相关性已衰减、经处理与抽象的子集）和记忆迁移函数（受重复频率、情绪显著性、与既有知识关联度支配）。真实系统常有工作记忆、情节缓冲、领域缓存等更多中间层。

**费曼一下**：把记忆按"多久有用"和"多重要"分层放置。刚发生的放手边，重要的沉到仓库，其余的让它自然淡出。

### 上下文隔离（context isolation）

**context**：绕开窗口限制并降低上下文污染的策略。Claude Code 的 subagent 系统是范例：每个 subagent 有独立上下文窗口、定制系统提示、受限工具权限，任务匹配时被委派、独立运行而不污染主对话。切分可沿功能维度（分析、执行、验证）或层级维度（规划、实现、评审），每个单元只拿最小必要权限，同时提升可靠性与可解释性。

**费曼一下**：别让所有事挤在一个脑子里。把子任务交给一个有独立记事本、只带必要工具的专职助手，做完把结论交回来，过程不脏主线。

### self-baking（上下文自烘焙）

**context**：论文对上下文抽象的命名——agent 有选择地"消化"自己的上下文，转成持久的知识结构，对应人从情节记忆生成语义记忆、把重复动作沉淀为习惯的过程。四种代表实现：层级记忆组织、自然语言摘要、按固定 schema 抽关键事实（如 CodeRabbit 的结构化案卷）、渐进压缩成语义向量。论文的判词是：self-baking 是记忆"存储"与"学习"的分界——没有它，agent 只是回忆；有了它，agent 才在积累知识。

**费曼一下**：光把笔记堆着不叫学会，得定期把它嚼碎、变成自己的结论。agent 也一样：会翻记录只是检索，能把记录炼成知识才是长本事。

### 轻量引用（lightweight references）

**context**：上下文隔离常用的配套手法：大块信息存在外部，模型窗口里只暴露简短引用。HuggingFace 的 CodeAgent 采用沙箱方案，庞大输出存沙箱、需要时才取回；schema 化状态对象同理，文件与日志留在外部存储，只上浮选定字段。两者都在降低 token 开销的同时保留对完整上下文的可达性。

**费曼一下**：桌上只放索引卡，资料放柜子里。要用哪份再去取，桌面不会被淹。

### 注意力之前的注意力（attention before attention）

**context**：论文对上下文选择的定位。即使窗口变长，模型仍受限于输入 token 的质量：无关或嘈杂的记忆片段会干扰推理、抬高成本，经验上 AI 编程表现常在窗口填充度超过约 50% 后下降。选择的考量因素包括语义相关性、逻辑依赖（如 MEM1 的依赖图遍历）、新近性与频率、信息重叠、用户偏好与反馈；常见过滤策略含分块（可用 AST 尊重语义边界）、embedding 检索、Grep 式非语义检索、知识图谱结构化检索与重排。

**费曼一下**：模型自己的注意力机制只在进了窗口之后起作用；决定"什么配进窗口"是更早、也更要紧的一次注意力。喂多了和喂少了，都会变笨。

### 语义操作系统（semantic operating system）

**context**：论文对终身上下文工程的方向性主张。面对存储瓶颈、处理退化（O(n²) 注意力摊薄、检索被相似噪声淹没、片段矛盾难调和）、系统不稳定（错误随记忆累积扩散）、评测困难（基准只测检索、无法追溯推理）四道坎，作者认为扩大窗口或提升检索准确率都不够，需要一个能随时间生长、具备类人添加/修改/遗忘能力、有替代 Transformer 扁平时序建模的新架构、且能自我解释推理链的系统。

**费曼一下**：把"记忆"当成一个需要操作系统来管的资源，而不是一个越买越大的硬盘。它得会整理、会忘、会解释自己为什么这么想。

### 数字存在（Digital Presence）

**context**：论文收尾提出的观念。马克思"人的本质是一切社会关系的总和"在以上下文为中心的 AI 时代获得新的计算含义：人越来越由自己生成的数字上下文定义——对话、决策、交互痕迹；这些上下文可以持续、演化，甚至在人离开后仍通过 AI 系统与世界互动。论文的原话是：人的心智也许无法上传，但人的上下文可以。

**费曼一下**：你留下的不是一份档案，而是一团还在起作用的上下文。它构成别人（和机器）眼中的你，并且可能比你活得久。

全文的思想网络有一个明确的圆心：上下文工程本身。它由两条线共同定义——Dey 2001 年的上下文定义给出它的对象（任何可刻画实体情境的信息），熵减给出它的本质（把高熵意图压成机器可解的低熵表示）。前者回答"我们在处理什么"，后者回答"我们为什么要费这个力气"。两者合起来，才使这门手艺可以脱离具体技术被谈论。

从圆心往外的第一层是历史轴。四阶段演化模型是把熵减这条本质放进时间后的必然产物：因为"力气"的大小与机器智能成反比，所以机器智能的每一次质变都会改写这门手艺的形态。原始上下文容忍度是这个模型真正的因变量刻度——不是看系统用了什么技术，而是看它能直接消化多生的输入。在这条轴上，意图翻译者是 1.0 的人类角色（人向机器靠拢），上下文协作是 2.0 的系统姿态（机器开始向人靠拢），两者构成同一条轴上的前后两点，而不是并列的两种风格。

从圆心往外的第二层是实践轴，按收集、管理、使用三个维度铺开。收集端的最小充分性与语义连续性原则设定了源头纪律：够用即可，且要保住意义而非数据。管理端以分层记忆架构为骨架，向下派生出两条互补的路径——上下文隔离处理"空间"问题（谁能看到什么，subagent 与轻量引用都是让主上下文保持干净的手段，后者是前者的落地技巧），自烘焙处理"时间"问题（累积的原始上下文如何被消化成持久知识）。使用端的核心是注意力之前的注意力：在模型自己的注意力起作用之前，先决定什么配进窗口。

两条轴在末端交汇。自烘焙一旦推到终身尺度，就撞上存储、处理、稳定性、评测四道坎，逼出语义操作系统这个更高层的构想——它是分层记忆、隔离、自烘焙、选择四件事被统一编排后的形态，也是这门手艺从"技巧集合"升级为"基础设施"的临界点。而数字存在是把语义操作系统再往前推一步的哲学结论：当上下文能被长期、完整、可演化地保存和调用，它就不再只是任务的输入，而成为身份本身的载体。全文因此形成一个闭环——开篇引马克思说人是社会关系的总和，结尾说人是自己上下文的总和，中间的所有技术细节，都是在回答如何把这个"总和"完整地交给机器。

## 费曼 x3

跟人说话可以省略一半。你说"帮我看看那个文件"，对方知道是哪个；你叹口气，对方知道该换个话题。这种把没说出口的部分补上的能力，是一种主动的熵减，人人都有，因此没人当它是能力。机器没有。于是省略掉的那一半必须有人补，而现在补的是你——所谓上下文工程，说穿了就是这份代偿劳动的名字。它给人的那种笨拙感不是错觉：你花的力气，恰好等于机器智能的欠账。

这个视角一旦立住，很多争论就自动消解了。上下文工程不是 2023 年发明的技巧。1990 年代做普适计算的人已经在问同一个问题，只是那时机器更笨，所以人要弯得更低——设计师干的活是"意图翻译者"，把复杂目标拆成机器能执行的结构化碎片。Dey 在 2001 年给出的定义比今天流行的宽得多：上下文是任何能刻画实体情境的信息。相比之下，把 context 等同于对话历史和系统提示，实在是一种退步。

真正有解释力的刻度不是模型参数，而是一个系统对原始上下文的容忍度——它能不能直接吃生的东西。要你切好摆盘才吃的是弱的，端上一堆乱七八糟也能吃的是强的。沿着这把尺子往前走，系统会从"感应到你进办公室就静音手机"变成"看你在写论文就帮你想下一节"，从 context-aware 走向 context-cooperative。差别不在感知精度，在是否参与你的工作。

而工程上最锋利的一句话，是关于记忆的：没有自我消化，agent 只是回忆；有了它，agent 才在积累。堆着的笔记不是知识，定期把它嚼碎、炼成结论才是。同理，模型自身的注意力只在进了窗口之后才起作用，决定什么配进窗口是更早也更要紧的一次注意力——过多和过少同样会让它变笨。

论文最后把话说到了它该说的地方。人的心智也许无法上传，人的上下文可以。你留下的对话、决策和痕迹并不只是档案，它们会继续演化、继续起作用。一个人是他全部上下文的总和——这句话现在有了计算意义上的重量。
