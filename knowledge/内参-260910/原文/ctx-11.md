Linear 将未来产品开发定义为 context 加 agency，并据此重构自身产品方向。它提出的关键问题是：任务列表能否升级成 Agent 可理解、可行动的协作系统。

## 导读

linear 与产品开发。

## 核心观点

这是 Linear 发布"下一阶段产品"的一篇愿景与发布文章。核心论点是一条"退化—信念—放大—重构"的逻辑链：问题追踪（issue tracking）最初是为软件开发的"交接模型（handoff model）"而造的，它的一整套优先级、协商、工作流仪式源于真实约束——"工程时间是稀缺的（Engineering time was scarce）"。但随时间推移，"复杂开始看起来像精密（complexity started to look like sophistication）"，开销不断膨胀，最终"流程本身成了工作（the process became the work）"。Linear 的相反信念是：最好的系统"移除开销，让团队专注于构建"。agent 把这条信念推得更远——规划、实现、代码评审开始"压缩（compress）"，人得以把时间还给"意图、判断与品味（intent, judgment, and taste）"。这一转变已被数据证实：coding agents 已进入 Linear 超过 75% 的企业工作区，过去三个月 agent 完成的工作量增长 5 倍，agent 撰写了接近 25% 的新 issue。由此，"下一个系统不是围绕交接设计的，而是围绕上下文与 agent 设计的"。因为"agent 不是读心者（Agents are not mind readers）"，它们只有通过上下文才有用；Linear 由此把自己定位为"把上下文转化为执行的共享产品系统"，并发布 Linear Agent、Skills、Automations，预告 Code Intelligence、Code Diffs、Linear Coding Agent，共同"压缩想法与实现之间的距离"。

## 旧范式：为"交接"而生的问题追踪系统

- 问题追踪（issue tracking）最初是"为软件开发的交接模型（handoff model）"而造：PM 先划定工作范围（scoped the work），工程师稍后接手（picked it up later）。
- 为了在角色与职能之间"小心地路由工作（route work carefully across roles and functions）"，系统里塞满了优先级排序、协商、工作流（prioritization, negotiation, and workflows），用来弥合交接留下的缝隙（bridge the gap）。
- 关键前提：这套"仪式（ceremony）"源于真实约束——"工程时间是稀缺的（Engineering time was scarce）"。当工程产能是瓶颈时，谨慎分配工作就有价值。

## 失败模式：复杂被误认为精密，"流程即工作"

- 随时间推移，"复杂开始看起来像精密（complexity started to look like sophistication）"。
- 一个系统能吸收的流程越多，它就显得越先进（The more process a system could absorb, the more advanced it seemed）。
- 结果是开销不断增长，最终"流程本身成了工作（the process became the work）"——管理机制本身，消耗掉了本该用于构建的精力。

## Linear 的相反信念：移除开销

- Linear 一贯建立在相反的信念之上：最好的系统"移除开销，让团队能专注于构建（remove overhead so teams can focus on building）"。
- 这条信念是全文的价值坐标：不是把流程打磨得更精致，而是把不必要的流程直接拿掉。

## agent 如何把这条信念推得更远

- agent 能让软件开发"简单得多（a lot simpler）"。
- 随着 agent 吸收更多程序性工作（procedural work），规划、实现、代码评审（planning, implementation, and code review）三个阶段开始"压缩（begin to compress）"。
- 人因此可以把更多时间花在意图、判断、品味（intent, judgment, and taste）上，更少时间用于"管理流程的机械环节（managing the mechanics of the process）"。

## 这一转变已在发生（数据）

- 今天，coding agents 已装进 Linear 超过 75% 的企业工作区（more than 75% of Linear's enterprise workspaces）。
- 过去三个月，agent 完成的工作量增长了 5 倍（grew 5x）。
- agent 撰写了接近 25% 的新 issue（authored nearly 25% of new issues）。
- 结论：在这个新世界里，"下一个系统不是围绕交接设计的，而是围绕上下文与 agent 设计的（designed around context and agents）"。

## 新范式的核心：上下文与共享系统

- "agent 不是读心者（Agents are not mind readers）。它们通过上下文才变得有用。"
- 需要被捕获的上下文包括：客户反馈、内部想法、战略方向、决策，以及代码（Customer feedback, internal ideas, strategic direction, decisions, and code）——都要放进一个"人与 agent 能共同工作的系统"。
- 这个系统应当：理解意图（understand intent）、把工作路由给正确的执行者（route work to the right actor）、在需要时升级（escalate when needed）、并保持执行推进（keep execution moving）。
- 它的作用是"帮团队把工作向前推进，而不是把他们困在流程里（not trap them inside the process）"。

## Linear 的定位：把上下文转化为执行

- 一句话定位："Linear is the shared product system that turns context into execution"——Linear 是把上下文转化为执行的共享产品系统。
- 它承载反馈、意图、决策、计划与代码（feedback, intent, decisions, plans, and code），把这些上下文"塑造成工作（shapes that context into work）"，并帮助人与 agent 把工作"一路带到生产环境（carry it all the way to production）"。

## 今日发布

- **Linear Agent**：一个原生 agent 界面，在你的产品上下文中工作，分析用户反馈，并生成项目、issue 和文档。
- **Skills（技能）**：把值得重复的工作流固化为可复用技能，让学习复利累积（compound your learning）。可通过斜杠命令手动触发，也可让 Linear 在相关时自动应用。
- **Automations（自动化）**：从 Triage 开始，在一个 issue 进入系统的那一刻触发 agent 工作流。每个新 issue 都为工作区增添上下文，Linear 能在它到达的那一刻就智能地精炼、综合、或据此采取行动。

## 即将推出

- **Code Intelligence**：Linear 能理解你的代码库、回答关于它的问题并进行调试。
- **Code Diffs**：在一个为人与 agent 协同迭代而生的、快速现代的界面里评审代码。
- **Linear Coding Agent**：Linear 自己写代码并自动修复 bug，由前沿模型与 harness 驱动，并用 Linear 原生的上下文与工具增强。

## 承接与收束

- 这些更新建立在此前的 Triage Intelligence，以及与云端 coding agents 及其他 AI 工具的深度集成之上。
- 通过把 agent 扎根于产品与代码库的完整上下文，Linear 正在"压缩想法与实现之间的距离（collapsing the distance between an idea and its implementation）"。
- 收束对照："Issue tracking was built for handoffs. Linear turns context into execution."——问题追踪为交接而生；Linear 把上下文转化为执行。作者称，正"与那些已经在塑造这一未来的团队一起建设"。

## 概念网络

### 关键概念

### 交接模型（handoff model）

**context**：文章开篇给出的旧范式。传统问题追踪是"为软件开发的交接模型（handoff model）"而造：PM 先划定范围（scoped the work），工程师稍后接手（picked it up later），中间靠优先级、协商、工作流来"弥合缝隙"。作者强调这套仪式源于真实约束——"工程时间是稀缺的"。

**费曼一下**：想象一条流水线，一个人做好半成品，交给下一个人接着做。为了保证不出错，中间要填一堆表格、开一堆会、排一堆优先级。这些手续本身不创造价值，只是为"交接"这个动作服务。当年之所以值得，是因为工程师人手太少，必须精打细算地分配他们的时间。

### 复杂被误认为精密（complexity looked like sophistication）

**context**：作者诊断旧系统退化的关键机制——"复杂开始看起来像精密（complexity started to look like sophistication）"。系统能吸收的流程越多，就显得越先进，于是开销不断累积。

**费曼一下**：一个东西看起来越复杂，我们往往就下意识觉得它越高级、越专业。软件流程也中了这个圈套：能塞进去的步骤、审批、字段越多，工具看着就越"强大"。但复杂不等于精密，很多时候它只是笨重而已。

### 流程即工作（the process became the work）

**context**：上一条误判的直接后果——"开销不断增长，流程本身成了工作（the process became the work）"。本该服务于构建的机制，反过来消耗了团队的主要精力。

**费曼一下**：本来流程是为了帮你把产品做出来，结果做到后来，大家一天的时间全花在维护流程本身上：更新状态、走审批、对齐字段。手段吃掉了目的，"管流程"变成了真正的工作，"做产品"反而成了副业。

### 移除开销（remove overhead）

**context**：Linear 的立身信念，与"流程即工作"正面对立——"最好的系统移除开销，让团队专注于构建（remove overhead so teams can focus on building）"。它是全文的价值坐标。

**费曼一下**：好工具的标准不是功能多，而是帮你把碍事的东西拿掉。与其把流程打磨得更精致，不如干脆删掉不必要的流程，让人把注意力还给"真正在造的那个东西"。少即是多。

### 阶段压缩（compression）

**context**：agent 把"移除开销"推得更远的机制。随着 agent 吸收程序性工作，规划、实现、代码评审（planning, implementation, and code review）三个原本分离的阶段"开始压缩（begin to compress）"。

**费曼一下**：过去写软件像接力赛：先规划、再实现、再评审，一棒一棒交。agent 能同时插手这几段活儿，于是几个阶段被挤到一起、几乎同时发生，中间的等待和交接被压扁了。整个链条从"串行"变得更像"并行"。

### 意图、判断与品味（intent, judgment, taste）

**context**：阶段压缩之后，留给人的高价值部分。agent 接走机械环节，人"可以把更多时间花在意图、判断和品味上（intent, judgment, and taste），更少时间管理流程的机械环节"。

**费曼一下**：当机器把重复、程序化的活儿包了，人剩下的就是那些机器替代不了的部分：想清楚到底要做什么（意图）、在权衡中拍板（判断）、以及分辨什么是好的、什么是将就（品味）。这三样恰恰是最难自动化、也最值钱的能力。

### agent 不是读心者（agents are not mind readers）

**context**：新范式的第一性原理——"agent 不是读心者。它们通过上下文才变得有用（Agents are not mind readers. They become useful through context）"。这句话直接推出"上下文"为何是新系统的核心。

**费曼一下**：再聪明的助手，你不告诉它来龙去脉，它也帮不上忙。agent 不会自己猜出你的目标、约束和历史决策，你得把这些信息喂给它。所以问题不在于 agent 够不够聪明，而在于你有没有把上下文摆到它面前。

### 上下文（context）

**context**：新系统的燃料与地基，也是标题所指驱动下一阶段的两大动力之一。需要被捕获的上下文包括客户反馈、内部想法、战略方向、决策与代码（Customer feedback, internal ideas, strategic direction, decisions, and code），且必须放进"人与 agent 能共同工作的系统"。

**费曼一下**：上下文就是"关于这件事你需要知道的一切"：用户在抱怨什么、团队为什么这么定、代码是怎么写的、之前拍过哪些板。把这些散落各处的信息收拢到一个地方，agent 和人才能站在同一张地图上干活。没有上下文，agent 就是聪明但失明。

### 共享产品系统（shared product system）

**context**：承载上下文的载体，也是 Linear 的自我定位内核——一个"人与 agent 能共同工作的系统（a system that humans and agents can work from together）"。它同时容纳反馈、意图、决策、计划与代码。

**费曼一下**：不是给人一个系统、给 agent 另一个系统，而是让两者共用同一个工作台。人在上面提需求、拍决策，agent 在同一处读取这些信息、接着往下做。共享的意思是：同一份上下文，人和机器都看得见、都能动手。

### 把上下文转化为执行（turn context into execution）

**context**：Linear 的一句话定位与核心机制——"Linear is the shared product system that turns context into execution"。系统承载反馈、意图、决策、计划、代码，"把上下文塑造成工作"，再帮人与 agent 把它"一路带到生产环境"。

**费曼一下**：光有一堆信息没用，关键是让信息自动变成"做出来的东西"。这套系统的价值在于打通"知道"到"做到"的最后一段路：反馈进来，变成任务，有人或 agent 去做，一直推到上线。上下文是原料，执行是成品。

### 意图理解、路由与升级（understand intent, route, escalate）

**context**：新系统应具备的运行能力清单——"理解意图、把工作路由给正确的执行者、在需要时升级、并保持执行推进（understand intent, route work to the right actor, escalate when needed, and keep execution moving）"。这是把上下文变成执行的具体动作。

**费曼一下**：一个好的调度系统要会三件事：听懂你到底想要什么（意图），把活儿派给最合适的人或 agent（路由），遇到自己搞不定的就往上交给能拍板的（升级）。这样工作才不会卡住，而是一直往前走，不被困在流程里空转。

### 技能化（Skills）

**context**：今日发布之一。把"值得重复的工作流固化为可复用技能（codify them as reusable skills）"，让学习复利累积（compound your learning）；可用斜杠命令手动触发，或让系统在相关时自动应用。

**费曼一下**：你摸索出一套好用的干活套路后，不该每次都从头再来。把它打包存下来，取个名字，下次一键调用——甚至系统会在合适的时候自动帮你用上。经验因此像利息一样越滚越多，而不是每次归零。

### 事件驱动的自动化（Automations）

**context**：今日发布之一，从 Triage 起步。"在一个 issue 进入系统的那一刻触发 agent 工作流（trigger agent workflows the moment an issue enters）"；每个新 issue 都增添上下文，系统能"在它到达的那一刻"就精炼、综合或采取行动。

**费曼一下**：不用等人有空来处理，事情一发生就自动开跑。新问题一进来，系统立刻去归类、去查重、去补充关联信息，甚至直接动手。把"人来了才处理"变成"事一来就处理"，等待时间被压到接近零。

### 缩短想法与实现之间的距离（collapsing the distance between idea and implementation）

**context**：全文的终极目标。通过把 agent 扎根于产品与代码库的完整上下文，Linear 正在"压缩一个想法与其实现之间的距离（collapsing the distance between an idea and its implementation）"，呼应收束句"Linear turns context into execution"。

**费曼一下**：传统上，从"我有个点子"到"它真的上线了"要经过漫长的传递、排期、返工。当 agent 手握全部上下文、能直接把想法往下推，这段路被大幅缩短——想到和做到之间的鸿沟越来越窄，几乎可以一步跨过去。

全文是一条清晰的"退化—信念—放大—重构"逻辑链。起点是**交接模型**：问题追踪为它而生，也因它塞满了流程仪式。这套仪式本有合理性（工程时间稀缺），但沿着**复杂被误认为精密**这条心理捷径不断加码，最终滑向**流程即工作**的失败模式——手段吃掉目的。这三者构成因果递进：交接模型是土壤，"复杂=精密"的误判是催化剂，"流程即工作"是恶果。

**移除开销**与"流程即工作"正面对立，是 Linear 的价值原点；文章其余部分都在论证 agent 如何把这条信念推向新高度。承接机制是**阶段压缩**：agent 吸收程序性工作，使规划、实现、评审彼此挤压合并；压缩之后腾出的空间，归还给人，就是**意图、判断与品味**。于是"移除开销 → 阶段压缩 → 人回到意图判断品味"构成一条自上而下的价值兑现链，而超过 75% 装机率、5 倍工作量增长、接近 25% 的新 issue 由 agent 撰写这组数字，是这条链"已经发生"的经验证据。

链条的另一半回答"如何让 agent 真正管用"。**agent 不是读心者**是第一性原理，它直接推出**上下文**为何是核心；上下文又必须寄居于**共享产品系统**——人与 agent 同看一张地图。三者层层支撑：读心者假设不成立，所以需要显式上下文，所以需要一个共享的承载系统。**把上下文转化为执行**是这套系统的使命陈述，而**意图理解、路由与升级**则是把使命落地的具体动作能力：理解要什么、派给谁、卡住时找谁。

**技能化**与**事件驱动的自动化**是"上下文转化为执行"的两种复利放大器：前者让好工作流沉淀复用、让学习滚雪球，后者让上下文在"进入系统的那一刻"就被处理，把等待压到零；二者都依赖前面的共享上下文，又反过来让上下文更快变成行动。所有这些线索最终汇入同一个终点——**缩短想法与实现之间的距离**：当 agent 扎根于完整上下文、能自己把工作一路推到生产，"想到"与"做到"之间的鸿沟被合上。于是全文首尾呼应：问题追踪为交接而生，而新范式由**上下文**与**行动能力**（agent 的执行）共同驱动，正如标题所言。
