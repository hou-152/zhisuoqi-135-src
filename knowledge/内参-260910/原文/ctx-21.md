## 核心观点

- 全文的判断很直白：一批曾被当成上下文工程最佳实践的做法，今天已经变成了神话（"previous context engineering best practices that had become myths"）。它们当年不是写错了，而是被模型能力的提升淘汰了。
- 这些旧实践有一个共同的形状：用显式约束替模型做决定——给死规则、给示例、把一切前置、反复强调。它们在弱模型时代是必要的护栏；在 Claude 5 世代，同一套护栏反而在压缩模型的判断空间。
- 新规则的方向因此反转：从「把知识灌满上下文」转向「让模型在需要的时刻找到正确的上下文」，从「约束行为」转向「设计接口与引用」。渐进披露（progressive disclosure）是贯穿全文的机制。
- 落地时分四个层面组装上下文：system prompt 绑定产品语境，CLAUDE.md 只写 gotchas，skills 做轻量指南并按需加载，references 优先给代码这类高保真材料。
- 收尾的动作项只有一个词：简化。Anthropic 自己在 Claude Code 上做了这件事，并新出了 claude doctor 命令帮用户自动做。作者是 Anthropic 技术团队成员 Thariq Shihipar。

## 旧护栏为什么会过期

- 起点是一个真实的工程约束：Claude Code 刚推出时，必须确保模型避开最坏情况，比如删除文件。于是团队会给出「可能并不总是成立」的强指令。
- 文中给出的原始样本是旧 system prompt 里关于注释的规定：默认不写注释，绝不写多段 docstring 或多行注释块，一行为上限；除非用户要求，不要创建计划、决策、分析类文档，从对话上下文工作而不是从中间文件工作。
- 这条指令对一部分 prompt 是错的：用户可能有自己的文档偏好，特别复杂的代码段也确实需要多行注释块。
- 但对老模型来说，没有这层护栏，Claude 写出的注释在很多情况下是错的，团队只能接受这个 tradeoff。判断这件事，当时模型做不了，只能由规则代做。
- 新模型有更好的判断力，不需要显式规则也能处理好这类决定。于是新 system prompt 换成了一句取向性的话："Write code that reads like the surrounding code: match its comment density, naming, and idiom."——不给结论，只给对齐的对象。

## 六组 then / now：规则如何反转

- **给规则 → 让 Claude 用判断力**：这是第一节展开的那条主线。护栏换成「与周围代码一致」这类可迁移的取向，把具体决定交回模型。
- **给示例 → 设计接口**：过去工具使用的第一条规则是给 Claude 示例。新模型上的发现相反——给示例反而把它们约束在某个特定的探索空间里（"giving examples actually constrains them to a certain exploration space"）。
- 替代做法是回到工具、脚本、文件本身的设计：Claude 拿到哪些参数，这些参数能不能更有表达力。
- 文中的样本是 Todo 工具：把 status 做成 pending、in_progress、completed 的枚举，本身就在暗示用法；而「同时只保留一项处于 in_progress」这条说明，则把期望行为定义清楚了。接口即指令。
- **全部前置 → 渐进披露**：因为 Claude Code 聚焦编码，早期 system prompt 里塞进了 code review 与 verification 的详细信息——它们不总被需要，但需要时至关重要。
- 现在 Claude Code 已经很擅长渐进披露，也就是在正确的时机加载正确的上下文；团队把 verification 与 code review 挪进了各自的 skill，由 Claude 自行选择调用。
- 渐进披露不只用于 skills，也用于工具：部分工具是 deferred loading，agent 必须先用 ToolSearch 搜到完整定义才能调用。这样可以拥有更多工具（例如 Task 系列），而它们在被需要之前不占用上下文。
- 同一条道理适用于你自己的 CLAUDE.md 和 Skill.md。一个常见神话是：必须把所有可能用到的实践都塞进这些文件，否则 Claude 找不到。正解是做成一棵能在正确时机加载的文件树。
- **反复强调 → 简洁的工具描述**：早期模型有时需要重复指令，也更容易听上下文窗口末尾而非开头的指令；于是 system prompt 里既提到工具，工具描述里又写一遍指令。
- 现在这些重复的示例可以删掉，工具怎么用就写在 tool description 里，不必回流到 system prompt。
- **把记忆写进 \`CLAUDE.md\` → 自动记忆**：过去鼓励用 # 热键把东西自动写进 CLAUDE.md 来保存记忆；现在 Claude 会自动保存与当前工作、与你本人相关的记忆。
- **简单 spec → 富引用**：plan mode 里 Claude Code 重度依赖 markdown 计划文件，把计划存成文件方便随时回看；另一条类似实践是把 spec 存在 codebase 里，供长周期项目中随时参照。
- 但现在 Claude 能处理越来越复杂的引用形式：不止简单的 markdown，还可以引用新 artifacts 功能生成的 HTML artifact。
- 引用也可以是代码：一份 spec 可以是一套详细的测试套件，也可以是另一个 codebase 里等待移植的函数。
- Rubric 是又一种引用形式。它让 Claude 借助 dynamic workflows 起 verifier agent，去尝试并验证你在某个领域的品味——例如「什么样的 API 设计算好设计」。

## 四个层面：怎么组装你的上下文

- **System Prompt**：与产品语境强绑定，告诉 Claude 它运行在什么产品里、在做什么。用 Claude Code 的人大概永远不需要改它；但如果你在搭自己的 agent harness，这里值得花大量时间。
- **\`CLAUDE.md\`**：保持轻量，简要说明这个 repo 是干什么的，然后把大部分 token 花在 codebase 内部的 gotchas 上——比如你的类型全部集中在一个 monolithic 文件里、别处没有。避免陈述那些 Claude 看一眼文件系统或 repo 就知道的显而易见的事。
- 大量使用渐进披露：如果你有若干独特的验证方法，就做一个 verification skill，再从 CLAUDE.md 引用它。
- **Skills**：把 skill 当作轻量指南，让 Claude 在需要时找到信息；不要做得过度约束，除非是高度重要的领域。
- 长 skill 尽量渐进披露，拆成多个文件分出去。
- Skill 最好用来编码你、你的团队或你的产品特有的观点、知识与最佳实践。
- **References**：可以用 @ 提及文件把它们作为引用，让 Claude 拿到关于当前计划的深入信息。
- 引用可以是 spec 文件、mockup，甚至整个 codebase。
- 一般优先选代码形式的文件，因为它给 Claude 的是清晰、高保真的指令，而且用的是它非常熟悉的语言。文中的对比很具体：一份设计的 HTML mockup，通常比对该设计的文字描述或一张截图产生更好的结果。

## 概念网络

### 关键概念

### 上下文工程（context engineering）

**context**：全文的主题域。它不是提问技巧，而是决定「模型在某个时刻看到什么」的工程活动——system prompt、CLAUDE.md、skills、tool description、references 都是它的构件。文章的全部讨论都是这些构件里该放什么、该在何时放。

**费曼一下**：给模型准备工作台。桌上摆什么、什么时候递过去、哪些东西放抽屉里等它来找——这是布置工作台的手艺，不是说话的手艺。

### 护栏型指令的过期

**context**：文章的核心机制。为老模型写的强指令（如「默认不写注释」）是必要护栏，代价是「would be wrong」于一部分 prompt，团队当年只能接受这个 tradeoff。模型判断力提升后，护栏留在原地就从保护变成了压制。

**费曼一下**：给学徒立的死规矩，等他成了熟练工还不撤，规矩就开始碍事了。旧实践变成神话，不是因为当初写错，而是因为条件变了。

### 判断力优先（let Claude use judgement）

**context**：第一组 then / now 的落点。做法是把结论式规定换成取向式指令，例如新 system prompt 那句 "Write code that reads like the surrounding code: match its comment density, naming, and idiom."——给对齐对象，不给具体答案。

**费曼一下**：不说「注释一行封顶」，而说「跟周围的代码一个样」。前者是替它决定，后者是告诉它拿什么当参照，剩下的它自己看着办。

### 示例的探索空间约束

**context**：推翻「工具使用第一条规则是给示例」的依据。文中的原话是给示例 "actually constrains them to a certain exploration space"。示例在弱模型上是脚手架，在强模型上变成了天花板。

**费曼一下**：你给了一个标准答案，它就不再去找更好的那个。示例既是引导也是围栏，模型越强，围栏的成本越高。

### 工具接口的表达力设计

**context**：取代示例的做法——去想工具、脚本、文件的设计，Claude 有哪些参数、这些参数能不能更有表达力。Todo 工具的 pending / in_progress / completed 枚举本身就在暗示用法，「同时只保留一项 in_progress」把期望行为定义了出来。

**费曼一下**：好工具自己会说明怎么用。把意图铸进参数和枚举，比在旁边贴一张使用说明更可靠——因为参数是模型必须经过的地方，说明只是它可能读到的地方。

### 渐进披露（progressive disclosure）

**context**：贯穿全文的机制，定义是「在正确的时机加载正确的上下文」。Claude Code 把 verification 与 code review 从 system prompt 挪进可被选择调用的 skill；CLAUDE.md 一节也要求「大量使用」它。

**费曼一下**：不要开场就把整本手册念完，而是把手册放在它伸手就能拿到的地方。上下文的稀缺性决定了：能延后加载的东西，就不该提前占位。

### 延迟加载工具（deferred loading）

**context**：渐进披露在工具层的实现。部分工具是 deferred loading，agent 必须先用 ToolSearch 搜索到完整定义才能使用；这让系统可以拥有更多工具（如 Task 系列），而它们在被需要前不消耗上下文。

**费曼一下**：工具箱里放一百把工具，但只在台面上摆目录。要用哪把再去取——工具数量的上限，就不再由台面大小决定。

### 上下文文件树

**context**：针对「CLAUDE.md 和 Skill.md 应当是所有已知实践的中央仓库」这一常见神话给出的替代结构：改成一棵能在正确时机加载的文件树。

**费曼一下**：与其写一本无限膨胀的百科全书，不如做一个索引加许多分册。中央仓库的问题不是信息不够，而是每次都得整本搬进来。

### 自动记忆（auto-memory）

**context**：第五组 then / now。过去鼓励用 # 热键把内容自动写进 CLAUDE.md 保存记忆；现在 Claude 会自动保存与当前工作、与你本人相关的记忆，记忆管理从用户手动动作变成系统职责。

**费曼一下**：过去要自己写便利贴贴在显示器上，现在助手自己记得住。人不必再兼任自己的档案员。

### 富引用（rich references）

**context**：第六组 then / now 的落点。从 plan mode 里的简单 markdown 计划文件，扩展到 HTML artifact、详细的测试套件、另一个 codebase 里待移植的函数、rubric——都可以充当 spec。

**费曼一下**：说明书不必是一段文字。一套能跑的测试、一份能渲染的原型，都是更硬的说明书，因为它们不容易被误读。

### Rubric 与 verifier agent

**context**：富引用中最特别的一种。Rubric 让 Claude 借 dynamic workflows 起 verifier agent，去尝试并验证你在某个领域的品味，文中的例子是「什么样的 API 设计算好设计」。

**费曼一下**：把「什么算好」写成可核对的评分标准，再派一个专门的检查员照单核对。这样品味不再只存在你脑子里，而变成流程里可执行的一环。

### gotchas 优先原则

**context**：CLAUDE.md 一节给出的 token 分配原则：保持轻量，简要说明 repo 用途，把大部分 token 花在 codebase 内部的 gotchas 上（如类型集中在一个 monolithic 文件里），并避免陈述 Claude 看文件系统或 repo 就知道的显而易见的事。

**费曼一下**：只写它猜不到的那部分。它能自己读代码看出来的事，你写一遍等于浪费预算；它一定会踩的那个坑，你不写就一定会踩。

### 代码即高保真引用

**context**：references 一节的选材偏好。优先选代码形式的文件，因为它给出清晰、高保真的指令，且用的是模型非常熟悉的语言；文中的对照是 HTML mockup 通常胜过对设计的文字描述或一张截图。

**费曼一下**：跟一个母语是代码的对象沟通，就用代码说话。同一个意图，越接近它的母语，转述过程中丢掉的信息越少。

全文的思想网络只有一个总开关：模型判断力的提升，使显式约束从收益变成了成本。上下文工程这门手艺没有被否定，被否定的是它在弱模型时代形成的一整套默认动作。总开关向下分出两条路径。

第一条路径是「减法」。护栏型指令的过期是最直接的推论：为最坏情况写的强规定（默认不写注释、别造中间文件）曾用错误率换安全，代价被明确接受为 tradeoff；护栏一撤，判断力优先就成了替代方案，取向式指令取代结论式规定。示例的探索空间约束与此同源却指向另一处：示例不再是脚手架而是天花板，于是重心从「示范怎么用」移到「把工具设计得会说话」，工具接口的表达力设计接手了原本由示例承担的引导职能。这里有一处值得注意的互补而非替代关系——判断力优先要求少给指令，接口的表达力设计却要求把意图铸进参数；两者的共同点是把指令从「说给模型听的话」变成「模型必须经过的结构」。反复强调的消失、以及记忆从 CLAUDE.md 迁往自动记忆，都是同一条减法路径的延伸：前者靠模型对长上下文的稳定性，后者靠系统替用户承担记账。

第二条路径是「重排」。渐进披露不减少信息总量，只改变信息出现的时机，它因此成为网络中扇出最广的枢纽：向下支撑延迟加载工具（ToolSearch 按需取定义，工具数量不再受上下文预算限制）、上下文文件树（推翻中央仓库式的 CLAUDE.md 神话）、以及 gotchas 优先原则（把有限的 token 让给模型猜不到的那部分）。这三者的关系不是并列的三条建议，而是同一原则在工具层、文件组织层、内容取舍层的三次落地。

第三簇概念处理的是引用质量而非上下文数量。富引用把 spec 的可能形态从 markdown 扩展到 HTML artifact、测试套件、待移植函数；它向下派生出两个方向——Rubric 与 verifier agent 把主观品味外化成可核对的标准并交给检查员执行，代码即高保真引用则把沟通语言换成模型的母语以减少转述损耗。这一簇与渐进披露构成互补：一个管「什么时候给」，一个管「给的东西够不够硬」。

网络最终收敛于简化上下文。它不是一条新的独立规则，而是前面所有推论的合力结果：文件树与 gotchas 优先直接压缩了常驻上下文的体积，减法路径则清掉了为旧模型留下的冗余护栏。claude doctor 的出现说明这件事已经足够程式化，可以交给工具自动执行——这也从侧面确认了整张网络的方向：上下文工程正从「写得更全」转向「留得更少、找得更准」。

## 费曼 x3

有一类知识的失效方式很特别：它没有被证伪，只是环境变了。为弱模型写的那些上下文工程规矩就是如此。默认不写注释、给足示例、把所有可能用到的实践都堆进一个文件——它们当年都是对的，而且是必要的。今天它们成了神话，原因不在写它们的人，而在被约束的对象已经不同了。

值得注意的是这些旧实践共同的形状：它们都在替模型做决定。给死规则是替它决定输出的样子，给示例是替它决定探索的范围，全部前置是替它决定什么时候需要什么。在判断力不足的年代，这种代劳是划算的交易——护栏写得再粗糙，也比让它删掉你的文件好。但代劳有个隐藏成本，只在模型变强之后才显形：给示例反而把它约束在某个特定的探索空间里。你以为在帮忙，其实在设天花板。

新规则的方向因此是把决定权还回去，但不是撒手不管。护栏没有消失，只是换了形态——从结论换成参照。旧 system prompt 规定注释一行封顶，新的只说一句：写出读起来像周围代码的代码，匹配它的注释密度、命名和惯用法。前者给答案，后者给对齐的对象。同理，与其在文档里教它怎么用工具，不如把意图铸进参数和枚举本身，让工具自己会说明怎么用。指令从「说给它听的话」变成「它必须经过的结构」，可靠性就不再依赖它有没有读到那句话。

真正贯穿全部新规则的，是渐进披露：在正确的时机加载正确的上下文。这一条改变的不是信息总量，而是信息出场的顺序。工具可以延迟加载，用到才去搜完整定义，于是工具数量不再受上下文预算限制；长文档可以拆成一棵能在需要时加载的文件树，而不是无限膨胀的中央仓库；项目说明文件里最该占篇幅的，是它读代码猜不到的那些坑，而不是它扫一眼文件系统就明白的显而易见的事。

这些结论其实都指向同一个动作：简化。有意思的是，这件事已经程式化到可以做成一个命令——claude doctor。而更值得琢磨的是它背后的规律：上下文工程的每一次进步，都不是发现了该多写什么，而是发现了哪些东西终于可以不写了。所以每次模型换代，值得先问的不是「还能加什么」，而是「哪条规矩该退休了」。
