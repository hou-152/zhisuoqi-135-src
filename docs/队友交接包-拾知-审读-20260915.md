## 1. 一句话：他做的是什么

**一套可独立运行的 AI 文章信息源**：从八个渠道持续发现 AI 文章，读原文、按固定编辑标准让模型筛选分类（四栏目 × 知识精选/探索推荐 × 优先推荐/候补/待补资料/不推荐）、英文文章单独翻译，再按日期定稿成一份顺序固定、内容冻结、可重复读取的推荐清单，供下游按「日期 + 栏目 + 篇数」只读拉取。

它解决的问题是**「互联网文章太多，个人挑不过来」**——把「每天读哪几篇」的挑选成本降下来。

## 2. 他的思路

### 2.1 核心机制（一条主线）

```
八个来源（OpenAI / Anthropic / Simon Willison / AI HOT / OpenAI News / 知乎搜索 ×3）
  → 分批发现候选、合并重复链接
  → 读取原文（切成 P001 段落，算 body_hash）
  → AI 分类筛选（四栏目 + 分区 + 四种结果 + 逐条引文证据）
  → 证据校验（引文必须真的在段落里、哈希必须一致）
  → 人工校准（可改判断、改顺序，改了就锁住）
  → 英文单独翻译（按段落 ID 对齐，不动原文）
  → 当日入围 + 同栏统一比较排序
  → 定稿：固定顺序 + 原文译文快照（content_version = SHA-256）
  → 按日期/栏目/篇数只读供给
```

三个设计立场值得记下来（都是他文档原话的意思）：
- **发现 ≠ 选中 ≠ 可推送**：找到一篇不等于选它，评审合格不等于今天能推。
- **GET 只读**：读现成清单不联网、不调模型、不花额度。
- **机器不许覆盖人**：人工校准过的文章，自动模型会直接拒绝评审。

### 2.2 跟我们「知所栖 135」哪里像（具体）

| # | 像在哪 | 他的证据 | 我们的证据 |
|---|---|---|---|
| 1 | **证据必须可回溯到原文位置** | `reviewer.py` 要求引文 ≥8 字且逐字出现在指定 `paragraph_id`；`body_hash` 必须和当前正文一致，否则拒绝导入 | 228 道决策题依据逐字命中 `456/456`、`sha256` 全一致；来源链 58 篇 → 49 个原始来源 → 76 张卡 |
| 2 | **机器产出与人的裁决分开记账，机器不许改人** | `reviewer.py`：文章带 `calibration.locked` 时，模型评审直接报错「人工校准，自动模型不会覆盖」 | 判据分 `misconceptionSource: derived`（机器推的）/ 无标记（人工配对）；`practice-readiness.mjs` 对 `derived` 一律不开放 |
| 3 | **冻结与版本** | `content_version` = SHA-256；同日期同版本固定前缀；改已定稿内容要显式 revision，撤回要写原因且返回 410 | Graph / 材料带校验和、夹具标注；`check-learning-materials` 校验哈希 |

### 2.3 跟我们哪里**根本不同**（一条，最要紧）

**他定义的是「什么值得读」，我们定义的是「有没有学会」。**

- 他**没有任何「学会」的定义**：没有判据、没有闸门、没有解锁、没有验收。他文档里三处明确划线：「不强制四栏齐全，**也不把每日推送排成课程**」「**不通过固定课程顺序来替代判断**」「案例设计与评分不在当前信息源代码中，**不能把推荐理由直接当成教学结论**」；README 也写「**知识树及学习案例不在本模块中**」。
- 我们的全部机制（问题 → 3 概念 → 1 阅读 → 3 决策 → 5 实验 → 费曼验收 → 漏点倒回 → **未过不解锁下一章**）**建立在固定顺序 + 判据闸门之上**。

所以判定是：**不是同构**（他没有教学闭环），**也不互斥**（他明确不碰教学，两边不会互相打脸），**是上下游互补**——他管「料从哪来、哪篇值得读」，我们管「读了到底学会没有」。

**一处要单独点出的口径冲突（不是教学机制，是模块口径）**：他那套「每日四栏推荐」如果被当成一个模块摆出去，就和我们已拍板的「模块 1 = 互动阅读器 · 3 = 案例决策场 · 5 = 技术实验台，**费曼是验收层不是模块**」冲突。它最多能当「1 阅读」的选料来源，不能当第 4 个模块。

**一处要点明的「不冲突」**：你提醒过「如果他是 agent 形态就是硬冲突」。**我查过，他不是**——全仓 Python 里没有任何 tool-calling / agent loop，只有一个 `interval=86400` 的批处理 `Runner` + 预算 + 退避 + 断点恢复（`worker.py`）。**他是确定性 workflow，与「管线是 workflow 不是 agent、对外禁说轻量 agent」这条口径一致，此处不冲突。**

## 4. 接口更换与类别划分（都不含凭据值）

### 4.1 两套接口的职责（他的说法）

| | DeepSeek 模型 API | 知乎内容 API |
|---|---|---|
| 作用 | 读文章材料，做分类筛选、逐段翻译、同栏排序 | 搜索知乎或全网，发现候选原文链接与摘要 |
| 配置字段 | `model.api_key` | `zhihu.access_secret` |
| 环境变量 | `DEEPSEEK_API_KEY` | `ZHIHU_ACCESS_SECRET` |
| 读现成日清单是否调用 | 不调用 | 不调用 |

他的分工原话是「**DeepSeek 负责理解，知乎负责发现**」。并明确：知乎搜索返回的 `ContentText` 是摘要，**不能当完整原文**；模型不会自己联网查证。

### 4.2 更换 API 的步骤（他文档 `交接文档/03-接口配置与转换.md`）

1. **只换 key 或模型**：改本地配置文件的 `model.api_key` / `model.model`（知乎改 `zhihu.access_secret`）。若存在同名环境变量，要先移除或更新——**环境变量优先级更高**。
2. **换成兼容 Chat Completions 的供应商**：把 `model` 改成 `provider: compatible` + 供应商 `base_url`（填根路径，程序自动补 `/chat/completions`）+ 真实模型 ID + 该供应商 key。**知乎配置保持不动。** 要求对方支持 messages、JSON object 输出、`choices[0].message.content`。
3. **换知乎账户或换平台**：换账户只改 Access Secret；**换平台不是换 key，是要新写适配器**（处理鉴权、分页、错误、额度），再返回统一候选结构接进 `sources.py`。三个知乎官方端点由代码固定登记，`sources.json` 里的 URL **不能绕过**这个限制——**即凭据不会被发往任意地址**（这条是安全设计，值得记）。
4. **配置优先级**（他写的 4 条）：`DEEPSEEK_API_KEY` > `AI_BASE_URL`+`AI_API_KEY`+`AI_MODEL`（三项必须齐，不齐则视为未配置，不混用两组凭据）> 包内配置文件；知乎单独判断，`ZHIHU_ACCESS_SECRET` 优先于本地文件。显式空值 = 禁用。
5. `python check_configuration.py` **只确认配置可用、不发请求、不打印密钥**（我读过源码，确实如此：输出只有 provider / model / 是否配置 / `network_requests: 0`）。

### 4.3 数据接入方式（三种，他文档 `交接文档/05` + `数据接入说明.md`）

1. **按日期拿推荐**（他推荐的）：接只读 8767，传 `date` + `column` + `count`（可选 `revision` / `include_reserve` / `include_content`），保留 `feed_id` / `entry_id` / `content_version`。
2. **同步整个库存**：接 8766 的游标接口 `/api/v1/changes?after=0&limit=50`，按 `article.id` 更新、保存 `next_cursor`。
3. **同机复用**：直接 import `Store` / `Service` / `DailyFeeds`，或读附带的 SQLite / JSONL。

返回的状态码分得很细，且**不许合并**：`200/ready`、`200/empty`（当天该栏定稿但为空）、`202/not_ready`（有草稿未定稿）、`404/unavailable`、`410/withdrawn`、`400`、`401`、`405`、`500`。他明确写「**不能把它们合并成今天没有文章**」。

### 4.4 类别划分方案

**四栏目**（代表不同的阅读收获，不要求按顺序学，也不保证每天都有）：
`general_knowledge` 通用知识（可反复用的方法）· `industry_knowledge` 行业知识（具体行业的任务/资料/约束，行业不限）· `usage_updates` 使用动态（模型与平台变化对我有什么影响）· `practice_ideas` 实践灵感（别人怎么用、值得试什么）。

**两条正交的标记轴**：
- `area` = **知识精选** / **探索推荐**（回答「这份材料处在什么阶段」，只对知识类文章有值，资讯为 null）；
- `tier` = **主荐** / **候补**（回答「今天先读哪几篇」）。

他特意写清这两个不是一回事：探索文章也可能成为当天主荐，精选文章也可能因难度或重合暂列候补。另外四种筛选结果是：优先推荐 / 候补 / 待补资料 / **不推荐**，后两类不能进入供给。

## 6. 风险清单

### 6.1 凭据风险（最要紧）

**事实（我核实过的）**：
- 明文凭据**只有一个文件**：`config/api.local.json`。里面两个字段：`model.api_key`（35 字符）和 `zhihu.access_secret`（40 字符）。

## 7. 对我们的参考价值

### 7.1 值得抄（3 条）

1. **人工审核的记账方式**（第 9.8 节详述）——人工结论回写成机器可读记录、带身份字段、带 per-item 锁、正文一变自动标记需复核。**这是这份包里最值钱的东西**，而且它正好对着我们的薄弱处。
2. **把证据校验做成「入库前的拒绝条件」，而不是「生成后的检查报告」**——他的 `validate_review` 是 fail-closed：引文 <8 字、引文不在指定段落、正向推荐没有正文、解析文章没有指向另一篇已读原文的核查证据，**任何一条都直接抛错，评审根本存不进去**。我们的同类校验（依据逐字命中、sha256 一致）目前是复核脚本里算出来给人看的。
3. **状态码不许合并的契约纪律**——「未生成 / 有草稿未定稿 / 已定稿但为空」是三个不同状态，不许合并成「今天没有文章」。我们的看板也有「可进入 / 材料缺口 / 缺少决策题」三态，但这条纪律他写得更死。

### 7.2 明确不抄（3 条）

1. **不抄他的 Python 实现**——两套运行时（他 Python + SQLite 长驻服务；我们 Node 24 零依赖 + 静态产物），合并只增加复杂度，没有收益。
2. **不抄他的「凭据随包发」做法**——已泄露，且直接违反我们的硬边界。**这条不是参考价值问题，是红线。**
3. **不抄他的知乎额度路径**——10 次/天、未实名，会把我们的采集节奏锁死在 3 次/天。我们自己的凭据实测剩余 4990/4998。**不共享凭据、不共享额度。**

补充一条**不抄但可参考**：他的「四栏目 × 探索/精选 × 主荐/候补」分类轴**不要并进我们的图谱**——我们已经有「图鉴卡 7 分类与概念地图 21 主题未建立映射」这条已知缺口，再叠一层没映射的轴是纯稀释。

### 9.8 本次「并思路」最该吸收的一样东西：他的人工审核设计 vs 我们的

#### 他的设计（逐条挖出来，都有源码依据）

| # | 机制 | 具体怎么做 |
|---|---|---|
| 1 | **评审材料包** `make_packet` | 生成一个自包含包：`rule_version` + 完整评审指令 + 正文（去掉译文）+ **最近 100 篇已评审历史** + 采用记录 + 引用核查说明。**上限 8 篇/批、240 KB**，超限**直接报错，不静默截断正文** |

| 7 | **密钥不进错误信息** | 模型报错落盘前 `replace(config['key'], '[redacted]')`；PROMPT 里有防注入条款 |

#### 并排放：谁强在哪

**他比我们强的（3 条，都是真的）**
1. **人工结论回写成机器可读记录、并与机器同闸门。** 我们的 `review.json` 里 `reviewer` 字段**只有脚本名**（`scripts/review-gen-decisions.mjs（独立复算；不采信产物自述）`），**人工抽审那 10 条只写在 md 表格里**——机器读不到，下次重跑产物时**没有任何机制拦住机器覆盖人的裁决**。
2. **per-item 的人工锁 + 正文变化自动失效。** 他的锁是**逐篇**的；我们的 `verdict` 是**整批一个值**（`usable` / `unusable`），锁不到「这一条我人看过了，别动」。
3. **评审材料包的上限与防截断 + 身份必填**，把「请人审」变成**可交接的动作单元**（8 篇/240 KB/身份署名）。我们的抽审是直接从产物里挑 10 条，没有材料包概念。

**我们比他的强的（3 条，也都是真的）**
1. **负控自检 `--selftest`。** 我们把复核检测器**跑在上一轮已判死的产物上，要求逐条复现判死**（v2 上必须复现 228 / 76 / 16 / 逐字照抄 228 / 依据 0 不符）。**他那边完全没有「判据有没有牙」的检测** —— 他的 `validate_review` 只验格式和引文可回溯，**不验这条判据能不能区分「会」和「不会」**。
2. **判据必须有「信息增量」的量化阈值。** 我们有：误解信息增量 ≥20 字（抠掉与正确条件的最长公共片段后的新增字符数）、「照抄边界原文即满足」判死（264/264 全中）、同单元判据重复（逐字撞或两两覆盖率 ≥50%）判死、极性一致。**他的闸门里没有对应的「这条判据是不是废话」**。
3. **判据与准入的机器闸门。** `practice-readiness.mjs` 读产物里的 `verdict` 字段（不是写死白名单）：`misconceptionSource === 'derived'` 一律不开，`verdict !== 'usable'` 一律不开。

#### 能不能并成一套：**能，而且这是这轮最值得做的一件事**

**分工很清楚**——两道闸门管的不是同一件事：
- **我们的机器闸门**管「**这条判据/这道题本身有没有牙**」（负控 + 信息增量阈值 + 捷径检测）→ **保留为第一道，不动**。
- **他的记账法**管「**人看过的结论怎么不被机器覆盖、怎么被机器读到**」→ **补成第二道**。

**具体合并动作（4 步，都可逆）：**
1. 人工抽审的结论从 md 挪进 `evidence/review-*/review.json`：每条带 `reviewer`（身份，人工就写人工 + 日期）、`verdict`（可用/偏弱/不可用三档照旧）、`note`。
2. `practice-readiness.mjs` 改成**同时**读「机器 verdict」和「人工 verdict」——两者都 `usable` 才开，任一是 `unusable` 就照实写理由。
3. 加 **per-item 锁**：人工审过的条目打 `locked`，复核脚本重跑时**跳过并保留**，不许覆盖；产物（判据/题）一变，自动置 `needs_recheck` 并要求重审。
4. 抽审的**抽样方式写进产物**（抽了几条、占多少、口径是什么）——他那边「抽审 10 条 = 3.8% 是抽样不是全检」这条自我限定，我们现在写在 md 里，应该进机器可读字段。

**一句话**：**他的记账法 + 我们的判据检测 = 一套完整的「机器先验牙、人再签字、签过不许改」的闸门；我们现在缺的只是后半段。**
