**成本对照（本次推断，按可见工作量估）**：

| 方案 | 改动量 | 风险 |
|---|---|---|
| 保持现状（GitHub Pages 静态版） | **0** | 费曼判定退化成机械覆盖（`mech`），不是真判定 |

**后果比"少两块功能"严重**：`:5502 chapterUnlocked` 要求上一章 `feynman === 'ok'`，而章末验收在公网域名上**永远拿不到 `ok`** → **第 2 章起永远不解锁，整条"阅读 → 费曼 → 解锁下一章"的链路在第一道门就停住**。
**最小修法**：生产入口注入 `LOCAL=true`（`isLocalHost()` 会直接返回常量 `true`；但那两处 `:5831`/`:6258` 是**内联正则**，不读 `LOCAL`，**必须一起改成读 `LOCAL` 或探测 `/api/health` 的 `llm` 字段**）——**这是上 Render 真正的第 1 号改动，比 `0.0.0.0` 更关键**。

⑥ **`/api/llm` 的重试与超时**——**设计上不重试**：`scripts/lib/llm.mjs:1-5` 明写「deliberately does not … retry requests, or choose fallbacks」；`serve-lib.mjs:142` 注释「超时原样记 `llm-timeout`，不重试、不回落」。超时值：服务端 30 s（`:143`），`/api/learn` 25 s（`:308`）；**但客户端更短**：读中即时费曼 15 s（`壳.html:5839`）、内参即时费曼 20 s（`:5394`）。上云后多一跳网络 + 冷启动，**客户端先超时、判成"未判定"的概率会明显上升**。要么调大客户端超时，要么接受"云上更容易未判定"。

⑦ **`Cache-Control: no-store` 会被 CDN 计划抵消**——`serve-lib.mjs:434-439` 给**所有静态文件**发 `no-store, must-revalidate`（`:431-433` 注释说明这是为了防止本地重建后旧标签页拿旧壳）。后果：**Cloudflare 放在 Render 前面也不会缓存那 5.30 MB 的壳和 11.76 MB 的 graph**，每一次打开都是回源全量传输，而 `node:http` **没有 gzip/brotli**。「Cloudflare 只做域名和 CDN」这一半，在当前代码下拿不到任何缓存收益——要拿到就得改这个响应头（并接受本地开发时缓存问题回归）。

⑧ **公开 URL = 公开的模型钱包**——`serve-lib.mjs` 全文**没有任何鉴权/CORS 头**（grep `Authorization` / `Access-Control` 零命中）。任何人 `curl` 你的 Render 域名就能用你的 DeepSeek key，限流只有"单进程 20 次/分"（`:70`）。最小缓解：加一个共享口令（header 或 query），或把 `LLM_RATE_MAX` 调低 + Render 侧开防火墙/限流。**这一条比"性能"重要**。

**这一轮基本定了**：形态 = **「可调用的方法 + 站内的反馈回路」**（API 出去的是概念/内参/LLM Wiki 素材 + 线路与上限；站内是编排与反馈；像 dbskill 那样卖方法不卖权威）。**唯一没定的是他自己点名的那条：内容正确性责任归谁** —— 它决定了今天最重的那批工作（228 题 / 264 判据 / 审计 / 误解语料）是"产品的核心资产"还是"反馈质量的素材"。**而"费曼做轻做重"是这条之下的一个子问题。**

**② 有没有互相矛盾的地方？**
有，最要紧的三条见 §5（76 单元 / 新契约 vs 页面文案 / 内容责任无人裁），其余 9 条也一并列了。

**③ 部署方案受形态影响吗？会不会固化一个还没定的东西？**
**会，但比上一版的判断更精确了**——新形态下，部署**不是**把形态定成 A（因为 A 已经被保留为载体），而是：
1. **把"内容权威"这个还没定的东西默认成"是"**：`staticRoot` + `defaultPage` 一设，公网根域名打开的就是**我们排的六章课程**。对访问者来说，"知所栖提供课程"当场成立——而负责人今天刚说「我按理来说不应该为他们的课程正确和错误承担责任」。**部署会让这句待讨论的话变成既成事实。**
2. **把"反馈质量"的一次快照固化成线上事实**：壳是构建产物，`76/70` 的 `open`、264 条"待验证区分度"、`realTrajectories: 0` 全烘在页面里。现在部署 = 把**连工作日志都没记**的状态发到公网。
3. **把 API 出口这件事挤到后面**：形态定稿后云端真正要承载的是"编排 + 反馈 + **出口**"，而出口今天**一条都没有**（§4-B）。如果先按老方案部署（只为壳服务），接下来每加一个出口都要回到同一台机器上改；**更省的做法是先定出口的数据形状（概念/内参/wiki 三个只读端点 + 配额），再决定它跑在哪。**
4. 另外两条技术性固化仍然成立：4 处"只有本机才调模型"的判断（第一部分 §7-⑤）不改就是残的；`Cache-Control: no-store`（§7-⑦）不改则 CDN 无收益。
