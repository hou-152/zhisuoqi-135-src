## 一、口径对齐（2026-09-11 已按 Codex 权威定义修正）

Codex（09-11 周四 09:52 会话）确认：**1 = 互动阅读器，3 = 案例决策场，5 = 技术实验台**；组合主线是「**读懂 → 判断 → 尝试**」。会议录音里「案例决策是第一个」为口误，已弃用。

框架已按此修正流转：读概念（1）→ 案例决策场（3）→ 技术实验台（5）→ 费曼验收。

**费曼的定位**（容易混，单独说）：费曼不是 1/3/5 之一，是方法论层。Codex 原话：「费曼式解释可以帮助暴露理解缺口，但不必每一步都要求用户讲一遍」。框架里它做**验收层**——这是会议录音里的共识（「三用于验收，验收又可以放到下一次交互里」），与 Codex 的五版共性「自己解释/选择/操作 → 获得有依据的反馈 → 留下可继续修正的结果」一致。

## 二、方法论底座（回应「功能背后有什么依据」）

| 来源 | 机制 | 落在框架哪里 |
|---|---|---|
| dbs-learning skill | 读真实反馈 → 调整下一篇的深度/角度/节奏 | 检验报告 → 定位漏点 → 倒回对应模块，「自适应梯度」即漏点倒回 |
| dbs-standard-answer skill | 历史同构比较 → 带条件的标准答案 | 案例决策场：先选、说理由，再看反例与遗漏条件，不给唯一正确答案 |
| 费曼学习法 | 用自己的话解释暴露缺口 | 费曼演练室（验收层） |
| Chi 自我解释研究（1994） | 学习者补出原文没写的关系，理解进步更大 | 阅读页要求组织自己的话；费曼复述 |
| Bastani 等（2025） | 裸 GPT 辅助撤掉后独立成绩降约 17%；加教学设计后负面影响消失 | **不做裸聊天**：所有 AI 介入都带结构（checklist、先选后评、改参数看结果） |
| Karpicke & Blunt（2011） | 提取重建优于概念图整理 | 验收靠「复述+倒回重做」，不靠画知识树 |

注意：三项研究都是小样本、任务特定的条件性证据，不是产品有效性的证明；「学会了」要区分完成任务 / 独立理解 / 记住 / 迁移，框架只记录「读过 / 判断过 / 动手过 / 复述通过」，不宣称掌握。

## 三、着重优化：费曼演练室（验收机制）

选它的理由：这是我在会上提的改造——费曼不是又一个学习模块，而是**检验机制**，给整条链路提供「学没学会」的信号。

当前实现：用自己的话讲「为什么像 PPT、怎么解决」→ 逐概念检查要点覆盖（讲到位 ✓ / 有漏点 △）→ 漏点带「回实验台补课」按钮 → 全通过才算验收。离线规则匹配是演示基线，代码留了 `LLM.endpoint` 接口位，接真模型后 `review()` 自动切换，UI 不动。

## 四、外接 LLM 怎么接：API vs Agent 不是二选一，且要用 AB 测试说话

（此节回应 09-11 的批评：此前只给了推理、没有成本数据。）

**两条路各自是什么**：

- B 单次 API：checklist 进 → JSON 判定出。无状态、可控、便宜、可离线回退。
- C Agent 形态：判漏前先调知乎检索工具查证据，多步工具调用。多花的是决策自由与运行成本——Codex 原话：「它是否比简单流程教得更好，目前没有项目证据」。

**AB 实验设计（跑一轮即可决策）**：

1. 样本：10 份真实复述（含故意写漏的点）+ 人工标注漏点真值。
2. 四组：A 离线规则（已实现，零成本基线）/ B 裸 LLM 单次调用 / C1 自建轻量管线（固定编排：检索知乎证据 2-3 条 → 对照 → 单轮判定，检索失败回退 B）/ C2 按 pi / penguin 参考架构实现（若与 C1 结构一致则并入 C1）。
3. 指标：漏点判定准确率（对照真值）｜每次耗时｜每次 token 成本。
4. 决策规则先定死：B 准确率 ≈ C → 用 B；C 组明显减少「把没学会误判成学会」才升级；C1 与 C2 打平 → 用 C1（自建可控、可回退）。
5. 跑一轮需要：一个 API key（谁出周六定）+ 约 1-2 小时。脚本可提前写好。

**参考 agent 修正（2026-09-11 深夜，出处已定位）**：团队说的「Penguin」来自 penguin-harness 推广视频，指的是 [Prism-Shadow/penguin-harness](https://github.com/Prism-Shadow/penguin-harness)（2.1k star、Apache-2.0、hiyouga/LlamaFactory 作者团队，活跃）——不是 Maximooch/penguin（6 star、WIP、AGPL，已剔除）。视频宣称核查与完整选型研究见 [docs/agent-选型调研.md](agent-选型调研.md)：结论不变——我们交付的是一条 **workflow**（预定义编排），penguin-harness 适合「要快速搭很多 agent」的场景，为单一判定管线引入它仍是过度设计。

**架构结论（2026-09-11 调研后修正，全文见 [docs/agent-选型调研.md](agent-选型调研.md)）**：我们的管线按 Anthropic 定义是 **workflow（预定义代码路径编排 LLM + 工具），不是 agent**，此前「轻量 agent」的说法不准确。决策规则：判定不需要证据 → 裸单轮调用就够；需要证据检索 → workflow（serve-135.mjs，已建成）；只有步骤不可预知、需模型自主规划时才用 agent 形态——我们的任务不属于此类。参考 agent 修正：PI（103.8k star）作为「薄循环即可」的佐证；Maximooch/penguin 剔除（6 star、WIP、AGPL）；penguin-harness 与其并非同源（此前混淆，已更正）。依据：Anthropic《Building Effective Agents》（2024-12，官方原话 "workflows offer predictability and consistency for well-defined tasks"）、AutoGPT 自主路线失败史、pi 仓库核实。
