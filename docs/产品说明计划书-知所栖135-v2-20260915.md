# 知所栖｜产品说明计划书

版本：2026-09-15；产品内容（崇铭）＋技术与交付字段（capo，已补全）。技术数字为 2026-09-15 本机实测口径，明细与验收脚本随代码仓库公开。

参赛方向：知识炼金场 · 社区 × 学习

一句话介绍：帮助用户把一篇有价值的文章，转化为自己能够理解、解释和使用的知识。

## 一、我们希望解决什么问题

用户读到一篇好文章，可能认同作者的观点，却没有弄清观点背后的概念与条件；也可能记住了一个方法，却不知道如何用到自己的问题上。读完、收藏和感觉熟悉，并不总能说明用户已经理解了内容。

知所栖关注阅读之后的这段过程：帮助用户说清文章在回答什么问题、依据是什么、何时适用，以及自己还有哪里没有理解。

我们采用降低无效阅读与理解成本的设计方向，让用户更轻松地阅读和理解文章。系统围绕文章梳理核心概念与观点，通过案例判断帮助用户理解适用条件，再以引导式复述检查理解中的遗漏，针对具体问题补充讲解。

## 二、产品如何帮助用户

产品以一篇用户认为有价值的文章为学习起点。围绕用户想弄懂的问题，组织文章中的问题、概念、观点、案例与方案，形成可追溯的学习材料。

五类材料各有用途：问题确定阅读目标，概念帮助理解，观点与依据用于比较，案例呈现具体条件，方案提供可尝试的方法。这些分类用于组织内容，不要求用户先学习分类体系，也不强迫每篇文章具备全部五类材料。

### 1. 先把文章讲清楚

用户选定文章或示例材料，指出自己不理解的内容。系统先解释与问题直接相关的概念、论述和条件，并提供对应出处。原文没有支持的解释或教学改编应作区分，避免把模型补充误认为作者的原意。

### 2. 通过案例判断理解适用条件

对适合比较的内容，提供一个简短情境与可比较方案，让用户选择并说明理由。反馈重点解释不同方案的条件、依据和局限。对于开放性决策，产品帮助用户比较，不把作者的选择或系统的偏好包装成唯一正确答案。

### 3. 用引导式复述发现缺口

系统围绕刚才的文章与案例判断提出具体问题，例如"你的选择依赖哪个条件""条件改变后，原来的理由还成立吗"，引导用户用自己的话解释。

反馈应明确已表达清楚的部分与待补充的部分，针对遗漏补讲，并回到原来的学习位置。用户补充短答时，应保留已有证据，不要求每次从头复述。复述结果只反映当前问题上的理解证据，不代表已经掌握整篇文章或所有应用场景。

用户可以暂停学习。未完成检验时记录为尚未检验，不能直接判定用户不会。

### 4. 用概念地图和学习路径组织后续学习

产品设有"内参""知识体系""实践空间"等入口。文章材料提供阅读起点，概念卡与关系视图帮助用户查看相关知识，学习路径则围绕具体目标安排先后顺序。

概念地图让用户看到一个概念与哪些知识相连；学习路径说明当前先学什么、为什么先学它，以及下一步是什么。用户在阅读中遇到陌生概念，可以借助这些入口了解背景，并把零散内容放回知识关系中理解。

学习记录与公共概念关系分别保存。某个概念出现在地图上，只表示它与内容有关；用户在具体学习活动中的解释与作答，才构成该次学习的反馈依据。

### 5. 当前学习路线示例

项目以 AI 相关内容作为首批学习材料，已有"理解 AI 如何持续行动"的六步路线：Agent、工具、Agent loop、状态子系统与进度持久化、Harness、验证闭环。

这条路线围绕"为什么 AI 能连续做事，而不只回答一次"展开。用户先了解当前概念及学习目标，阅读相关材料，完成案例判断，再用自己的话解释本章关键关系。出现遗漏时，系统提供补讲，用户补充后返回原来的学习位置。章末检验与阅读中的即时反馈分别记录，帮助用户明确当前进度。

这个示例体现了产品如何把文章中的概念连接成一段可继续的学习过程：既能围绕单篇内容理解，也能沿相关概念逐步深入。

## 三、与知乎生态的契合

知乎提供文章、回答、经验与观点讨论等内容。知所栖希望在这些内容的阅读过程中，帮助用户进一步理解概念、辨认适用条件，并将内容用于具体问题。

面向知乎场景，我们希望保留文章标题、作者与原文入口，让学习活动可以回到出处；围绕用户的疑惑组织解释与案例对照，使优质内容在一次阅读之后仍能被再次理解和使用。

我们希望促进有目的的继续阅读和回访。用户发现一个具体理解缺口后，可以选择继续查阅相关内容，并知道这次阅读要解决什么问题。与持续增加信息量相比，这种继续阅读具有明确目标，也保留"先到这里"的选择。

## 四、产品特色

**文章拆解与学习活动相连接。** 问题、概念、观点、案例与方案既用于梳理文章，也为解释、判断和复述提供材料，使阅读内容能够进入具体的学习活动。

**反馈落实到具体遗漏。** AI 围绕本次学习目标回应用户的解释，指出需要补充的关系或条件；补充回答沿用先前已经表达清楚的部分，让交流能够持续推进。

**知识关系与学习顺序相配合。** 概念地图提供探索视角，学习路线提供当前可以采取的步骤。用户既可以查阅知识之间的联系，也可以围绕一个目标完成有顺序的学习。

**保留学习过程，支持继续。** 作答、复述和暂停位置为后续学习提供上下文，帮助用户回到先前的问题，继续处理尚未讲清的部分。

## 五、技术实现方案

### 1. 整体架构与部署

产品是「单文件 Web 应用 + 一个本地服务」的两层结构，没有数据库和运维负担。

前端是一个自包含的 HTML 文件（原生 JavaScript，无框架、无运行时依赖）：概念地图、内参阅读、学习流程与判定交互都在这一个文件里，可离线打开。服务端是一个 Node.js 本地服务（仓库内 `scripts/serve-135.mjs`），负责静态托管与六个接口——健康检查、提示词读取、知乎检索桥接、模型调用代理、学习记录保存、数据读取；模型密钥只存在于服务端进程，不下发到浏览器。

本次交付形态有三种，由同一份代码构建：①公网单文件版（GitHub Pages 托管，零服务端，判定走离线规则并如实标注）；②本地完整版（一条命令启动，全部接口与真实模型判定可用）；③macOS 桌面版（Electron，学习记录落本地文件）。部署方式：公网版托管在 GitHub Pages（仓库 hou-152/zhisuoqi-135），构建脚本从同一份源一键生成；本地版 `node scripts/serve-135.mjs` 即起。

### 2. 内容处理与知识组织

内容分「策展期批处理」与「使用时生成」两段。

文章进入系统在策展期完成：订阅源当日新增收藏被拉取为原文快照落盘，模型流水线为每篇生成三种学习材料（三级笔记、概念辞典、AI 费曼问答），构建脚本再把全部期数的页面数据烘焙进单文件。用户学习时读到的正文与出处都是预生成的，产品不现场抓取网页。

五类语义与概念关系来自一条七步的确定性管线：抽取、合并去重、模型富化（领域／类型／定义／掌握证据／验收问句）、依赖边生成与环检测、地图与 wiki 构建、体检校验。当前规模：1070 个概念、681 条前置依赖、21 个主题领域；每条依赖边带审核结论（成立／弱化／推翻后修正），判否的边留档可翻案。另有 538 个五类语义单元（问题 141 · 概念 76 · 观点 169 · 案例 76 · 方案 76）与六章学习材料——来源链为 58 篇文章 → 49 个原始来源 → 76 张卡片，逐条可核对回原文。

预处理与运行时的边界：材料、概念地图、页面数据全部预生成并有体检脚本把守（材料体检 581 项、地图与全链路体检 465 项等）；学习进行中，模型只生成四类内容——案例判断的反馈、复述的判读、针对漏点的补讲、知乎实时检索结果。

### 3. AI 反馈与学习流程

模型与服务商：DeepSeek API。本地版的调用经服务端代理，浏览器不接触密钥；知乎开放平台的「直答」模型也实测过可承接复述判定，作为备选。

模型负责的环节：构建期负责概念富化、依赖边判定与内参三产物；学习时负责决策题的判定反馈、复述判读与补讲。全部是单轮调用，预定义编排——这是「检索增强的判定 workflow」，不是自主 agent。

复述判据是预写的：每个检验点有一套要点判据，并配「判据 → 常见误解 → 教学动作 → 对应材料」的四级映射。模型按判据输出「通过／待复核／未过」，并列出已覆盖与遗漏的要点；已说清楚的部分保留证据，用户补充短答时不必从头复述。费曼复述未通过不解锁下一章，修改复述即清空通过状态。

补讲与回到原位置由确定性代码记账：学习状态由全链路 Graph 的 transition 边驱动（4591 节点／14487 边，只有 transition 能改变学习状态），补讲完成后回到发起漏点的那一步，不重讲整段；暂停后从原步骤恢复；系统异常不记为学习者缺口；并发的过期判定结果作废。

规则与模型的分工：解锁门控、状态跳转、进度计数全部是预设规则；模型只做语义判读与补讲文本，无权直接改变学习状态。公网版无服务端时，判定退回离线规则并如实标注，不冒充模型判定。

### 4. 知乎能力接入

接入方式：知乎开放平台官方 CLI（v0.6.0，凭证仅存本地），本地服务以 `/api/search` 桥接其「全网搜索」接口。

调用环节：主流程的案例与证据环节。进入「3 决策」时，系统按当前课题关键词实时检索知乎，案例卡使用真实文章的标题与可点回原文的链接。验收脚本对此有专门断言（引擎标识与运行模式一致，当前为 C1-pipeline(llm+live-search)），防止检索层被静默跳过。

一个真实调用在体验中的用途：学习一章进入决策环节时，系统对课题发起一次知乎搜索（实测 0.77 秒返回 3 条真实结果），案例卡直接由这批结果渲染，点卡片即回到知乎原文对照——案例不是编造的示例，而是当天能打开的知乎内容。

其他已实测接口：热榜、「问题-回答」（可取真实回答摘要，是「把真实知乎问题当学习材料」的入口）、直答模型、知识库。公网静态版有意不发起任何知乎调用（零服务端形态）。

### 5. 学习记录与数据保存

保存位置：公网版全部记录在浏览器 localStorage（学习进度、判定标记、视图布局），不建账号体系、不上传服务器。本地版经保存接口落本地文件；桌面版学习记录落 `~/Documents/知所栖-135/学习记录.json` 真文件；复述草稿即写即存，中途关闭不丢。

暂停恢复：状态按「当前步」记账，未完成检验记录为「尚未检验」，不判「不会」；再次进入从原步骤继续，已说清的复述证据保留。

数据是否发送至模型服务：用户的作答与复述文本会作为请求内容发给模型服务商（DeepSeek）用于判读与补讲，这是唯一的外发；除此之外无其他上传。公网版无服务端，数据完全不出浏览器。

## 七、后续发展

后续将围绕知乎优质内容，进一步连接文章阅读、知识理解与持续学习，提升文章利用率，并促进有目的的继续阅读和回访，增强用户与知乎内容及创作者之间的联系。

**提升文章利用率。** 将同一篇文章中的概念、观点、案例与方法用于解释、案例比较和复述检验，并保留作者与原文入口。用户可以在遇到新问题时重新查阅、对照和应用，使优质文章在首次阅读之后继续发挥价值。

**围绕学习需要推荐内容。** 根据用户尚未理解的概念、当前问题与主动选择的兴趣，推荐相关知乎文章或回答，并说明推荐内容能帮助解决什么问题。探索由用户自主订阅的主题更新和阅读提醒，让下一次阅读承接已有的学习过程。

**通过持续学习增强用户粘性。** 将学习记录、待解决的问题与相关知乎内容连接起来，让用户再次进入时可以继续此前的阅读与探索。以持续获得理解和应用上的帮助作为回访理由，逐步形成阅读、学习、回到原文和继续探索的使用习惯。

同时扩展文章类型和适合内容的实践环节，完善来源核验与内容审核。后续通过实际使用观察文章回访、相关内容继续阅读与学习恢复情况，评估这些功能是否真正帮助用户更好地利用知乎内容。
